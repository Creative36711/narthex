# Chronicle Forge — гайд для ИИ-генераторов кампаний

Этот документ — техническое руководство для внешнего ИИ-агента Chronicle Forge.
Полная кампания, включая модули и медиа, передаётся одним архивом `.chronicle`.
Для текстовой/структурной правки без медиа остаётся запасной формат
`MonolithDoc` JSON; он не заменяет пакет при работе с бинарными файлами.

Формальные ограничения — `docs/campaign.schema.json` (JSON Schema типов
движка). Нарушения схемы не роняют импорт: валидатор достраивает заглушки и
отключает битое, но цель — кампания **без единого предупреждения**.

## 0. С чего начать (это первое, что читает агент)

### Как работать с кампанией Chronicle Forge через ИИ-агента

Ты — автор кампаний для Chronicle Forge. Мастер прислал пакет задания для
внешнего ИИ. В режиме редактирования корневые файлы архива — полный Campaign
Package, включая локальные медиа. В `__chronicle_ai__/` лежат задача мастера,
руководство, схема, бланк дизайн-документа и, если запускалась проверка,
отчёт по структуре, медиа и плейтесту. При создании новой кампании исходного
пакета нет: назначенный приложением ID записан в задаче.

#### Что сделать

1. Прочитай `__chronicle_ai__/TASK.md` и `README.md`, затем руководство,
   схему и отчёт проверки.
2. Выполни запрос целиком и сразу. Не останавливайся на плане, не жди «ок» и
   не задавай уточняющих вопросов: при нехватке вводных прими разумные
   допущения и запиши важные решения в дизайн-документ.
3. Для полной кампании или задачи с медиа верни один готовый `.chronicle`:
   Campaign Package с `campaign.json`, `world.json`, `manifest.json`, всеми
   модулями и требуемыми медиафайлами. Не включай в результат
   `__chronicle_ai__/`.
4. Если мастер явно просит только текстовую/структурную правку без медиа и
   архив создать нельзя, допустимый запасной вариант — полный MonolithDoc JSON.
   Его можно загрузить через «Файл → Импорт из JSON», но JSON не содержит
   бинарные медиафайлы и не заменяет `.chronicle` для полной передачи.

##### Новая кампания

Сначала заполни `campaign.design_doc` человеческим языком по
`design-template.md`, затем **в том же ответе** создай по этому плану всю
кампанию. Используй ID, который приложение заранее выдало и записало в
`__chronicle_ai__/TASK.md`; не придумывай другой. В документе опиши:

- паспорт: название, жанр и тон, объём (сцены, НПС, квесты), ключевая идея;
- завязку и мир: кто герой, чего хочет, кто мешает;
- главы — в порядке, в каком игрок их увидит;
- сцены: название, место, роль в истории, что там можно сделать;
- персонажей: кто, чего хочет, что знает, где стоит, в каком настроении бывает;
- квесты и концовки: как завершается успехом и как провалом;
- задействованные механики — простыми словами, без имён эффектов;
- рамки баланса: бой, цены, урон, сутки;
- ограничения движка и принятые обходные решения;
- журнал решений: что изменилось с прошлой версии и почему.

Пиши простыми словами: документ читает человек, который не писал код, —
поэтому в нём не должно быть имён полей и типов формата. Единственное
исключение — приложение бланка «Соответствие разделам JSON».

##### Правка существующей кампании

Работай с приложенными файлами, не генерируй кампанию заново. Сначала обнови `design_doc`
под изменения — что и почему меняется, плюс запись в журнале
решений, — затем в том же ответе внеси правки. Сохрани `campaign.id` в точности:
он выдан приложением, не является названием и участвует в ключах сохранений.
Не переименовывай и не перезаписывай ID сущностей. Не удаляй и не заменяй
контент вне задачи. На каждой итерации обновляй дизайн-документ вместе с
кампанией.

#### Правила (строго)

1. Формальная граница — приложенная JSON Schema и гайд. Ссылайся только на
   существующие id, не добавляй полей вне схемы и не удаляй обязательные.
2. Тексты на русском; id сущностей — латиницей с префиксом секции.
   `campaign.id` — выданная приложением идентичность: при редактировании
   сохраняй её; для новой кампании используй назначенный в задаче ID.
3. **Никаких переименований и переиспользования id сущностей**: «устаревшее» —
   удали и создай новое. Переименование ломает ссылки и сохранения.
4. Для медиа предпочитай файлы внутри пакета и относительные пути. Не оставляй
   важный контент только по временной внешней ссылке. Для скачанных материалов
   сохрани источник и условия использования; не выдумывай разрешение на права.
5. Запрещено выдумывать значения вне перечня типов из гайда (состояния сцен,
   типы условий, эффектов, хуков звука). Нет нужной механики — скажи об
   этом прямо, не выдумывай полей.
6. Если не хватает механики — не подменяй её костылём из флагов, а честно
   опиши в блоке обратной связи (ниже) и предложи рабочий обходной путь.
7. Для квестов сохраняй различие между id стадии и ключом записи журнала:
   ключ `journal_entries` (например, `j_search`) — самостоятельный внутренний
   id, не имя стадии. Стадия публикует текст отдельным эффектом
   `journal_update`; не делай ключи стадийными id.
8. Не меняй через данные кампании надписи, состав или расположение системного
   интерфейса. В главном меню движок сам рисует бренд/версию и кнопки «Новый
   забег», «Продолжить», «Кампании», «Как играть», «Настройки», «Редактор»;
   агент может менять только `meta.title`, `meta.description` и поддерживаемые
   данные темы: `theme.profile`, `theme.accent`, `theme.fonts`, `theme.tokens`,
   `theme.menu.background`, `theme.menu.dim`, `theme.menu.ken_burns`,
   `theme.menu.title_art`, `theme.end.background`; `theme.custom_css` — только
   для внешнего вида, не для подмены системных строк или функций. Не рисуй
   надписи кнопок или название поверх уже выводимого движком текста. Фон меню
   и `title_art` назначай раздельно; после правок темы проверяй читаемость
   настроек, справки, создания персонажа и игровых окон.
9. Настройки в брифе необязательны. Учитывай только явно заданные параметры;
   пропущенный аспект не превращай в требование и выбери сам либо оставь
   неопределённым. Не назначай баланс диалогов/боёвки по умолчанию.
10. Для `char_creation` точно распределяй бюджеты каждого шаблона и каждого
    сочетания происхождения с призванием. Учитывай нижний порог, обязательные
    навыки, `skill_cap` и бесплатные бонусы происхождения; не допускай
    недорасхода или перерасхода. Подписи потребностей в HUD делай короткими,
    предпочтительно до 18 знаков, а надписи в иллюстрациях держи внутри
    безопасных полей и не дублируй ими системные заголовки.

#### Как сообщать о проблемах формата — блок `cf-feedback`

В финале ответа по кампании добавь fenced-блок `cf-feedback` с JSON-массивом.
Если претензий к движку/схеме нет — добавь пустой массив `[]`.

```cf-feedback
[
  {
    "id": "missing-effect:set_mood",
    "kind": "missing_effect",
    "detail": "Нужно переключать эмоцию NPC правилом: в реестре есть портреты состояний, но менять их нечем.",
    "workaround": "Сейчас ставлю флаг и ловлю его в диалоге на эмоцию реплики.",
    "severity": "mid"
  }
]
```

`id` — стабильный ключ; `kind` — `missing_effect`, `missing_condition`,
`doc_gap`, `schema_gap`, `validator_wrong` или `other`; `detail` описывает
недостающую возможность; `workaround` — обход; `severity` — `low`, `mid` или
`high`.

## 0б. Бланк гейм-дизайнерского документа (файл `design-template.md` в чемодане)

### Гейм-дизайнерский документ кампании

Заполняй документ первым, затем в том же ответе выполняй задачу целиком и
возвращай готовый полный JSON. Не останавливайся на документе, не жди
«ок» и не задавай уточняющих вопросов. Если вводных не хватает, прими
разумные решения и зафиксируй важные допущения в журнале. Обновляй документ
на каждой итерации. Пиши простыми словами — его читает человек, который не
писал код.

Документ — рабочий план для мастера, а не этап согласования: мастер читает
его вместе с готовой кампанией и при необходимости просит правку. Пиши
столько, сколько нужно для решения, и обязательно веди журнал решений. Имена
полей и типов формата в теле документа не нужны: единственное место, где они

## 1. Главные правила

1. **Всё декларативно.** Никакого кода, выражений и скриптов — только данные:
   условия, эффекты, правила, диалоги. Ты не «программируешь» поведение —
   описываешь его.
2. **Всё по-русски.** Все `label`, описания, реплики, тексты — на русском.
   `id` — латиницей. Сырой id игроку не показывается: в интерфейсе везде
   русские названия.
3. **Кампания должна звучать и выглядеть без единого бинарного файла.**
   Сцены рисуются примитивами (`art`), катсцены — слайдами с `art`, звуки и
   музыка синтезируются из JSON (см. §13–14). Картинки/аудио-файлы не
   нужны — их мастер потом подставит сам.
4. **Один документ = полная кампания.** Не бывает «частичных» вставок:
   импорт заменяет содержимое кампании целиком.

## 2. Структура документа

```json
{
  "campaign":   { … },              // метаданные и реестры (§3)
  "world":      { "regions": [ … ] }, // регионы и локации (§4)
  "scenes":     { "<id>": { … } },  // сцены (§5)
  "entities":   { "<id>": { … } },  // НПС и предметы (§7)
  "rules":      { "<id>": { … } },  // правила (§8)
  "quests":     { "<id>": { … } },  // квесты (§9)
  "arenas":     { "<id>": { … } },  // гекс-арены боёв (§10)
  "cutscenes":  { "<id>": { … } },  // слайд-катсцены (§11)
  "encounters": { "<id>": { … } },  // необязательно: таблицы случайных встреч (§12)
  "recipes":    { "<id>": { … } },  // необязательно: рецепты крафта (§14б)
  "codex":      { "<id>": { … } },  // необязательно: записи кодекса (§14з)
  "dialogues":  { "<id>": { … } }   // диалоги конструктора (§13)
}
```

Обязательные ключи: `campaign`, `world`, `scenes`, `entities`, `rules`,
`quests`, `arenas`, `cutscenes`, `dialogues`. Необязательные: `encounters`,
`recipes`, `codex`; если они не нужны, их можно опустить или передать пустыми
объектами. Все словари ресурсов — **по id объекта**; внутреннее поле `id`
должно совпадать с ключом.

### Campaign Package и монолит — два разных обменных формата

Распакованный Campaign Package хранится несколькими файлами. Архив `.chronicle`
содержит ту же структуру каталогов; это не монолитный JSON. Отдельная команда
«Экспорт JSON» создаёт именно MonolithDoc из примера выше.

```text
campaign.json                 CampaignMeta
world.json                    WorldDef
manifest.json                 CampaignManifest
scenes/<имя>.json             SceneDef
entities/<имя>.json           EntityDef (NPC или предмет)
rules/<имя>.json              RuleDef
rules/<файл-встреч>.json      EncounterFileDef: { "encounter_tables": [...] }
arenas/<имя>.json             ArenaDef
quests/<имя>.json             QuestDef
cutscenes/<имя>.json          CutsceneDef
recipes/<имя>.json            RecipeDef
codex/<имя>.json              CodexEntryDef
dialogues/<имя>.ink           исходник, который читает движок
```

`manifest.json` обязан содержать массивы `scenes`, `entities`, `rules` и
`dialogues`; массивы `arenas`, `quests`, `encounters`, `cutscenes`, `recipes`,
`codex` можно опустить, если раздел пуст. **Элементы этих массивов — только
имена файлов относительно каталога модуля, без префикса каталога**: например,
`"entities": ["item_latte.json"]`, а не `"entities/item_latte.json"` —
редактор сам добавляет `entities/` при построении пути. `encounters` ссылается
на имена файлов в каталоге `encounters/` (или `rules/` для обратной совместимости),
каждый из которых содержит обёртку `encounter_tables`. Файл встреч НЕ должен попадать в `manifest.rules`: там
ждут только `RuleDef`, и таблица встреч без `conditions` сломает движок
при старте забега (правило без массива условий). Один файл — один раздел
манифеста. В `manifest.dialogues` перечисляются только `.ink`
(например, `"mark.ink"`), а не визуальный sidecar `.dlg.json`.

Для диалога конструктор дополнительно хранит `dialogues/<имя>.dlg.json`
(`DlgDoc`); при сохранении из конструктора `.ink` генерируется из него. Сырой
рукописный `.ink` (без `.dlg.json`) в редакторе конвертируется в `DlgDoc`
кнопкой «Открыть в конструкторе» (`inkToDlgDoc` — плоскости условий, ответов,
проверок навыков; семантика сохраняется). В монолите передаётся только
`DlgDoc` либо объект `{ "label": "…", "ink": "…" }` для сырого Ink. Имена
файлов перечислены в манифесте; имена словарей в монолите — это id.

Типы модулей и монолита описаны в `src/shared/types.ts`. Их схема
`docs/campaign.schema.json` содержит `$defs` для MonolithDoc, `index.json` и
отдельных модулей; `npm run audit:campaign-formats` сверяет примеры,
экспорт/импорт и промпт генератора.

## 3. Соглашения по id

- Латиница, цифры, `_`: `tavern_hall`, `npc_maeva`.
- Стабильные префиксы (по типу объекта):
  `region_`, `loc_`, `scene_`, `npc_`, `item_`, `player_`, `rule_`, `quest_`,
  `stage_` (стадии квестов), `arena_`, `cutscene_`, `enc_`, флаги — без
  префикса, но говорящие: `forest_ambush_cleared`.
- id — это ещё и «имя файла»: диалог `maeva` ляжет в `dialogues/maeva.ink`.
- **Никогда не переиспользуй id** под разными объектами и не меняй id по
  ходу текста: на них завязаны все ссылки. В редакторе переименование id
  запрещено жёстко, а в обновлениях кампании оно считается ломающим
  изменением (сохранения игроков перестанут открываться) — см.
  `docs/compatibility.md`.

## 4. campaign — метаданные и реестры

```json
"campaign": {
  "id": "my_campaign", "title": "Моя кампания", "version": "0.1.0",
  "engine_version": "0.8.0", "min_engine": "0.8.0", "package_format": 1,
  "author": "ИИ", "description": "…",
  "tick_label": "час", "ticks_per_day": 24,
  "time_of_day": { "morning": 6, "day": 10, "evening": 18, "night": 22 },
  "starting_region": "region_valley", "starting_location": "loc_town",
  "starting_scene": "scene_tavern", "starting_tick": 8,
  "needs": [ … ], "currencies": [ { "id": "silver", "label": "Серебро", "symbol": "SM", "item_id": "item_silver" } ],
  "skills": [ { "id": "persuade", "label": "Убеждение" } ],
  "item_categories": [ { "id": "food", "label": "Еда", "restores_needs": ["need_hunger"] }, { "id": "currency", "label": "Валюта" } ],
  "slot_types": [], "flags": [ { "id": "met_guard", "label": "Поговорил с караульным" } ],
  "factions": [ { "id": "faction_guild", "label": "Гильдия", "base_disposition": 0, "description": "Торговое объединение города." } ],
  "default_player": "player_hero",
  "dice_rules": { "critical_divisor": 5, "special_divisor": 2, "fumble_from": 96 },
  "max_companions": 2
}
```

- **`design_doc`** — гейм-дизайнерский документ кампании (строка Markdown,
  необязательно). Ведёт его генератор по бланку `design-template.md`:
  сначала составляет документ, затем в том же ответе выполняет задачу целиком;
  не ждёт подтверждения «ок» и не задаёт уточняющих вопросов. На каждой
  итерации обновляет документ вместе с правками. Мастер читает его в
  редакторе («Проект → Дизайн-документ») и при необходимости просит изменения.
  Пиши простыми словами, без имён полей и типов формата — единственное
  исключение в бланке: приложение «Соответствие разделам JSON».
- **Потребности** (`needs`): `{ id, label, max, decay_per_tick,
  critical_threshold, restore_per_tick?, on_zero_effect?,
  decay_when?, restore_when? }`. Подпись `label` видна в узком HUD: держи её
  короткой (желательно до 18 знаков), а число оставляй отдельным счётчиком;
  полное название доступно игроку по подсказке. Условия `decay_when`/`restore_when`
  соединены по «И», у каждого — свойство-массив:
  `{ "type": "time_of_day", "values": ["evening", "night"] }`,
  `{ "type": "in_location", "locations": ["loc_tavern"], "not": true }` —
  «не в одной из», `{ "type": "has_item", "items": ["item_cloak", "item_fur"],
  "not": true }` — «нет ни одного из», `{ \"type\": \"weather\", \"weather\": \"weather_snow\",
  \"not\": true }` — «пока НЕ эта погода»: потребность может убывать или
  восстанавливаться от погоды («Тепло тает, пока метель»). Пример «Тепло»:
  убывает вечером/ночью,
  если нет плаща ИЛИ шубы и герой не в таверне/казарме/храме.
- **`currencies`**: `id` — ключ валюты, по нему задаются цены в `value`;
  `item_id` — id предмета-монеты в `entities`, и именно его количество в
  инвентаре образует доступный баланс. Если `item_id` опущен в старой кампании,
  движок использует соглашение `item_<id>`. Например, `id: "silver"` и
  `item_id: "item_silver"`; не путай идентификатор валюты с предметом-монетой.
- **`dice_rules`** — пороги d100 («щедрые» по умолчанию: крит ≤ навык/5,
  особый ≤ навык/2, провал 96–100; классика BRP: /20, /5, 96–100 при навыке
  < `fumble_low_skill`).
- **Шрифты и типографика** (`fonts`, `theme.fonts`). Движок поддерживает полноценное шрифтовое оформление кампании под выбранный жанр и эпоху.
  - **Реестр шрифтов (`meta.fonts`)**: массив гарнитур, подключаемых движком через `@font-face` (форматы `.woff2`, `.woff`, `.ttf`, `.otf` из папки `assets/fonts/` или внешние URL):
    ```json
    "fonts": [
      {
        "id": "font_title",
        "label": "Gothic Display",
        "src": "assets/fonts/gothic.woff2",
        "weight": "700",
        "style": "normal"
      },
      {
        "id": "font_notes",
        "label": "Old Handwriting",
        "src": "assets/fonts/handwriting.woff2",
        "weight": "400"
      }
    ]
    ```
  - **Шрифтовые роли в игре (`meta.theme.fonts`)**: привязка гарнитур к 3 слоям UI:
    - `"display"` — заголовочный шрифт: название кампании в главном меню, заголовки сцен, имена персонажей в диалогах, шапки экранов.
    - `"body"` — основной текст: описание локаций, реплики диалогов, описание предметов, кнопки действий.
    - `"hand"` — рукописный стиль: записки, найденные дневники, страницы журнала расследования, свитки кодекса.
    Если роль не назначена явно, движок применяет типографику из выбранного профиля темы (`theme.profile`).
  - **Тонкая настройка типографики (`meta.theme`)**:
    - `"font_scale"`: общий множитель масштаба текста всей игры (`0.8` .. `1.4`, по умолчанию `1.0`).
    - `"font_sizes"`: объект точных базовых размеров в пикселях:
      - `"body"`: основной текст и описания предметов/сцен (по умолчанию 15px);
      - `"display"`: заголовки локаций, сцен, экранов (по умолчанию 20px);
      - `"dialogue"`: реплики диалогов и кнопки ответов (по умолчанию 16px);
      - `"ui"`: кнопки, списки, мелкие надписи интерфейса (по умолчанию 13px).
    - `"line_height"`: множитель межстрочного интервала (`1.2` .. `2.0`, по умолчанию `1.5`).
    - `"letter_spacing"`: межбуквенный интервал (например `"0.02em"`).
    - `"size_adjust"` у конкретного шрифта в `meta.fonts`: поправка масштаба гарнитуры (`0.8` .. `1.3`, по умолчанию 1.0).
- **Оформление и тема (`meta.theme`)**. Визуальный профиль игры и атмосфера:
  **`theme.profile`** — визуальный профиль игры. Каталог из 13 направлений:
  `"forge"` (фирменный стиль Chronicle Forge, **по умолчанию**), `"epic-fantasy"`,
  `"dark-fantasy"`, `"myth-folklore"`, `"gothic-horror"`, `"cosmic-horror"`,
  `"noir"`, `"historical"`, `"wilderness"`, `"postapocalypse"`, `"scifi"`,
  `"cyberpunk"`, `"modern"`. Каждый профиль — цельный художественный набор:
  палитра, шрифтовые роли, стиль панелей и именованный атмосферный эффект;
  это оформление, а не механика — на правила, `dice_rules` и данные не влияет.
  Старые кампании с `"fantasy"`/`"horror"`/`"survival"` читаются автоматически
  (сопоставлены с `"dark-fantasy"`/`"gothic-horror"`/`"wilderness"`), новые
  кампании создавайте с id из каталога выше. Поверх профиля допустимы
  переопределения: `theme.accent` (акцентный цвет), роли шрифтов
  `fonts.body/display/hand`, фон и затемнение меню, фон финала,
  `theme.atmosphere: false` (выключить атмосферный эффект).
  У меню — фон, затемнение `dim` 0…0.9, медленный зум `ken_burns`, `title_art` (лого
  кампании); `theme.end.background` — фон экрана финала. Без `theme` —
  фирменный профиль «Chronicle Forge» и всё по умолчанию.
  **Категорический запрет на `theme.custom_css` для ИИ:** поле `custom_css`
  («Полный CSS мастера») предназначено **исключительно для человека-мастера**.
  ИИ-агенту использовать `theme.custom_css` **ЗАПРЕЩЕНО**. Для оформления ИИ обязан
  использовать только штатный инструментарий: профили `theme.profile`, акцент `theme.accent`,
  токены поверхностей `theme.tokens` (`panel`, `cards`, `inset`, `log`), реестр `meta.fonts`
  и роли `theme.fonts`.
  **Граница главного меню:** движок сам рисует бренд Chronicle Forge, подпись
  движка, версии и кнопки «Новый забег», «Продолжить», «Кампании», «Как играть»,
  «Настройки» и «Редактор» (часть кнопок зависит от состояния/сборки). Эти
  надписи и расположение не являются текстом кампании: не пытайся менять их
  через `campaign.json`, `theme`, картинку или CSS. Для текста главного меню
  доступны `meta.title` и `meta.description`; для его оформления — `theme.profile`,
  `theme.accent`, `theme.fonts`, `theme.tokens`, `theme.menu.background`,
  `theme.menu.dim`, `theme.menu.ken_burns`, `theme.menu.title_art`,
  `theme.end.background`.
  Фон меню и `title_art` — разные роли: не назначай один и тот же файл обоим,
  если это даёт двойное изображение; `title_art` лучше делать отдельным
  компактным логотипом/артом без повторного названия кампании и без надписей
  кнопок/служебного интерфейса. Само название и описание уже выводит движок.
  Не запекай UI-текст в иллюстрации: это ухудшает читаемость и не локализуется.
  В `theme.tokens` светлые поверхности допустимы — движок подбирает для них
  контрастные роли текста, но проверяй итоговое меню и окна визуально.
- **Реестры** (`skills`, `item_categories`, `flags`, `factions`, `slot_types`)
  нужны редактору для списков. У фракции обязательны `id`, `label`,
  `base_disposition`; необязательные `description` и `hidden` задают справку и
  скрывают служебную фракцию из листа персонажа. Флаги вне реестра всё равно
  работают, но добавь их — мастеру будет понятнее. У каждого флага реестра
  ОБЯЗАТЕЛЬНО заполняй `description` («для чего нужен»: какое событие
  запоминает и где читается) — аудит кампании помечает флаги без пояснения
  предупреждением, а следующий агент споткнётся о безымянную память мира.
- `slot_types` — типы слотов сцены (`{ "id": "person", "label": "Персонаж" }`
  и т.п.). Встроенных типов нет: объявляй все, которые используешь в
  `"type"` слотов (обычно персонаж/предмет/контейнер/животное).
  `equipment_slots` — слоты экипировки, тоже только от кампании (см. 14д).
- **`features`** — профиль механик (необязательно; всё, что не указано,
  включено): `{ "map":…, "inventory":…, "needs":…, "skills":…,
  "relationships":…, "trade":…, "combat":…, "time":… }` (булевы). Пример для
  камерного хоррора без карты и боёвки: `"features": { "map": false,
  "combat": false, "needs": false }`. Семантика: `combat:false` — конфликты
  из `start_combat` разрешаются немедленной победой (применяется `on_victory`);
  `skills:false` — проверки навыков заканчиваются успехом без броска;
  `trade:false` — прилавки не открываются. Не выключай механики, на которых
  держится твой контент.

### 4.0 Оформление, атмосфера и интерфейс (100% инструментарий)

ИИ-сценарист владеет полным арсеналом художественного оформления игры.
**Категорический запрет на `custom_css`:** поле `custom_css` («Полный CSS мастера») предназначено исключительно для живого человека-мастера. ИИ строит стилистику только через структурированные свойства:

1. **Визуальный профиль `theme.profile`:**
   13 стартовых художественных наборов (`VisualProfileId`):
   - `forge` (базовый стиль Chronicle Forge по умолчанию);
   - `dark-fantasy` (тёмное фэнтези, золотой акцент, гравюрная рамка);
   - `epic-fantasy` (двойная золотая кайма, благородный синий);
   - `myth-folklore` (древние мифы, фольклор, дерево и узоры);
   - `gothic-horror` (готический хоррор, глубокие виньетки, холодная палитра);
   - `cosmic-horror` (космический хоррор Лавкрафта, чернильная тьма);
   - `noir` (монохром, высокий контраст, дымчатые панели);
   - `historical` (исторический пергамент, строгая классика);
   - `wilderness` (дикая природа, хвоя, кора, естественный камень);
   - `postapocalypse` (ржавчина, пепел, грязная охра);
   - `scifi` (научная фантастика, звёздный синий, чистые линии);
   - `cyberpunk` (неон, контрастные тёмные поверхности);
   - `modern` (современный лаконичный реализм).

2. **Атмосферный шейдер `theme.atmosphere`:**
   `true` (по умолчанию) включает фирменный шейдер профиля (виньетка, дымка, гравюрные тени). `false` отключает его для чистого кадра.

3. **Акцентный цвет `theme.accent`:**
   Шестнадцатеричный цвет (`#e5a93c`, `#38bdf8` и т.д.). Переопределяет цвет активных кнопок, подсветок интерактивных зон, рамок фокуса и выделений.

4. **Тоны поверхностей `theme.tokens` (мастерская докрутка палитры):**
   - `panel` — фон основных окон, панелей и подложки диалогов (например, `"#1a1e28"`);
   - `cards` — фон карточек предметов, кнопок выбора, ячеек характеристик (например, `"#222838"`);
   - `inset` — колодцы полей ввода, инвентарные ячейки, шкалы прогресса (например, `"#141720"`);
   - `log` — фоновая подложка строк журнала событий (например, `"#12151d"`).
   Движок автоматически рассчитывает читаемые цвета текста под заданные тоны.

5. **Рамка-орнамент панелей `theme.frame`:**
   Декоративная кайма вокруг всех игровых окон (PNG-изображение с прозрачной сердцевиной):
   - `image` — относительный путь к PNG (`"assets/img/ui/frame_ornament.png"`);
   - `slice` — глубина среза орнамента по краям в px (по умолчанию 30);
   - `width` — видимая толщина рамки на панели в px (по умолчанию 20).

6. **Шрифтовая подсистема:**
   - Реестр шрифтов в `fonts`: `[{ "id": "f_cinzel", "label": "Cinzel", "src": "assets/fonts/cinzel.woff2", "weight": "700" }]`;
   - Назначение ролей в `theme.fonts`:
     - `body` — основной текст описаний, диалогов и подсказок;
     - `display` — заголовки локаций, сцен, панелей и меню;
     - `hand` — рукописный текст (записки, дневники, цитаты кодекса);
   - `theme.font_scale` — общий коэффициент масштабирования шрифтов (например, 1.05).

7. **Атмосферные названия системных кнопок `ui_labels`:**
   Адаптация системного интерфейса под атмосферу сеттинга (в `meta` кампании):
   - `inventory` — название кнопки и шапки инвентаря (например, «Сумка дознавателя»);
   - `journal` — журнал заданий («Дело № 137» или «Бортовой журнал»);
   - `map` — карта («Схема ярусов» или «Лоция»);
   - `camp` — привал/отдых («Перекур» или «Привал»);
   - `codex` — энциклопедия («Архив Надзора» или «Бестиарий»);
   - `craft` — верстак («Сборка» или «Алхимия»);
   - `character` — досье героя («Личное дело» или «Анкета»);
   - `pass_turn` — завершение хода в бою («Выждать» или «Держать строй»);
   - `flee` — отступление («Бежать» или «Отход»).

8. **Каноническое обозначение характеристик (СТРОГО):**
   Во всех локализациях (русской, английской и любых будущих) главные характеристики ВСЕГДА обозначаются латиницей:
   `STR`, `CON`, `SIZ`, `DEX`, `INT`, `POW`, `CHA`, `EDU`, а также `HP`, `MP`, `AP`.
   Русские сокращения («СИЛ», «ВЫН», «РОСТ», «ЛОВ») запрещены: весь интерфейс движка и чемодан стандартизированы под общепринятый BRP-формат.

### 4.1 Версии и совместимость

- `version` — версия кампании (semver, `1.4.2`). Растёт при каждом выпуске
  обновления.
- `min_engine` — минимальная версия движка Chronicle Forge, на которой
  кампания работает корректно. Поле `engine_version` устарело, но читается
  как то же самое; при генерации пиши оба одним значением. При правке
  существующей кампании сохрани оба значения из исходного файла. Для новой
  кампании используй версию движка, переданную приложением в исходном пакете
  или задании. **Не копируй сюда `campaign.version` и не выдумывай `1.0`: это
  независимые номера.** Сейчас движок этой версии гайда — `0.8.0`.
- `package_format` — версия формата пакета (`1`). Ставь текущую.
- `save_base_version` — сохранения от какой версии кампании ещё
  поддерживаются. **При первой генерации не заполняй**: поле проставляет
  редактор при публикации обновления, когда найдены ломающие изменения
  (удалённые персонажи, предметы, сцены, стадии квестов, реестры).
- `chapters` — главы кампании: `[{ id, label, order?, description? }]`; сцены,
  правила, квесты и катсцены помечаются полем `chapter` (id главы). Упорядочивай
  главы по ходу истории («1 — пролог», «2 — основная часть»). Двигатель главы
  не различает — это группировка в редакторе и опора для выкладывания частей.
- `series` — место кампании в серии: `{ base?, part?, label? }`. Основная
  игра: без `base`, `part: 1`. Продолжение (DLC): `base` = id базовой кампании,
  `part: 2+`, `label` — название части. Поддержка «пролог бесплатно, дальше —»:
  пролог — самостоятельный пакет, продолжение — пакет с заполненным `series`.
- `attribution` — публикация: `{ author?, origin_url?, published_at?, note? }`.
  Кто придумал/собрал кампанию и где лежит каноническая копия (GitHub-репозиторий
  мастера; git-история доказывает первую публикацию). Поля публикации НЕ
  входят в отпечаток кампании: подпись считается от канонической формы без
  них, чтобы «перелив» с чужим титулом распознавался как копия.

При правке существующей кампании не удаляй объекты без нужды: каждое удаление
id — ломающее изменение для сохранений игроков. Косметика (названия,
описания, иллюстрации, музыка) и правки баланса сохранения не ломают.

## 5. world — регионы и локации

```json
"world": { "regions": [ {
  "id": "region_valley", "label": "Долина", "map_image": "",
  "map_art": { … ArtDoc … }, "map_size": { "w": 1280, "h": 720 },
  "parent_region": null,
  "locations": [ {
    "id": "loc_town", "label": "Город", "position": { "x": 640, "y": 360 },
    "travel_connections": [ { "to": "loc_forest", "cost_ticks": 3 } ],
    "scenes": ["scene_tavern", "scene_market"],
    "arrival_scene": "scene_tavern"
  } ]
} ] }
```

- Переход **между локациями** — только через глобальную карту
  (`travel_connections`); сценами герой ходит внутри локации.
- `arrival_scene` — куда попасть, придя в локацию с карты (по умолчанию —
  первая сцена списка `scenes`).
- `map_image` — файл/ссылка; `map_art` — карта, нарисованная примитивами
  (§6). Координаты `position` — в системе карты (map_size).
- `hidden: true` — локация скрыта, пока не откроется эффектом
  `reveal_location`.

### Как вставить в карту реальное изображение (растровую карту):
1. В `RegionDef` укажи путь к файлу: `"map_image": "assets/img/maps/region_valley.jpg"`.
2. Задай точные размеры в `"map_size"`: например, `{ "w": 1920, "h": 1080 }` или `{ "w": 1280, "h": 720 }`.
3. **Удали поле `map_art`**, если оно было сгенерировано как процедурная заглушка: движок отдаёт приоритет растру, но чистота JSON защищает от путаницы.
4. Расставляй маркеры локаций `"position": { "x": ..., "y": ... }` в пределах системы координат `map_size`. Движок автоматически отрендерит карту, маркеры и дорожную сеть со стрелками связей.

## 6. ArtDoc — рисунок из JSON (сцены, катсцены, карты)

`ArtDoc` — векторная картинка: слои примитивов в координатах холста
**1280×720** (у сцен и слайдов — та же система, что у слотов):

```json
"art": {
  "canvas": { "w": 1280, "h": 720 },
  "background": "#1a2230",
  "layers": [
    { "label": "небо", "shape": { "type": "rect", "x": 0, "y": 0, "w": 1280, "h": 380,
      "fill": { "gradient": { "from": "#2b3a55", "to": "#7f9bb8", "angle": 90 } } } },
    { "label": "холм", "shape": { "type": "polygon", "points": [0,380, 260,240, 520,380], "fill": "#2f4a34" } },
    { "label": "дверь", "shape": { "type": "rect", "x": 1046, "y": 388, "w": 96, "h": 176, "fill": "#5a3a22", "radius": 6 } },
    { "label": "лунный свет", "shape": { "type": "ellipse", "cx": 980, "cy": 120, "rx": 70, "ry": 70, "fill": "#e8e6d8", "opacity": 0.35 } }
  ]
}
```

Сцена уже показывает название в интерфейсе: не дублируй его крупным текстом
внутри рисунка. Если надпись действительно нужна как часть мира (например,
вывеска), размещай её внутри холста с запасом от краёв и проверяй на экране.
Не закрывай большую часть сцены однотонной прямоугольной «плашкой»: крупные
стены и объекты должны читаться как часть локации, иметь детали/светотень и
не перекрывать важные точки сцены.
Примитивы: `rect` (x,y,w,h,fill,stroke,radius), `ellipse` (cx,cy,rx,ry),
`polygon` (points:[x1,y1,…]), `line` (x1,y1,x2,y2,color,width),
`text` (x,y,text,size,color,align,bold). У каждого — `opacity`, `rotate`.
Заливка `fill` — цвет (`"#4a7"`) или линейный градиент
(`{"gradient": {"from": "#000", "to": "#fff", "angle": 45}}`).

**Правило слотов: сначала рисуешь объект — потом ставишь слот по его же
координатам.** Нарисовал дверь прямоугольником `x:1046, y:388, w:96, h:176`
— слот/зону перехода кладёшь туда же:

```json
"navigation": [ { "label": "Выйти к рынку", "go_to_scene": "scene_market",
                  "area": { "x": 1046, "y": 388, "w": 96, "h": 176 } } ]
```

Это главная причина ArtDoc: генератор сам знает, где что нарисовал.

**Соотношение ArtDoc и растровых иллюстраций (`image`):**
- Векторный `ArtDoc` создаётся как процедурная заглушка, чтобы кампания выглядела цельно и работала сразу при первой генерации без ожидания генерации файлов картинок.
- Когда для состояния сцены или слайда готово полноценное растровое изображение (`image`: `.jpg`, `.png`, `.webp`), движок автоматически даёт ему высший приоритет в отображении.
- **Очистка заглушек:** при добавлении нормального изображения `image` обязательно **удаляй поле `art`** из соответствующего состояния, чтобы не раздувать JSON сотнями строк неиспользуемого векторного кода.

## 7. scenes — сцены

```json
"scene_tavern": {
  "id": "scene_tavern", "label": "Зал таверны", "location": "loc_town",
  "canvas": { "w": 1280, "h": 720 },
  "states": [
    { "id": "state_base", "label": "Основное состояние", "image": "assets/img/scenes/tavern_base.jpg", "condition": null },
    { "id": "state_night", "label": "Ночь", "image": "assets/img/scenes/tavern_night.jpg", "condition": { "time_of_day": ["night"] } }
  ],
  "slots": [
    { "id": "slot_barkeep", "label": "За стойкой", "type": ["person"],
      "x": 560, "y": 320, "w": 140, "h": 320, "default_entity": "npc_barkeep", "condition": null }
  ],
  "navigation": [
    { "label": "На улицу", "go_to_scene": "scene_market", "area": { "x": 40, "y": 360, "w": 120, "h": 240 } },
    { "label": "На карту", "open_map": true, "area": { "x": 1160, "y": 40, "w": 100, "h": 100 } }
  ]
}
```

- `states` — фоны и состояния сцены. **Строгий регламент порядка и названий состояний:**
  1. **Первым (`states[0]`) ВСЕГДА идёт базовое (основное) состояние сцены** — без условий (`"condition": null`). Это гарантирует, что в редакторе сцен мастер сразу видит чистое дневное/базовое состояние комнаты, а не ночной частный случай. Называйте его чисто («Основное состояние», не пишите в названии странные «Всегда» или «Днём»).
  2. **Затем идут альтернативные состояния с условиями** (`condition: { time_of_day, flag, not_flag }`) — ночь, разруха, пожар, осада.
  Движок в игре автоматически отдаёт приоритет специфическим состояниям с условиями, если они выполнены, а при отсутствии активных условий возвращается к базовому состоянию. У фона — **либо `image` (файл/ссылка), либо `art`**.
- `slots` — места, куда встают НПС/предметы (`type` фильтрует, кого можно:
  `person` / `item` / `container` / `animal` или свои типы кампании).
- `navigation` — только **внутри локации**: `go_to_scene` (сцены ТОЙ ЖЕ
  локации) или `open_map: true` (выход из локации). Переходов «в другую
  локацию» не существует — только через карту.
- `particles` — кинематографические частицы атмосферы сцены: `"dust"` (пылинки в лучах света),
  `"steam"` (клубы пара и дыма), `"sparks"` (искры), `"embers"` (тлеющие угли),
  `"rain"`, `"snow"`, `"fog"`, `"ash"`, `"none"`. Движок накладывает их живым слоем поверх сцены.
- `narrative_intro` — вводное кинематографичное повествование сцены (стиль визуальной новеллы). Массив строк либо объектов с озвучкой и звуковыми эффектами:
  `"narrative_intro": [ "Холодный пар поднимался из шахты...", { "text": "Впереди послышался металлический скрежет.", "voice": "assets/audio/voice/intro1.mp3", "sfx": "snd_latch" } ]`.
  - `narrative_intro_once` (boolean, по умолчанию `true`): показывать только один раз за забег (просмотренные сцены запоминаются в `seen_narrative_intros`). При `false` показывается каждый раз при входе на сцену.
  - Подписи кнопок листания: глобально настраиваются в `meta.ui_labels` (`scene_intro_next`: «Далее ▶», `scene_intro_done`: «Осмотреться ▶»), либо индивидуально в `SceneDef`: `narrative_intro_next_label`, `narrative_intro_done_label`.

### Хотспоты окружения vs Спрайты предметов на сцене:
- Если интерактивный объект (ящик с кладью, шкаф, вентиль, дверь, терминал) **уже нарисован на фоне сцены**, НЕ задавай предмету `scene_sprite`!
- В слоте сцены укажи `"environmental": true` (или движок определит беспрайтовый предмет автоматически).
- **Оформление беспрайтовых хотспотов**: у предметов без спрайта отображается **только чистая центрированная подпись** — ровно так же, как у зон переходов (`nav-zone`). Никаких уродливых рамок, фоновых плашек, маркеров с кружками и глифов ни в покое, ни при наведении мыши! Сцена остаётся абсолютно чистой и кинематографичной.
- При наведении курсора подпись предмета мягко подсвечивается золотом.
- А при зажатии игроком клавиши `Tab` (или клике на кнопку глаза в шапке сцены) над всеми активными точками сцены плавно всплывают красивые светящиеся линзы, исключая пиксель-хантинг.
- Свойство `scene_sprite` задавай только предметам, которые реально накладываются поверх фона (выброшенный ключ, выпавший сверток, лут на полу).

## 8. entities — НПС и предметы

```json
"npc_barkeep": {
  "id": "npc_barkeep", "type": "npc", "label": "Хозяйка Марта",
  "description": "Хозяйка таверны. Знает все новости города и ценит порядок.",
  "portrait": { "neutral": "" },
  "stats": { "STR": 11, "CON": 12, "SIZ": 13, "DEX": 10, "INT": 13, "POW": 11, "CHA": 14 },
  "skills": { "persuade": 45, "bargain": 50 },
  "inventory": [ { "item": "item_silver", "quantity": 20 } ],
  "equipment": { "weapon": "item_knife" },
  "dialogue": "dialogues/marta.ink",
  "slot_type": "person",
  "schedule": [ { "time_range": [8, 22], "location": "loc_town", "scene": "scene_tavern", "slot": "slot_barkeep" } ],
  "faction": "faction_town",
  "trader": { "sells": [ { "item": "item_bread", "price": 2 } ], "buys": true, "buy_rate": 0.5 }
}
```

У каждой сущности (NPC и предмета) есть поле `description` — **обязательное**
краткое описание в стиле мира: игрок видит его при наведении на сущность в
игре (имя + описание). Описание может **меняться в ходе игры** действием
`set_description` (в правилах, диалогах и квестах): укажите `entity` (id
сущности) и `text` (новый текст). Так описание отражает состояние мира —
например, «Маэва благодарна после задания с крысами».

**Три изображения НПС** (блок 3 ТЗ) — каждое для своего места, с фолбэками:

- `portrait` (обязателен) — **портрет для диалога**, `состояние → картинка`
  (состояния — из реестра эмоций кампании, базовое — `neutral` или `default`).
  **Мимика и эмоции персонажа поддерживаются движком в реальном времени**: не дублируй
  один и тот же файл во все ключи! Для ключевых персонажей задавай разные кадры выражения
  лица (например, neutral, angry, sad, afraid). В диалоге мимика мгновенно
  переключается тегом реплики `# emotion: angry` либо командой `~ set_entity_state("npc_id", "angry")`.
- `scene_sprite` — **спрайт в сцене**: картинка с вырезанным фоном
  (прозрачный PNG), которой персонаж стоит в слоте сцены. Нет — в сцене
  используется портрет `neutral`. Размер спрайта в слоте настраивается полем
  слота `sprite_scale` (1 = по высоте слота).
- `combat_figure` — **фигурка боя**: отображается на арене вместо круглого
  жетона (без рамки) и разворачивается при движении/атаке. Режим `figure_mode`:
  `topdown` — вид сверху (поворот, по умолчанию), `side` — вид сбоку (зеркало
  влево/вправо), `static` — не разворачивать. Нет фигурки — рисуется круглый
  жетон из `token` (а нет `token` — из портрета `neutral`).
- `combat_figure_states` — **состояния фигурки боя**: объект `ключ → картинка`.
  Ключи: `dead` (персонаж погиб), `down` (без сознания/выведен из боя),
  `id статуса` (пока статус активен — бафф, горение…). Нет ключа — обычная фигурка.
- `shadow: false` — убрать мягкую тень под спрайтом/фигуркой (по умолчанию есть).
- `breathe: false` — отключить эффект живого дыхания спрайта в сцене. **Обязательно отключай (`"breathe": false`) для роботов, автоматонов, механизмов, големов, турелей и нежити.** Для живых персонажей эффект включён по умолчанию. У предметов по умолчанию отключён, но может быть включён (`"breathe": true`) для живых/пульсирующих артефактов (мимик, био-сердце).
- `unknown_label` — **механика «Незнакомец» (инкогнито до знакомства)**: имя или описание
  персонажа, пока герой не узнал, кто это (например, «Незнакомка в платке», «Мужчина со шрамом»).
  Пока имя не раскрыто, игрок видит `unknown_label` над спрайтом в сцене, в тултипах и в шапке
  диалога. Имя раскрывается эффектом `learn_name` («Вы узнали: «Незнакомка в платке» — это Ира Ярова»),
  командой в Ink `~ learn_name("npc_ira")` или правилом. Проверить статус знакомства можно
  условием `npc_known`.

**⚠️ ВАЖНО: Требования к изображениям**

Без фона (прозрачный PNG с альфа-каналом):

- **Эмблема/лого меню (`theme.menu.title_art`)** — ОБЯЗАТЕЛЬНО прозрачный фон:
  арт рисуется поверх `theme.menu.background`, и собственный фон картинки
  превращается в чёрный/белый квадрат посреди меню.
- **Спрайты для сцен (`scene_sprite`)** — ОБЯЗАТЕЛЬНО с прозрачным фоном (PNG с альфа-каналом).
- **Фигурки боя (`combat_figure`)** — ОБЯЗАТЕЛЬНО с прозрачным фоном.
- **Рамка интерфейса (`theme.frame`)** — ОБЯЗАТЕЛЬНО прозрачный PNG (9-срезов).
- **Портреты (`portrait`)** — могут быть с фоном или без, но рекомендуется прозрачный фон.
- **Иллюстрации кодекса и предметов** — рекомендуется прозрачный фон для лучшей интеграции.

С фоном (сплошное полноэкранное изображение):

- **Фон главного меню (`theme.menu.background`)** и **фон финала (`theme.end.background`)**.
- **Фоновые изображения сцен и катсцен** (состояния сцены, слайды катсцен).

Не используй белый или цветной фон для спрайтов и фигурок — они будут отображаться с артефактами!
Аудит кампании проверяет углы картинок ролей «без фона» на прозрачность и
помечает непрозрачные предупреждением.
14. Подписи реестров (`skills`, `skill_categories`, `crimes`, `price_events`,
    `flags`, `statuses`, `needs`, `factions`) пиши человекопонятно, без код
    id, префиксов и служебных символов: именно эти строки видят игрок в HUD
    и мастер в редакторе («Бой», а не `fight`; «Перекрытые поставки», а не
    `price_blockade*1.5`). Код id живёт в отдельном поле и назначается сам.

```json
"item_bread": {
  "id": "item_bread", "type": "item", "category": "food",
  "label": "Хлеб", "description": "Тёплый каравай.", "image": "",
  "weight": 0.3, "stackable": true,
  "value": { "silver": 2 },
  "on_use": { "effects": [ { "type": "change_need", "need": "need_hunger", "delta": 25 } ], "consume": true }
}
```

- `image` — изображение предмета: отображается миниатюрой в инвентаре и окне торговли, крупной иллюстрацией в карточке детального осмотра предмета, а также в галерее выбора улик при `present_item`. При отсутствии `image` движок использует первый кадр `scene_sprite` или нейтральный портрет.
- `dialogue` — всегда путь `dialogues/<id>.ink` (не голый id без папки; импорт
  починит, но лучше сразу писать путь). Сам диалог — §13, ключ `<id>`.
- `stats` — характеристики BRP (по умолчанию 10). HP/MP считаются от них.
- `schedule`/`presence_overrides` — расписание перемещений («днём в таверне,
  ночью в казарме»); `presence_overrides` важнее и живёт, пока стоит флаг.
  **Пустой `schedule: []`** — это «расписания нет», не «персонаж нигде».
  Такой НПС показывается через `default_entity` слота (как стационарный
  проп). Непустой `schedule` с другой сценой **блокирует** `default_entity`
  в текущей — не дублируй одну и ту же сущность и слотом, и расписанием.
- `base_disposition` — стартовое отношение к NPC. Диалоги/эффекты
  `change_disposition` копят **личный** сдвиг по id персонажа (фракция
  необязательна). Итог в проверках: base + личный + фракция + настроение.
- **Показать NPC только по флагу** — не выдумывай новую механику: у NPC
  `presence_overrides: [{ "flag": "…", "scene": "…", "slot": "…" }]` важнее
  `schedule` и `default_entity`. Пока флаг поднят — персонаж только там;
  иначе живёт по расписанию (или нигде, если schedule пуст и default не его).
- `loot_table` — что выпадет после боя: `[{ "item", "chance", "min"?, "max"? }]`.
- `natural_weapon` — когти/зубы: `{ "skill": "brawl", "damage": "1d6",
  "damage_bonus": true, "range": 1, "attacks_per_round": 1, "parry_capable": false }`.
- Категория (`category`) управляет свойствами: `food`/`drink`/`medicine`
  восстанавливают потребности/HP из `on_use`, `weapon`/`armor` — бой
  (`weapon_data`, `armor_data`), `container` — контейнеры сцены.
- `quest_item: true` — сюжетный/квестовый предмет: игрок не может случайно выбросить его из инвентаря или продать торговцу в лавке (защита от потери критических улик, ключей и артефактов).

**Предмет в сцене** (интерактив): поля предмета, влияющие на его жизнь в слотах:

- `scene_sprite` — картинка предмета в слоте сцены (целиком, как у НПС).
  Нет — слот выглядит пустым (ни портретов, ни обычного изображения там не будет).
- `portrait` — состояния портрета предмета `emotion → картинка` для окна действий
  (ключи — из реестра эмоций кампании; `neutral` — по умолчанию).
- `interactable_when` — массив условий (тот же формат, что в §9): пока условия
  ложны, предмет в слоте — «декорация»: виден, но не нажимается.
- `interact_hint` — короткая подсказка действия под курсором при наведении на предмет в сцене («Осмотреть замок», «Повернуть вентиль», «Собрать травы»). Если не задан — игроку показывается обычное описание предмета.
- `interact_options` — варианты действий при клике (мини-диалог с портретом
  предмета и описанием):

```json
"interact_options": [
  {
    "label": "Собрать траву",
    "hint": "можно только в ясную погоду",
    "emotion": "open",
    "conditions": [ { "type": "weather_is", "value": "clear" } ],
    "effects": [ { "type": "add_item", "item": "item_herb", "qty": 1 } ],
    "message": "Набрали охапку пахучей зелени.",
    "consume": true,
    "sound": "use"
  }
]
```

Если `interact_options` не задан — работает старое одно действие `on_interact`
(либо просто показывается описание).

## 8б. Рецепт: интерактивный проп / говорящий предмет

Колодец, зеркало, радиоточка, сейф, доска объявлений — на бумаге это всё
«пропы». В движке у них **два разных пути**, и путать их нельзя: предупреждение
«используется как персонаж, но описана как предмет» на импорте означает, что
агент выбрал не тот путь. Выбирай по тому, что делает игрок.

### Путь 1. Говорящий объект — это `type: npc`

Колодец, зеркало, радиоточка, статуя, altar: объект **отвечает или отдаёт
сведения**. Клик открывает диалог — так и задумано дизайном.

```json
"npc_well": {
  "id": "npc_well", "type": "npc", "label": "Старый колодец",
  "description": "Каменный колодец с истёртым ободом. Внутри темно.",
  "portrait": { "neutral": "assets/img/prop/well.jpg" },
  "dialogue": "dialogues/well.ink",
  "slot_type": "prop",
  "schedule": [],
  "stats": { "STR": 8, "CON": 8, "SIZ": 8, "DEX": 8, "INT": 8, "POW": 8, "CHA": 8 },
  "skills": {}
}
```

- `type` — обязательно `npc`. Именно поэтому «говорящий предмет» и выглядит
  как персонаж: для движка это персонаж, который стоит на месте.
- Стационарность: пустой `schedule: []` (или расписание только с одной сценой) —
  он никуда не уходит. Никаких перемещений. Обязательно поставь его
  `default_entity` в слот сцены — иначе на экране его не будет.
- Боя нет: не задавай `combat_ai`, не ставь в `enemies` боя. Если нужна защита
  (например, огрызок из колодца), это отдельный `npc` рядом, а не сам колодец.
- `dialogue` — `.ink`; вход в диалог даёт эффект `start_dialogue` из правила
  или клик по слоту (клик по НПС в сцене сам открывает его диалог).
- `portrait.neutral` — картинка в окне диалога; состояния (`angry`, `calm`…)
  добавляются по желанию и переключаются `set_entity_state`. Пустая строка
  `""` в portrait/art/image допустима (нет файла ещё) — UI не ставит битый
  `<img>`, показывает плейсхолдер.

### Путь 2. Осматриваемый объект — это `type: item` в слоте сцены

Сейф, доска объявлений, сундук, брошенная телега: объект **осматривается и
обычно что-то выдаёт**. Ему не нужна реплика.

```json
"item_safe": {
  "id": "item_safe", "type": "item", "category": "misc", "label": "Железный сейф",
  "description": "Тяжёлый сейф с чуть погнутой дверцей.",
  "weight": 40, "stackable": false,
  "scene_sprite": "assets/img/prop/safe.jpg",
  "portrait": { "neutral": "assets/img/prop/safe.jpg" },
  "interact_options": [
    {
      "label": "Взломать",
      "conditions": [ { "type": "has_item", "item": "item_lockpicks" } ],
      "effects": [
        { "type": "skill_check_gate", "skill": "stealth", "difficulty": 55,
          "success_effects": [ { "type": "add_item", "item": "item_ledger", "quantity": 1 },
                                { "type": "set_flag", "flag": "safe_opened" } ],
          "fail_effects": [ { "type": "show_message", "text": "Замок щёлкнул и не поддался." } ] }
      ],
      "message": "Внутри — гроссбух казнака."
    }
  ]
}
```

- `type: item`, ставится в **слот сцены** (`scenes[].slots[].default_entity`).
- Реакции: `description` (виден при наведении), `use_with` (предмет →
  слот: «ключ к двери», §14е), `interact_options`/`on_interact` (варианты
  действий) и **правила-триггеры** на `flag_set`/`player_enters_scene`.
- Такой объект не разговаривает. Если ему всё-таки нужно сказать реплику —
  это путь 1 (объяви его `npc`).

### Как не ошибиться (коротко)

| Хочется | Тип | Куда кликает игрок |
| --- | --- | --- |
| объект говорит/отвечает | `npc` + `dialogue` | в диалог |
| объект осматривается/отдаёт | `item` + `interact_options` | в варианты действий |
| объект открывается ключом | `item` + `use_with` в слоте | в применение ключа |
| объект меняет мир по событию | `item`/`npc` + правило | правило ловит флаг/сцену |

## 8в. Пирамида приоритетов генерации ассетов (Asset Generation Milestones)

ИИ-агент или сценарист не может сгенерировать 200 изображений одновременно из-за ограничений контекста и времени. Генерация строится строго **поэтапно по 4 уровням приоритета**:

```
        ▲
       / \     Уровень 4: Вторичные детали (иконки лута, погодные вариации)
      /───\
     /     \    Уровень 3: Сюжетное погружение (катсцены интро/концовок, quest_item)
    /───────\
   /         \   Уровень 2: Атмосфера и бой (эмоции NPC, боевые арены, фигурки)
  /───────────\
 /             \  Уровень 1: КРИТИЧЕСКИЙ КАРКАС (титул, фоны сцен, нейтральные лица, карта)
─────────────────
```

### Уровень 1: Критический каркас (100% играбельный билд)
Это абсолютный минимум, без которого кампания визуально не запускается:
1. **Главная обложка/титул кампании** (`meta.title_art` или `cover`): формирует лицо проекта.
2. **Базовые фоны всех стартовых и ключевых сцен** (`scene_*.jpg`): игрок видит мир, а не заглушки.
3. **Основные портреты ключевых NPC с нейтральной эмоцией** (`neutral`): диалоги оживают.
4. **Растровая карта главного региона** (`map_image`): топология мира и дорожная сеть.
*(На этом этапе все предметы и ящики оформляются как невидимые хотспоты `environmental: true` без отдельных картинок, а боевые фигурки и звуки используют системные фолбэки).*

### Уровень 2: Атмосфера и боевой слой
Кампания оживает в динамике:
1. **Эмоциональные портреты NPC** (`angry`, `scared`, `happy`): реакция персонажей на выборы игрока.
2. **Фоны тактических боевых арен** (`arena_*.jpg`): атмосфера схваток.
3. **Боевые фигурки персонажей** (`combat_figure`): топдаун или изометрические токены на гексах.

### Уровень 3: Сюжетное погружение
Кинематографичные моменты:
1. **Слайды вступительных и финальных катсцен** (`cutscenes`): интро, ключевые сюжетные видения и эпилоги.
2. **Спрайты ключевых сюжетных предметов** (`quest_item`): артефакты, гроссбухи, важные улики.

### Уровень 4: Полировка и вторичные детали
Финальный лоск:
1. Иконки обычного расходного инвентаря (бинт, отмычка, факел, монеты).
2. Альтернативные погодные или временные вариации фонов сцен (дождь, ночь, закат).
3. Второстепенные статисты (стражник у ворот, прохожий).

> **Правило для ИИ:** Всегда начинай работу со сборки **Уровня 1**. Мастер может скорректировать требования или заказать генерацию пакетом под конкретный этап.

## 9. rules — правила

```json
"rule_ambush": {
  "id": "rule_ambush", "label": "Засада на дороге", "once": true, "manual": false,
  "conditions": [
    { "type": "player_enters_location", "location": "loc_forest" },
    { "type": "flag_not_set", "flag": "forest_ambush_cleared" }
  ],
  "effects": [
    { "type": "start_combat", "enemies": [ { "entity": "npc_bandit", "count": 2 } ],
      "arena": "arena_forest", "intro": "Из-за деревьев выскакивают разбойники!",
      "on_victory": [
        { "type": "set_flag", "flag": "forest_ambush_cleared" },
        { "type": "show_message", "text": "Тропа снова тиха." }
      ] }
  ]
}
```

- Условия списка соединены по «И» (для «ИЛИ» — `conditions_any` с группами).
  Полный список условий — §9б.
- Полный список эффектов — §9в. Здесь только то, что чаще всего нужно рядом с
  самим правилом.
- `trigger` в правилах (`RuleDef.trigger`) — **событийные триггеры движка**:
  - `always` (по умолчанию) — правило проверяется при каждом изменении состояния мира;
  - `enter_scene` — срабатывает в момент входа на сцену;
  - `leave_scene` — срабатывает при попытке игрока уйти со сцены (может перехватить переход);
  - `interact` — срабатывает при взаимодействии с объектом/слотом сцены;
  - `time_tick` — срабатывает на каждом тике времени при отдыхе, сне или переходе между локациями.
  - **КРИТИЧЕСКИ ВАЖНО для стартовых правил пролога (`rule_intro`)**: стартовое правило на нулевой тик (`tick_elapsed: 0`) или запуск вступительной катсцены ОБЯЗАНО иметь `trigger: "always"` (или опускать поле `trigger`). НЕ ставь `trigger: "time_tick"` на вступительные правила — иначе правило будет ждать первого реального тика времени (сна/отдыха) и при старте новой игры катсцена не запустится!
- **Перехваты навигации в зонах перехода сцен (`NavigationZone`)**:
  - `conditions` — условия доступности перехода (все должны выполниться);
  - `blocked_message` — атмосферное сообщение при блокировке (например, «Дверь заперта на засов изнутри»);
  - `intercept_dialogue` — диалог-оклик перед уходом: при клике на выход вместо перехода запускается разговор (например, караульный окликает героя перед дверью);
  - `intercept_rule` — id правила-перехватчика.
- `show_message` показывает сообщение с необязательным портретом:
  `{ "type": "show_message", "text": "…", "portrait": "assets/img/npc/…jpg" }`.
  В редакторе путь к портрету не вводится вручную: берётся портрет одного из
  существующих персонажей или загружается своё изображение.
- `once: true` — срабатывает один раз за забег; `manual: true` — не
  проверяется само, вызывается из диалога (`fire_rule`) или потребностью
  (`on_zero_effect`).

## 9б. Полный список условий

Правило, рецепт, `interact_options`, `use_with` и параметры достижений берут
условия из одного списка. Условия соединяются по «И»; для «ИЛИ» есть
`conditions_any` (группы) и сами операторы `and`/`or`/`not`.

### Условия мира и героя

| Тип | Поля | Когда истинно |
| --- | --- | --- |
| `player_enters_location` | `location` | герой вошёл в локацию |
| `player_enters_scene` | `scene` | герой вошёл в сцену |
| `flag_set` | `flag` | флаг поднят |
| `flag_not_set` | `flag` | флаг не поднят |
| `variable_compare` | `var`, `operator` (`==`/`!=`/`<`/`>`/`<=`/`>=`), `value` | сравнение переменной |
| `time_of_day` | `value` (строка или список: `"night"`, `["evening","night"]`) | сейчас такое время суток |
| `tick_elapsed` | `min_tick` | прошло ≥ N тиков (проверяется после `advanceTicks`/переходов) |
| `weather_is` | `weather` (`""` — ясно) | текущая погода равна |
| `has_item` | `item`, `min_quantity?` | у героя есть предмет (количество ≥) |
| `equipped` | `item` | предмет надет / экипирован на герое |
| `entity_alive` / `entity_dead` | `entity` | сущность жива / в списке мёртвых |
| `in_party` | `entity` | персонаж в отряде |
| `disposition_ge` / `disposition_le` | `target` (фракция или NPC), `threshold` | отношение ≥ / ≤ |
| `has_status` | `status` | статус активен на герое |
| `random_chance` | `probability` (0..1) | случайный бросок |

### Условия проверок и потребностей

| Тип | Поля | Когда истинно |
| --- | --- | --- |
| `skill_ge` | `skill`, `threshold` | навык героя ≥ порога |
| `stat_ge` | `stat` (`"POW"`), `threshold` | характеристика ≥ |
| `hp_ge` / `hp_le` | `threshold` | здоровье ≥ / ≤ |
| `luck_ge` | `threshold` | удача ≥ |
| `fatigue_ge` / `fatigue_le` | `threshold` | усталость ≥ / ≤ |
| `sanity_ge` / `sanity_le` | `threshold` | рассудок ≥ / ≤ |
| `need_ge` / `need_le` | `need`, `threshold` | потребность ≥ / ≤ |
| `quest_at_stage` | `quest`, `stage` | квест на стадии |

### Условия хроники и прогресса (между забегами)

| Тип | Поля | Когда истинно |
| --- | --- | --- |
| `meta_counter` | `key`, `ge` | счётчик хроники ≥ `ge` |
| `meta_achievement` | `id` | достижение открыто |
| `meta_currency_ge` | `currency`, `threshold` | метавалюта ≥ |
| `level_ge` | `level` | уровень героя ≥ |
| `has_feat` | `id` | черта уже есть |
| `passion_ge` | `id`, `value` | страсть ≥ |
| `allegiance_ge` | `id`, `points` | привязанность/принадлежность ≥ |
| `wealth_ge` | `level` | уровень достатка ≥ |
| `reputation_ge` | `threshold` | репутация ≥ |
| `power_level_ge` | `level` (`"normal"`, `"heroic"`, `"epic"`, `"superhuman"`) | режим сложности кампании ≥ |
| `crime_committed` | `id?`, `min_bounty?` | зарегистрированное преступление (с фильтром) |
| `bounty_total_ge` | `threshold` | суммарный долг ≥ |

**`meta_counter` — «а сколько раз это уже было».** Ключи: `endings_seen`
(сколько **разных концовок** видел игрок), `runs`, `deaths`, `victories` и
любой счётчик забега: `kills`, `quests_completed`, `ticks_survived`,
`travels`, `dialogues` (для них берётся сумма прошлых забегов **плюс**
текущий). Работает только при включённом `meta.metaprogress`. Пример
NG+-ветки: «герой, видевший 2+ концовок, получает реплику-предложение» —

```json
{ "type": "meta_counter", "key": "endings_seen", "ge": 2 }
```

### Логика

| Тип | Поля |
| --- | --- |
| `and` | `conditions` — все истинны |
| `or` | `conditions` — хотя бы одно истинно |
| `not` | `condition` — вложенное условие ложно |

## 9в. Полный список эффектов правил

Эффекты работают в правилах, в `use_with` предметов, в `interact_options`,
в переходах квестов и в генераторах. Полный список — не «на самое важное»:
**если эффекта нет в этой таблице, его нет в движке.**

### Флаги, переменные, состояние мира

| Тип | Поля | Что делает |
| --- | --- | --- |
| `set_flag` / `clear_flag` | `flag` | поднять / сбросить флаг |
| `set_variable` / `change_variable` | `var`, `value` / `delta` | записать / изменить переменную |
| `set_description` | `entity`, `text` | заменить описание сущности (видно при наведении) |
| `set_entity_state` | `entity`, `state` (`""` — обычный облик) | сменить состояние облика персонажа: портрет в диалоге и спрайт в сцене |
| `change_scene_state` | `scene`, `state` | сменить фон сцены на другое состояние |
| `set_weather` | `weather` (`""` — ясно) | сменить погоду |
| `advance_time` | `ticks` | промотать мир |
| `teleport_player` | `location`, `scene?` | перенести героя |
| `spawn_entity` / `remove_entity` | `entity` (+`scene`,`slot`) | поставить/убрать сущность |
| `block_path` / `unblock_path` | `from`, `to` | закрыть/открыть дорогу между локациями |
| `reveal_location` | `location` | открыть точку на карте |

### Проверки и ветвления

| Тип | Поля | Что делает |
| --- | --- | --- |
| `skill_check_gate` | `skill`, `difficulty`, `success_effects`, `fail_effects` | бросок навыка → две ветки |
| `stat_check` | `stat`, `multiplier?`, `modifier?`, `success_effects`, `fail_effects` | бросок характеристики |
| `opposed_check` | `skill`, `entity?`/`against_skill?`/`against_value?`, `tie?`, `success_effects`, `fail_effects` | противоборство (герой против NPC) |
| `group_stat_check` | `skill?`/`stat?`, `helpers?`, `need?`, `success_effects`, `fail_effects` | сцепленная проверка героя и союзников |
| `start_pursuit` | `label?`, `skill?`, `every_ticks?`, `fails_to_catch?`, `on_fail` | погоня: каждые N тиков цепочка проверок; провал → `on_fail` |
| `stop_pursuit` | — | погоня окончена (оторвались) |
| `hazard_fall` | `meters`, `skill?` | падение с высоты (урон + смягчающая проверка) |
| `fire_rule` | `rule` | вызвать другое правило по id |

### Герой: вещи, здоровье, навыки

| Тип | Поля | Что делает |
| --- | --- | --- |
| `add_item` / `remove_item` | `item`, `quantity?` | выдать/забрать предмет |
| `change_need` | `need`, `delta` | сдвинуть потребность |
| `change_hp` | `delta` | здоровье ± |
| `change_skill` | `skill`, `delta` | изменить навык |

### `fire_rule` — правило вызывает правило

Раньше вызвать правило из правила было нельзя, и вместо этого всей мирились
на паре «предмет ставит флаг → отдельное правило ловит `flag_set`». Теперь
эффект есть и в правилах, и в `use_with`, и в `interact_options`:

```json
{ "type": "fire_rule", "rule": "rule_open_safe" }
```

Правила кампании:

- вложенных вызовов не больше **2** (эффект → правило → правило; третий
  уровень отбрасывается и пишется в журнал);
- правило не должно вызывать себя напрямую и транзитивно — петля ловится
  «Проверить кампанию» отдельным предупреждением с цепочкой;
- семантика `once` вызываемого правила сохраняется: повторный вызов — no-op.

## 10. quests — квесты

`journal_entries` — это словарь **внутренний ключ → русский текст записи**.
Ключи записей независимы от id стадий: например, stage_start может
публиковать запись j_start. Связывай их только через эффект `journal_update`
(`quest` + точный `text_key`). Не переименовывай ключ в id стадии и при любом
изменении ключа обновляй все ссылки на него. Редактор показывает текст записи
и стадию, которая её публикует, а не технический ключ.

```json
"quest_relic": {
  "id": "quest_relic", "label": "Утраченная реликвия", "description": "Найти медальон.",
  "journal_entries": { "j_start": "Марта просит найти фамильный медальон." },
  "stages": [
    { "id": "stage_start", "label": "Поиски", "on_enter_effects": [ { "type": "journal_update", "quest": "quest_relic", "text_key": "j_start" } ],
      "transitions": [ { "to": "stage_done", "conditions": [ { "type": "has_item", "item": "item_medallion" } ] } ] },
    { "id": "stage_done", "label": "Возвращение", "final": true, "outcome": "success" }
  ]
}
```

У каждой стадии есть `id` и русское `label`; переходы — `transitions` с
условиями; `final` + `outcome` — завершение. `journal_entries` — тексты
записей журнала по `text_key`.

## 11. arenas — арены боёв

Гексовое поле `hex_grid` (`cols`, `rows`, `hex_size`, `offset: "odd-r"`,
`blocked_hexes`, `difficult_terrain`), `spawn_zones.player` / `spawn_zones.enemy`
— списки гексов `[col, row]`, 0-based. `image` — фон/вид сверху (можно
пустым). `music` — id трека реестра (§14).

## 12. cutscenes — слайд-катсцены

```json
"cutscene_intro": {
  "id": "cutscene_intro", "label": "Пролог", "music": "music_omen",
  "slides": [
    { "art": { … }, "text": "Долина Каэрдена спала под пеплом…", "duration": 6, "transition": "panzoom" },
    { "art": { … }, "text": "Сожжённый караван.", "transition": "fade" },
    { "image": "", "video": "", "art": { … }, "text": "Ворота города.", "transition": "slide" }
  ]
}
```

- Кадр слайда — **одно из**: `art` (ArtDoc), `image` (файл/ссылка),
  `video` (mp4-ссылка или YouTube — работает только онлайн; это исключение).
- `text` — подпись поверх кадра снизу; `duration` — секунды (по умолчанию —
  по длине текста); `transition` — `cut` | `fade` | `slide` | `panzoom`;
  `voice` — озвучка слайда (§13.1).
- Запуск: эффект `play_cutscene` (`{ "type": "play_cutscene", "cutscene": … }`)
  из правила, квеста или диалога. Стартовую катсцену кампании вешай на
  правило с условием `tick_elapsed` (первый тик забега), `once: true`, `trigger: "always"` (или без поля `trigger`).

## 13. dialogues — диалоги конструктора

### 13.0 Разговор словами (мастерский сценарий, поле `script`)

Мастер-человек пишет разговоры **текстом**, а не узлами: текст лежит в том же
`.dlg.json` в поле `script`, а `nodes` — структура, которую из него собрал
редактор (её читают формы и генератор ink). Если ты пишешь разговор словами,
правила такие:

- `=== Название узла ===` — новый узел; первый узел — начало разговора.
  Без узлов разговор тоже соберётся (первые строки станут началом).
- `— реплика` — говорит собеседник (тире можно не ставить: строка без
  пометки и так реплика). Ремарка автора — `* действие` (в игре курсив).
- `? Ваш ответ.` — вариант игрока; строки после него — ответ собеседника.
- `[если Сделка с Вольтом]` / `[иначе]` — условие для блока ниже или для
  следующего варианта; `[проверка: Убеждение ≥ 45]` (или `— сложно`) и
  `[при успехе]` / `[при провале]` — проверка навыка с ветками.
- `[таймер: 18 → Молчание]`, `[одноразовый]` — дедлайн на раздумье и
  «вариант срабатывает один раз». Таймер работает в реальных секундах на наборе вариантов:
  если игрок молчит, движок уходит в назначенный узел или завершает разговор.
- `→ команда` — то, что меняет мир: `запомнить: <флаг>`, `выдать: <предмет> ×2`,
  `забрать: …`, `отношение: <кто> +20`, `квест: <название> — <стадия>`,
  `правило: <название>`, `облик: <кто> — <состояние>`, `катсцена: <название>`,
  `кодекс: <название>`, `рецепт: <название>`, `статус N`, `потребность ±N`,
  `здоровье ±N`, `торговля`, `изготовление`, `время N`, `погода: <название>`,
  `перейти: <узел>`, `конец`, `остаться`.
- В реплике допустимы пометки в конце: `#облик`, `#озвучка: путь`.
- Названия берутся из реестров кампании (`meta.flags`, `meta.skills`, предметы,
  квесты, …) — служебных id мастер не пишет и не видит. `или` в условии не
  поддерживается (список условий соединяется через «и») — импорт предупредит.
- Ошибка в тексте — не «тихий сбой»: редактор показывает строку и подсказку
  («не понимаю команду», «похожие названия»), а текст остаётся у мастера.
- Важно для ИИ: все узлы и переходы должны иметь понятные человеческие названия на русском
  языке («=== Начало разговора ===», «=== Варианты ответов ===», «=== Стычка ===», «=== Выбор ===»).
  Запрещено оставлять служебные английские кноты (guard, fight, choice, hesitate, dead),
  так как они попадают в интерфейс мастера в Конструкторе. Условия вариантов в ink
  пишутся строго до скобок: `+ { условие } [Текст ответа]`, а не после них.
- **История разговора (Dialogue Backlog):** движок автоматически накапливает полную хронологию
  реплик, ремарок автора и сделанных игроком выборов. В правом верхнем углу диалогового окна
  игроку всегда доступна кнопка **«История»**, открывающая прокручиваемую ленту разговора.

Если ты отдаёшь кампанию монолитом (JSON для «Импорт кампании»), разговор можно
написать текстом:

```json
"dialogues": {
  "marta": { "version": 2, "label": "Марта, хозяйка таверны", "script": "=== Начало разговора ===\n— Добро пожаловать!", "nodes": [] }
}
```

Редактор разберёт `script` в формы и соберёт ink сам. Но в готовом
`.chronicle`-пакете движок исполняет `dialogues/<имя>.ink`: если собираешь пакет
руками, ink в нём обязателен (текст `script` его не заменяет).

```json
"dialogues": {
  "marta": {
    "version": 2,
    "label": "Марта, хозяйка таверны",
    "nodes": [
      { "id": "main", "label": "Начало разговора",
        "sections": [ { "steps": [
          { "kind": "line", "line": { "text": "Добро пожаловать! В кошеле {счёт:item_silver} марок серебром.", "emotion": "happy" } }
        ] } ],
        "choices": [
          { "text": "Что слышно?", "sections": [ { "steps": [
              { "kind": "line", "line": { "text": "Говорят, в лесу разбойники. Берегись, дорогой." } }
            ] } ], "goto": "stay" },
          { "text": "До встречи.", "sections": [], "goto": "end" }
        ] }
    ]
  }
}
```

- `nodes[0]` — начало разговора. Узел: `sections` (реплики НПС с условиями и
  эффектами) + `choices` (варианты игрока). Предпочтительный id стартового
  узла — `main` (так же генерирует редактор). Допустимы `n_start` и любые
  другие: при отсутствии knot `main` движок входит в **первый** `=== knot ===`
  в ink-тексте.
- `steps` — список `{"kind":"line","line":{…}}` и `{"kind":"effect","effect":{…}}`
  вперемешку (порядок важен). У секции можно задать `conds`, ветку
  `else_steps`, и уводящие `goto` / `else_goto`.
- **Ремарка и облик реплики — в самой реплике**: `line.action: true` —
  это авторская ремарка («Она долго смотрит на жетон»), в игре она
  идёт курсивом и **не меняет** лицо собеседника; `line.emotion: "angry"` —
  состояние портрета на эту реплику; `line.voice: "assets/voice/x.mp3"` —
  озвучка. В рукописном ink: `Текст. # action`, `# emotion: angry`,
  `# voice: assets/voice/x.mp3` — теги пишутся в конце строки.
  **Ремарки обязательны**: без `# action` описание действия выглядит как
  реплика героя — игрок «слышит» то, что должно было произойти на экране.
  Правило простое: говорит персонаж — пометки нет; происходит действие —
  пометка ремарки есть.
- **Смена облика по ходу реплики** (сильнее, чем `emotion`): эффект
  `set_entity_state` — `{ "type": "set_entity_state", "entity": "npc_ira",
  "state": "angry" }`; `state: ""` возвращает обычный облик. В ink:
  `~ set_entity_state("npc_ira", "angry")`.
- **`goto`**: `""` — продолжить, `"stay"` — остаться на тех же вариантах,
  `"end"` — конец, или id другого узла. Перепрыгивания на несуществующие
  узлы валидатор заменяет на `end`.
- Условия варианта (`conds`): `flag`, `item_ge`, `has_item`, `disp_ge`,
  `quest`, `in_party`, `hp_ge`, `has_status`, `weather_is`, `skill_ge`
  (навык не ниже порога), `meta_counter` (счётчик хроники — «новый круг»,
  достижения). У каждого — `not: true` для отрицания. Проверка навыка —
  `check: { skill, difficulty, mods?, success: { sections, goto },
  fail: { sections, goto } }`.
- **Запись условий в рукописном ink**: `+ { get_flag("x") } [Текст]`,
  `+ { not (get_flag("x")) } [Текст]`, `+ { has_item("item_tea") and not
  (get_flag("drank")) } [Текст]` — импорт понимает и `not (…)`, и `and`.
  Условие через `or` конструктор не выражает (список условий соединяется
  через «и»): импорт предупредит и оставит первое условие, второе доделай
  в коде ink.
- **Таймер на раздумье** (узел с вариантами): поле `timer` —
  `{ "seconds": 15, "node": "узел_молчания" }`. Игрок видит полоску
  обратного отсчёта; по нулю разговор уходит в узел `node`, а без него —
  заканчивается. В рукописном ink это `~ set_dialogue_timer(15, "узел")`,
  а `~ set_dialogue_timer(15, "")` — просто конец разговора (второй аргумент
  в самой команде обязателен; `0` снимает таймер). Таймер
  ставь там, где молчание — часть сцены (погоня, допрос, «Тихая» у двери),
  и не ставь короче 5–8 секунд: игрок должен успеть прочитать варианты.
  Импорт ink читает `~ set_dialogue_timer(N, "узел")` из узла-развилки
  обратно в поле `timer` — круг «выгрузка → импорт → выгрузка» дедлайн
  не теряет; строка в узле без вариантов ответа — ошибка мастера, импорт
  скажет об этом и покажет, куда её перенести.
- **«Ответь за три секунды или промолчи»** собирается из дедлайна и узла
  молчания: варианты ответа + `timer { seconds: 3, node: "молчание" }`
  (в ink — `~ set_dialogue_timer(3, "молчание")` перед строкой вариантов).
  Таймер идёт в реальном времени, пока игрок выбирает реплику;
  истёк — сцена уходит в узел молчания (отказ, пауза, «он не выдержал»).
  Держи на таком узле 2–3 варианта и читаемый корень, иначе игрок не успеет.
  Для автотаймера на отдельную реплику используй тег `# timer: 3`
  (или `# timeout: 3`) в конце строки: полоска времени покажет секунды, и по
  истечении диалог перейдёт дальше сам.
- Эффекты реплик: `set_flag`, `add_item`/`remove_item` (поле количества в
  диалоге называется `qty`), `fire_rule`, `join_party`, `open_trade` (открывает
  торговлю и закрывает диалог), `open_craft` (открывает изготовление и
  закрывает диалог; поле `recipe` подсвечивает нужный рецепт), `start_quest`,
  `advance_time`, `change_need`, `change_hp`, `sleep`, `change_disposition`,
  `play_cutscene`, `set_description` (`entity`, `text` — динамически меняет
  описание сущности при наведении), `apply_status`/`remove_status`,
  `set_weather`, `unlock_codex`, `unlock_recipe`, `set_entity_state`
  (смена облика персонажа: `entity`, `state`; пусто — обычный облик),
  `learn_name` (`entity` — раскрыть настоящее имя незнакомца),
  `go_to_scene` (`scene` — перейти в другую сцену прямо из диалога),
  `start_combat` (`arena` — начать бой, закрывает диалог),
  `change_scene_state` (`state`, `scene?` — сменить декорацию/состояние сцены под диалогом),
  `game_over_death`/`game_over_victory` (`message?` — завершить игру гибелью или победой).
  «Остальное» из §9в в диалоге недоступно — пиши это правилом и зови
  `fire_rule`.
- Конструктор (`generateInk`) **обязан** объявить `EXTERNAL` для каждой
  команды, которую вызывает `~ …` в сгенерированном ink: в том числе
  `unlock_recipe`, `open_craft`, `present_item`, `set_dialogue_timer`, `unlock_codex`,
  `apply_status`, `set_weather`,
  `set_description`, **токены реплик** (`get_player_name` для `{имя}`,
  `get_hp_max`, `get_currency`…) и прочие из таблицы ниже. Без `EXTERNAL`
  inkjs не скомпилирует файл — диалог не откроется.

### 13.2 Сырой Ink: внешние команды

Если диалог написан руками в `.ink`, движок отдаёт наружу функции вида
`~ имя(аргумент)`. В начале файла перечисли `EXTERNAL имя(…)` для **каждой**
используемой команды (редактор делает это сам). Полезные (полный список —
в `src/core/dialogue.ts`):

| Команда | Что делает |
|---|---|
| `~ set_flag("лес_зачищен")` | поднять флаг |
| `~ add_item("item_x", 2)` / `~ remove_item("item_x", 1)` | выдать/забрать |
| `~ fire_rule("rule_open_safe")` | вызвать правило (вложенность та же) |
| `~ start_quest("quest_x")` | начать квест |
| `~ change_disposition("npc_maeva", 5)` | личное отношение к NPC (±); + base + фракция |
| `~ apply_status("poisoned", 12)` | статус на 12 тиков |
| `~ set_weather("rain")` / `{ weather_is("rain"): … }` | погода и проверка |
| `~ unlock_codex("codex_rat")` / `~ unlock_recipe("recipe_tonic")` | кодекс и рецепт |
| `~ join_party("npc_bor")` / `~ in_party("npc_bor")` | отряд |
| `~ sleep(8)` | сон: время, отдых, рост |
| `~ roll_table("enc_road")` | бросить таблицу событий сейчас |
| `~ gen("npc_names", "first")` | значение генератора |
| `~ stat_roll("POW", 5)` / `~ opposed_roll("persuade", "npc_bor")` | проверки 0/1 |
| `{ skill_check("sneak", 60): … }` / `~ skill_check(…)` | бросок навыка героя: 1 — успех, 0 — провал; две ветки пиши двумя условными блоками или выборами с условием |
| `~ open_trade("npc_marka")` | открыть торговлю с NPC прямо из реплики |
| `~ open_craft("recipe_valve")` / `~ open_craft()` | открыть изготовление из реплики или сцены; с id — нужный рецепт подсвечен «нужно сейчас», без — весь список |
| `~ present_item("узел_успеха", "узел_неудачи", "item_id")` / `~ present_item("ok", "fail", "")` | предложить игроку предъявить предмет/улику из сумки прямо в разговоре: открывает выбор предметов, блокируя реплики. Если предъявлен указанный `item_id` — переход в `узел_успеха`, при неверном предмете или отмене — в `узел_неудачи`. Без третьего аргумента (`""`) принимается любой предъявленный предмет |
| `~ play_sound("snd_shot", 0.9)` | воспроизвести звуковой эффект из `meta.sounds` или путь к файлу прямо из реплики диалога |
| `~ set_dialogue_timer(15, "узел_молчания")` | дедлайн на раздумье у текущих вариантов ответа: по нулю разговор уходит в узел; `~ set_dialogue_timer(15, "")` — просто заканчивается; `0` снимает. Второй аргумент обязателен в самой команде (иначе inkjs не скомпилирует `EXTERNAL set_dialogue_timer(s, t)`), а в документе конструктора поле `timer.node` можно не указывать |
| `~ set_entity_state("npc_irena", "angry")` | сменить эмоцию/облик персонажа репликой (портрет и спрайт); `""` — обычный облик |
| `~ clear_flag("flag_id")` / `~ set_flag("flag_id", false)` | сбросить флаг; в сценарии конструктора: `→ забыть: Флаг` |
| `{ in_party("npc_bor") }` | проверка присутствия спутника в отряде (1 или 0) |
| `{ npc_known("npc_guard") }` / `{ is_name_known("npc_guard") }` | проверка знакомства с NPC (1 или 0) |
| `~ learn_name("npc_guard")` | раскрыть настоящее имя персонажа игроку (механика «Незнакомец») |
| `~ go_to_scene("scene_gate")` | перейти в указанную сцену прямо из диалога (смена ракурса, переезд, телевизор) |
| `~ start_combat("arena_deep")` | начать бой прямо из диалога (диалог закрывается, открывается боевая арена) |
| `~ change_scene_state("night")` | сменить состояние/декорацию текущей сцены прямо под диалогом |
| `~ game_over_death("Ты сгинул в шахте...")` | завершить игру гибелью героя с сообщением/эпилогом |
| `~ game_over_victory("Город спасён!")` | завершить игру победой с сообщением/эпилогом |

Значения состояния читаются функциями `get_flag`, `get_stat`, `get_hp`,
`get_skill`, `get_need`, `get_currency`, `get_disposition`, `quest_stage`,
`has_item`, `item_count`, `has_status`, `has_meta_achievement`, `get_meta_counter` (счётчики хроники: `endings_seen`,
`runs`, `deaths`, `victories`, `kills`, `quests_completed`, `ticks_survived`,
`travels`, `dialogues`; реплика «нового круга» ловится как
`{ get_meta_counter("endings_seen") > 0: … }`) и сравниваются
в обычном синтаксисе Ink.

**Безопасные конструкции сырого Ink (обязательно).** Разные сборки inkjs
по-разному переносят «вольный» стиль, и игрок видит служебные строки
(«true» посреди разговора) или теряет реплики. Пиши так:

- Условие выбора — ТОЛЬКО перед квадратными скобками:
  `+ { not (get_flag("x")) } [Текст реплики.]`. Запись условия ПОСЛЕ скобок
  (`+ [Текст.] { cond }`) запрещена: часть сборок печатает значение условия
  отдельной репликой.
- Условные текстовые блоки — в одну строку: `{ get_flag("x"): Проходите. }`.
  Многострочные блоки `{ cond:` … `}` в некоторых сборках inkjs теряют текст
  и обрывают сцену; если текста много — выноси его в отдельный узел под
  условием-выбором или используй обычную строку с `if`-узлом.
- Реплики не должны содержать системных литералов и вывода выражений:
  строки вида `true`, `false`, голые числа результатов проверок движок
  отсекает как служебные, но и писать их в текст реплики нельзя.
- Проверки навыков в Ink: вызываются через `~ temp r = roll_check("навык", сложность)` или `~ temp r = skill_check("навык", сложность)`. Ветвление результата оформляйте компактно тернарным переходом `{ r: -> узел_успеха | -> узел_провала }` либо парными проверками `{ r == 1: ... }` и `{ r == 0: ... }`. Конструктор диалогов движка автоматически распознаёт обе формы и строит визуальные блоки успеха/провала.
- **Ремарки действий с озвучкой рассказчика**: строка с ремаркой действия может содержать одновременно `# action` и `# voice: assets/voice/narr_x.mp3` (а также `# sfx: sfx_id`). Движок воспроизводит голос рассказчика от начала до конца, оформляет текст ремарки курсивом со стрелкой `→`, и не переходит к следующим фразам до завершения аудио.
- Автотаймер строки (`# timer: N`): при наличии озвучки (`# voice: ...`) таймер не обрывает голос диктора — движок ждёт завершения аудио (`max(timer, audio.duration)`).
- Каждую внешнюю функцию, вызываемую как `~ fn(...)` или в условии,
  объявляй `EXTERNAL fn(a0, …)` в шапке файла — иначе inkjs не скомпилирует.

**Ошибка компиляции ink** содержит id диалога (`dlg_…` / путь) — ищи его в
сообщении, а не только «Syntax error». Сломанный диалог не валит весь забег:
движок мягко отказывает (диалог не открывается), остальные сцены работают.

### 13.1 Текст реплики: токены и озвучка

Вместо кода — **токены** (мастер и генератор пишут по-русски, движок
подставляет значения):

| токен | значение |
|---|---|
| `{имя}` / `{герой}` | имя героя (обращение) |
| `{здоровье}` / `{здоровье_макс}` | здоровье сейчас / максимум |
| `{мана}` / `{мана_макс}` | мана сейчас / максимум |
| `{удача}` | остаток очков удачи |
| `{уровень}` / `{опыт}` | уровень и очки опыта |
| `{день}` | день забега |
| `{счёт:item_silver}` | сколько штук предмета у героя |
| `{потребность:warmth}` | значение потребности |
| `{навык:persuade}` | значение навыка |
| `{стат:INT}` | значение характеристики |
| `{валюта:silver}` | сколько единиц валюты у героя |

Пример: `Рад видеть, {имя}. У тебя {счёт:item_silver} марок серебром`.

**Чистота текста реплик (правило для сценариев и ИИ):**
Диалоговое окно движка автоматически отображает портрет и имя говорящего (NPC или героя) из метаданных узла/сущности.
В самом тексте реплики (`text` или строке сценария) **запрещено** приписывать имя говорящего и обрамлять всю реплику в кавычки прямой речи:
- ❌ `Ирина: «Вы из дознавателей? Мы вас ждали.»`
- ❌ `Сержант Валент: Что вам здесь нужно?`
- ❌ `«Мы должны спешить!»`
- ✅ `Вы из дознавателей? Мы вас ждали.`
- ✅ `Что вам здесь нужно?`
- ✅ `Мы должны спешить!`

Озвучка реплики:
`"voice": "assets/voice/marta_01.ogg"` (файл) или ссылка; без файла реплику
может прочитать синтезатор браузера (галочка в настройках игрока).

### 13.3 Семантика диалогов и поведение вариантов

Этот раздел описывает точную семантику диалоговых вариантов и переходов.
Для ИИ-генератора это нормативное руководство: не отступайте от описанного
поведения, иначе диалоги будут работать не так, как задумано.

#### Типы диалоговых вариантов

| Тип | DlgDoc (конструктор) | Ink (сырой) | Поведение |
|-----|---------------------|-------------|----------|
| **Повторяемый** | `once: undefined` или `once: false` | `+ ` | Вариант доступен всегда, можно выбирать многократно в одном разговоре |
| **Одноразовый (в разговоре)** | `once: true` | `* ` | Исчезает после выбора до конца текущего разговора; при новом разговоре возвращается |
| **Повторяемый (явный в Ink)** | (не применяйте в DlgDoc) | `+ ` | Всегда доступен, даже после выбора |

**Важное уточнение по Ink**: одной метки `+` недостаточно, если ветка ответа
уходит в `END` или `DONE`. Чтобы вариант был действительно повторяемым,
ответ должен возвращать к хабу вариантов (`-> node_hub` или `-> stay`,
или просто не указывать `->` и продолжить поток).

#### Вопросы, которые можно задавать снова

- **Повторяемый вариант**: ответ возвращает к узлу вариантов (`goto: "stay"`
  в DlgDoc или `-> node_hub` в Ink). Не завершайте разговор после ответа.
- **Пример**: Вопросы типа «Сколько времени?», «Где я?», «Что слышно?» —
  игрок может спрашивать многократно.

#### Варианты, исчезающие после выбора

- **Одноразовый вариант**: `once: true` в DlgDoc или `* ` в Ink.
- **Поведение**: после выбора исчезает до конца текущего разговора;
  при новом разговоре (новая Story) возвращается.
- **Важно**: Для постоянного исчезновения между разговорами используйте
  флаг и условие: `conds: [{ type: 'flag_not_set', flag: 'variant_used' }]`,
  и в эффектах ответа ставьте этот флаг.

#### Повторяемый вариант в Ink

- **Маркер `+`**: делает вариант доступным всегда.
- **Ограничение**: Если ветка ответа заканчивается `-> END` или `-> DONE`,
  то `+` не спасает — вариант всё равно исчезнет после выбора. Чтобы он
  оставался, ответ должен возвращать к хабу: `-> node_hub` или `-> stay`.

#### Переходы: `goto`, `stay`, `end`

| Переход | DlgDoc | Ink | Точное поведение |
|---------|--------|-----|----------------|
| **Продолжить** | `goto: ""` или не указан | (нет `->`) | Продолжает текущий поток реплик НПС |
| **Остаться на хабе** | `goto: "stay"` | `-> node_hub` | Возвращает к текущему набору вариантов |
| **Завершить разговор** | `goto: "end"` | `-> DONE` или `-> END` | Закрывает диалог, игрок возвращается в игру |
| **Переход к узлу** | `goto: "node_id"` | `-> node_id` | Переход к другому узлу в том же диалоге |

**Когда уместно каждое**:
- `stay` — когда после ответа НПС должен снова показать те же варианты
- `end` — когда разговор логически завершён
- перехода к узлу — когда нужно перейти к другой теме или стадии диалога

#### Новый разговор = новая Story

- При каждом новом разговоре движок создаёт новую `Story` из Ink-исходника.
- Это значит, что все `once`-выборы (`* ` в Ink) возвращаются.
- Для постоянного исчезновения варианта между разговорами **обязательно**
  используйте флаг/условие или другой реально поддерживаемый механизм.

#### Обработка эффектов при повторах

**Правило**: Не выдавайте предмет, не списывайте ресурс и не ставьте сюжетный
эффект повторно без замысла.

- Для одноразовых действий используйте `once: true`
- Для условных действий используйте проверку по флагу:
  `conds: [{ type: 'flag_not_set', flag: 'action_done' }]`
- В эффектах ответа ставьте флаг: `{ type: 'set_flag', flag: 'action_done' }`

**Пример неправильного подхода**:
```json
// ❌ ПЛОХО: предмет будет выдаваться каждый раз
{
  "text": "Дай мне хлеб",
  "once": false,
  "sections": [{
    "steps": [
      { "kind": "effect", "effect": { "type": "add_item", "item": "item_bread", "qty": 1 } }
    ]
  }],
  "goto": "stay"
}
```

**Пример правильного подхода**:
```json
// ✅ ХОРОШО: предмет выдаётся только один раз
{
  "text": "Дай мне хлеб",
  "once": true,
  "sections": [{
    "steps": [
      { "kind": "effect", "effect": { "type": "add_item", "item": "item_bread", "qty": 1 } },
      { "kind": "effect", "effect": { "type": "set_flag", "flag": "got_bread_from_npc" } }
    ]
  }],
  "goto": "stay"
}
```

#### Разница между завершением диалога и завершением забега

- **Завершение диалога** (`goto: "end"`): Закрывает окно диалога. Игрок
  возвращается в игру. Кампания продолжается.
- **Завершение забега** (`game_over_victory`, `game_over_death`):
  Заканчивает весь забег. Показывает экран финала. Кампания завершена.

**Не смешивайте эти события!** Завершение диалога не влияет на прогресс
кампании, если только в эффектах диалога явно не вызваны эффекты завершения
забега.

#### Примеры полных диалогов

##### A) Несколько повторяемых вопросов, каждый ответ возвращает к одному хабу

**DlgDoc:**
```json
{
  "version": 2,
  "label": "Тавернщик",
  "nodes": [{
    "id": "main",
    "label": "Начало",
    "sections": [{
      "steps": [
        { "kind": "line", "line": { "text": "Чем могу помочь, путник?" } }
      ]
    }],
    "choices": [
      {
        "text": "Сколько времени?",
        "sections": [{
          "steps": [
            { "kind": "line", "line": { "text": "Сейчас {день}-й деньбега." } }
          ]
        }],
        "goto": "stay"
      },
      {
        "text": "Где я нахожусь?",
        "sections": [{
          "steps": [
            { "kind": "line", "line": { "text": "Вы в таверне \"У старого дуба\""." } }
          ]
        }],
        "goto": "stay"
      },
      {
        "text": "Сколько стоит ночлег?",
        "sections": [{
          "steps": [
            { "kind": "line", "line": { "text": "Пять серебряных марок." } }
          ]
        }],
        "goto": "stay"
      },
      {
        "text": "Пока.",
        "sections": [],
        "goto": "end"
      }
    ]
  }]
}
```

**Структура ink-файла диалога.** Узел с вариантами редактор пишет как
`=== <узел> ===` (реплики и эффекты) плюс `=== <узел>_hub ===` (варианты),
и на входе импорт понимает **обе** формы: и `main_hub`, и отдельный узел с
ответами под любым именем (`hub`, `topics`…), который возвращает к себе
через `-> hub`. Внутри узла-ответов допустимы вводные строки — ремарки,
эффекты, `~ set_dialogue_timer(…):` они становятся началом узла, а строки
`+ [текст]` / `* {условие} [текст]` — вариантами.

**Эквивалентный Ink:**
```ink
=== main ===
Чем могу помочь, путник?
-> main_hub

=== main_hub ===
[Сколько времени?]
    Сейчас {get_run_day()}-й день.
    -> main_hub
[Где я нахожусь?]
    Вы в таверне "У старого дуба".
    -> main_hub
[Сколько стоит ночлег?]
    Пять серебряных марок.
    -> main_hub
[Пока.]
    -> DONE
- -> main_hub
```

##### C) Сюжетный выбор с побочным эффектом, который нельзя выполнить повторно

**DlgDoc:**
```json
{
  "version": 2,
  "label": "Кузнец",
  "nodes": [{
    "id": "main",
    "label": "Начало",
    "sections": [{
      "steps": [
        { "kind": "line", "line": { "text": "Нужна помощь с доспехами, воин?" } }
      ]
    }],
    "choices": [
      {
        "text": "Отремонтируй мой меч (+10 серебра)",
        "once": true,
        "conds": [
          { "type": "has_item", "item": "item_silver", "count": 10 }
        ],
        "sections": [{
          "steps": [
            { "kind": "effect", "effect": { "type": "remove_item", "item": "item_silver", "qty": 10 } },
            { "kind": "effect", "effect": { "type": "set_flag", "flag": "sword_repaired" } },
            { "kind": "line", "line": { "text": "Готово! Ваш меч как новый." } }
          ]
        }],
        "goto": "stay"
      },
      {
        "text": "Пока.",
        "sections": [],
        "goto": "end"
      }
    ]
  }]
}
```

**Эквивалентный Ink:**
```ink
EXTERNAL remove_item(id, n)
EXTERNAL set_flag(f)
EXTERNAL has_item(id)

=== main ===
Нужна помощь с доспехами, воин?
-> main_hub

=== main_hub ===
* [Отремонтируй мой меч (+10 серебра)] { has_item("item_silver") >= 10 }
    ~ remove_item("item_silver", 10)
    ~ set_flag("sword_repaired")
    Готово! Ваш меч как новый.
    -> main_hub
+ [Пока.]
    -> DONE
- -> main_hub
```

**Поведение**: Вариант ремонта исчезает после выбора и не появляется
даже в новом разговоре, потому что используется проверка по флагу
`has_item("item_silver") >= 10`.

## 14. encounters — случайные встречи

В пакете файлы таблиц встреч размещаются в каталоге `encounters/` (например,
`encounters/enc_streets.json`) с обёрткой `{ "encounter_tables": [ ... ] }`.
В монолите они хранятся в словаре `encounters`.

```json
"enc_forest": {
  "id": "enc_forest", "rolls": 1,
  "entries": [
    { "weight": 5, "type": "nothing" },
    { "weight": 2, "type": "combat", "enemies": [ { "entity": "npc_wolf", "count_min": 1, "count_max": 2 } ], "arena": "arena_forest" },
    { "weight": 1, "type": "dialogue", "entity": "npc_hermit" }
  ]
}
```

Типы записей: `nothing`, `combat`, `dialogue`, `skill_check`, `event`.
Таблицу вешаем на дорогу: `travel_connections[].random_encounter_table`.

### Рецепт: детективное расследование и поиск улик
1. **Интерактивный осмотр:** слот сцены (тело или предмет окружения с действием осмотра или переходом в диалог).
2. **Проверка навыка:** `skill_check` при взаимодействии со слотом или в реплике диалога.
3. **Улики и выводы:** при успехе выдаётся предмет-улика с флагом `quest_item: true` (защита от случайной продажи), устанавливается сюжетный флаг (`set_flag`) и открывается запись в `unlock_codex` (категория «Улики»).
4. **Предъявление улики в диалоге:** проверяется условием наличия предмета в инвентаре: `+ { has_item("item_ledger") } [Предъявить гроссбух инспектору] -> confront`.
5. **Журнал квеста:** стадия квеста продвигается на шаг вперёд (`advance_quest`), где мастер описывает в журнале сделанные героем логические выводы.

### Рецепт: изменение сцены и звуков после событий (починка помпы, тревога)
Включение звукового слоя после сюжетного действия (например, гул помпы после ремонта) оформляйте через условные слои `AmbientRule` или через состояния сцены:
- **Через условный звуковой слой `AmbientRule` в массиве `ambient` сцены или локации**:
  ```json
  "ambient": [
    "snd_wind",
    {
      "conditions": [ { "type": "flag_set", "flag": "pump_repaired" } ],
      "sounds": [ "snd_pump_hum" ],
      "volume": 0.85
    }
  ]
  ```
- **Через второе состояние сцены (`states` сцены)**: первое состояние активно по умолчанию, второе — при условии `{ "type": "flag_set", "flag": "pump_repaired" }` со своим фоном и зацикленным звуком в свойствах состояния.
- **Либо через звуковой хук взаимодействия**: параметр `sound` в вариантах действия интерактивного объекта сцены (`interact_options`).

### Рецепт: суточное освещение сцены (`lighting`)
По умолчанию движок накладывает на открытые сцены мягкий атмосферный суточный шейдер в зависимости от фазы дня (утро, день, закат, ночь).
Если сцена находится в помещении, подвале или шахте — укажите в сцене:
- `"lighting": "indoor"` — ровный теплый свет ламп без затемнения ночью.
- `"lighting": "none"` — отключение суточных фильтров.
### Рецепт: ветвления туннелей и подземелий
1. **Граф локаций:** несколько связанных сцен подземелья через `connections` в `world.json`.
2. **Условные развилки:** правила с условиями проверок или флагов, открывающие альтернативные переходы.
3. **Случайные события в переходах:** таблицы `encounters` на путях между туннелями создают атмосферу опасности и нелинейности.

## 14б. recipes — крафт (блок 4 ТЗ «Гибкий движок»)

```json
"recipe_bandage": {
  "id": "recipe_bandage", "label": "Бинт из ткани",
  "description": "Простая повязка из подручной ткани.",
  "inputs": [ { "item": "item_cloth", "quantity": 2 } ],
  "tools": [ "item_knife" ],
  "requires": [ { "type": "flag_set", "flag": "learned_first_aid" } ],
  "skill": { "id": "first_aid", "difficulty": 40 },
  "time_ticks": 2,
  "output": { "item": "item_bandage", "quantity": 1 },
  "message": "Вы аккуратно свернули бинт."
}
```

- `inputs` — компоненты, **расходуются**. `tools` — инструменты, нужны в
  инвентаре, **не расходуются**.
- `requires` — обычные условия (как в правилах): крафт доступен, только когда
  все выполнены. Иначе в списке подсвечивается, чего не хватает.
- `skill` — проверка навыка при изготовлении (механика BRP): **провал
  сохраняет материалы**, успех ставит «галочку» роста навыка. Нет `skill` —
  крафт всегда удаётся, если хватает компонентов.
- `time_ticks` — сколько тиков занимает изготовление (0/нет — мгновенно).
- `output` — результат. `message` — своё сообщение об успехе (необязательно).
- Игрок открывает крафт кнопкой «Крафт» в HUD (появляется, только если в
  кампании есть хотя бы один **открытый** рецепт).

### Рецепт, который открывается по ходу игры

Поле `known: false` прячет рецепт: его нет ни во вкладке «Крафт», ни в списке.
Открывает его эффект `unlock_recipe { recipe }` — из правила, из `interact_options`,
из `use_with` или из диалога (`~ unlock_recipe("recipe_…")`).

```json
"recipe_herbal_tonic": {
  "id": "recipe_herbal_tonic", "label": "Травяной настой", "known": false,
  "inputs": [ { "item": "item_herb", "quantity": 2 }, { "item": "item_clean_water", "quantity": 1 } ],
  "skill": { "id": "first_aid", "difficulty": 35 },
  "output": { "item": "item_tonic", "quantity": 1 },
  "message": "Настой получился мутным, но тёплым."
}
```

Поле `known` необязательное; его отсутствие = «известен с начала». Старые
кампании и сейвы от этого не страдают. `requires` у закрытого рецепта всё
равно пишутся, а не прячутся: рецепт не «запрещён», а ещё не найден.

### Рабочие места (`workbench`) и условия (`conditions`)

- `workbench: true` или `workbench: "item_id"` (строка с id сущности или категорией оборудования: `"item_stove"` для кухонной плиты, `"item_anvil"` для кузнечной наковальни, `"item_bench"` для верстака):
  - Предмет нельзя изготовить «на бегу» в поле на коленке. В походных условиях рецепт показывает предупреждение: `⚠ Требуется: Кухонная плита` или `⚠ Требуется: Верстак или мастерская`.
  - Изготовление становится доступным, когда персонаж находится в сцене с нужным станком/мебелью, в локации с мастерской или когда игрок подошёл к станку и нажал «Открыть мастерскую» (`open_craft`).
  - При открытии крафта от предмета окно взаимодействия с предметом немедленно закрывается, открывая чистую панель крафта со статусом активного рабочего места.
- `conditions`: массив условий (`Condition[]`), при которых рецепт доступен и виден для изготовления (например, знание черты, уровень навыка, прочитанный чертёж или стадия квеста). В отличие от однократного `unlock_recipe`, рецепт с `conditions` автоматически рассчитывает доступность по текущему состоянию героя.
- `category`: строка категории рецепта для группировки мастером и фильтрации игроком.

## 14в. statuses — статусы (яд, кровотечение, баффы; блок 5 ТЗ)

Реестр `statuses` в `campaign.json` (как `needs`):

```json
"statuses": [
  {
    "id": "status_poison", "label": "Отравление",
    "description": "Яд медленно подтачивает силы.",
    "scope": "world", "duration": 12,
    "dot": { "hp": 1 },
    "skill_mods": [ { "skill": "spot", "delta": -10 } ],
    "mov_mod": -1,
    "on_expire": [ { "type": "set_flag", "flag": "poison_cured" } ],
    "apply_message": "Яд разливается по жилам."
  }
]
```

- `scope`: `world` — длительность в **тиках**, `combat` — в **раундах боя**,
  `both` — действует и там и там.
- `dot` — урон за тик/раунд. В мире статус **не убивает** героя (минимум 1 HP);
  в бою — может добить.
- `skill_mods` — модификаторы навыков (влияют на все проверки игрока, включая
  диалоги, крафт и бой); `mov_mod` — прибавка к движению в бою (итог ≥ 1).
- `on_apply` / `on_expire` — обычные эффекты; `apply_message` / `expire_message` —
  строки в журнале.
- Эффекты: `apply_status { target: "player", status, duration? }`,
  `remove_status { target, status }`; условие `has_status { status }`.
- В диалогах: условие `«Есть статус»` и действия «Наложить/Снять статус».

## 14г. abilities и мораль (блок 6 ТЗ)

Реестр `abilities` в `campaign.json`:

```json
"abilities": [
  {
    "id": "ability_rat_bite", "label": "Ядовитый укус",
    "description": "Крыса вонзает отравленные клыки.",
    "mp_cost": 0, "cooldown_rounds": 2, "range": 1,
    "skill": "bite",
    "kind": "status", "status": "status_rat_poison", "status_duration": 3
  }
]
```

- `kind`: `damage` (`damage: "1d6+2"` — бонус силы НЕ добавляется, броня цели
  поглощает), `status` (накладывает статус; `status_duration` — раунды),
  `heal` (`heal: "1d6"` — цель: любой союзник в радиусе).
- `skill` — навык попадания (цель уклоняется/парирует, как от атаки); нет
  навыка — применение гарантированное. `mp_cost`, `cooldown_rounds` (0 — без
  кулдауна), `range` в гексах.
- НПС получают способности полем `"abilities": ["ability_…"]` (и мораль:
  `"morale": { "below_hp_pct": 25, "flee_chance": 60 }` — ниже порога HP враг
  в начале хода может сбежать; сбежавший не убит и лута с него нет).
- Игрок — способностями своей сущности (кнопки в панели боя).
- ИИ применяет готовую способность вместо атаки с шансом 50%.

## 14д. слоты экипировки (блок 7 ТЗ)

```json
"equipment_slots": [ { "id": "helm", "label": "Шлем" }, { "id": "amulet", "label": "Амулет" } ]
```

- Встроенных слотов **нет**: реестр целиком задаёт кампания. Если нужны
  оружие и броня — объяви `{ "id": "weapon", "label": "Оружие" }` и
  `{ "id": "armor", "label": "Броня" }` сами (плюс любые свои: шлем, амулет…).
- У предмета `"equip_slot": "helm"` — надевается в этот слот. Старым
  предметам без `equip_slot` слот выставляется миграцией по данным
  (`weapon_data` → Оружие, `armor_data` → Броня).
- В бою броня = **сумма очков всех надетых предметов с бронёй** (шлем+кираса
  работают вместе). Оружие — предмет в слоте `weapon`.
- `equipment` у НПС/игрока — словарь `слот → предмет` (ключи `weapon`/`armor`
  у старых кампаний остаются валидными).

## 14е. use_with — предмет на слоте сцены (блок 8 ТЗ, «ключ к двери»)

```json
"slots": [ {
  "id": "slot_chest", "label": "Запертый сундук", "type": ["item"],
  "x": 950, "y": 480, "w": 130, "h": 110, "shape": "rect",
  "default_entity": "item_locked_chest", "condition": null,
  "use_with": [ {
    "item": "item_tavern_key", "consume": true,
    "effects": [ { "type": "add_item", "item": "item_silver", "quantity": 20 },
                 { "type": "remove_entity", "entity": "item_locked_chest" } ],
    "message": "Замок щёлкает. Внутри — кошель серебра."
  } ]
} ]
```

- Клик по слоту: НПС → диалог; есть `use_with` и предмет в инвентаре →
  модалка выбора (несколько предметов — выбор, расход помечен); иначе —
  обычное поведение слота.
- `consume: true` — предмет расходуется (по умолчанию — нет).
- Пустые слоты с `use_with` и подходящим предметом тоже кликабельны
  (дверь, нарисованная на фоне).

## 14ж. календарь и погода (блок 9 ТЗ)

### Календарь (в `campaign.json`)

```json
"calendar": {
  "year_label": "год Пепла",      // подпись эры; нет — без неё
  "start_year": 137,              // начальный год (по умолчанию 1)
  "days_per_month": 30,           // дней в месяце (по умолчанию 30)
  "months": ["Углемес", "Гаревей"],  // циклятся; нет — «Месяц 1»
  "day_names": ["Пепельник", "Кузнецов"]  // циклятся; нет — без имён
}
```

День = `floor(tick / ticks_per_day)`. Дата появляется в HUD под часами
(«1 Углемес, Пепельник, 137-й год Пепла»). Условий/эффектов по дате нет —
для отсрочек используйте `tick_elapsed`.

### Дедлайн кампании в HUD (`meta.deadline_ticks` и `meta.deadline_label`)

Если кампания или сценарий ограничены по времени (расследование за 72 часа, приближающаяся катастрофа, отбытие поезда):
- `"deadline_ticks"`: общее число тиков от старта до дедлайна (например `72`). При значении >0 движок автоматически выводит в центре HUD наглядный индикатор обратного отсчёта (`⏳ 48 ч`).
- `"deadline_label"`: подпись таймера в HUD (например, `"До затопления"` или `"До срока"`).
- При остатке меньше суток (`ticks_per_day`) индикатор подсвечивается тревожным янтарно-красным цветом, а по истечении срока пульсирует красным.

### Погода

Реестр в `campaign.json`:

```json
"weathers": [
  { "id": "weather_ashfall", "label": "Пеплопад", "overlay": "ash",
    "ambient": ["snd_wind"] }
]
```

- `overlay` — id визуального слоя из реестра `overlay_layers` в
  `campaign.json` (`[{ "id": "rain", "label": "Дождь" }, …]`): список слоёв
  целиком задаёт кампания, редактор строит селект «Слой» из него. Движок умеет
  рисовать классы `weather-rain` / `weather-snow` / `weather-fog` /
  `weather-ash`; свой id получает класс `weather-<id>`. Поле можно не задавать —
  без слоя. Слой полупрозрачный, клики не перехватывает.
- `ambient` — id зацикленных звуков из реестра `meta.sounds`: подмешиваются к эмбиенту
  локации/сцены, пока погода активна. Важно: id звуков в `ambient` обязаны точно совпадать
  с id в `meta.sounds` (канонический префикс звуков в редакторе — snd_, например snd_wind;
  не путайте префиксы snd_ и sfx_, иначе звук не найдётся и выведется технический id).

Текущая погода хранится в `state.weather` (id; нет — ясно).

- Эффект `{ "type": "set_weather", "weather": "weather_ashfall" }`
  (`"weather": ""` — снова ясно). Пишет в журнал.
- Условие `{ "type": "weather_is", "weather": "weather_ashfall" }`
  (пустая строка = «сейчас ясно»). Оба доступны правилам, условиям сцен и
  диалогам (`~ set_weather(...)`, `{ weather_is(...) : ... }`).
- В музыкальных правилах (`MusicCondition`) и условиях сцены
  (`SceneCondition`) есть поле `weather` — менять музыку/показ по погоде.

## 14з. кодекс/бестиарий (блок 10 ТЗ)

Разблокируемые лор-записи: твари, места, события. Игрок видит их в панели
«Кодекс» (кнопка в HUD появляется, только когда открыта хотя бы одна запись).

### Формат

Записи лежат в разделе `codex` манифеста (файлы `codex/*.json`):

```json
{
  "id": "codex_rat_giant",
  "label": "Гигантская крыса",
  "category": "creatures",
  "text": "Основной текст записи…",
  "image": "assets/img/codex/rat.png"
}
```

- `category` — id из `meta.codex_categories`. Встроенные категории
  (используются, если своих нет): `creatures` (Существа), `places` (Места),
  `chronicles` (Хроники). Без `category` запись попадает в «Хроники».
- Свои категории: `"codex_categories": [{"id":"…","label":"…"}]` в campaign.

### Разблокировка

Эффект `{ "type": "unlock_codex", "entry": "codex_rat_giant" }`:

- добавляет запись (повтор — no-op);
- показывает игроку сообщение «Новая запись в кодексе: …»;
- доступен правилам и диалогам (`~ unlock_codex("…")`).

Состояние — `state.codex_unlocked` (список id).

Если в `campaign.json` задан `char_creation`, перед новым забегом игрок видит

```json
  "choose_name": true,

    {
      "id": "profession_soldier",
      "label": "Солдат",
      "description": "Строевая выучка и сталь в руках.",
      "stats": { "STR": 11, "CON": 10, "SIZ": 10, "DEX": 9, "INT": 6, "POW": 5, "CHA": 5 },
      "skill_bonus": { "sword": 10, "brawl": 5 },

  "callings": [
    {
      "id": "calling_mercenary",
      "label": "Наёмник",
      "description": "Жил клинком: рубка, кулаки и умение увернуться.",
      "skills": { "sword": 60, "brawl": 30, "dodge": 40 }
    }
  ]
}
```

- Происхождение — **шаблон для новичка**: мастер сам решает, сколько их и
  какие; встроенных происхождений нет. В каждом шаблоне укажи все семь
  характеристик в `stats`; сумма `max(0, stats[k] - stat_limits.min)` должна
  быть **ровно** `total_points` — ни остатка, ни перерасхода. Все значения
  должны быть внутри `stat_limits`. Если бюджет или лимиты не позволяют
  собрать шаблон, измени бюджет/лимиты или не добавляй этот шаблон.
- Призвание (`callings`) — **второй шаблон**, но уже для НАВЫКОВ. Его
  `skills` — абсолютные проценты, включая бесплатный бонус выбранного
  происхождения. Для каждого сочетания происхождения и призвания вычисли
  нижнюю границу навыка как `max(skill_floor, mandatory ? 25 : 0) +
  profession.skill_bonus[skill]`; пропущенный в шаблоне навык остаётся на
  этой границе. Потрачено — сумма `max(0, min(skill_cap, skills[skill]) -
  нижняя_граница)` по всем навыкам. Она должна быть **ровно** `skill_points`
  для каждого сочетания, с учётом `mandatory_skills`, `forbidden_skills` и
  `skill_cap`. Не допускай ни остатка, ни перерасхода. Убедись, что бюджет
  вообще помещается под лимиты; иначе снизь его или убери несовместимый
  шаблон.
- `total_points` — стартовый бюджет характеристик; `stat_limits` — рамки
  каждой из семи характеристик. Точный расход обязателен для шаблонов;
  индивидуально игрок может перераспределять эти очки.
- `skill_points` — бюджет покупок навыков (можно опустить — тогда покупки
  запрещены). `skill_cap` / `skill_floor` — пределы навыка сверху и снизу
  (задают мастера; обязательные навыки стартуют не ниже 25 %).
  `forbidden_skills` нельзя повышать покупками.
- `skill_bonus` профессии бесплатен: он повышает нижнюю границу навыка и сам
  не расходует очки; бюджет призвания считается сверх этой повышенной границы.
  При смене происхождения покупки игрока сохраняются, бесплатные бонусы
  пересчитываются.
- Редактор проверяет исходные шаблоны и включает ошибки/недорасход в отчёт;
  экран создания безопасно подгоняет устаревшие шаблоны под бюджет, но это
  страховка, а не замена точному распределению при генерации.
- `items` — стартовое снаряжение профессии.
- `choose_name` — поле имени героя (иначе имя шаблона).
- Кнопка «Начать забег» активна, только когда выбор валиден (ничего не
  превышает бюджетов и рамок); все сообщения — по-русски, с названиями
  навыков из реестра.
- Выбор сохраняется в сейве и переживает перезапуск забега.

## 14й. финальные экраны — концовки (разные финалы)

Экран завершения забега не один: мастер объявляет в `campaign.json` реестр
`endings` — столько финалов, сколько нужно (победные, трагические, «серые»).

```json
"endings": [
  { "id": "ending_bandit_slain", "label": "Банда разбита мечом",
    "title": "Дороги снова чисты",
    "text": "Йорек мёртв, караваны идут…",
    "tone": "victory", "on": "victory",
    "image": "assets/img/endings/roads.jpg",
    "conditions": [ { "type": "quest_at_stage", "quest": "quest_bandit_threat", "stage": "completed_fight" } ] },
  { "id": "ending_ashes", "label": "Пепельный финал",
    "title": "Пепел принял ещё одного", "tone": "death", "on": "death" }
]
```

- При завершении забега движок берёт **первую** концовку, у которой совпадает
  исход (`on`: `death` / `victory` / нет — любой) и выполнены все `conditions`
  (обычные условия: флаги, квесты, отношения…). Не подошла ни одна — стандартный
  экран исхода. Порядок в списке важен: **сначала узкие** (флаг/квест), **общие
  в конец** (пустые `conditions` перехватят всё).
- **Дедлайн без realtime-таймера** (драмы, «последний поезд»): `starting_tick` +
  правило `once` с `tick_elapsed` (после хода времени / `advanceTicks` правила
  проверяются сами) → `banner` / `teleport_player` / `set_flag` / `game_over_*`.
  Таймер на реплику в диалоге в формате **не** нужен и не выдумывается.
- `tone` — тон оформления (`death` / `victory` / `neutral`); нет — по исходу.
- `image` — фон финала (иначе фон темы `theme.end.background`); `text` — текст
  на экране (иначе причина исхода). Статистика забега показывается всегда.
- В редакторе — блок «Финальные экраны (концовки)» во вкладке «Основное»:
  заголовок, тон, исход, текст, фон и условия; превью не нужно — финал
  проверяется завершением забега.

## 15. Звук и музыка без файлов (SoundDoc / MusicDoc)

Реестры в `campaign`:

```json
"music_tracks": [ { "id": "music_tavern", "label": "Вечер в таверне",
  "src": { "mood": "спокойная", "tempo": 72, "key": "D", "scale": "минор",
           "layers": ["пад-аккорды", "бас"], "progression": ["i","VI","III","VII"], "seed": 42 },
  "volume": 0.8, "loop": true } ],
"sounds": [ { "id": "sfx_coin", "label": "Звон монеты",
  "src": { "zzfx": [1, 0.05, 1200, 0, 0.03, 0.05, 2, 1, 4, 0.05, 0, 0, 0.06, 0, 0, 0, 0, 0.6, 1, 0] } } ],
"ui_sounds": { "menu_music": "music_menu", "click": "sfx_click", "travel_depart": "sfx_steps", "combat_start": "sfx_horn" },
"default_music": ["music_forest"], "combat_music": ["music_battle"]
```

- `src` звука/музыки — файл, ссылка ИЛИ синтез: `SoundDoc`
  (`{"zzfx": […до 20 чисел]}` — параметры в духе ZzFX/jsfxr, по порядку:
  громкость, разброс, частота Гц, атака, сустейн, затухание, форма волны
  (0 синус…4 шум), изгиб формы, скольжение тона, ускорение скольжения,
  скачок тона, время скачка, повтор, шум, FM-модуляция, биткраш, эхо,
  громкость сустейна, кривая затухания, клиппинг; пропуски = значения по
  умолчанию, но числа пишем явно — это валидный JSON) и `MusicDoc`
  (`mood: тревожная|спокойная|боевая|торжественная|таинственная`, `tempo`,
  `key`, `scale`, `layers: ["пад-аккорды","арпеджио","бас","перкуссия"]`,
  `progression: ["i","VI",…]`, `seed` — детерминизм). Музыкальный генератор
  всегда играет по гамме — мимо не бывает.
- У звука может быть **массив** источников: каждый проигрыв выбирает
  случайный вариант («скрип двери» — три разных скрипа под одним id).
- Привязка музыки: у локации и сцены — список «условия → треки»
  (`music: [{ "tracks": ["m1","m2"], "shuffle": true, "conditions": […]}]`;
  условия — `conditions` поддерживают как время суток / погоду / флаги, так и любые стандартные `Condition` движка — квесты, предметы, здоровье; первый истинный блок
  побеждает; один трек — луп, несколько — плейлист со сменой и кроссфейдом
  ~1.5–2 с, `shuffle` — вперемешку без повтора подряд).
  Приоритет: катсцена → сюжетный оверрайд (`override_music`) → бой (`arena.music`, иначе `campaign.combat_music`) →
  сцена → локация → `campaign.default_music` → тишина.
  `ui_sounds.menu_music` — id **трека** для главного меню.
- Сюжетный оверрайд музыки: эффект `override_music` (с полями `tracks`, `fade`) форсирует драматичный трек поверх текущей сцены, а `clear_music_override` возвращает музыку локации.
- Прямые звуки на элементах мира:
  - Связи локаций `TravelConnection`: `sound` (звук пути — шум поезда, плеск волн, стук копыт), `sound_volume`, `depart_sound` (гудок, свисток), `arrive_sound` (скрип тормозов).
  - Рецепты крафта `RecipeDef`: поле `sound` (звон наковальни, бульканье зелья, шитьё) и `sound_volume`.
  - Состояния сцены `SceneStateDef`: поле `sound` воспроизводится один раз при смене состояния сцены (запуск механизмов, спуск шлюза) и `sound_volume`.
  - Слоты сцены `SlotDef`: поле `sound` воспроизводится при клике по слоту и `sound_volume`.
  - Статусы героя `StatusDef`: `apply_sound` (звук при получении статуса — удушье, кашель, благословение) и `remove_sound` (звук при исцелении/спаде).
  - Действия с предметом `ItemInteractOption`: поле `sound` воспроизводит точный звук действия напрямую и `sound_volume`.
  - Реплики диалогов: команда `~ play_sound("snd_id", 0.9)` или строчный тег `# sfx: snd_id` (выстрел, стук в дверь, звон монет).
  - Остановка звука: эффект `{ "type": "stop_sound", "sound": "snd_alarm" }` для прекращения воспроизведения долгого звука или петли.
- Звуки взаимодействий (`sounds` у сущности, категории предмета, типа слота):
  карта вида `{"pickup": "sfx_coin", "use": "sfx_drink", "equip": "sfx_armor", "unequip": "sfx_cloth"}`. Хуки — открытые строки с каскадным поиском.
- `ui_sounds` — звуковая тема интерфейса с каскадом:
  - Панели (открытие): `panel:inventory` (сумка), `panel:log` (журнал расследования / хроника событий, синоним `panel:journal`), `panel:meta` (хроника забегов и метапрогресс, синоним `panel:chronicle`), `panel:map` (карта ярусов/мира), `panel:craft` (верстак/мастерская), `panel:character` (лист героя), `panel:codex` (архив/кодекс), `panel:saves` (сохранения), `panel:help` (справка). Если конкретный ключ не задан — играет общий `panel_open` / `panel:open`.
  - Панели (закрытие): `panel:<id>:close` (например `panel:inventory:close`, `panel:log:close`) с автоматическим фоллбэком на общий `panel_close` / `panel:close` и тихий клик `click`.
  - Кнопки и осмотр: `click` (нажатие кнопок), `message` (всплывающее окно сообщения, осмотр предмета на сцене).
  - Перемещения: `scene_transition` (смена сцены по клику на зону навигации), `travel_depart` (отправление между локациями), `travel_arrive` (прибытие на место).
  - Вещи и награды: `item_get` (получение предмета), `item_lose` (утрата/сдача предмета), `coin` (получение или трата монет/валюты), `craft` (изготовление предмета по рецепту).
  - Экипировка: `equip` (надевание оружия/брони), `unequip` (снятие предмета в инвентарь).
  - Диалоги: `dialogue_present` (звук при предъявлении улик и предметов в диалоге через `~ present_item`).
  - Прогресс: `quest_started` (получение нового задания), `quest_completed` (успешное завершение квеста), `skill_up` (рост навыка).
  - Бой: `combat_start` (начало схватки), `hit` (попадание по врагу/герою), `miss` (промах), `crit` (критический удар), `parry` (парирование щитом/оружием), `heal` (исцеление/зелье), `flee` (попытка побега), `kill` (гибель противника), `death` (смерть героя), `victory` (победа в бою), `defeat` (поражение), `error` (невозможность подготовить способность или выполнить действие).
- `ui_labels` — настраиваемые надписи системных меню и кнопок интерфейса:
  словарь вида `{"inventory": "Сумка дознавателя", "journal": "Дело № 137", "map": "Схема ярусов", "camp": "Перекур", "codex": "Архив Надзора", "pass_turn": "Выждать", "flee": "Бежать"}`.
  Пусто — системные надписи по умолчанию.
- **Требование:** сгенерированная кампания звучит сразу — музыка локаций,
  тема меню, базовые звуки взаимодействий. Всё синтетикой, мастер потом
  заменит на файлы.

## 16. Валидация и автопочинка

Импорт не падает из-за ошибок — их чинят, а список показывают мастеру:

- нет сущности/сцены/локации/квеста/арены → создаётся **заглушка**;
- переход в несуществующую/чужую сцену → зона отключается или становится
  «открыть карту» (между локациями — только карта);
- пустые квесты получают стадию «Начало», пустые сцены — состояние «Обычное»;
- переходы диалога на несуществующие узлы → `end`;
- флаги/фракции/навыки без реестра → дописываются в реестр;
- `set_entity_state` с состоянием, которого нет у персонажа → пустое
  состояние добавляется, мастеру говорится загрузить картинку;
- `unlock_recipe` на несуществующий рецепт → рецепт-заглушка (закрыт);
- `fire_rule` на несуществующее правило → правило-заглушка;
- сломанные мелочи (пустые зоны, лишние записи расписания) → удаляются.

**Совпадение id не теряет содержимое.** Если два объекта в пакете делят один
id, второй переименовован (`имя_2`), а в отчёте сказано, что ссылки кампании
по-прежнему ведут к первому. Имя файла — это id без лишних символов, поэтому
`item_старый-ключ` и `item_старый_ключ` дали бы один файл и второй объект
молча затёрся бы первым: теперь такой файл получает суффикс, и в отчёте
названы оба имени. Следи за префиксами из §3 — они убирают такие совпадения
заранее.

Отчёт выглядит так: «Импортировано с 12 предупреждениями» + список.
После импорта мастер жмёт «Сохранить» — и кампания пишется на диск.
Список текстовый и копируется целиком — его показывают агенту, поэтому
формат менять нельзя.

**Повторы схлопываются.** Если одно и то же случилось с 28 сущностями, в
отчёте будет одна строка со счётчиком и именами, а не 28 строк. Формат строки
не меняй — по нему агент читает отчёт:

> Сущность «item_статуя» используется как персонаж, но описана как предмет —
> оставлено как есть (таких 28: item_статуя, item_ящик, item_сундук, …)

Две одинаковые строки не сворачиваются: мастеру имена нужны. Кнопка
«Скопировать отчёт для ИИ» отдаёт **полный** список без схлопывания.


**Проверка кампании** (отдельная кнопка, не только импорт) дополнительно
ищет: петли правил через `fire_rule` (с самой цепочкой), несуществующие
`fire_rule`/`unlock_recipe`, состояния облика, которых нет у персонажа, и
слоты, лежащие мимо нарисованных объектов. Каждая находка — отдельная
строка с названием объекта.

## 18. Чеклист генератора

- [ ] `starting_region/location/scene` указывают на существующие объекты,
      стартовая сцена принадлежит стартовой локации.
- [ ] У каждой локации есть `scenes` и `arrival_scene`; между локациями —
      только `travel_connections`, из сцен — только `go_to_scene` (свои) и
      `open_map`.
- [ ] Все `id` уникальны, с префиксами, все ссылки (сущности, сцены, локации,
      квесты, арены, катсцены, диалоги, стадии, слоты) существуют.
- [ ] У каждого квеста ≥1 стадии, у каждой сцены ≥1 состояние с `art`.
- [ ] Слоты и зоны лежат поверх нарисованных объектов (координаты ArtDoc!).
- [ ] Диалоги: у каждого узла есть выход (`goto`), у текстов — токены вместо
      чисел-констант, где уместно; стартовый knot — `main` (или первый knot
      будет входом); в ink есть `EXTERNAL` для всех `~ unlock_*` / `~ set_*`.
- [ ] Стационарные NPC/пропы: `schedule: []` **и** `default_entity` в слоте;
      бродячие — непустой `schedule`, без дубля default в чужой сцене.
- [ ] Пути ассетов: либо реальный файл, либо `""` / отсутствие поля (не
      выдуманный path — UI покажет плейсхолдер, а не битую картинку).
- [ ] Пролог — катсцена из `art`-слайдов + правило на старте (`once: true`).
- [ ] Есть музыка (меню + локации), тема `ui_sounds` и пара звуков —
      синтетика (SoundDoc/MusicDoc), чтобы кампания звучала сразу.
- [ ] Все тексты по-русски; описания и label заполнены.

## 19. Возможности движка сверх ядра (за последние раунды)

Эти поля уже в типах и в схеме; их можно (и нужно, где уместно) использовать:

- **Состояния облика существа** — канон такой: эмоция/состояние = ключ, под
  которым у персонажа записана картинка. Ключи берутся из его же
  `portrait` (`emotion → image`) и `scene_sprite_states`, а общий реестр
  состояний — `meta.emotions` («сердит», «счастлив», «испуган», плюс
  встроенное «Обычный»). Портрет в диалоге переключает реплика
  (`DlgLine.emotion`), спрайт в сцене — свойство слота `sprite_state`.
  **Правилами облик меняет эффект `set_entity_state { entity, state }`**
  (пустая строка `state` возвращает обычный облик); он сильнее и `emotion`
  реплики, и `sprite_state` слота. Отдельных «настроений» и эффекта
  «переключить настроение» в формате нет — и не выдумывай их.
  Автоматика есть только у портрета героя (`char_creation.portraits[].states`):
  там состояние подбирается по активному статусу, иначе `wounded` при
  HP < 50%, иначе `tired` при любой потребности ≤ 25. У фигурки в бою
  `combat_figure_states` ключи — `dead`, `down` и id статусов.
- **Преследования** — «ведут» героя, и облаву устраивает тот же эффект
  `start_pursuit`. Живая форма:
  `{ label?, skill?, every_ticks?, fails_to_catch?, on_fail }`.
  Пока преследование активно, каждые `every_ticks` тиков (умолчание 4) герой
  и до двух союзников проверяют цепочкой `skill` (умолчание `stealth`);
  цепочка провалов подряд ≥ `fails_to_catch` (умолчание 1) — погоня настигла,
  срабатывает `on_fail` и преследование гаснет. `stop_pursuit` обрывает его
  раньше. Пример «скрытно уходим, иначе догонят и вступают в бой»:

```json
{
  "type": "start_pursuit",
  "label": "Сторожа барона",
  "skill": "stealth",
  "every_ticks": 3,
  "fails_to_catch": 1,
  "on_fail": [
    { "type": "start_combat", "enemies": [ { "entity": "npc_guard", "count": 2 } ],
      "arena": "arena_gate" }
  ]
}
```

  Полей `chance_warns`, `arena` и `hunters` у этого эффекта **нет** (старый
  гайд их обещал — отсюда и были расхождения с форматом): арена задаётся
  в `on_fail`, число преследователей движком не выбирается.
- **Уровни сложности игрока**: `meta.difficulties[]` — пресеты множителей
  (урон/потребности/цены). Большой список — выбор на создании персонажа;
  одиночный — «как задумано».
- **Самочувствие NPC** (`state.npc_mood`, 0…100, по умолчанию 50) — «в каком
  настроении собеседник»: движок сам двигает его по расписанию дня
  (`+10` за сон в ночные часы, `−10` за бодрствование), оно сдвигает итог
  проверок убеждения (до ±25 к отношению) и выводится подсказкой в шапке
  разговора («бодр и расположен» / «измотан и раздражён»). Поля «wellness»
  у статусов нет — не выдумывай его. Прямого эффекта «задать самочувствие»
  тоже нет: влияй расписанием NPC и отношением (`change_disposition`), а
  «как выглядит» — состояниями портрета (`set_entity_state`, §19).
- **New Game+**: `meta.new_game_plus { keep, boost }` — победа открывает
  «новый круг» с переносом наследия; `boost` — шаги ужесточения за круг.
- **Оформление кампании тонче**: `theme.tokens` (панели/карточки/колодцы/журнал)
  и `theme.frame` — PNG-рамка панелей 9-срезом.
- **Портрет героя**: `char_creation.portraits[]` (галерея мастера) и
  `char_creation.portrait_layers[]` (составной облик по сегментам: лицо/волосы/
  одежда); у каждого варианта `states` — кадры под состояния (`wounded`,
  `tired`, статус из реестра) — портрет в листе персонажа живой.

## 20. Что не трогать из интерфейса

- Редактор уже по-русски, без id в подписях. Не используй id в тексте игрока.
- id менять запрещено: «устаревшее» поле помечай, создавай новое.
- Контент не хардкодить: всё — через реестры (статусы, навыки, профессии,
  виды, погода, эмоции, сложности, портреты).
