## Visible-error: старый случай, его negatives и выбранный путь

**Выбран путь: дополнение к ADR 1.17 со статусом `proposed`, а не заявление об эквивалентности.** Карточка STAB-1.42 не содержит ответа Мастера в поле `Ответ` на момент этой проверки. §2.6 и userscript в этой работе не переписывались.

- **Старый случай:** `B:_tools/ScriptCat/tests/visible-error-master-smoke.mjs:28-41` утверждает, что оба видимых error paths немедленно вызывают pause/notification, что монитор не делает повторную отправку, запускается до recovery, проверяет ошибку в ручном режиме до auto-mode guard и включает текст ошибки в оповещение. Старый тест-файл ссылается на отсутствовавший `dispatch.user.js`, поэтому это исторический оракул, не успешный запуск на B.
- **Сравниваемый новый случай, указанный в карточке:** `E:_tools/ScriptCat/tests/visible-error-master-smoke.mjs:52-63` — matching fresh expectation, один вызов bounded retry и ноль пауз при успешном первом retry. Это семантически не эквивалентно старому немедленному pause. Для точности: данный блок вставлен; прямой diff-hunk старого `:28-41` — новый `:81-92`, где проверяется pause для несвязанного первого отказа.
- **Факты текущей реализации:** `_tools/ScriptCat/narthex.user.js:68-69` задаёт один resend и окно свежести 180 секунд; helper `:3173-3208` проверяет живое ожидание/role/sentAt/свежесть/бюджет, но не классифицирует текст отказа; monitor `:3483-3512` при первом подходящем отказе пытается поставить retry, а на втором/несвязанном отказе ставит pause. Тест `visible-error-master-smoke.mjs` сам исполняет production monitor, но инжектирует границы и stub retry; живую Arena он не имитирует.
- **Manual-mode negative отдельно:** текущий `tick` возвращается на `_tools/ScriptCat/narthex.user.js:10119`, если авто выключен, это не ручной «Шаг» и нет `pending`/`expect`; вызов monitor находится позже, на `:10147`. Поэтому idle manual case старого теста не покрыт новой пробой и фактически расходится. Если есть `pending` или `expect`, guard пропускает тик и visible-error monitor выполняется. Новая проба `visible-error-master-smoke.mjs:173-181` проверяет только порядок monitor перед setup/обычной работой, не этот guard.
- **Отдельно закрытые negatives новой пробы:** нет прямого `.click()`/`sendButton`/reload из монитора (`:31`); второй отказ сохраняет `runId` (`:67-79`); несвязанный первый отказ ставит pause (`:81-92`); повторный alert дедуплицируется, UI card отдельно эскалируется ровно один раз (`:94-114`); пустая страница — no-op (`:116-121`); pause уведомляет с приоритетом 5 и сохраняет `pending`/`expect` (`:124-170`); ошибка проверяется до обычной dispatch-работы (`:173-183`). Старое «никакой retry вообще» изменено на «нет немедленного клика, допускается queued bounded retry» и отражено в предложенном ADR, а не объявлено сохранённым.
- `narthex-error-pause-smoke.mjs:107-127` отдельно сохраняет негатив «сам visible-error monitor не перезагружает страницу»; дополнительная временная recovery-перезагрузка ограничена и заканчивается pause после исчерпания бюджета.
- **Вопросы** о первом отказе и ручном idle-режиме (каждый с A/B/C и default «оставить как есть») записаны в [`docs/decisions/STAB-1.17-visible-error.md`](../../docs/decisions/STAB-1.17-visible-error.md). **Фактическое решение проверки:** обе семантики расходятся или не закрыты новой пробой; ответа Мастера нет; выбран разрешённый карточкой путь ADR `proposed`. До ответа старые требования §2.6 остаются нормативными; proposal не выдаётся за approval. После ответа статус должен стать `accepted` или `rejected` с датой, без теста, замораживающего статус.

## Legacy response normalizer: отдельное решение §2.6

**Выбран путь: отдельный ADR `proposed` + вопрос; legacy cases не объявлены эквивалентными текущему Gateway.** `scriptcat-gateway-smoke.mjs` строки B `:14-40` содержали 5 положительных форм (result wrapper, top-level, JSON `content`, `data.file`, Drive URL) и два negatives (result без ID и unrelated generic ID); B `:42-71` требовали ровно один retry malformed-success с теми же Dispatch/Run. При этом B-тест с самого начала читает отсутствующий `dispatch.user.js` (`:4`), удалённый commit `03cf84241f55ccdb645aa6a79b08bce6548a6097`, и потому не исполнялся как рабочая probe на B.

- V:`_tools/ScriptCat/narthex.user.js:1807-1861` возвращает любой `ok:true` response как есть; GM retry ограничен сетевыми исключениями, затем есть fetch fallback. `appendToJournal:6977-6985` извлекает только `fileId` или `result.fileId`; JSON wrapper, `data.file`, Drive URL и malformed-success retry не входят в этот runtime path.
- Текущий `scriptcat-gateway-smoke.mjs:60-82` проверяет один response, содержащий одновременно top-level и nested `result`; `:84-112` проверяет retry только сетевой ошибки и сохранение пары Dispatch/Run. `narthex-journal-recover-smoke.mjs:82-120` тоже даёт production helper fixture сразу с двумя ID-полями, а не отдельный result-only case. Эти пробы исполняются, но не сохраняют все старые normalization assertions.
- `_tools/ScriptCat/README-авторизация.md:19` на V всё ещё обещает top-level/result совместимость и один retry успешного ответа без распознанного ID; это расходится с текущим кодом выше. README вне scope, здесь он не менялся. Idempotent Apps Script `createLog` не доказывает client malformed-success retry.
- Вопрос с вариантами A/B/C и default «оставить старый оракул» записан в [`docs/decisions/STAB-1.17-gateway-normalizer.md`](../../docs/decisions/STAB-1.17-gateway-normalizer.md). **Фактическое решение проверки:** старый и текущий пути семантически неэквивалентны; ответа Мастера нет, поэтому выбран ADR `proposed`; до ответа старый оракул не объявляется снятым, а текущий runtime — одобренным.
