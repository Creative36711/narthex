# Narthex: передача хода между ИИ-агентами

Скрипт для ScriptCat, который превращает страницы Arena в конвейер:
Координатор выдаёт задачу → исполнитель работает, коммитит, пушит и **сам
сливает свой PR** → ход возвращается Координатору. Цикл идёт, пока Координатор
не скажет `done`.

Версия: **1.4.8**. Файл: `narthex.user.js`. Старый `dispatch.user.js` (кампании)
остаётся как есть и с новым скриптом не связан.

## Текущая миссия и план

Миссия NAR-1 — **фаза 1 текущего плана** ([`docs/phases.md`](../../docs/phases.md)):
вынос ядра из `engine.ts` без изменения поведения. План — гипотеза, а не канон:
число и порядок фаз меняются. Дальше по плану — шов «движок / пак», `adventure`
и FMV, второй рантайм, студия по пакам, мастерская и 1.0.

Транспорт о фазах ничего не знает и знать не должен: он передаёт ход, читает
карточки и мержит только через исполнителя. План живёт в репозитории, состав
миссии — в Notion.

Предупреждение о ветке-снимке в техническом блоке остаётся в силе: 2026-10-23
сессия снова оказалась на снимке без общей истории с `main`
(`git merge-base HEAD origin/main` пуст). Поэтому Executor по-прежнему обязан
начинать с `git reset --hard origin/main` и ветки от `origin/main`.

### «Шаг» — это один шаг

1. Нажатие без ожидания: определить ход и **отправить** сообщение.
2. Нажатие при отправленном сообщении: **прочитать ответ**.
   - ответа ещё нет → «Жду ответ …», ничего не отправляется;
   - ответ без маркера → **одно** напоминание этой же роли;
   - маркер есть → запись в Notion и **отправка** следующему агенту.
3. Нажатие во время работы агента → «ещё отвечает», без действий.

Фон (таймер) в ручном режиме только досылает очередь после перехода на страницу
адресата. Ответы и новые задания — исключительно по нажатию.

### Отладка в консоли браузера

Включается одним из трёх способов и **сохраняется в ScriptCat**, поэтому работает
и после перехода на страницу другого агента — там, где всё и ломается:

1. открыть адрес с `?cfn-debug` (например, `https://arena.ai/agent/<id>?cfn-debug`);
2. нажать **🐞** в панели (кнопка подсвечена, пока отладка включена);
3. в консоли: `__narthex.debug(true)`.

Что печатается: снимок страницы при загрузке, состояние каждого тика, каким
селектором найден редактор, есть ли активная кнопка Send и что её перекрывает,
путь вставки текста, результат каждого клика и проверки доставки. Панель при
этом остаётся краткой — в ней только вехи.

Команды в консоли:

| Команда | Что делает |
|---|---|
| `__narthex.state()` | снимок: роль, очередь, ожидание, редактор, Send, карточки, последнее сообщение |
| `__narthex.step()` | один шаг вручную |
| `__narthex.sendButton()` | что скрипт считает кнопкой Send: найдена, активна, перекрыта |
| `__narthex.panels()` / `__narthex.closePanel()` | какие карточки видны / закрыть один раз |
| `__narthex.messages()` | id и начало сообщений в чате |
| `__narthex.resend()` | вернуть задание из ожидания в очередь |
| `__narthex.debug(false)` | выключить |

**Почему карточка возвращается.** Её показ решает backend: после закрытия она может
отрисоваться снова, уже поверх кнопки Send. Поэтому карточка закрывается и перед
вставкой текста, и перед кликом Send, а результат клика проверяется — «отправлено»
пишется только когда сообщение действительно ушло.

## Что нужно до установки

| Компонент | Зачем | Где взять |
|---|---|---|
| Notion-токен | читать и писать карточки | внутренний токен рабочего пространства; хранится только в ScriptCat |
| Шлюз Drive | тексты заданий и логи ответов | `drive-gateway.gs` (v1.5), развернуть как веб-приложение от своего имени |
| Ключ шлюза | подпись запросов | Script Properties → `CF_GATEWAY_KEY` |
| URL шлюза | адрес `/exec` | после развёртывания |

Скрипт обращается ровно к четырём адресам: `api.notion.com`,
`script.google.com`, `script.googleusercontent.com` и `ntfy.sh` (если

## Установка

1. Развернуть `drive-gateway.gs` (Развёртывание → Новое развёртывание →
   Веб-приложение → «от моего имени», доступ «всем»). Скопировать URL `/exec`.
2. В Script Properties задать `CF_GATEWAY_KEY` — любую длинную строку.
   Папки шлюз создаст сам при первом `ping`: `Arena/logs` и `Arena/payloads`.
3. Установить `narthex.user.js` в ScriptCat.
4. Открыть любую страницу `https://arena.ai/agent/<id>` и нажать **⚙** в панели
   Narthex (правый нижний угол). Альтернатива: `https://arena.ai/?cf-auth-setup=1`
   — параметр из адреса убирается сам.
5. Заполнить: Notion-токен, URL шлюза, ключ. Нажать «Проверить».
   Успех — строка «Настройка сохранена: <имя>, шлюз pong».

## Где включается цикл

Панель Narthex — **правый нижний угол**, видна на любой странице `arena.ai`.
Работает она только там, где id из адреса совпадает с `Agent URL` активной
роли; на остальных страницах «Шаг» пишет в лог, почему ничего не сделал.

| Кнопка | Что делает |
|---|---|
| **▶ Включить** | включает автоцикл: тик каждые 15 с, бесконечно |
| **⏸ Стоп** | выключает автоцикл (та же кнопка после включения) |
| **▶ Продолжить** | появляется вместо «Стоп», когда цикл на паузе: показывает причину и снимает её после подтверждения |
| **Шаг** | один тик вручную, даже если автоцикл выключен; на паузе спрашивает подтверждение |
| **🔔** | ntfy: топик, токен, тихий и громкий тесты, проверка связи, открыть топик |
| **🧹** | очистить журнал (память панели и сохранённый хвост) |
| **⚙** | заново ввести токен, URL и ключ |
| **✕** | остановить автоцикл и снять паузу |

### Ручной режим: кнопка «Шаг»

«Шаг» — один тик, независимо от того, включён автоцикл или нет. Состояние
живёт в Notion, поэтому ручной и авто-режимы переключаются в любой момент и
ничего не теряется: «Шаг» снимает паузу, «▶ Включить» подхватывает с того же
места. Начать стоит с «Шага» — первый прогон видно по шагам.

Одна задача = несколько кликов, между ними агенты думают сами:

| Клик | Страница | Что происходит |
|---|---|---|
| 1 | Координатор | просит Координатора спланировать ход (не чаще раза в 60 с) |
| 2 | Координатор | отправляет запрос в чат агента; тот выбирает роль и задачу |
| 3 | Координатор | читает маркер `CF_COORDINATOR_RESULT`, ставит карточке `Running` и переходит на страницу исполнителя |
| 4 | Исполнитель | отправляет задание в чат; агент коммитит, пушит, открывает и сливает PR |
| 5 | Исполнитель | ждёт бейдж мержа (до 90 с, затем сам нажимает Create/Merge как аварийный выход; общий предел — 5 минут), пишет `Submitted` и возвращает на Координатора |
| 6 | Координатор | разбирает `Submitted`, ставит `Accepted` или `Rework`, выдаёт следующий ход |

Если клик ничего не сделал, панель пишет причину: пустой `Agent URL`, агент
ещё отвечает, очередь другой роли, не прошла минута после прошлого плана или
цикл стоит на паузе. Молчаливого «нажал и тишина» больше нет.

**Что происходит между кликами 1 и 2.** План или задание ScriptCat не печатает
сам — он кладёт текст в очередь и переходит на страницу адресата. После
загрузки страница берёт задание из очереди, вставляет его в редактор и нажимает
Send — даже в ручном режиме. Поэтому «перешёл к Координатору» и «тишина» —
разные вещи: в журнале будет либо «Задание отправлено.», либо причина, по
которой оно осталось в очереди (нет поля ввода — повтор через 5 с; агент ещё
отвечает; кнопка Send не найдена — пауза). Если в журнале «Снял просроченную
отправку из очереди» — это остаток прошлой попытки: нажатие «Шаг» после этого
сразу идёт дальше, второй раз нажимать не нужно.

### Плашка завершённой задачи

После ответа агента Arena показывает плашку «задание выполнено» — она лежит
поверх чата и закрывает редактор. ScriptCat закрывает её **до** вставки текста
(тот же приём, что в `dispatch.user.js`): ищет панель по классам, внутри —
кнопку `Close`/`Закрыть` или последнюю кнопку шапки. Если кнопки не видно,
это пишется в журнал, а задание всё равно не теряется.

Автостарт без клика: добавить `?cf-auto` к адресу страницы
(`https://arena.ai/agent/<id>?cf-auto`). Параметр читается один раз и
удаляется из адреса через `history.replaceState`.

Порядок запуска: заполнить `Agent URL` у Координатора и у первой пятёрки ролей
→ открыть страницу Координатора → **▶ Включить**. Дальше скрипт сам ищет
активную миссию и активные карточки.

## Как это работает

```
[Координатор] --CF_COORDINATOR_RESULT next=<роль>--> [исполнитель]
      ^                                                   |
      |                              работа в своей зоне, commit, push,
      |                              gh pr create, gh pr merge
      |                                                   |
      +-------- Submitted <-- Continue <------------------+
```

* **Тик** — раз в 15 секунд на странице агента, чей `Agent URL` есть в «Ролях».
  Пока автоцикл выключен, скрипт только показывает состояние.
* **Ход Координатора** — сначала разбираются `Submitted`, затем выдаётся
  следующая карточка `Ready` с наименьшим `Sequence`. План запрашивается не
  чаще раза в 60 секунд — иначе Координатор получал бы новый ход на каждый тик.
* **Ход исполнителя** — ScriptCat ждёт маркер `CF_AGENT_RESULT`, пишет ответ в
  лог Drive, ждёт мерж, записывает `Check`, `Report SHA`, `Branch` и переводит
  карточку в `Submitted`.
* **Пауза** — любая ошибка (нет карточки, PR не слился за 5 минут, Notion
  отказал) останавливает цикл и пишет причину в панель. Это защита от тихого
  проскальзывания, а не сбой.

### Состояния PR: Merged, Closed, Timeout

Бейдж в интерфейсе Arena даёт три разных состояния, и «закрыт» — не то же
самое, что «провален».

| Состояние | Как выглядит | Что делает ScriptCat |
|---|---|---|
| **Merged** | бейдж `Pull request merged` | жмёт Continue, пишет ветку, карточка → `Submitted` |
| **Closed** | бейдж `Pull request closed` и кнопка Continue | жмёт Continue, пишет ветку; дальше смотрит маркер |
| **Timeout** | ни бейджа, ни Continue за 5 минут | пауза, причина в панели, карточка остаётся `Running` |

**Почему Closed нельзя считать ошибкой.** Тот же бейдж показывает PR, слитый
руками через GitHub: после `Merge pull request` на сайте Arena кнопки
Create/Merge исчезают, остаётся `Closed` и Continue. То есть по внешнему виду
отличить «слито» от «закрыто без мержа» невозможно — из ScriptCat нет доступа
к API GitHub.

Поэтому различение идёт по маркеру исполнителя:

```
CF_AGENT_RESULT {"dispatch_id":"…","run_id":"…","status":"submitted","check":0,"report":"…","pr":42,"merged":true}
```

* `merged: true` (или `status: "merged"`) → карточка `Submitted`, ссылка на PR
  из поля `pr` пишется в колонку `PR`;
* маркера о мерже нет → работа в `main` не попала: **`Rework`** с причиной в
  «Ответ», строка в лог Drive, ход возвращается Координатору. Цикл не стоит.

`Rework` в этом одном случае ставит скрипт, а не Координатор: он констатирует
факт «работа не влита». Дальше решение (перевыдать, разбить, закрыть) принимает
Координатор — в сводке ему приходит счётчик `Rework`.

### Мерж: кто его делает

Мерж — часть хода исполнителя, а не отдельное действие человека. В задании
стоит требование:

```bash
git add -A && git commit -m "<номер>: <суть>"
git push -u origin HEAD
gh pr create --fill --base main      # если PR уже есть — пропустить
gh pr merge --squash --delete-branch
```

Почему не кнопками: **Create pull request** и **Merge pull request** пишут
команду в чат, агент отвечает новым сообщением `chat-message-…`, и учёт хода
сбивается — скрипт принимает этот ответ за результат следующей задачи.

ScriptCat нажимает только **Continue** — она не порождает ответа агента и
работает без его участия. После Continue рабочая ветка меняется, скрипт читает
её из шапки (`span.min-w-0.truncate`) и пишет в карточку.

Кнопки Create/Merge остаются как аварийный выход: если через 90 секунд после
ответа PR не слит, скрипт нажимает их сам (по одному разу). Это признак того,
что исполнителю не поставили требование мержа — дефект инструкции, а не
штатный маршрут. Если и после этого PR оказался закрыт без мержа — карточка
уходит в `Rework` (см. ниже).

### Технический блок в каждом сообщении

Любое сообщение, которое ScriptCat отправляет агенту, начинается блоком
`<!-- CF_TECH v1 -->` … `<!-- /CF_TECH -->`. Внутри — не задание, а факты о
среде, и первая строка это прямо говорит, чтобы агент не спутал блок с
текстом Координатора.

Зачем: Arena выдаёт сессию с ветки-снимка без общей истории с `main` (замер
2026-10-22: 46 файлов `main` в дереве отсутствуют, расхождение 27 364 строки).
Агент, который об этом не знает, коммитит в мёртвую историю, а его PR
показывает удаление чужой работы. Регламент такого не предотвращает — его
читают не всегда, а блок приходит с каждым заданием.

Содержание выбирается по полю **`Функция`** в базе «Роли»:

| `Функция` | Блок |
|---|---|
| `Executor` | репозиторий, предупреждение о снимке, ритуал старта (`fetch` → `merge-base` → `reset --hard origin/main` → ветка от `origin/main`) |
| `Auditor` | «ты не пишешь», источник истины — `origin/main`, чтение файлов `git show origin/main:<путь>`, проверка слитого PR |
| `Coordinator` | git не нужен; инструменты — Notion и Drive |

Неизвестная или незаполненная `Функция` трактуется как `Executor`: забытое поле
безопаснее в сторону «проверь ветку», чем в сторону «делай что хочешь».
Аудитор при этом не ждёт мержа — иначе каждый аудит стоил бы пяти минут
простоя.

### Маркеры

Исполнитель заканчивает ответ строкой:

```
CF_AGENT_RESULT {"dispatch_id":"…","run_id":"…","status":"submitted","check":0,"report":"…"}
```

`check: 0` → поле `Check = pass`, иначе `fail`. `report` попадает в `Report SHA`
(обрезка 200 знаков). Совпадение по `dispatch_id` обязательно: ответ на другую
задачу не закроет текущую.

Координатор заканчивает ответ строкой:

```
CF_COORDINATOR_RESULT {"mission_id":"…","turn_id":"…","status":"completed","next":"Kernel"}
```

`next` — имя роли или `done`. `done` переводит миссию в «Завершена» и
выключает автоцикл: это единственный способ остановить бесконечность.

**Если маркера нет.** Ответ агента без маркера — не приговор и не повод звать
Мастера сразу. Скрипт ждёт, пока ответ перестанет расти (20 с), затем один раз
напоминает агенту точный шаблон (до двух напоминаний). Напоминание — не новое
задание: агенту сказано не повторять сделанное, а только закончить ответ
строкой-маркером. После двух напоминаний цикл встаёт на паузу и ждёт Мастера:
дальше автоматика не знает, закончена работа или нет.

Водяной знак ставится на странице адресата в момент отправки, поэтому чужая
переписка и эхо собственного задания не считаются ответом.

### Зависшие задачи

Задача в `Running` дольше 45 минут возвращается в `Ready` — иначе один
незагрузившийся агент останавливает всю миссию.

## Журнал

Панель показывает последние записи и счётчик `N/200`. Хранится только хвост:
при каждой записи и при загрузке страницы старые строки отбрасываются, поэтому
журнал не растёт бесконечно. Кнопка **🧹 Очистить** стирает и память панели, и
сохранённый хвост; единственная запись, которая останется, — «Журнал очищен».

Журнал — это диагностика, а не архив: история хода живёт в Notion (`Ответ`,
`Branch`, `PR`) и в Drive (`Arena/logs`), по файлу на пару Dispatch-Run.

## Пауза: цикл ждёт Мастера

Пауза останавливает всё: тики не идут, «Шаг» спрашивает подтверждение, а
статус краснеет и показывает причину. Ставится она в четырёх случаях:

| Причина | Что произошло |
|---|---|
| `arena-error` | в последнем сообщении пользователя виден алерт Arena |
| `ui-error` | в интерфейсе появилась красная карточка ошибки |
| `marker` | агент ответил без маркера после двух напоминаний |
| `error` | исключение цикла: Notion, Drive, шлюз, ветка после мержа, Send |

Одна и та же видимая ошибка не ставит паузу дважды: после «Продолжить» Мастер
уже её видел. Снимает паузу только человек — кнопкой **▶ Продолжить** (с
подтверждением и текстом причины) или **Шаг**. Пауза помнит режим: если цикл
стоял ручным, он ручным и останется.

## ntfy: тихие вехи и громкие тревоги

В ntfy уходят только важные события; рутина остаётся в журнале.

| Уровень | Priority | Когда |
|---|---|---|
| тихий | 2 (`memo`) | ход выдан, ответ записан → `Submitted`, пауза снята Мастером, зависшая задача возвращена в `Ready` |
| громкий | 5 (`warning`) | пауза и любая ошибка, таймаут PR, маркер не пришёл после напоминаний, видимая ошибка Arena, миссия завершена |

Настройка — кнопка **🔔**: топик (имя `arena-…` или ссылка `https://ntfy.sh/arena-…`),
необязательный access token, «Тихий тест», «Громкий тест», «Проверка связи» и
«Открыть топик». Пустой топик выключает уведомления. Громкая пауза дублируется
коротким гудком в браузере — на случай, если телефон молчит.

**Если пуша нет, диалог говорит, где порвалось.** Успех показывает путь
(`ScriptCat` через `GM_xmlhttpRequest` или запасной `fetch`) и HTTP-код; ошибка
называет оба пути и падает в журнал; зависший запрос через 25 с сам сообщает о
себе. Дальше — по шагам: «Проверка связи» отвечает, жив ли `ntfy.sh`; «Открыть
топик» открывает веб-страницу топика — если сообщение видно там, сервер его
принял, и искать надо в подписке приложения ntfy, а не в скрипте.

**Почему версия 1.4.0 молчала.** Пуш собирался в HTTP-заголовки `X-Title` и
`X-Tags`, а заголовки допускают только ISO-8859-1. Кириллица в заголовке — это
ошибка ещё на этапе формирования запроса: менеджер скриптов его не отправлял и
не звал ни `onload`, ни `onerror`, промис оставался вечным, диалог — пустым.
1.4.1 кладёт всё в JSON-тело, где UTF-8 разрешён.

## Ограничения

* Скрипт **не решает**, что делать: очередь, приёмка и завершение — в Notion.
  Он только исполняет решение Координатора.
* Один Координатор на миссию. Два — гонка за одну карточку.
* Скрипт не работает в фоне: вкладка должна быть открыта на странице агента,
  а браузер — не в спящем режиме.
* Паузу снимает только человек: автоцикл не «перезапускается сам» после ошибки,
  иначе один и тот же сбой повторялся бы бесконечно.
* Селекторы кнопок привязаны к разметке Arena; при её изменении нужен ремонт в
  одном месте — `createPr()`, `mergePr()`, `continueButton()`, `branchName()`.

### Скрытые бейджи в DOM

Проверка на разметке Arena (октябрь 2026) показала дефект, который был в 1.2.0–1.2.1
до пробы: `document.querySelector('[aria-label="Pull request merged"]')`
находил **скрытый** бейдж, оставшийся от прошлого состояния, на странице, где
виден только «Closed». Закрытый без мержа PR считался слитым, и работа уходила
в main, не попав туда.

Поэтому состояния читаются через `badgeVisible()` — поиск по всем совпадениям
с проверкой видимости (`getClientRects()` + computed style). Последовательность
проверок в `ensureMerged` — Merged → Closed → Continue — при этом сохраняется:
Continue показывают оба состояния, и он не должен перебивать Closed.

## Раскладка на Диске

```
Arena/            единственная папка, которую создаёт система
  Gateway         этот Apps Script (создаёт человек)
  logs/           лог на каждую пару Dispatch-Run
  payloads/       тексты заданий длиннее 2 000 знаков
```

В корне Диска шлюз не создаёт ничего. Пришёл `folderId` не из Arena — запрос
отклоняется; id старой папки dispatch-скрипта принимается, но файл всё равно
пишется в `Arena/logs`. Папка `Narthex — логи` от версии 1.4 при первом
обращении переносится внутрь Arena и переименовывается в `logs` — старые
логи остаются на месте.

Правила для агентов (что куда писать, как называть, что делать при прямом
доступе к Drive) — `docs/agents/drive.md`.

Первая команда — синтаксис, вторая — инварианты состояний (порядок проверок,
видимость бейджей, `Rework` при закрытии без мержа), третья — технический блок
(что и кому дописывается), четвёртая — раскладка Диска (шлюз на макете Apps
Script), пятая — что id источников данных совпадают с рабочим пространством. Все четыре должны отработать без ошибок: скрипт с
чужими id молча ничего не найдёт и будет выглядеть «выключенным».
