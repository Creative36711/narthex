# Narthex: передача хода между ИИ-агентами

Скрипт для ScriptCat, который превращает страницы Arena в конвейер:
Координатор выдаёт задачу → исполнитель работает, коммитит, пушит и **сам
сливает свой PR** → ход возвращается Координатору. Цикл идёт, пока Координатор
не скажет `done`, — и останавливается только когда миссию приняла приёмка.

Версия: **1.4.85**. Файл: `narthex.user.js`. Старый `dispatch.user.js` (кампании)
удалён 27.10.2026: он не развивался и путал при обновлении — из двух файлов
ставили не тот. История файла остаётся в git.

## Текущая миссия и план

Миссия NAR-1 — **фаза 1 текущего плана** ([`docs/phases.md`](../../docs/phases.md)):
вынос ядра из `engine.ts` без изменения поведения. План — гипотеза, а не канон:
число и порядок фаз меняются. Дальше по плану — шов «движок / пак», `adventure`
и FMV, второй рантайм, студия по пакам, мастерская и 1.0.

Транспорт о фазах ничего не знает и знать не должен: он передаёт ход, читает
карточки и мержит только через исполнителя. План живёт в репозитории, состав
миссии — в Notion.

Предупреждение о ветке-снимке в техническом блоке остаётся в силе: 2026-10-23
сессия снова оказалась на снимке без общей истории с `main`
(`git merge-base HEAD origin/main` пуст). Поэтому Executor по-прежнему обязан
начинать с `git reset --hard origin/main` и ветки от `origin/main`.

   скрипт склеивал их через `String`. Теперь `optionLabel()` читает

## Что изменилось в 1.4.84

**Карточка в Running без хода — не работа: ↺ снимает ход целиком, а сироты
возвращаются в Ready сами.**

Мастер, 28.10: «Неправильно, что когда сбрасываешь шаг, задача остаётся в
Running. Координатор дал новую задачу, а эта так и висит». Так и было: ↺ чистил
только хранилище скрипта, а карточка в Notion оставалась выданной.

1. **↺ снимает ход, а не память.** Кнопка сначала возвращает в Ready карточку
   текущего хода (снимает «Run ID» и «Started At», пишет причину в журнал
   хода), потом чистит очередь, ожидание и защиту от повторов, и только потом
   проверяет остальные карточки. В диалоге сказано, что произойдёт — и что
   будет, если агент ещё работает (его ответ придёт в чат уже без карточки).

2. **Running без хода возвращается в Ready сам.** В Running карточку ставит
   только транспорт — этим он берёт её в работу. Значит Running без живого
   ожидания означает, что работу никто не ведёт: скрипт про неё забыл (сброс,
   обновление, другая вкладка), а Координатор видит «1 Running» и выдаёт вместо
   неё следующую карточку. Прежде такая карточка висела 45 минут и потом всё
   равно возвращалась — но уже после того, как ход ушёл не туда. Теперь
   `sweepOrphans` возвращает её сразу (пауза `orphanGraceMs` — 2 минуты, чтобы
   не отнять карточку у другой вкладки), до того как Координатор увидит очередь.
   Не трогаются три вещи: карточка текущего хода, всё пока идёт отправка или
   транспорт занят ответом приёмки/вопросом/планом, и карточка, выданная только
   что.

3. **Running в очереди объяснён Координатору.** В промпте плана сказано: Running
   ставит транспорт на время хода и сам возвращает карточку в Ready, если хода
   нет; перевыдавать такую карточку не надо.

4. **Выдача без очереди не оставляет карточку в Running.** Если `sendToRole` не
   поставил текст в очередь (сработала защита от повтора — то же сообщение
   уходило этой роли минуту назад), карточка возвращается в Ready и причина
   называется в журнале. Прежде она оставалась Running без ожидания.

5. **Координатор не берёт ход, пока отвечает исполнитель.** Если открыть (или
   перезагрузить) страницу Координатора во время ответа агента, прежний код
   запрашивал новый план — и `requestPlan` перезаписывал `K.expect`. Ожидание
   живого хода пропадало, карточка оставалась в Running. Теперь скрипт
   открывает страницу того, чей ответ ждёт; ждёт он только свой ход — `plan` и
   `reminder` разбираются маркером, как и раньше.

**Повторная выдача той же карточки больше не сходит за доставку.**

Мастер, 28.10, 19:38: «Скрипт врёт, что задание отправлено, по факту текст
остался в поле ввода». В журнале между «Убрал плашку» (19:38:48) и «Задание
отправлено (8043 символов)» (19:38:49) не было ни клика, ни ожидания.

1. **Ключ доставки был общим у двух выдач одной карточки.** Ключом служила
   строка задания, обрезанная на 90 знаках: `Задача <заголовок> (dispatch
   <id карточки>, run <id выдачи>)`. Номер выдачи в эти 90 знаков не
   помещался, поэтому повторная выдача («проверка ответа не прошла, выдаю
   заново») давала тот же ключ. Теперь в ключ идут оба номера — `dispatch
   <карточка>, run <выдача>`: у повторной выдачи он новый.

2. **Доставка — только сообщение, которого не было до попытки.** Проверка
   `lastUserSays` отвечала на вопрос «в чате есть реплика с этой строкой» и
   находила ПРОШЛУЮ реплику, лежавшую в транскрипте. Отсюда «отправлено»
   через секунду после вставки. Теперь `deliver` снимает снимок своих реплик
   до клика (`userNodeIds`) и подтверждением считает только сообщение с id,
   которого в снимке нет (`userSaysSince`). Две страховки: сообщение, которое
   Arena съела ошибкой, не в счёт; реплика с явно старым id-временем тоже —
   так выглядит транскрипт, доехавший уже после снимка.

3. **Текст в поле ввода отменяет успех, но второго клика не будет.** Если
   новое сообщение в чате есть, а поле всё ещё держит текст (Arena не всегда
   его очищает), скрипт не кликает второй раз — он пишет об этом в журнал
   предупреждением и продолжает ждать ответа. Повторный клик отправил бы то
   же задание дважды.

4. **«Отправлено» стало проверяемым.** В журнале теперь назван id сообщения:
   `Задание отправлено (8043 символов, сообщение 0199a1c0-…)` — по нему видно
   в чате, что именно ушло. Водяной знак ожидания тоже ставится на это
   сообщение, поэтому ответ агента читается строго после него. Если журнал
   снова разойдётся с глазами, снимок для разбора снимается в консоли:
   `copy(JSON.stringify(__narthex.send(), null, 2))` — там поле ввода, кнопка
   Send, ключ доставки, свои реплики с id и временем и последний отказ.

Разбор отсеивал «шаблонные» значения — наши же примеры вроде `<роль|done>` или
`<решение: …>`, — но делал это по знаку `<` или `>` в любом месте строки и с
требованием, чтобы всё значение было ASCII-путём. Живой ответ приёмки
«…6<7, порог не достигнут…» (кириллица, пробелы, `<`) попадал в «шаблоны» и

отсутствие маркера у агента.

Теперь шаблон — это **пара** скобок вокруг описания: всё значение в скобках
(`<путь>`, `<решение>`) или скобки внутри текста с описанием внутри
(`<роль|done>`, `<чего именно не хватает: роль, доступ>`). Одиночный `<`
(сравнение, «a < b») шаблоном не считается; `<div>`/`<b>` из кода — тоже.

Второе: журнал различает «маркера нет» и «маркер есть, но разбор его

## Что изменилось в 1.4.80

**Миссию закрывает приёмка, а не Координатор.**

До этой версии `next: "done"` сам ставил «Завершена» и гасил автоцикл. Проверка
перед этим была формальной — «в очереди ноль карточек», то есть «всё ли
выдано», а не «получилось ли то, о чём миссия». Разницу видел только человек,
и только если открывал «Итог». Мастер сформулировал правило так: цикл
останавливается, когда миссия **точно** закрыта.

Теперь `done` — это передача на приёмку:

- роль с функцией **Reviewer** (в базе «Роли» — `Warden`) получает промпт с
  ТЗ-оракулом, «Итогом» миссии, очередью и принятыми карточками (ответ и PR
  каждой) и отвечает маркером
  `CF_REVIEW_RESULT {"mission_id":"…","turn_id":"…","verdict":"accept|rework","remarks":"…"}`;
- `accept` → «Завершена», дата, автоцикл выключен, громкий пуш. Событие
  объявляется тем же ключом, что и в `missionDoneNotice`, поэтому второго пуша
  про то же закрытие нет;
- `rework` → «Возвращена», дата, `Круг + 1`, замечания в карточку миссии, ход
  возвращается Координатору: он разбирает замечания карточками;
- возврат **без замечаний** — не возврат: пауза `review-empty` с просьбой
  дописать причину. Приёмка без причины превращается в «ещё круг, потому что
  не понравилось»;
- больше `reworkLimit = 3` доработок не бывает: четвёртый возврат не запускает
  работу, а останавливает цикл паузой `rework-limit` и зовёт Мастера. Если три
  круга не сошлись, расходится постановка, а не работа, — четвёртый не сойдётся
  тоже.

Без вердикта миссия не закрывается вовсе. Если роли с функцией Reviewer нет,
цикл встаёт на паузу `no-reviewer`: принимать некому, и «закрыть за компанию» —
это то же самое, что не проверять. Закрытие в обход приёмки тоже видно: когда
«Завершена» появляется без отметки `cfn-review:<id>`, `missionDoneNotice` не
объявляет конец работы, а ставит паузу `closed-unreviewed` — один раз на
закрытие, с двумя выходами: принять (тогда «Продолжить» закрывает как обычно)
или вернуть миссию с замечаниями.

Маркер не про эту миссию, пустой вердикт и вердикт вне `accept|rework` — пауза,
а не догадка: `marker-mismatch`, `review-empty`, `review-marker`.

Координатору в промпте теперь сказано: `done` — передача, «Состояние» сам не
ставь, перед `done` допиши «Итог» (что сделано, чем проверено, какие долги
остались). Прежние гейты остались на месте и проверяются до приёмки: живые
карточки (`done-with-open`) и возврат без раздела «Возврат» в «Итоге»
(`done-with-remarks`) миссию к приёмке не пропускают.

Проба: `tests/narthex-review-gate-smoke.mjs` (12 случаев: ветка `done`, промпт,
`accept`, `rework`, предел, возврат без причины, чужой маркер, неизвестный
вердикт, ожидание, приёмка без роли).

### Вопросы агентов отвечает приёмка, а не Мастер

Мастер 28.10 сформулировал правило: «на доработки всегда отвечаешь ты, на
вопросы тоже ты». До этой версии вопрос ложился строкой в «Вопросы» со сроком
в сутки, цикл шёл по варианту по умолчанию, а ответ Мастера мог не прийти
вовсе — и вопрос жил в базе неделю.

Теперь ход переключается на приёмку **сразу**, как только вопрос записан:

- любое поле `question` из маркера (исполнителя или Координатора) ставит вопрос
  в очередь `cfn-answer-queue`; следующий тик, где нет незавершённого хода,
  уходит к роли с функцией `Reviewer` с промптом `answer`;
- приёмка отвечает `CF_ANSWER_RESULT {"question_id":"…","turn_id":"…","verdict":"answer","answer":"…"}`
  — ответ пишется в «Ответ», статус становится `Решено`, и на следующем ходе он
  уезжает агентам строкой «Ответы на вопросы»; ход возвращается Координатору,
  потому что `next` из хода с вопросом считался без ответа;
- `verdict: "master"` — единственный законный повод позвать Мастера: приёмка
  физически не может решить (нужен новый агент в Arena, доступ, ключ, смена ТЗ
  или оракула). Тогда пауза `answer-needs-master`, вопрос остаётся «Ждёт», и
  Мастер отвечает руками;
- пустой ответ, неизвестный вердикт и чужой `question_id` — паузы
  `answer-empty`, `answer-marker`, `marker-mismatch`, а не догадка.

Правило остановки стало жёстче с обеих сторон:

- **Координатор** вправе встать только с `need: "<роль>"`, и только если этой
  роли действительно некому отвечать: её нет в «Ролях», «Статус» не «Активна»
  или пуст «Agent URL». Остановка без роли или с активной ролью не принимается:
  ход возвращается ему же с причиной (`requestPlan`), а вторая такая попытка
  подряд даёт паузу `blocked-norole`. Раньше `blocked` будил Мастера сразу и
  без проверок;
- **приёмка** встаёт только вердиктом `master` (и это громкий пуш). Всё
  остальное она решает сама.

Громкие пуши убраны там, где человек больше не нужен: новый вопрос, отложенный
вопрос, новое `proposed`-предложение, возврат миссии и пауза

панель есть, телефона нет). Громкими остались: пауза по делу (нет роли,

Срок у вопроса остался страховкой на случай, когда приёмки нет вовсе: тогда
вопрос закрывается вариантом по умолчанию, как раньше.

## Что изменилось в 1.4.45

**Агент спросил вместо работы — цикл отвечает сам и записывает вопрос.**

24.10 в 17:25 Kernel на середине NAR-1.12 остановился и выставил опрос: «May I

Для цикла это конец хода без маркера: работа не сдана, карточка висит в

  Координатор перечисляет в `Scope` прямо — иначе исполнитель остановится на

Капча. Журнал Мастера (53), 23.10:

  `isConnected` и `document.contains`; если узел отвалился — поле перечитывается
  и текст вставляется заново (одна повторная попытка). Отвязанный узел больше
  не даёт «успеха»: `textContent` пишется только в живое поле;
- **никаких «первых попавшихся кнопок».** Кнопка отправки — это кнопка в форме

  `send`/`submit`/`отправ`. Запасной путь «первая доступная кнопка в родителе
  редактора» удалён полностью. Осталась одна страховка: если в документе ровно
  одна кнопка с точным названием отправки — берётся она, даже если геометрия не
  сошлась;
- **кнопка пересчитывается перед самим кликом**, а не берётся из начала
  попытки: за время паузы DOM мог смениться;
- **текст проверяется перед каждым кликом**: если он пропал вместе с полем,
  он вставляется заново, а не отправляется пустота;
- **диалог поверх чата называется причиной**: пока он открыт, фокус уходит в
  него, и в паузе это теперь сказано прямо («поверх чата открыт диалог Arena»).

- пока у скрипта есть неотправленное задание, `releaseStalled` не делает ничего;

перевыдача.

### Как ведёт себя фоновая вкладка

Скрипту не нужен ни фокус окна, ни видимость страницы: он ищет элементы и
нажимает их из кода, вставка идёт через `execCommand`, буфер обмена и
`requestAnimationFrame` не используются. Поэтому цикл в фоне работает.

Но браузер режет таймеры в скрытой вкладке: сначала до одной секунды, а через
пять минут — до одного пробуждения в минуту. Отсюда три следствия:

1. Ответ агента замечается не за 15 секунд, а в среднем за минуту: цикл
   остаётся правильным, просто медленнее.
2. Проверки, которые ждут кнопку, растянуты (см. выше) — иначе Continue можно
   было не дождаться и оставить агента без новой ветки.
3. Вкладка может быть выгружена из памяти («Экономия памяти» в Chrome) — тогда
   цикл останавливается молча. `arena.ai` стоит добавить в исключения, а
   вкладку — закрепить.

Фон в журнал не пишется: с 1.4.28 убрано и единственное оповещение «браузер
режет таймеры» — Мастер работает в другой вкладке постоянно, и строка
повторялась без пользы. Сами растянутые ожидания остались: они делают работу
правильной, а не объясняют её.

Ничего в ScriptCat для этого настраивать не нужно: это обычный страничный
скрипт. А вот ntfy-топик стоит заполнить: пауза в фоновой вкладке иначе
останется незамеченной.

### Кому нужна ссылка на журнал

Задание пишется в журнал при выдаче хода, ответ дописывается, когда скрипт
принял маркер. Исполнителю читать свой журнал незачем — перед ним карточка и

ней не восстановить. Поэтому строка со ссылкой — только в промпте Координатора
и только когда в очереди есть Submitted.

### Как работает автоцикл

1. Мастер жмёт **▶ Включить** на любой странице Arena.
2. Цикл смотрит, где есть работа, и открывает нужную страницу сам.
3. Дальше — как в ручном режиме, только без «Шага»: ждёт ответа агента,
   проверяет маркер, пишет карточку, возвращает ход Координатору, выдаёт
   следующую карточку.
4. Останавливается сам только по `next:"done"`. Пауза — на ошибке на экране,
   на молчании агента, на отсутствии маркера после напоминаний и на переходах
   по кругу.
5. Автоцикл живёт в текущей вкладке: новое открытие браузера — снова ручное
   включение. Две вкладки с автоциклом одновременно не нужны: они делят одно
   хранилище и могут отправить одно и то же дважды.

### Почему приёмка и выдача расходились на два хода

Координатор честно следовал промпту: «Твой ход. Ровно одно действие». Принять

описан как законченный: судьба Submitted и следующая Ready-карточка — один
ответ. Если Координатор всё равно вернул ход себе, скрипт не встаёт: он даёт
ему ещё один ход с прямым указанием, чего не хватает, и только третий подряд
промах останавливает цикл.

### Почему «Stop generating» появлялся, когда ответа уже нет

Три независимые причины, все закрыты:

1. **Скрытая панель.** В Arena у сообщения есть панель действий; пока на неё
   не навели мышь, она погашена `opacity: 0` **на обёртке**. У самой кнопки
   прозрачность единица, размеры есть — для прежней проверки она была видна.
2. **Протухшее сообщение.** Кнопка Stop осталась в DOM сообщения, которое уже
   закончилось подписью `Response ended …`. Это прошлое, а не работа.
3. **Заставка загрузки.** Сразу после перехода на страницу агента Arena
   показывает Stop на время отрисовки транскрипта — один кадр.

### Что происходит после бейджа Merged

1. Скрипт читает ответ агента и его маркер.
2. Пишет ответ в журнал попытки.
3. Видит бейдж **Merged** (или карточку PR), ждёт **Continue** и нажимает её —
   именно это выдаёт агенту новую ветку вместо уже слитой.
4. Ждёт, пока кнопка исчезнет, читает имя новой ветки и пишет его в карточку.
5. Ставит карточке `Submitted` (+ `Check`, `Report SHA`, ссылка на PR) и
   возвращает ход Координатору.

Если PR-карточки на странице нет вообще (ответ читают на странице агента, а
бейджи живут на странице PR), скрипт 8 секунд ждёт появления карточки и только
потом верит маркеру `merged: true`; Continue в этом случае нажать нечего, и об
этом есть отдельная строка в журнале. Если исполнитель не заявил о мерже —
карточка уходит в `Rework` с причиной.

### Почему после обновления всплывало «прошлое»

ScriptCat хранит `cfn-pending` / `cfn-expect` вне вкладки: обновление скрипта
их не обнуляет. Если прошлая попытка успела записать ожидание, но сообщение в
чат не попало (вкладку закрыли, клик по Send не дошёл), новый запуск видел
«ожидание» без отметки отправки — и ссылался на него.

Теперь при смене версии такая запись снимается один раз при загрузке, а
настоящая отправка (с `sentAt`), очередь с текстом и защита от повторов
остаются: обновление посреди хода не теряет задание.

### Кнопка ↺

Спрашивает подтверждение и перечисляет, что снимется, например:
`очередь: «Coordinator», 1840 симв.; ожидание: «Coordinator», plan; защита от повторов`.
После неё ход начинается с чистого листа — нажмите «Шаг».

### «Шаг» — это один шаг

1. Нажатие без ожидания: определить ход и **отправить** сообщение.
2. Нажатие при отправленном сообщении: **прочитать ответ**.
   - ответа ещё нет → «Жду ответ …», ничего не отправляется;
   - ответ без маркера → **одно** напоминание этой же роли;
   - маркер есть → запись в Notion и **отправка** следующему агенту.
3. Нажатие во время работы агента → «ещё отвечает», без действий.

Фон (таймер) в ручном режиме только досылает очередь после перехода на страницу
адресата. Ответы и новые задания — исключительно по нажатию.

## Установка

1. Развернуть `drive-gateway.gs` (Развёртывание → Новое развёртывание →
   Веб-приложение → «от моего имени», доступ «всем»). Скопировать URL `/exec`.
2. В Script Properties задать `CF_GATEWAY_KEY` — любую длинную строку.
   Папки шлюз создаст сам при первом `ping`: `Arena/logs` и `Arena/payloads`.
3. Установить `narthex.user.js` в ScriptCat.
4. Открыть любую страницу `https://arena.ai/agent/<id>` и нажать **⚙** в панели
   Narthex (правый нижний угол). Альтернатива: `https://arena.ai/?cf-auth-setup=1`
   — параметр из адреса убирается сам.
5. Заполнить: Notion-токен, URL шлюза, ключ. Нажать «Проверить».
   Успех — строка «Настройка сохранена: <имя>, шлюз pong».

## Где включается цикл

Панель Narthex — **правый нижний угол**, видна на любой странице `arena.ai`.
Работает она только там, где id из адреса совпадает с `Agent URL` активной
роли; на остальных страницах «Шаг» пишет в лог, почему ничего не сделал.

| Кнопка | Что делает |
|---|---|
| **▶ Включить** | включает автоцикл: тик каждые 15 с, бесконечно |
| **⏸ Стоп** | выключает автоцикл (та же кнопка после включения) |
| **▶ Продолжить** | появляется вместо «Стоп», когда цикл на паузе: показывает причину и снимает её после подтверждения |
| **Шаг** | один тик вручную, даже если автоцикл выключен; на паузе спрашивает подтверждение |
| **🔔** | ntfy: топик, токен, тихий и громкий тесты, проверка связи, открыть топик |
| **🧹** | очистить журнал (память панели и сохранённый хвост) |
| **⚙** | заново ввести токен, URL и ключ |
| **✕** | остановить автоцикл и снять паузу |

### Ручной режим: кнопка «Шаг»

«Шаг» — один тик, независимо от того, включён автоцикл или нет. Состояние
живёт в Notion, поэтому ручной и авто-режимы переключаются в любой момент и
ничего не теряется: «Шаг» снимает паузу, «▶ Включить» подхватывает с того же
места. Начать стоит с «Шага» — первый прогон видно по шагам.

Одна задача = несколько кликов, между ними агенты думают сами:

| Клик | Страница | Что происходит |
|---|---|---|
| 1 | Координатор | просит Координатора спланировать ход (не чаще раза в 60 с) |
| 2 | Координатор | отправляет запрос в чат агента; тот выбирает роль и задачу |
| 3 | Координатор | читает маркер `CF_COORDINATOR_RESULT`, ставит карточке `Running` и переходит на страницу исполнителя |
| 4 | Исполнитель | отправляет задание в чат; агент коммитит, пушит, открывает и сливает PR |
| 5 | Исполнитель | ждёт бейдж мержа (до 90 с, затем сам нажимает Create/Merge как аварийный выход; общий предел — 5 минут), пишет `Submitted` и возвращает на Координатора |
| 6 | Координатор | разбирает `Submitted`, ставит `Accepted` или `Rework`, выдаёт следующий ход |

Если клик ничего не сделал, панель пишет причину: пустой `Agent URL`, агент
ещё отвечает, очередь другой роли, не прошла минута после прошлого плана или
цикл стоит на паузе. Молчаливого «нажал и тишина» больше нет.

**Что происходит между кликами 1 и 2.** План или задание ScriptCat не печатает
сам — он кладёт текст в очередь и переходит на страницу адресата. После
загрузки страница берёт задание из очереди, вставляет его в редактор и нажимает
Send — даже в ручном режиме. Поэтому «перешёл к Координатору» и «тишина» —
разные вещи: в журнале будет либо «Задание отправлено.», либо причина, по
которой оно осталось в очереди (нет поля ввода — повтор через 5 с; агент ещё
отвечает; кнопка Send не найдена — пауза). Если в журнале «Снял просроченную
отправку из очереди» — это остаток прошлой попытки: нажатие «Шаг» после этого
сразу идёт дальше, второй раз нажимать не нужно.

### Плашка завершённой задачи

После ответа агента Arena показывает плашку «задание выполнено» — она лежит
поверх чата и закрывает редактор. ScriptCat закрывает её **до** вставки текста
(тот же приём, что в `dispatch.user.js`): ищет панель по классам, внутри —
кнопку `Close`/`Закрыть` или последнюю кнопку шапки. Если кнопки не видно,
это пишется в журнал, а задание всё равно не теряется.

Автостарт без клика: добавить `?cf-auto` к адресу страницы
(`https://arena.ai/agent/<id>?cf-auto`). Параметр читается один раз и
удаляется из адреса через `history.replaceState`.

Порядок запуска: заполнить `Agent URL` у Координатора и у первой пятёрки ролей
→ открыть страницу Координатора → **▶ Включить**. Дальше скрипт сам ищет
активную миссию и активные карточки.

### Автоцикл: что делает сам и когда останавливается

Автоцикл не «нажимает всё подряд»: он повторяет тот же шаг, что кнопка
**Шаг**, и подчиняется тем же предохранителям. Проверено 25.10 по коду 1.4.57.

| Предохранитель | Как работает |
|---|---|
| **Флаг** | `sessionStorage` (`cfn-auto-enabled`), а не хранилище скрипта: переживает переходы по страницам агентов в этой вкладке, но исчезает с браузером. Новый запуск — только вручную **▶ Включить** (или `?cf-auto` для этой вкладки). Старое значение из хранилища скрипта снимается при старте. |
| **Тик** | раз в 15 с и сразу при возврате во вкладку (`visibilitychange`): в фоне таймеры режутся. Пока автоцикл выключен, тик только показывает состояние. |
| **Замок** | один шаг за раз (`busy`). Если шаг молчит 120 с — ни одной отметки жизни, а `sleep`/`waitFor` их ставят каждые несколько секунд — блокировка снимается и шаг повторяется. Дважды; третий раз подряд — пауза `kind:"step"`, потому что это уже поломка, а не один зависший запрос. |
| **Пауза** | любая ошибка (Notion, шлюз Drive, капча, ошибка на экране, невыданный маркер, ложный отказ мержа) ведёт в `pause()`: громкий ntfy с priority 5 и звук. Тик паузу не обходит — снимает только человек кнопкой **Продолжить**. |
| **Тишина агента** | 30 минут без единого сообщения **и** без Stop/плашки «думает» — передача снимается, пауза `no-reply`, карточка возвращается в Ready. Пока агент работает (виден Stop или «думает»), ожидание не рвётся: длинная задача может идти часами. |
| **Брошенные карточки** | `Running` старше 45 минут возвращается в Ready, но только если по карточке нет живого хода скрипта (нет очереди отправки и ожидания). Это не лимит на работу агента. |
| **Опросы** | опрос в чате вместо ответа разбирается раньше напоминаний; три опроса подряд — пауза (`pollPauseCount`). |
| **Мерж** | предел 5 минут; через 90 с после бейджа ScriptCat сам нажимает Create/Merge как аварийный выход. `Closed` провалом не считается: слитый руками PR выглядит так же. |

Чего автоцикл не делает: не меняет статусы ролей и `Agent URL`, не правит
оракул, не пишет в чужие зоны, не досылает отправку без отметки `sentAt`
(след прошлой попытки снимается, а не отправляется заново) и не досылает её
же старше 10 минут (неотправленное задание с уже возвращённой карточкой ждёт
Мастера до двух часов — это `undeliveredTtlMs`). Одна честная оговорка: если выключить автоцикл посреди
хода, незавершённая отправка или уже отправленное задание **доигрываются** —
иначе оно потерялось бы; новых ходов после этого не начинается.

## Как это работает

```
[Координатор] --CF_COORDINATOR_RESULT next=<роль>--> [исполнитель]
      ^                                                   |
      |                              работа в своей зоне, commit, push,
      |                              gh pr create, gh pr merge
      |                                                   |
      +-------- Submitted <-- Continue <------------------+
```

* **Тик** — раз в 15 секунд на странице агента, чей `Agent URL` есть в «Ролях».
  Пока автоцикл выключен, скрипт только показывает состояние.
* **Ход Координатора** — сначала разбираются `Submitted`, затем выдаётся
  следующая карточка `Ready` с наименьшим `Sequence`. План запрашивается не
  чаще раза в 60 секунд — иначе Координатор получал бы новый ход на каждый тик.
* **Ход исполнителя** — ScriptCat ждёт маркер `CF_AGENT_RESULT`, пишет ответ в
  лог Drive, ждёт мерж, записывает `Check`, `Report SHA`, `Branch` и переводит
  карточку в `Submitted`.
* **Пауза** — любая ошибка (нет карточки, PR не слился за 5 минут, Notion
  отказал) останавливает цикл и пишет причину в панель. Это защита от тихого
  проскальзывания, а не сбой.

### Состояния PR: Merged, Closed, Timeout

Бейдж в интерфейсе Arena даёт три разных состояния, и «закрыт» — не то же
самое, что «провален».

| Состояние | Как выглядит | Что делает ScriptCat |
|---|---|---|
| **Merged** | бейдж `Pull request merged` | жмёт Continue, пишет ветку, карточка → `Submitted` |
| **Closed** | бейдж `Pull request closed` и кнопка Continue | жмёт Continue, пишет ветку; дальше смотрит маркер |
| **Timeout** | ни бейджа, ни Continue за 5 минут | пауза, причина в панели, карточка остаётся `Running` |

**Почему Closed нельзя считать ошибкой.** Тот же бейдж показывает PR, слитый
руками через GitHub: после `Merge pull request` на сайте Arena кнопки
Create/Merge исчезают, остаётся `Closed` и Continue. То есть по внешнему виду
отличить «слито» от «закрыто без мержа» невозможно — из ScriptCat нет доступа
к API GitHub.

Поэтому различение идёт по маркеру исполнителя:

```
CF_AGENT_RESULT {"dispatch_id":"…","run_id":"…","status":"submitted","check":0,"report":"…","pr":42,"merged":true}
```

* `merged: true` (или `status: "merged"`) → карточка `Submitted`, ссылка на PR
  из поля `pr` пишется в колонку `PR`;
* маркера о мерже нет → работа в `main` не попала: **`Rework`** с причиной в
  «Ответ», строка в лог Drive, ход возвращается Координатору. Цикл не стоит.

`Rework` в этом одном случае ставит скрипт, а не Координатор: он констатирует
факт «работа не влита». Дальше решение (перевыдать, разбить, закрыть) принимает
Координатор — в сводке ему приходит счётчик `Rework`.

### Мерж: кто его делает

Мерж — часть хода исполнителя, а не отдельное действие человека. В задании
стоит требование:

```bash
git add -A && git commit -m "<номер>: <суть>"
git push -u origin HEAD
gh pr create --fill --base main      # если PR уже есть — пропустить
gh pr merge --squash --delete-branch
```

Почему не кнопками: **Create pull request** и **Merge pull request** пишут
команду в чат, агент отвечает новым сообщением `chat-message-…`, и учёт хода
сбивается — скрипт принимает этот ответ за результат следующей задачи.

ScriptCat нажимает только **Continue** — она не порождает ответа агента и
работает без его участия. После Continue рабочая ветка меняется, скрипт читает
её из шапки (`span.min-w-0.truncate`) и пишет в карточку.

Кнопки Create/Merge остаются как аварийный выход: если через 90 секунд после
ответа PR не слит, скрипт нажимает их сам (по одному разу). Это признак того,
что исполнителю не поставили требование мержа — дефект инструкции, а не
штатный маршрут. Если и после этого PR оказался закрыт без мержа — карточка
уходит в `Rework` (см. ниже).

### Технический блок в каждом сообщении

Любое сообщение, которое ScriptCat отправляет агенту, начинается блоком
`<!-- CF_TECH v1 -->` … `<!-- /CF_TECH -->`. Внутри — не задание, а факты о
среде, и первая строка это прямо говорит, чтобы агент не спутал блок с
текстом Координатора.

Зачем: Arena выдаёт сессию с ветки-снимка без общей истории с `main` (замер
2026-10-22: 46 файлов `main` в дереве отсутствуют, расхождение 27 364 строки).
Агент, который об этом не знает, коммитит в мёртвую историю, а его PR
показывает удаление чужой работы. Регламент такого не предотвращает — его
читают не всегда, а блок приходит с каждым заданием.

Содержание выбирается по полю **`Функция`** в базе «Роли»:

| `Функция` | Блок |
|---|---|
| `Executor` | репозиторий, предупреждение о снимке, ритуал старта (`fetch` → `merge-base` → `reset --hard origin/main` → ветка от `origin/main`) |
| `Auditor` | «ты не пишешь», источник истины — `origin/main`, чтение файлов `git show origin/main:<путь>`, проверка слитого PR |
| `Coordinator` | git не нужен; инструменты — Notion и Drive |

Неизвестная или незаполненная `Функция` трактуется как `Executor`: забытое поле
безопаснее в сторону «проверь ветку», чем в сторону «делай что хочешь».
Аудитор при этом не ждёт мержа — иначе каждый аудит стоил бы пяти минут
простоя.

### Маркеры

Исполнитель заканчивает ответ строкой:

```
CF_AGENT_RESULT {"dispatch_id":"…","run_id":"…","status":"submitted","check":0,"report":"…"}
```

`check: 0` → поле `Check = pass`, иначе `fail`. `report` попадает в `Report SHA`
(обрезка 200 знаков). Совпадение по `dispatch_id` обязательно: ответ на другую
задачу не закроет текущую.

Координатор заканчивает ответ строкой:

```
CF_COORDINATOR_RESULT {"mission_id":"…","turn_id":"…","status":"completed","next":"Kernel"}
```

`next` — имя роли или `done`. `done` переводит миссию в «Завершена» и
выключает автоцикл: это единственный способ остановить бесконечность.

**Если маркера нет.** Ответ агента без маркера — не приговор и не повод звать
Мастера сразу. Скрипт ждёт, пока ответ перестанет расти (20 с), затем один раз
напоминает агенту точный шаблон (до двух напоминаний). Напоминание — не новое
задание: агенту сказано не повторять сделанное, а только закончить ответ
строкой-маркером. После двух напоминаний цикл встаёт на паузу и ждёт Мастера:
дальше автоматика не знает, закончена работа или нет.

Водяной знак ставится на странице адресата в момент отправки, поэтому чужая
переписка и эхо собственного задания не считаются ответом.

### Зависшие задачи

Задача в `Running` дольше 45 минут возвращается в `Ready` — иначе один
незагрузившийся агент останавливает всю миссию.

## Журнал

Панель показывает последние записи и счётчик `N/200`. Хранится только хвост:
при каждой записи и при загрузке страницы старые строки отбрасываются, поэтому
журнал не растёт бесконечно. Кнопка **🧹 Очистить** стирает и память панели, и
сохранённый хвост; единственная запись, которая останется, — «Журнал очищен».

Журнал — это диагностика, а не архив: история хода живёт в Notion (`Ответ`,
`Branch`, `PR`) и в Drive (`Arena/logs`), по файлу на пару Dispatch-Run.

## Пауза: цикл ждёт Мастера

Пауза останавливает всё: тики не идут, «Шаг» спрашивает подтверждение, а
статус краснеет и показывает причину. Ставится она в четырёх случаях:

| Причина | Что произошло |
|---|---|
| `arena-error` | в последнем сообщении пользователя виден алерт Arena |
| `ui-error` | в интерфейсе появилась красная карточка ошибки |
| `marker` | агент ответил без маркера после двух напоминаний |
| `error` | исключение цикла: Notion, Drive, шлюз, ветка после мержа, Send |

Одна и та же видимая ошибка не ставит паузу дважды: после «Продолжить» Мастер
уже её видел. Снимает паузу только человек — кнопкой **▶ Продолжить** (с
подтверждением и текстом причины) или **Шаг**. Пауза помнит режим: если цикл
стоял ручным, он ручным и останется.

## ntfy: тихие вехи и громкие тревоги

В ntfy уходят только важные события; рутина остаётся в журнале.

| Уровень | Priority | Когда |
|---|---|---|
| тихий | 2 (`memo`) | ход выдан, ответ записан → `Submitted`, пауза снята Мастером, зависшая задача возвращена в `Ready` |
| громкий | 5 (`warning`) | пауза и любая ошибка, таймаут PR, маркер не пришёл после напоминаний, видимая ошибка Arena, миссия завершена |

Настройка — кнопка **🔔**: топик (имя `arena-…` или ссылка `https://ntfy.sh/arena-…`),
необязательный access token, «Тихий тест», «Громкий тест», «Проверка связи» и
«Открыть топик». Пустой топик выключает уведомления. Громкая пауза дублируется
коротким гудком в браузере — на случай, если телефон молчит.

**Если пуша нет, диалог говорит, где порвалось.** Успех показывает путь
(`ScriptCat` через `GM_xmlhttpRequest` или запасной `fetch`) и HTTP-код; ошибка
называет оба пути и падает в журнал; зависший запрос через 25 с сам сообщает о
себе. Дальше — по шагам: «Проверка связи» отвечает, жив ли `ntfy.sh`; «Открыть
топик» открывает веб-страницу топика — если сообщение видно там, сервер его
принял, и искать надо в подписке приложения ntfy, а не в скрипте.

**Почему версия 1.4.0 молчала.** Пуш собирался в HTTP-заголовки `X-Title` и
`X-Tags`, а заголовки допускают только ISO-8859-1. Кириллица в заголовке — это
ошибка ещё на этапе формирования запроса: менеджер скриптов его не отправлял и
не звал ни `onload`, ни `onerror`, промис оставался вечным, диалог — пустым.
1.4.1 кладёт всё в JSON-тело, где UTF-8 разрешён.

## Ограничения

* Скрипт **не решает**, что делать: очередь, приёмка и завершение — в Notion.
  Он только исполняет решение Координатора.
* Один Координатор на миссию. Два — гонка за одну карточку.
* Скрипт не работает в фоне: вкладка должна быть открыта на странице агента,
  а браузер — не в спящем режиме.
* Паузу снимает только человек: автоцикл не «перезапускается сам» после ошибки,
  иначе один и тот же сбой повторялся бы бесконечно.
* Селекторы кнопок привязаны к разметке Arena; при её изменении нужен ремонт в
  одном месте — `createPr()`, `mergePr()`, `continueButton()`, `branchName()`.

### Скрытые бейджи в DOM

Проверка на разметке Arena (октябрь 2026) показала дефект, который был в 1.2.0–1.2.1
до пробы: `document.querySelector('[aria-label="Pull request merged"]')`
находил **скрытый** бейдж, оставшийся от прошлого состояния, на странице, где
виден только «Closed». Закрытый без мержа PR считался слитым, и работа уходила
в main, не попав туда.

Поэтому состояния читаются через `badgeVisible()` — поиск по всем совпадениям
с проверкой видимости (`getClientRects()` + computed style). Последовательность
проверок в `ensureMerged` — Merged → Closed → Continue — при этом сохраняется:
Continue показывают оба состояния, и он не должен перебивать Closed.

## Раскладка на Диске

```
Arena/            единственная папка, которую создаёт система
  Gateway         этот Apps Script (создаёт человек)
  logs/           лог на каждую пару Dispatch-Run
  payloads/       тексты заданий длиннее 2 000 знаков
```

В корне Диска шлюз не создаёт ничего. Пришёл `folderId` не из Arena — запрос
отклоняется; id старой папки dispatch-скрипта принимается, но файл всё равно
пишется в `Arena/logs`. Папка `Narthex — логи` от версии 1.4 при первом
обращении переносится внутрь Arena и переименовывается в `logs` — старые
логи остаются на месте.

Правила для агентов (что куда писать, как называть, что делать при прямом
доступе к Drive) — `docs/agents/drive.md`.

## Проверка перед запуском

```bash
node --check narthex.user.js
node _tools/ScriptCat/tests/narthex-closed-state-smoke.mjs
node _tools/ScriptCat/tests/narthex-tech-info-smoke.mjs
node _tools/ScriptCat/tests/drive-gateway-arena-smoke.mjs
grep -n 'C.notionV\|C.roles\|C.requests\|C.missions\|C.pageUrl' narthex.user.js
```

Первая команда — синтаксис, вторая — инварианты состояний (порядок проверок,
видимость бейджей, `Rework` при закрытии без мержа), третья — технический блок
(что и кому дописывается), четвёртая — раскладка Диска (шлюз на макете Apps
Script), пятая — что id источников данных совпадают с рабочим пространством. Все четыре должны отработать без ошибок: скрипт с
чужими id молча ничего не найдёт и будет выглядеть «выключенным».
