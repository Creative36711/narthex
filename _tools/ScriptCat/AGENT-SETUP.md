# Инструкция ИИ-агенту: подготовка ScriptCat для нового проекта

## Цель и границы

Помоги владельцу подготовить **один** userscript Relay/ScriptCat 1.6.0 для другого проекта, не переписывая его под проект. Краткая инструкция для владельца — [INSTALL.md](./INSTALL.md); пошаговое подключение Notion, GitHub, Google Drive и Gateway — в [руководстве владельца](./README-авторизация.md); технические ограничения — [PORTABILITY.md](./PORTABILITY.md). Для воспроизведения системы работы обязательно прочитай [переносимый регламент](./TEAM-PLAYBOOK.md), а для построения более полной схемы баз используй [NOTION-TEMPLATE.json](./NOTION-TEMPLATE.json). Актуальные файлы — в этом каталоге; используйте реальные относительные пути или проверенный адрес репозитория владельца.

**Что переносится:** структура четырёх баз, транспорт и описанный регламент ролей/маркеров/приёмки. **Что не возникает автоматически:** содержимое и история старых баз, уставы с актуальными URL, сами Arena-агенты, проектные инварианты, реальные команды-оракулы и их доказательства. Их необходимо подготовить для нового проекта и отдельно проверить; шаблон не является полной копией исторического пространства Notion.

**Это инструкция по настройке, а не разрешение на запуск.** До изменений объясни, какие операции только читают, а какие создают/изменяют данные. Используй существующие ресурсы лишь с разрешения владельца; не трогай активные миссии, карточки, источники Notion, файлы Drive, PR и сохранённые ключи старого проекта. Не запускай автоцикл, тестовую миссию или живую пробу без отдельного разрешения. Не удаляй старые `proposed` ADR и не отключай watcher; наличие копии/ссылки в Notion не доказывает фактическое рассмотрение.

**Секреты не нужны агенту.** Не проси в диалоге токен Notion, GitHub-токен, ключ шлюза, значение реестра, пароль или код подтверждения; не выводи и не записывай их в чат, логи, документы, Git или PR. Владелец сам вводит доступы в доверенном интерфейсе и копирует проектный ключ из закрытого журнала Apps Script в окно ScriptCat. Маскированные поля всё равно доступны коду страницы и расширениям. Проверяй владельца шлюза: приложение получает переданный ему ключ, даже если URL на `script.google.com`.

## Что спросить без секретов

- Название проекта, GitHub `owner/repo`, существующая базовая ветка PR, ссылка на страницу регламента Notion, безопасное имя Drive-папки внутри `Arena` (например `synapse`).
- Ссылки на **четыре отдельные** базы/источника Notion: «Роли», «Миссии», «Запросы», «Обратная связь». Для профиля нужны UUID **data source**, а не view. Если есть только ссылки на базы, владелец может сам воспользоваться поиском ID в форме профиля с временным токеном. Допустимы только четыре разные базы с ровно одним доступным data source в каждой; токен не сохраняется.
- Ссылки на страницы действующих агентов Arena, функции и имена ролей, их зоны записи и гейты. Нужен ровно один активный Coordinator, минимум один активный Reviewer и минимум один активный Executor или Auditor. Используй реально полученные ссылки/ID, не придумывай их. Все `Agent URL` активных ролей — разные страницы вида `/agent/<id>` на **том же origin**, что и вкладка ScriptCat.
- Доступен ли владельцу Google-аккаунт для своего доверенного Apps Script и отдельного проектного ключа, готовы ли агенты и Notion-интеграция к нужным правам. Наличие включённого GitHub-коннектора Arena не означает, что у userscript есть GitHub-токен; для публичного репозитория токен userscript обычно необязателен.

Не требуй новый доступ, роль или создание ресурса, если существующий действительно соответствует контракту и владелец разрешил его использовать. Для нового проекта не подставляй рабочие базы, журналы и секреты другого проекта. Если сделать новые ресурсы невозможно, сообщи блокер; не подменяй их старыми.

## Схема Notion

Ниже минимальный контракт, совпадающий с независимой [фикстурой проверки](./regression-tests/fixtures/notion-schema-minimal.json). Имена и регистр точные; `title`, `rich_text`, `select`, `url`, `date`, `number` — **типы свойств Notion API**. В частности, `Статус` и `Dispatch State` должны быть `select`, а не другим типом Notion Status. Дополнительные свойства допустимы. Создавай/изменяй базы только с согласия владельца; безопаснее отдельные пустые базы с этой схемой, чем копия с чужими рабочими строками.

### Роли

| Тип | Обязательные свойства |
|---|---|
| `title` | `Роль` |
| `select` | `Функция`, `Статус` |
| `url` | `Agent URL` |
| `rich_text` | `Зона записи`, `Гейт` |

`Функция`: `Coordinator`, `Executor`, `Auditor`, `Reviewer`. `Статус`: `Активна` (дополнительные варианты возможны). В строках должны быть непустые и согласованные имена ролей, реальные Agent URL и разумные зоны/гейты проекта. Значение `Кому` у задач — имя из `Роль`, а не функция или ID агента.

### Миссии

| Тип | Обязательные свойства |
|---|---|
| `title` | `Миссия` |
| `select` | `Состояние` |
| `date` | `Создана`, `Завершена`, `Возвращена` |
| `number` | `Круг` |
| `rich_text` | `Замечания`, `Итог` |
| `url` | `ТЗ URL` |

`Состояние`: `Активна`, `Возвращена`, `Завершена`, `Провалена`. Миссия и ТЗ описывают **данный проект**. Активной или возвращённой может быть только одна миссия. Каждая карточка должна иметь точный `Mission ID` — UUID её страницы; название служит для людей, не для сопоставления.

### Запросы

| Тип | Обязательные свойства |
|---|---|
| `title` | `Запрос` |
| `select` | `Кому`, `Dispatch State`, `Check` |
| `number` | `Sequence` |
| `date` | `Started At`, `Submitted At` |
| `url` | `PR` |
| `rich_text` | `Миссия`, `Mission ID`, `Dependency`, `Run ID`, `Recipient Agent ID`, `Output Drive File ID`, `Payload Drive File ID`, `Намерение`, `Инварианты`, `Acceptance`, `Свободно`, `Scope`, `Ответ`, `Branch`, `Report SHA` |

`Dispatch State`: `Draft`, `Ready`, `Running`, `Submitted`, `Accepted`, `Rework`, `Blocked`. `Check`: `pass`, `fail`. `Кому`: имена **всех активных** ролей `Executor` и `Auditor` из базы «Роли», написанные точно так же. Обычные рабочие карточки Reviewer не выдаются. Поля состояния, Run и журнала в ходе цикла заполняет скрипт: не подменяй `Output Drive File ID` ссылкой на произвольный отчёт.

### Обратная связь

| Тип | Обязательные свойства |
|---|---|
| `title` | `Вопрос` |
| `select` | `Статус` |
| `date` | `Срок`, `Доставлено` |
| `url` | `Материал` |
| `rich_text` | `По умолчанию`, `Ответ`, `Варианты`, `Роль`, `Карточка`, `Миссия`, `Что блокирует` |

`Статус`: `Ждёт`, `Решено`, `Принят дефолт`, `Отменён`. Дополнительная формула `Тип` не является логикой решения. Для нового предложения передавай в маркере `question` с текстом, начинающимся `ADR:`, полным контекстом и последствиями, тремя вариантами, ссылкой на материал при наличии и `default: "оставить как есть"`. Шаблон вопроса: `{"text":"ADR: …","options":["…","…","оставить как есть"],"default":"оставить как есть","hours":24}`. Фактический ответ приёмки обязателен; истечение срока или default не решают ADR. Старые `proposed` из `docs/decisions` сохраняются до полного переноса и ответа; при ссылках указывай полный путь/имя файла, не только номер карточки.

### Более полная схема и создание баз

[NOTION-TEMPLATE.json](./NOTION-TEMPLATE.json) содержит **схемы свойств** всех четырёх баз без чужих ID и записей. Это расширение минимальной схемы выше: в «Ролях» есть URL `Устав` и статусы `Ждёт`, `Отключена`; в «Миссиях» — `ТЗ SHA`, `Координатор`, состояния `Черновик`, `Пауза`; в «Запросах» — `Dependency`, `Проверка`, а `Check` включает `none`. Цвета select сохранены как подсказка интерфейсу. `Dependency` оставь пустым или укажи UUID страниц зависимостей через запятую: скрипт проверяет Accepted, миссию и отсутствие Check=fail, но не планирует работу за Coordinator.

`Кому` в шаблоне намеренно без опций: добавь имена **реальных** ролей нового проекта, совпадающие с `Роль`, до проверки допуска. Если хочется визуально повторить все опции исходной базы, можно добавить и имена остальных ролей, но это не разрешает выдавать Reviewer рабочие карточки. Для «Обратной связи» формула `Тип` вынесена в `afterCreate`: она зависит от `Вопрос` и `Материал`, служит только подсказкой и не влияет на решение.

Создавать базы/страницы разрешено только после согласия владельца. При работе через Notion-коннектор:

1. Найди согласованную родительскую страницу, реально доступную интеграции. Для каждой из четырёх баз вызывай создание базы под этой страницей: заголовок — массив rich text объектов, а `properties` — соответствующий объект из `databases` JSON (например, `databases.roles.properties`). Для нового проекта предварительно подставь реальные options у `Кому`; не передавай весь JSON как одну схему и не используй старые ID.
2. Из результата/чтения базы получи **её** data source ID. Вызови `get_data_source` для каждого и сверяй точные имена, типы и значения; при несоответствии исправь или сообщи блокер. Только после чтения конкретной схемы создавай строки ролей, используя реально полученные URL и свойственные данному проекту гейты.
3. После создания всех полей «Обратной связи» добавь формулу `Тип` отдельно из `afterCreate.feedback`, если доступный API/интерфейс поддерживает формулу, и прочитай схему повторно. Если интерфейс не поддерживает её установку, сообщи владельцу и предложи добавить вручную; совместимый цикл не зависит от этой подсказки.
4. Создай/адаптируй страницу регламента по [TEAM-PLAYBOOK.md](./TEAM-PLAYBOOK.md) и проектное ТЗ по его шаблону; свяжи их с ролями и `ТЗ URL`. Оракулы, инварианты, зоны и команды сверяй с реальным проектом. Держи подготовленную миссию в `Черновик` до отдельного согласия на запуск.

Шаблон воспроизводит поля и типы, но не копирует записи, исторические значения, содержимое страниц, ссылки на старых агентов, права, фильтры/виды и расположение колонок. Если нужна именно историческая копия, сначала согласуй отдельный экспорт/миграцию, проверку доступа и приватности. Notion API/коннектор могут не создавать все представления: их настройка может потребовать интерфейса владельца. Не обещай точный клон после создания схемы.

## Порядок сопровождения владельца

1. **Проверка.** Установи, что репозиторий и базовая ветка существуют, четыре источника доступны и соответствуют схеме, роли и `Кому` согласованы. Это только чтение. Прямой URL пользователей и data source UUID — не токены, но и их передавай только при необходимости. У проверки schema есть границы: она не тестирует права записи, содержимое старых карточек, подлинность владельца шлюза или полный рабочий цикл.
2. **Подготовка.** Если владелец разрешил создание ресурсов, подготовь отдельные базы и необходимые роли в его проекте. Составь по [регламенту](./TEAM-PLAYBOOK.md) проектные уставы, ТЗ, оракулы, инварианты и шаблоны карточек; согласуй их с владельцем. Не выдавай пример команды за существующую проверку. Не копируй чужую очередь, `Running`/`Submitted` или секреты. Не выдумывай значения и не исправляй старые данные молча. Для доступа к базе владелец подключает свою интеграцию; для работы агентов настраиваются соответствующие сервисы Arena.
3. **Установка.** Попроси владельца установить [relay.user.js](./relay.user.js) в ScriptCat. Если прежний userscript уже установлен — остановить работу, сохранить резервную копию и выполнить [порядок переноса](./INSTALL.md#2-если-есть-прежняя-установка); идентичность установки и доступность старого GM-хранилища не гарантированы. В форме **⚙ Подключения → Управление проектами → Новый профиль** владелец вводит repo, branch, ссылки регламента/обратной связи, имя папки и четыре data source ID; создаёт профиль и нажимает **Открыть выбранный проект**. Профиль получает UUID и остаётся на удержании.
4. **Drive.** Владелец вручную разворачивает доверенный [drive-gateway.gs](./drive-gateway.gs) с [appsscript.json](./appsscript.json), ставит в Script Properties `CF_SETUP_PROJECT_ID` и `CF_SETUP_PROJECT_FOLDER`, запускает `setupProjectGateway` и приватно переносит проектный ключ в ScriptCat. Регистрация создаёт папки `Arena/<имя>/{logs,payloads}` и ключ. Она не усыновляет существующую одноимённую папку и не идемпотентна; при ошибке не советуй слепо повторять или удалять папки. Новую версию кода нужно отдельно развернуть в Web App. Старый общий `CF_GATEWAY_KEY` и реестр существующих проектов не сбрасывать.
5. **Подключение и допуск.** Владелец в новом профиле сохраняет Notion, доверенный `/exec`, проектный ключ и при необходимости GitHub-токен; запускает **Проверить всё**. Затем в управлении проектами нажимает **Проверить подключения и разрешить работу** и принимает решение в подтверждении. При проверке используется чтение схемы и GitHub; Drive `ping` должен подтвердить проект/папку. При смене сохранённых доступов допуск нового профиля отзывается, его нужно пройти снова. После допуска изменение границ источников требует нового профиля.
6. **Не запускать за владельца.** После переключения даже разрешённый профиль остаётся на удержании. Кнопка **Шаг** снимает удержание и сразу выполняет один шаг; **Включить** снимает удержание и запускает автоцикл. Не нажимай их на этапе подготовки. После снятия удержания фоновые сторожа могут создавать записи в Notion. Для пилота предложи отдельные тестовые ресурсы, явно перечисли ожидаемые записи и получи согласие, если его ещё нет. Проверяй только одну активную вкладку на проект: атомарность между вкладками не гарантирована.

## Роли и маркеры во время согласованного пилота

Скрипт передаёт роль, контекст проекта и шаблон в соответствующий ход. Следуй фактическому промпту, ТЗ и системным ограничениям среды; не придумывай `mission_id`, `turn_id`, `dispatch_id`, `run_id` или номер PR. Не отправляй один маркер вместо отчёта.

- **Coordinator** ведёт задачи в Notion, не делает код/PR и не выдаёт Reviewer обычные задачи; в конце своего хода — `CF_COORDINATOR_RESULT` с корректными `mission_id` и `turn_id`.
- **Executor** выполняет только свой Scope, соблюдает ограничения закреплённой ветки и сдаёт отчёт с `CF_AGENT_RESULT` и `dispatch_id`/`run_id`. Для действительного мержа указывает подтверждаемый PR данного repo/base; `pr:null, merged:true` не является доказательством.
- **Auditor** только читает и сдаёт факты с `CF_AGENT_RESULT`; его находки исправляет исполнитель.
- **Reviewer / Warden** независимо принимает миссию, возвращает на доработку или зовёт владельца; не правит код и карточки. Миссия: `CF_REVIEW_RESULT` с `mission_id`, `turn_id` и `accept`, `rework` или `master`. Вопрос: `CF_ANSWER_RESULT` с `question_id`, `turn_id` и решением `answer` либо причиной `master`. Лимит возвратов вызывает владельца. Если у старой карточки Reviewer оракул отдельно требует `CF_REVIEW_RESULT`, отчёт всё равно сдаётся финальным `CF_AGENT_RESULT` с `status:"submitted", pr:null` и правильными dispatch/run; один вердикт карточку не сдаёт.

Новый профиль проверяет repo/base и GitHub-состояние перед принятием подтверждения мержа. Это не доказывает, что произвольный видимый DOM-бейдж относится к тому же PR; проверяй фактические ссылки и останавливайся при неоднозначности. Утверждение об успешном живом цикле допустимо только после реального прогона с доказательствами, не по мокам.

## Итог владельцу

Дай короткий отчёт: ссылки на установку и инструкции, что подготовлено, какие проверки были read-only, что создано по согласованию, какие права/сервисы остались для ручной настройки и **был ли на самом деле выполнен** разрешённый живой тест. Если живого теста не было, говори «готово к ограниченному пилоту после ручной настройки», а не «полностью проверено в вашем проекте». Никогда не включай в отчёт значения секретов.
