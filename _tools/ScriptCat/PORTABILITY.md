# ScriptCat 1.5.0: проекты, переносимость и сопровождение

Этот документ описывает реализацию `narthex.user.js` 1.5.0 и
Drive Gateway 1.6. Установленную у пользователя версию и развёрнутый шлюз
нельзя считать обновлёнными, пока их не обновили отдельно. Цикл автоматически
не запускается. Короткая инструкция — [INSTALL.md](./INSTALL.md), инструкция
для другого ИИ-агента — [AGENT-SETUP.md](./AGENT-SETUP.md), переносимый
регламент и проектные шаблоны — [TEAM-PLAYBOOK.md](./TEAM-PLAYBOOK.md),
расширенная схема четырёх баз — [NOTION-TEMPLATE.json](./NOTION-TEMPLATE.json),
настройка доступов — [README-авторизация.md](./README-авторизация.md).

## Что настраивается, а что остаётся общим

Один ScriptCat работает с несколькими профилями: у каждого своё имя, четыре
источника Notion, адрес страницы проекта и обратной связи, `owner/repository`,
базовая ветка и имя папки Drive. Notion-, GitHub- и Drive-доступы,
уведомления, очередь, ожидания, пауза, кэши и остальные значения `cfn-*` хранятся
раздельно. При этом логика Arena, клики, роли, `CF_*`-маркеры, работа
Coordinator и Reviewer/Warden, порядок приёмки и предел возвратов общие.
Это перенос в **такую же рабочую систему**, а не конструктор произвольных
схем или адаптер к другой платформе.

Для сохранения совместимости профиль **Narthex** использует прежние ключи и
адреса без переноса, а новый профиль получает UUID и префикс
`project:<uuid>:`. Имя — только подпись; оно не определяет, куда пишутся
данные. Выбор проекта и автоцикл привязаны к вкладке через `sessionStorage`.
Если выбор вкладки недоступен или профиль повреждён, скрипт не подставляет
Narthex вместо него.

**Одна активная вкладка на проект.** Это обязательное эксплуатационное
ограничение: межвкладочной атомарности у GM-хранилища и Notion нет. Закройте
дубли, остановите автоцикл и дождитесь завершения запущенных операций перед
переключением или изменением доступов. На время открытого окна откладываются
новые шаги; уже начатые запросы могут закончиться. Возвращение в проект ставит
удержание: сторожа и ожидающий автоматический шаг не выполняются, пока человек
не выполнит явный ручной шаг или не включит цикл. Работа в скрытой вкладке
зависит от браузера, сон устройства или выгрузка вкладки её останавливают.

## Подготовка нового проекта

1. Создайте **отдельные** базы «Роли», «Миссии», «Запросы», «Обратная связь»
   с совместимой схемой. Выдайте интеграции Notion доступ к каждой. Проверьте
   скопированные записи: активные/возвращённые миссии, Ready/Running/Submitted,
   старые URL агентов, ссылку на ТЗ и Drive ID могут относиться к другому
   проекту. Не запускайте живой цикл поверх случайно скопированной очереди.
2. В `⚙ Подключения → Управление проектами → Новый профиль` задайте четыре **data source
   ID**, ссылки Notion, репозиторий `owner/repo`, базовую ветку и отдельное
   безопасное имя папки, например `synapse`. ID базы, её представления и
   data source — разные сущности.
3. Если у вас ссылки на четыре отдельные базы, вставьте ссылки в четыре поля и
   нажмите **«Найти ID источников по ссылкам»**. Для этого временно введите
   токен Notion в поле поиска: отправляются только GET-запросы к API Notion,
   токен не сохраняется и очищается после попытки. Если у базы несколько
   источников, выберите нужный data source вручную; неоднозначный результат не
   подставляется. В пути ссылки должен быть ID самой базы; параметр `?v=` с ID представления игнорируется.
4. Сохраните профиль и скопируйте показанный UUID. В Apps Script **вручную**
   зарегистрируйте этот UUID и то же имя папки функцией `setupProjectGateway()`
   по [инструкции шлюза](./README-авторизация.md#новый-проект-drive-gateway-16).
   Нужен проектный ключ, не общий старый `CF_GATEWAY_KEY`.
5. Выберите новый профиль и нажмите «Открыть выбранный проект»; вкладка
   перезагрузится на удержании. В едином окне
   **Подключения** сохраните его токен Notion, URL шлюза, проектный ключ Drive
   и при необходимости GitHub-токен. Секреты вводятся в браузере на доверенной
   странице, **не в чат**. Сохранённые значения в поля не подставляются.
6. Откройте **Управление проектами → Проверить подключения и разрешить работу**. Проверка читает схему,
   активные роли, ветку GitHub и подтверждение UUID/папки шлюза. Это не проверка
   прав записи и не аудит содержимого старых карточек. После подтверждения
   сторожа вопросов и предложений могут создавать строки Notion; автоцикл не
   запускается. На удержании сторожа ждут ручного шага/включения цикла.
7. Человек отдельно проверяет права записи, содержимое источников и проектные
   инструкции. Запуск и продолжение цикла остаются его решением.

До первого допуска открытый профиль можно исправить с сохранением UUID и
доступов. После допуска **менять источники в этом профиле нельзя**, даже если
допуск позже отозван: для других баз/репозитория/папки создайте новый профиль
и разберите незавершённые очереди вручную. Смена Notion-, Drive- или
GitHub-доступа снимает допуск нового профиля и требует повторной проверки.
Состояние старого профиля автоматически не переносится и не удаляется.

## Контракт Notion

Новые источники должны сохранять точные имена полей, типы и select-варианты.
Проверяемый минимальный набор зафиксирован независимо в
[`regression-tests/fixtures/notion-schema-minimal.json`](./regression-tests/fixtures/notion-schema-minimal.json).
Важные группы:

- **Роли:** title `Роль`; select `Функция` (`Coordinator`, `Executor`,
  `Auditor`, `Reviewer`) и `Статус` (`Активна`); `Agent URL`, `Зона записи`,
  `Гейт`. Нужны ровно один активный Coordinator, хотя бы один активный Reviewer
  и исполнитель или аудитор. Активные адреса — разные страницы `/agent/<id>`
  на том же `arena.ai` / `www.arena.ai` origin, где открыта вкладка.
- **Миссии:** `Миссия`, `Состояние`, даты, `Круг`, `Замечания`, `Итог`,
  `ТЗ URL`; состояния `Активна`, `Возвращена`, `Завершена`, `Провалена`.
- **Запросы:** `Запрос`, `Миссия`, `Кому`, `Sequence`, `Dispatch State`,
  идентификаторы выдачи, даты, `PR`, `Check`, Drive ID, содержимое и оракул.
  В `Кому` должны быть имена активных исполнителей/аудиторов; состояния от
  `Draft` до `Accepted`, `Rework` и `Blocked` должны совпадать.
- **Обратная связь:** `Вопрос`, `Статус`, `По умолчанию`, `Ответ`, `Варианты`,
  `Срок`, `Доставлено`, `Материал`, роль/карточка/миссия и `Что блокирует`.
  `Тип` может быть формулой-подсказкой, но не определяет решение.

Скрипт проверяет перечисленные основные поля и варианты, роли и ветку только
чтением. Прямые права менять Notion, состав карточек, содержимое ТЗ и фактическую
изоляцию внешних ресурсов он не доказывает. `missionSame()` сопоставляет
названия эвристически, а пустое поле «Миссия» в задаче исторически допустимо;
профили и раздельные источники не заменяют внимательной проверки данных.

## Предложения и обратная связь

Новые предложения направляются в Notion через структурированный `question`:
полный контекст, варианты и default сохраняются в строке/теле страницы и идут
Reviewer. `CF_ANSWER_RESULT` и правило, что фактическое решение не заменяется
таймером или default ADR, сохранены. Переполнение поддерживаемого текста или
нечитаемые блоки вызывают явный отказ, а не тихое усечение. Незавершённый
POST/PATCH сохраняется для повторной попытки; при восстановлении проверяется
существующая строка, а отвеченное не переписывается.

**Старый GitHub ADR watcher остаётся включённым:** пока старые `proposed`
лежат в `docs/decisions`, он может находить их и передавать на приёмку.
Некоторые существующие строки Notion содержат лишь ссылку на старый ADR — это
не перенос полного контекста и не принятое решение. Не удаляйте старые файлы,
не отключайте watcher и не меняйте их статус автоматически; нужен отдельный
проверенный перенос и фактический ответ. В новом проекте с аналогичными ADR
тоже сохраняйте совместимый каталог `docs/decisions` и формат.

## Drive и GitHub: границы и риски

Шлюз 1.6 разделяет новые проекты: `Arena/<имя>/logs` и
`Arena/<имя>/payloads`, отдельный ключ на UUID, проверка принадлежности папок
и запрет чтения/записи за пределами разрешённых подпапок. Клиент перед каждой
проектной операцией повторно проверяет `ping`. Созданные вручную папки шлюз
не присоединяет автоматически и при ошибке регистрации может оставить созданные
части для проверки. Перемещение/переименование папок ломает проверку.

Legacy Narthex использует `Arena/logs`, `Arena/payloads` и общий
`CF_GATEWAY_KEY`. **Старый master key широк:** legacy `read` может прочесть
любой текстовый файл, доступный владельцу шлюза, по известному ID. Не выдавайте
его как изолированный ключ проекта. Apps Script работает от владельца и в
манифесте запрашивает широкий Google Drive scope; для сильной изоляции
используйте отдельный Google-аккаунт/шлюз и проверяйте доступы Google вручную.
Адрес стандартного `/exec` — тоже адрес программы владельца, а не гарантия её
добросовестности. Секреты в DOM-формах доступны коду страницы и расширениям.

Новые профили требуют проверяемый PR своего репозитория и заданную базовую
ветку до запасных кнопок; перед принятием DOM `Merged`/`Continue` результат
повторно сверяется с GitHub. Неизвестное состояние или чужой repo/base
останавливают обработку, а не объявляют мерж подтверждённым. API-проверка не
является гарантией того, что произвольная разметка Arena относится к этому же
PR: наблюдайте интерфейс и не включайте чужую сессию параллельно. Для
существующего Narthex оставлен прежний режим совместимости.

## Сборка и тесты

Редактируйте **исходники**, не сгенерированный файл:

| Части | Содержимое |
|---|---|
| `src/00-header.js`–`03-utils.js` | метаданные, конфигурация, профили/хранилище, утилиты |
| `04`–`12` | уведомления, панель, подключения, профили, HTTP, Notion |
| `13`–`19` | DOM Arena, сообщения, ввод, опросы, восстановление и PR |
| `20`–`23` | технический контекст, промпты, исполнитель и Coordinator |
| `24`–`27` | обратная связь, legacy ADR watcher, приёмка и ответы |
| `28`–`29` | цикл и запуск |
| `build.mjs` | детерминированно склеивает все части в одну closure; oracle проверяет версию |
| `narthex.user.js` | единственный устанавливаемый сгенерированный файл; его имя/namespace сохранены |
| `drive-gateway.gs` | отдельный исходник для Google Apps Script, не включён в bundle |

```bash
npm ci                         # только для npm/браузерных проверок проекта
npm run scriptcat:build        # после изменений src
npm run scriptcat:check        # побайтовое сравнение с bundle
node --check _tools/ScriptCat/narthex.user.js
for f in _tools/ScriptCat/tests/*.mjs _tools/ScriptCat/regression-tests/*.mjs; do node "$f" || exit 1; done
npm run build && npm run lint && npm audit --audit-level=high
```

Браузерные пробы `browser-tests/connections.mjs` и `profiles.mjs` используют
Playwright/Chromium и блокируют внешнюю сеть. Они включены в CI; для ручного
запуска укажите `NARTHEX_PARITY_BROWSER_PREFIX` на каталог, содержащий
`node_modules/playwright-core` и `node_modules/@sparticuz/chromium`. Тесты и макеты не заменяют проверку установленного
расширения, реального шлюза и изолированных тестовых данных. Live-сервисы
меняйте только после согласования и остановки цикла.
