# ScriptCat и Google Drive: настройка и текущий процесс

## Назначение

Userscript берёт статусы и очередь из Notion, задания — по Drive ID, а ответы — из последнего сообщения агента в DOM. Ready-задачи выполняются последовательно по возрастанию `Sequence`: одновременно допускается не более одной Running-задачи, Submitted-задача блокирует запуск следующей до вердикта Координатора. По умолчанию включён ручной режим. Кнопка «Передать ход вручную» у Координатора запускает только первую задачу очереди; на странице исполнителя задание вставляется и один раз отправляется кнопкой Send. После ответа исполнитель нажимает кнопку для проверки и записи результата. Координатор вносит вердикт прямо в Drive и Notion; затем очередь может продолжиться. Автоматический режим также берёт только первую Ready-задачу и отправляет каждый Run через интерфейс Arena. После тихого обрыва он может подготовить один новый Run: максимум две отправки всего (исходная и один автоматический повтор). Любая видимая ошибка в последнем сообщении или интерфейсе немедленно останавливает автоматизацию и вызывает Мастера. Userscript не перезагружает страницу и не отправляет ошибочное сообщение повторно автоматически. В автоматическом режиме видимые карточки опроса/аудио автоматически пропускаются кнопкой Skip; в ручном режиме никаких автоматических действий нет.

## Настройка Google Apps Script Gateway

1. Откройте **https://script.google.com/** под Google-аккаунтом, где лежат задания и журналы, нажмите **Новый проект**.
2. Откройте `Code.gs`, удалите шаблон и вставьте содержимое `ScriptCat/drive-gateway.gs` из этой ветки.
3. В настройках проекта включите **Show appsscript.json manifest file** и вставьте содержимое `ScriptCat/appsscript.json`.
4. Сохраните проект. Выберите функцию `setupGatewayKey` и нажмите **Выполнить**. Проверьте аккаунт Google и подтвердите Drive-доступ.
5. В журнале выполнения скопируйте значение `CF Gateway key (keep private)`. Храните ключ только в ScriptCat; не отправляйте его в чат. Повторный запуск покажет тот же ключ. Для отзыва удалите Script Property `CF_GATEWAY_KEY`, запустите функцию заново и обновите ключ в ScriptCat.
6. Нажмите **Развернуть → Новое развертывание → Веб-приложение**. Выберите **Выполнять как: Я**, доступ — **Все**, затем разверните.
7. Откройте URL `/exec`. Должен отобразиться безсекретный ответ `{"ok":true,"service":"Narthex Drive gateway","version":"1.2"}`.
8. Установите актуальный `ScriptCat/dispatch.user.js` из GitHub-ветки проекта в ScriptCat и перезагрузите Arena.
9. Для проверки авторизации откройте страницу Arena агента с `?cf-auth-setup=1`, нажмите кнопку и введите URL `/exec` и ключ. Проверка делает только `ping`, не трогает буфер, Notion или файлы. Удалите параметр после проверки.

После изменения `drive-gateway.gs` нужна новая версия веб-развёртывания: **Развернуть → Управление развертываниями → Изменить → Новая версия → Развернуть**. URL останется прежним. `createLog` возвращает `fileId` и `name` как в верхнем уровне JSON, так и в `result` для совместимости; userscript понимает оба формата и при успешном ответе без распознанного ID делает одну безопасную повторную попытку с теми же Dispatch/Run ID. Повторный `createLog` возвращает существующий файл, не создавая ещё один. Развёртывание Gateway не обязательно для совместимости обновлённого userscript со старой версией, но нужно, чтобы опубликованный ответ тоже содержал верхнеуровневый `fileId`. Текущая версия Narthex userscript берётся из поля `@version` файла [`narthex.user.js`](./narthex.user.js), а не задаётся числом в этой инструкции. Скрипт включает корреляцию ручной отправки, нормализацию ответа `createLog`, маркерный цикл Координатора и максимум две автоматические отправки на Dispatch (исходная плюс один повтор). Переключатель подписан по действию: «Запустить автоочередь», «Остановить автоочередь» или «Возобновить автоочередь»; для запуска/возобновления требуется подтверждение. Для отправки скрипт выбирает видимую активную кнопку Send, включая семантическую Submit-кнопку формы редактора, кратко ждёт её готовности и перепроверяет непосредственно перед кликом. Если кнопку безопасно подтвердить не удалось, скрипт не нажимает её и не останавливает всю автоочередь: фиксирует `manualSendRequired`, оставляет промпт в редакторе, просит один ручной клик и запрещает повторный авто-клик для этого Run; обнаруженная ручная отправка учитывается в лимите, мониторинг ответа продолжается. Любая видимая ошибка в последнем сообщении или интерфейсе останавливает автоматизацию и уведомляет Мастера; автоматических перезагрузок и повторной отправки ошибочного сообщения нет. Полный HTML чата в Drive не записывается. Обновите userscript в ScriptCat.

## Текущий рабочий поток

- Источник текста задания — свойство **Payload Drive File ID** конкретной строки Notion «Запросы». `01_Эстафета.md` не является источником текста каждого задания.
- В ручном режиме Координатор использует кнопку внутри виджета: `Submitted` — показывается ссылка на лог самой ранней по `Sequence` задачи, и очередь ждёт вердикта; `Running` — при явном ручном действии повторно выдаётся незавершённая задача; иначе запускается первая `Ready` по `Sequence`. Несколько `Ready` не считаются неоднозначностью: все они остаются в очереди и выполняются по одной. В автоматическом режиме действует тот же порядок; любая `Submitted` или `Running` блокирует запуск следующей задачи.
- Повтор `Running` — новая попытка того же задания и того же агента: создаются новый Run ID и новый Dispatch-Run лог, старый лог не меняется и его ссылка сохраняется в поле `Ответ`. Поэтому поздний ответ со старым Run ID не будет принят.
- После нажатия Координаторской кнопки задание читается из Drive по указанному в Notion ID, для него создаётся отдельный Dispatch-Run лог, затем текст вставляется в редактор и один раз отправляется кнопкой **Send message**. Последнее сообщение на странице Координатора не захватывается как ответ исполнителя. В ручном режиме при ошибке/тихом обрыве повторной отправки нет; повторный запуск выполняется только явным действием Координатора. Сверка вставки нормализует пробелы и переносы строк; отличающийся черновик не перезаписывается. Повторный вызов с тем же Run идемпотентен. После завершённого ответа кнопка сверяет роль, единственную `Running`-задачу и актуальные Dispatch/Run ID, затем сохраняет ответ и открывает страницу Координатора. В автоматическом режиме действуют те же проверки, одна отправка приходится на каждый Run; при тихом обрыве допускается максимум две отправки всего (исходная и один повторный Run). В задании требуется точная последняя строка `CF_AGENT_RESULT {"dispatch_id":"…","run_id":"…","status":"submitted"}`. Берётся последнее сообщение с `data-agent-transcript-message="true"` и `id="chat-message-…"`; `data-chat-message-id` сохраняется вместе с Dispatch ID, Run ID и Agent ID для идемпотентности.
- Скрипт извлекает только текст последнего сообщения, а не весь `outerHTML` страницы. Если в сообщении есть видимый контейнер prose, берётся текст именно из него, чтобы панель действий/интерфейс после ответа не загрязняли текст и не мешали конечному маркеру. Текст контейнера собирается обходом видимых узлов с сохранением границ абзацев/блоков; это включает конечный маркер даже если `innerText` у клона DOM пропустил хвостовые абзацы. Удаляются управляющие элементы и свёрнутые панели размышлений. Полная HTML-разметка/история чата в Drive не отправляется.
- Тайм-аут Arena проверяется по DOM-контейнеру последнего user-сообщения `#chat-message-…` и его вложенному `[role="alert"]`, а текст запроса берётся из `[data-user-message-layout="true"]`. Для восстановления сохраняются только ID/текст сообщения, тип корреляции и состояние единственного повтора; HTML контейнера не сериализуется и не отправляется в Drive.
- Перед записью проверяются последний отдельный непустой ряд `CF_AGENT_RESULT`, его `dispatch_id`, `run_id` и `status`. Переносы строк нормализуются, невидимые разделители и неразрывные пробелы удаляются/нормализуются, но маркер по-прежнему обязан быть завершающей строкой ответа. Сообщение с маркером старого Run не принимается. Если генерация ещё идёт, маркер отсутствует/не совпадает, или последнего сообщения нет, запись не производится и статус остаётся `Running`.
- Порядок подтверждения: дождаться маркера и окончания генерации → сверить роль и актуальную Running-задачу в Notion → извлечь и проверить DOM-сообщение → добавить запись в текущий `DispatchID_RunID.md` → установить `Submitted` → показать подтверждение и открыть Координатора. Если Gateway теряет ответ после фактической записи, userscript читает лог и сверяет точный idempotency-маркер; повторный append автоматически не выполняется. Повторный запуск или клик по той же паре DOM message ID/Dispatch/Run ID безопасен: шлюз распознаёт уже добавленную запись и позволяет завершить обновление статуса без дублирования и без чтения буфера.
- Автозахват отслеживает добавление узлов и изменение текстовых узлов DOM, затем ждёт короткий период тишины; это позволяет увидеть маркер, добавленный в уже существующее сообщение. Он запускается только при точном конечном маркере текущего Run и не принимает текст без маркера. Кнопка остаётся ручным повторным действием и показывает этап обработки.
- Координатор проверяет этот же журнал. Свой вердикт и краткое обоснование Координатор **напрямую** дописывает в тот же файл Drive, а затем сам обновляет в Notion `Dispatch State` и `Ответ` (`Accepted`, `Ready` для повтора или `Blocked`). Вердикт Координатора не переносится автоматически. После сдачи результата Executor получает correlated handoff на страницу именно Координатора; для продолжения автоматического цикла после проверки Координатор должен завершить ответ точной последней строкой `CF_COORDINATOR_RESULT {"campaign_id":"…","turn_id":"…","status":"completed"}` (для review-turn также обязательны `dispatch_id` и `run_id`). Без маркера цикл не запускает следующую задачу; после двух автоматических напоминаний автоматика ставится на паузу. Перезагрузка вкладки не сбрасывает состояние. В свёрнутом или развёрнутом окне Narthex в правом нижнем углу на странице того же Координатора появляется отдельная кнопка «Сбросить лимит напоминаний»; по нажатию нужно явно подтвердить (`Да`/`Нет`) сброс только лимита напоминаний текущего хода; Dispatch/Run, отправки задачи и записи Notion/Drive не очищаются и не повторяются. После подтверждения возобновляется проверка, а новые напоминания получают свежие turn ID.
- После корректного маркера userscript перечитывает Notion. Если есть Ready-задача текущей кампании, автоматически запускается только первая по `Sequence`; любые `Submitted`/`Running` или сохранённый незавершённый ход Координатора блокируют конкурирующую передачу. Если Ready-задач нет и нет Submitted/Running, в автоматическом режиме prompt с текущей очередью, ссылкой на кампанию и динамическими критериями уходит **Координатору**. Он должен либо создать следующую Ready-задачу только в этой кампании, либо установить `Состояние команды` = `Завершена — ждёт Мастера`, если критерии действительно выполнены. Сам факт пустой очереди не завершает кампанию; после валидного маркера без Ready и без terminal flag цикл останавливается и просит внимания Мастера.
- При terminal flag (`Завершена — ждёт Мастера` или `Ожидает решения Мастера`) скрипт выключает автоматическую очередь, не очищает флаг и не активирует следующую кампанию. Возобновление возможно только после явного решения Мастера в Notion и отдельного включения автоматизации. Если автоматизацию включили во время старого/ручного ответа Координатора без сохранённой корреляции, скрипт сначала дождётся окончания генерации и направит Координатору одну сверку текущего состояния с новым маркером; повторного запуска задачи при этом нет.
- Каждый отправляемый промпт получает технический блок контекста: прямую ссылку на страницу устава именно назначенной роли из Notion → «Роли», короткое напоминание о её полномочиях и ссылку на постоянный регламент пяти кампаний. Уведомление о результате для Координатора получает ссылку на страницу Координатора и отдельно на глобальный регламент. Сохранённая ручная передача от прежней версии дополняется недостающим блоком при подготовке.
- Граница кампании обязательна и для ручной координации, и для автоматического режима. Перед созданием Run/лога userscript сопоставляет поле `Кампания` Dispatch с полем `Папка` в Notion → «Кампании» и пропускает задачу только для кампании со статусом `В работе`, `На ревью` или `Доработка`. Пустая/несопоставленная кампания, статус `Ждёт` или `Готово` блокируют передачу до любых побочных действий. После явного разрешения Мастера следующую кампанию нужно перевести из `Ждёт` в `В работе`; возврат текущей кампании на доработку фиксируется статусом `Доработка`. Поля `Критерии завершения` и `Состояние команды` — источник истины из Notion; userscript подставляет критерии текущей кампании в prompt Координатору, но сам не меняет поля кампании и не открывает следующую кампанию. Тексты критериев редактируются в Notion, не в коде. Accepted отдельной задачи, merge в main, свободная Ready-очередь или молчание не означают завершение кампании и не дают разрешения на переход.
- Каждая попытка хранится в отдельном журнале в **«Логи передач по Dispatch-Run»**. Шлюз разрешает создание и добавление только в эту папку; существующие журналы шлюзом не удаляются, не перемещаются и не перезаписываются.
- Кнопка сразу показывает этап обработки («Проверяю Notion…», «Считываю последнее сообщение…», «Сохраняю ответ…», «Обновляю Notion…»). При ошибке она показывает причину и возвращается в исходное состояние. Дополнительная техническая диагностика пишется в DevTools → Console с префиксом `[ChronicleForge:diagnostic]`: состояние режима/паузы, доступность DOM-сообщения и маркера, захваченный message ID, ошибки сверки Notion/Drive. Текст ответа целиком и секреты не выводятся; одинаковые события ограничены по частоте.

## Ручной и автоматический режимы

- Вместо отдельных плавающих кнопок используется единый виджет в правом нижнем углу: в нём находятся режим, журнал действий/ошибок (последние 60 записей сохраняются между переходами), сворачивание и очистка журнала. В ручном режиме кнопка действия находится внутри виджета; в автоматическом режиме она скрыта. При включённой автоматизации рядом всегда доступна кнопка «Остановить автоматику», в том числе на паузе; переключение не удаляет текущую задачу или её лог. Только в ручном режиме при точном сообщении «Другое действие уже выполняется» userscript предлагает подтверждением снять lock; отказ сохраняет блокировку, а подтверждение не повторяет действие автоматически.
- Переключатель режима по умолчанию установлен в ручной. В ручном режиме передача запускается только основной кнопкой Координатора; после проверки содержимого задания оно вставляется в редактор и один раз отправляется кнопкой Send. Повторной отправки при ошибке/тихом обрыве нет. Исполнитель после ответа также должен нажать кнопку, чтобы сохранить его и открыть Координатора. Автоматически открывается только страница Координатора после успешной сдачи ответа — это сохраняет текущую эстафету.
- Нажмите «Запустить автоочередь» и подтвердите запуск. На странице Координатора выбирается первая Ready-задача по возрастанию `Sequence`; при нескольких Ready запускается только одна. Следующая не начнётся, пока текущая не перешла в Submitted и Координатор не записал вердикт в Notion. Running и Submitted блокируют очередь. Автоматический режим допускает максимум две отправки всего — исходную и один повтор — при тихом обрыве. Любая видимая ошибка останавливает режим и вызывает Мастера; автоматической перезагрузки или повтора ошибочного сообщения нет.
- На странице исполнителя задание вводится в contenteditable-композер и отправляется только при подтверждённой видимой и активной кнопке **Send message** или связанной с редактором submit-кнопке. В обоих режимах текст вводится через интерфейс Arena, без копирования задания в буфер; вставка сверяется до отправки. Если редактор содержит другой текст или вставка не совпала, чужой ввод не перезаписывается и автоматизация ставится на паузу. Если кнопку Send распознать не удалось, скрипт ничего не нажимает: промпт остаётся в редакторе, этот Run переходит в режим одного ручного клика без авто-повтора, а мониторинг результата продолжает работать. Диагностика сохраняет безопасные подписи и состояния кнопок рядом с композером.
- В автоматическом режиме видимые карточки опросов и выбора аудио пропускаются кнопкой **Skip**; если нажатие не сработало и карточка осталась видимой, очередь ставится на паузу для проверки. В ручном режиме автоматического Skip нет. Любая видимая ошибка в последнем сообщении или интерфейсе останавливает автоматизацию и вызывает Мастера. Скрипт не перезагружает страницу и не повторяет ошибочное сообщение; при ручном режиме автоматической отправки также нет.
- Автоматический режим ждёт ответ и конечный маркер. Его можно включить уже на странице исполнителя во время ручной Running-попытки: мониторинг текущего ответа запускается сразу и периодически перепроверяет DOM, даже если ручная отправка уже очистила pending-промпт. Если генерация не началась за 90 секунд либо остановилась без валидного маркера на 18 секунд, запускается следующая попытка с новым Run и отдельным логом; допускается максимум две отправки всего: исходная и один повтор. После второй неудачи очередь ставится на паузу для решения человека. Ручной режим не повторяет отправку при тихом обрыве. Маркер должен совпадать с текущими Dispatch ID, Run ID и Submitted-статусом.
- Перед автоотправкой скрипт закрывает оставшуюся видимую панель завершения, которая может перекрыть редактор; если её кнопка закрытия не распознана, скрипт не отправляет задание и ждёт ручного закрытия. После успешной передачи результата, записи в Drive и обновления Notion userscript сразу переходит на Координатора. Если маркер уже принят и Dispatch стал `Submitted`, но переход прервался, повторная сверка узнаёт этот же Dispatch/Run, не добавляет дубликат в Drive и восстанавливает переход. На странице Координатора скрипт вставляет уведомление в пустой редактор и один раз нажимает **Send**. Если редактор содержит другой текст или плашку нельзя закрыть, чужой текст не перезаписывается; уведомление остаётся сохранённым для ручной отправки. Если Send недоступен или нажатие не подтвердилось, ход сохраняется, уведомление остаётся в редакторе/очереди для ручной отправки, а очередь ждёт его `CF_COORDINATOR_RESULT` и не отправляет повторно. Уведомление не копируется в буфер обмена. Переключение в ручной режим останавливает будущие автоматические действия; уже начатую генерацию оно не отменяет. Буфер обмена не используется.
- Нажмите **ntfy** в заголовке виджета, укажите случайный topic и при необходимости токен, затем выберите **Сохранить и тестировать**. Тест и все записи журнала отправляются на ntfy.sh с низшим приоритетом; высокий приоритет, локальный звуковой сигнал и отдельный push используются только при переходе автоматизации в состояние «остановлена — требуется Мастер». Topic без токена доступен любому, кто знает его имя, поэтому используйте длинное случайное название или приватный topic с токеном. ScriptCat должен разрешить домен `ntfy.sh` при обновлении userscript.
- Работа в другой вкладке — только best effort, не гарантия: пока Arena-документ загружен, DOM-клики и вставка обычно выполняются и в скрытой вкладке, но браузер может замедлить таймеры, остановить страницу или выгрузить её. Скрипт повторно запускает проверки при возврате фокуса/видимости, а переходы выполняет без отложенного таймера; это не предотвращает приостановку браузером. Для надёжной очереди оставляйте Arena открытой, не выгружайте вкладку и не переводите устройство в сон; уведомления ntfy могут сообщить об остановке, даже если вкладка скрыта.

## Роли и безопасность

В Notion → **Роли** хранятся `Dispatch Function`, `Arena Agent ID`, `Arena Agent URL` и `Execution Target`. Ровно одна роль должна быть `Coordinator`; исполнители — `Executor`, люди — `Human`. Userscript читает реестр динамически. Захват лога включён только для роли `Executor`, совпадающей с URL и адресатом задачи; страница Координатора не может случайно отправить собственный ответ как лог исполнителя.

Для `campaign-2` единственный владелец управления кампанийной веткой `arena/7bb65e7e-campaign-2` — TGD. Все остальные роли, включая Producer, могут только просматривать ветку: им нельзя поручать переключение/создание/удаление или изменение веток, правки файлов, commit или push. Права на изменение метаданных PR не предполагаются и допускаются только при прямом поручении и подтверждённом доступе; merge/close в `main` — только Мастер. Producer формирует read-only оценку по доступным материалам и передаёт найденные расхождения Координатору/TGD; недоступность чтения фиксируется как ограничение, а не повод просить права на запись.

Веб-приложение доступно по публичному URL, поэтому ключ шлюза — секрет. Шлюз выполняется с полномочиями владельца Google-аккаунта. Запись ограничена одной папкой, но `read` принимает текстовые Drive file ID из Notion и сам по себе не ограничен папкой; поэтому защита устройства и доступа к ScriptCat обязательна. Google OAuth-токен не хранится в userscript и вручную в чат не передаётся.
