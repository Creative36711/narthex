# Подключение Notion, Google Drive, GitHub и Gateway

[Главная](./README.md) · [Установка](./INSTALL.md) · [Инструкция агенту](./AGENT-SETUP.md) · [Ограничения и восстановление](./PORTABILITY.md)

Это пошаговая инструкция **для владельца** нового проекта Relay 1.6.0. Названия кнопок Google, Notion и GitHub могут немного отличаться в зависимости от языка и версии интерфейса. Агента можно попросить подготовить схемы и сопровождать настройку по [AGENT-SETUP.md](./AGENT-SETUP.md), но секреты он не должен получать.

## Сначала: что именно подключается

| Сервис | Для чего | Что вводится в ScriptCat |
|---|---|---|
| Notion | Роли, миссии, карточки и обратная связь | Токен вашей интеграции и четыре ID источников данных |
| GitHub | Чтение состояния репозитория, PR и предложений | `owner/repository`, базовая ветка и, если нужен, токен чтения |
| Google Drive | Файлы заданий и журналы | Напрямую токен Google не вводится: используется свой Gateway |
| Drive Gateway | Ваше веб-приложение Google Apps Script, работающее с Drive | Адрес `/exec` и отдельный ключ данного проекта |

**Подключения Arena для агентов и подключения userscript — разные вещи.** Например, включённый в Arena GitHub-коннектор не подставляет токен в ScriptCat, а токен ScriptCat не даёт агенту доступа к GitHub. При необходимости включите для агентов коннекторы Arena к Notion, Google Drive и GitHub и убедитесь, что у них есть доступ к нужным ресурсам. У GitHub-коннектора Arena используется его тумблер; отдельного разрешения в интерфейсе ScriptCat для агента нет.

**Секреты вводит только владелец в доверенных интерфейсах.** Не отправляйте агенту в чат и не помещайте в репозиторий, документы или отчёты токены, пароли, коды подтверждения, ключ шлюза и реестр шлюза. Не публикуйте снимки экрана или журналы с этими значениями. Маскировка полей не скрывает их от кода открытой страницы и расширений: используйте доверенную страницу Arena и проверенный браузер.

Перед изменением существующего подключения остановите автоцикл, дождитесь начатых действий и сохраните резервную копию по [INSTALL.md](./INSTALL.md). Для одного проекта оставляйте только одну активную вкладку.

## 1. Notion: базы, интеграция и доступ

1. Подготовьте четыре **разные** базы нового проекта: «Роли», «Миссии», «Запросы», «Обратная связь». Их структуру агент может создать с вашего согласия по [NOTION-TEMPLATE.json](./NOTION-TEMPLATE.json) и [инструкции агенту](./AGENT-SETUP.md#схема-notion). Это схема, не готовые записи и не копия старой истории. Заполните настоящие роли и подготовьте регламент и ТЗ нового проекта.
2. Если подходящей интеграции ещё нет, откройте [портал разработчика Notion](https://app.notion.com/developers/connections), выберите **Internal connections → Create a new connection** и нужное рабочее пространство. Для создания может потребоваться владелец workspace. В **Configuration** включите возможности **Read content**, **Update content**, **Insert content** и сохраните настройки. Они нужны для чтения, изменения и создания записей цикла.
3. Дайте **именно этой интеграции** доступ к четырём базам и необходимым страницам проекта. Например, на странице Notion откройте **••• → Connections → Add connection** и выберите интеграцию; либо используйте **Content access → Edit access** в портале. Доступ к родительской странице может наследоваться её дочерними страницами — проверьте, что открываете нужное. Включённый коннектор Arena сам по себе доступ этой интеграции не выдаёт.
4. В **Configuration** найдите API token интеграции. Не вставляйте его в чат; он понадобится вам в форме профиля и в **⚙ Подключения** ниже. Если используете разрешённую существующую интеграцию, новый токен создавать не обязательно, но её доступ и возможности всё равно нужно проверить.
5. Сохраните для себя ссылки на четыре базы, страницу регламента и базу «Обратная связь». Для профиля нужны UUID **data source**, а не ID представления. Если известны только ссылки, форма профиля ниже может найти ID автоматически при помощи вашего токена: у каждой базы при этом должен быть ровно один доступный data source. При неоднозначности получите нужные ID из схемы Notion, например с помощью подключённого агента, не передавая ему токен.

Подробности и актуальные названия меню — в [документации Notion](https://developers.notion.com/guides/get-started/internal-connections).

## 2. GitHub и доступ агентов Arena

1. Убедитесь, что репозиторий и базовая ветка существуют. В профиле понадобится `owner/repository`, например `team/project`, и точное имя ветки, например `main`. В Arena включите GitHub-коннектор для агентов, которым предстоит работа в репозитории; права на push и PR зависят от реального подключения и репозитория, а не от токена ScriptCat.
2. Для **публичного** репозитория ScriptCat обычно может читать GitHub без токена; анонимные запросы ограничены GitHub. Для **приватного** репозитория нужен отдельный токен чтения, если подходящего ещё нет.
3. Для нового токена откройте GitHub **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**. Выберите владельца репозитория, срок действия и нужный репозиторий. В **Repository permissions** задайте **Contents: Read-only** и **Pull requests: Read-only**; GitHub автоматически добавляет обязательный доступ к метаданным. Для репозитория организации токен может требовать подтверждения организации.
4. Сохраните токен в надёжном месте и позднее самостоятельно вставьте его в поле GitHub окна **⚙ Подключения**. Этот токен предназначен для чтения userscript: он не заменяет подключение агента к GitHub и не даёт агенту права на commit, push или merge. Не передавайте токен агенту в чат и не вставляйте его в команды Git.

Автоматический поиск существующих предложений `proposed` смотрит `docs/decisions/` в базовой ветке. Если этот механизм нужен в новом репозитории, создайте там каталог с отслеживаемым файлом, например `.gitkeep`, и размещайте предложения в нём. Отсутствие каталога не останавливает основной цикл, но watcher не сможет прочитать предложения. Старые предложения другого проекта не удаляйте и не переносите без отдельного решения.

Подробности о токене — в [документации GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

## 3. Создайте профиль ScriptCat

1. Установите [relay.user.js](./relay.user.js) в расширение ScriptCat по [INSTALL.md](./INSTALL.md). На доверенной странице Arena откройте **⚙ Подключения → Управление проектами → Новый профиль**. Создание профиля само не создаёт ресурсы во внешних сервисах и не запускает цикл.
2. Заполните имя проекта, четыре UUID источников Notion, HTTPS-ссылки на регламент и базу обратной связи, `owner/repository`, базовую ветку и имя папки Drive. Папка — отдельное имя внутри `Arena`, например `project-one`: латинские строчные буквы, цифры, `.`, `_`, `-`; первый символ — буква или цифра. Не используйте `..`, `logs` или `payloads` как имя проекта.
3. Если вместо UUID у вас ссылки на четыре базы, вставьте ссылки в соответствующие поля, временно введите свой токен в **Токен для поиска ID** и нажмите **Найти ID источников по ссылкам**. Кнопка читает базы и подставляет ID; временное поле очищается, токен не сохраняется. Эта проверка не подтверждает права записи или полную схему.
4. Нажмите **Создать профиль**. Его UUID показан в сообщении и в строке **ID:** под списком сохранённых профилей. Это **ID профиля**, не ID базы или миссии: он понадобится для Gateway. Выберите профиль и нажмите **Открыть выбранный проект**. Вкладка перезагрузится, профиль останется на удержании и не запустится автоматически.

## 4. Google Drive: создайте собственный Gateway

Gateway — это код [drive-gateway.gs](./drive-gateway.gs), который владелец разворачивает как своё веб-приложение в Google Apps Script; это не отдельная папка в Google Drive. Его развёртывание и операции с Drive могут зависеть от квот и правил вашего Google-аккаунта.

### 4.1. Код и разрешения Google

1. Войдите в Google-аккаунт, чей Drive должен хранить журналы, и откройте [Google Apps Script](https://script.google.com/). Создайте **новый** проект. Для уже работающего шлюза сначала согласуйте обновление и сохраните его конфигурацию; не заменяйте чужой код или манифест вслепую.
2. В редакторе нового проекта замените содержимое файла кода полным текстом [drive-gateway.gs](./drive-gateway.gs). В **Project Settings / Настройки проекта** включите показ файла **appsscript.json** в редакторе. В новом проекте замените манифест содержимым [appsscript.json](./appsscript.json), затем сохраните проект.
3. Манифест запрашивает **широкий доступ к Google Drive аккаунта**, а не только к одной папке. Код выполняется с полномочиями владельца развёртывания. Сначала проверьте аккаунт, код и разрешения; предоставляйте их только своему доверенному проекту. Если Google или администратор блокирует развёртывание, выясните причину, а не обходите ограничение.

### 4.2. Регистрация проекта и ключ

1. В Apps Script откройте **Project Settings → Script Properties** и добавьте свойства:

   | Свойство | Значение |
   |---|---|
   | `CF_SETUP_PROJECT_ID` | UUID профиля из строки **ID:** в ScriptCat |
   | `CF_SETUP_PROJECT_FOLDER` | Точно то же имя папки, которое указано в профиле, например `project-one` |

   Сохраните свойства. Не подставляйте ID репозитория, базы или миссии вместо UUID профиля.
2. Вернитесь в редактор, выберите в списке функций **setupProjectGateway** и нажмите **Run / Выполнить** один раз. При первом запуске Google попросит владельца авторизовать приложение: проверьте аккаунт и запрашиваемые разрешения. Функция создаст в корне его Drive папки `Arena/<имя>/logs` и `Arena/<имя>/payloads`, зарегистрирует профиль и выпустит **проектный ключ**.
3. В журнале выполнения Apps Script найдите ключ проекта и перенесите его непосредственно в поле **Ключ шлюза** в ScriptCat. Журнал и Script Properties могут содержать секреты: не показывайте их агенту и не публикуйте. Для нового профиля используется именно проектный ключ; запускать `setupGatewayKey()` и копировать общий `CF_GATEWAY_KEY` не нужно.
4. Регистрация **не** присоединяет уже существующую одноимённую папку и **не** перезаписывает зарегистрированный профиль. Ошибка могла оставить частично созданные папки. Не запускайте функцию повторно вслепую и не удаляйте папки или реестр: сначала с владельцем выясните состояние.

### 4.3. Развёртывание веб-приложения

1. Выберите **Deploy / Развернуть → New deployment / Новое развёртывание → Web app / Веб-приложение**. Укажите выполнение **от себя / Me**, то есть от владельца нужного Google-аккаунта.
2. Для вызова из userscript выберите доступ **Anyone / Все**, допускающий обращение без входа в Google. Это делает веб-адрес доступным извне: операции Gateway проверяют ключ проекта, поэтому не раскрывайте ключ и используйте только свой проверенный код. Сам адрес `script.google.com` не доказывает, кому принадлежит приложение. Если политика аккаунта не позволяет нужный доступ, остановитесь и обсудите это с администратором.
3. Нажмите **Deploy** и скопируйте URL веб-приложения вида `https://script.google.com/macros/s/…/exec`. Нужен **`/exec`**, а не тестовый `/dev`. Если Google запросит разрешения, подтвердите их только после проверки своего проекта и аккаунта.
4. При последующем изменении кода одного сохранения недостаточно: откройте **Deploy → Manage deployments**, выберите действующее развёртывание, **Edit → New version → Deploy**. Это обновляет выбранное развёртывание; не сбрасывайте свойства и ключи. Перед обновлением общего шлюза проверьте совместимость всех его клиентов.

Справка Google: [создание веб-приложения](https://developers.google.com/apps-script/guides/web), [свойства скрипта](https://developers.google.com/apps-script/guides/properties), [управление развёртываниями](https://developers.google.com/apps-script/concepts/deployments).

При необходимости старой совместимости владелец может отдельно задать `CF_LEGACY_LOG_FOLDER_NAME` и `CF_LEGACY_RUN_LOG_FOLDER_ID`; по умолчанию чужие папки не предполагаются. Не удаляйте старые ключи, реестр и журналы. Перенос локального состояния в новый профиль **не переносит** прежние Drive-журналы автоматически.

## 5. Сохраните и проверьте подключения

1. Убедитесь, что в открытой вкладке выбран **новый профиль**, затем откройте **⚙ Подключения**. Введите токен Notion, доверенный URL Gateway `/exec`, **проектный** ключ и, при необходимости, GitHub-токен. При запросе подтверждения доверия к URL подтвердите его только для своего проверенного шлюза.
2. Нажмите **Проверить всё**: проверяются введённые поля, но они **ещё не сохраняются**. Затем нажмите **Сохранить**. Пустое поле секрета сохраняет прежнее значение; для удаления используется отдельный флажок. Изменение сохранённых доступов снимает допуск проекта и потребует повторной проверки.
3. Если владелец разрешает работу проекта, откройте **Управление проектами → Проверить подключения и разрешить работу**, прочитайте результаты и подтвердите допуск. Проверяются основные поля и роли Notion, базовая ветка GitHub и `ping` шлюза. Автоцикл эта кнопка не запускает. На только что переключённом профиле остаётся удержание; после его снятия фоновые сторожа вопросов и предложений могут создавать или изменять записи Notion.
4. Кнопки **Шаг** и **Включить** снимают удержание и начинают работу — не нажимайте их до отдельного согласия и готовности миссии. Для живой пробы согласуйте отдельные тестовые ресурсы и ожидаемые записи.

«Проверить всё» читает четыре источника Notion и метаданные репозитория, а `ping` подтверждает ответ Gateway и совпадение UUID и папки проекта. Проверки **не** доказывают право записи в Notion, доступ к конкретному PR или файлам, корректность произвольных старых карточек и успешность полного цикла. Для прежнего режима Gateway `ping` может создать или переместить старые папки; новый зарегистрированный профиль проверяет свою существующую структуру.

## Если что-то не подключается

- **Notion: 401, 403 или 404.** Проверьте токен, рабочее пространство, возможности интеграции и доступ именно к четырём нужным базам. Если поиск ID сообщает о нескольких источниках, укажите правильный data source ID вручную; не подставляйте ID представления.
- **GitHub: 403 или 404.** Проверьте `owner/repository`, доступ к приватному репозиторию, срок и права токена, подтверждение организации и возможный лимит запросов. Ответ 404 сам по себе не доказывает, что репозиторий или PR отсутствует.
- **Gateway не отвечает или не подтверждает проект.** Проверьте доверенный `/exec`, развёрнутую версию, доступ веб-приложения, аккаунт владельца, UUID профиля, имя папки и **проектный**, а не общий ключ. Не отправляйте ключ и журналы в чат. Если папки уже существуют или регистрация прервалась, сначала разберите состояние без повторной регистрации.
- **Браузер показывает ответ `/exec` на обычный GET.** Это ещё не проверка ключа, проектного `ping`, прав записи или целого цикла; используйте кнопки ScriptCat и согласованный пилот.
