# Платформа: архитектура под пять направлений

Архитектура платформы, версия 2 (2026-10-23). Документ фиксирует, что меняется
при переходе от «движка визуальных новелл» к платформе: границы, слои, паки,
мастерскую и порядок работ. **Зачем** всё это — в [`vision.md`](./vision.md),
**в каком порядке** — в [`phases.md`](./phases.md) (гипотеза, не канон).

## 1. Что уже есть и на что можно опереться

Прежде чем что-то ломать, полезно назвать активы, которые уже работают в
пользу платформы:

- **Контент — данные, а не код.** `CampaignData` — это словари сцен, сущностей,
  правил, диалогов; пакет кампании — набор файлов плюс `manifest.json`; есть
  монолитный JSON для обмена и генерации.
- **Флаги возможностей.** `CampaignFeatures` (`map`, `combat`, `trade`,
  `skills`…) и `featureOn()` — это уже реестр возможностей, только
  захардкоженный списком полей.
- **Схемы вместо ручных форм.** `schemas.ts` + `Fields.tsx` — редактор уже
  строит формы по описанию типов (`TypeSchema`), а не по вёрстке.
- **Инструмент проверки.** `cf-play` умеет читать пакет, строить граф,
  прогонять маршруты и выдавать вердикт без исходников движка.
- **Кит и паспорт набора.** `__chronicle_ai__` + `KIT.json` — версионирование
  того, чем пользуется агент.

Вывод: платформа не начинается с нуля. У неё уже есть формат, валидатор,
инструмент и способ доставки. Менять надо не это, а границу между ядром и
направлениями.

## 2. Главная ставка: два рантайма, а не пять

Пять направлений из таблицы выглядят как пять движков. По факту это не так.
Разложим по требованиям к исполнению:

| Направление | Что реально нужно | Новый рантайм? |
|---|---|---|
| Narrative & Branching | пошаговое состояние, сцены, диалоги, флаги | нет, есть |
| Adventure (пак, не направление) | то же плюс аватар, курсор, соединение предметов, видео | нет, тот же цикл |
| State-Machine & UI | пошаговое состояние, переходы, карты/предметы | нет, тот же цикл |
| Grid & Strategy | пошаговое состояние + сетка + поиск пути | нет, тот же цикл |
| Endless & Physics 2D | непрерывное время, 2D-физика, генерация | да |
| Spatial Action | непрерывное время, 3D, анимация, физика | да, самый дорогой |

Три направления из пяти — это **один и тот же пошаговый рантайм** с разными
«режиссёрами»: один разыгрывает сцену, второй — партию в карточной игре,
третий — ход в тактике. Разница не в исполнении, а в модели состояния и
представлении.

Отсюда архитектурная формула:

> **Общее ядро + два исполнителя + паки возможностей.**

- **Ядро**: формат, реестр возможностей, детерминированная симуляция,
  сохранения и миграции, события, ввод.
- **Исполнитель A — пошаговый** (narrative, state-machine, grid).
- **Исполнитель B — реального времени** (2D-физика, позже 3D).
- **Пак** (capability pack) — то, что направление добавляет: модуль поведения,
  панели редактора, правила валидации, пробы для `cf-play`, шаблон проекта.

Такой разрез даёт честный ответ на вопрос «как мы потянем пять направлений»:
мы пишем два рантайма и шесть паков, а не пять движков. И порядок работ
определяется стоимостью, а не порядком в таблице:

1. Narrative (есть).
2. Adventure — тот же цикл и тот же пак-шов; проверяет расширяемость без нового
   директора (аватар, курсор, соединение предметов, FMV).
3. State-Machine & UI — тот же цикл, новый директор; дешёвый шаг.
4. Grid & Strategy — плюс сетка, A\*, экономический тик.
5. Endless & Physics 2D — первый настоящий новый рантайм.
6. Spatial Action — последний; 3D-рендер, модульная анимация, физика.

другой пак. Студия не знает конкретных паков — она читает их манифесты.

## 4. Формат проекта v2

Сейчас пакет — это `campaign.json` + `manifest.json` со списками файлов.
Для платформы нужен уровень выше, не ломая существующие кампании.

```json
{
  "format": 2,
  "id": "…",
  "kind": "narrative",
  "caps": ["narrative", "map", "combat"],
  "engine": { "min": "0.9", "tested": "0.9.3" },
  "entry": "world.json",
  "manifest": "manifest.json"
}
```

- `kind` — шаблон проекта (то, что видит автор в студии).
- `caps` — включённые возможности; это расширение `CampaignFeatures`.
- Старый `campaign.json` читается как `format: 1, kind: "narrative"` — миграция
  без потерь, обратная совместимость сохраняется навсегда (или до явного
  объявления «формат 1 не поддерживается», с мигратором).

## 5. Контракт пака

Пак — это каталог с манифестом и четырьмя обязательными частями. Если хотя бы
одной нет, пак не считается готовым.

```json
{
  "id": "narrative",
  "runtime": "turn",
  "version": "1.0.0",
  "provides": {
    "schema": "schema/narrative.schema.json",
    "panels": ["ScenePanel", "DialoguePanel", "FlowPanel"],
    "validators": ["dangling-goto", "unreachable-scene"],
    "probes": ["reachability", "dialogue-coverage"]
  },
  "saves": { "namespace": "narrative", "migrations": 3 },
  "requires": { "core": ">=1.0" }
}
```

Четыре обязательных части:

1. **Схема** — типы состояния и данных пака.
2. **Панели** — вкладки студии, которые пак приносит.
3. **Валидаторы** — статические правила; те же, что видит `cf-play`.
4. **Пробы** — динамические сценарии для прогона: «дойти до сцены X», «сыграть
   партию», «проверить, что ход не зависает».

Плюс необязательные: шаблоны проектов, миграции сейвов, превью-рендер.

## 6. Студия: один редактор, а не пять

Ответ на вопрос «свой редактор на направление или один»: **один шелл,
панели по возможностям**. Причины:

- Пять редакторов — это пять наборов багов, пять систем импорта и пять
  способов потерять данные.
- Редактор уже построен на схемах; скрыть лишнее дешевле, чем поддерживать
  пять приложений.
- Автор переходит между направлениями без переучивания.

Как это выглядит практически:

- Открывается проект → читается `kind` и `caps` → студия показывает только
  панели этих паков. Полей 3D в нарративном проекте не существует, а не
  «серые и недоступные».
- Три уровня раскрытия: **Основное** (сцена/диалог/правило), **Расширенное**
  (все поля пака), **JSON** (сырой документ). Новичок не видит 400 полей,
  опытный не упирается в потолок.
- Импорт чужого проекта с неизвестным паком: студия предупреждает, показывает
  проект только для чтения и предлагает поставить пак, а не молча теряет поля.

## 7. Мастерская без хостинга

Ограничение «мы не храним игры и ресурсы» — правильное по деньгам, но у него
есть три последствия, которые надо заложить сразу.

**1. Единица публикации — манифест, а не архив.**
Запись в каталоге — это `{id, title, author, kind, manifest_url, manifest_sha256,
size_estimate, license}`. Ресурсы лежат у автора где угодно: Drive, Dropbox,
свой сервер, GitHub Releases. Каталог хранит ссылку и хэш.

**2. Целостность и живучесть ссылок.**
Скачивая проект, платформа проверяет `sha256` манифеста и файлов. Если ссылка
умерла — честное «источник недоступен», а не пустая сцена. Автор может указать
зеркала (`mirrors: []`), платформа пробует их по порядку. Для офлайна —
экспорт в `.narthex` (уже есть) и локальный кэш.

**3. CORS — реальная стена.**
Браузер не даст скачать ресурсы с чужого домена без заголовков. Значит:
десктоп (Tauri) тянет что угодно, веб-плеер — только с CORS-дружественных
источников. Это надо сказать авторам в гайде, а не выяснять на релизе.

Каталог — это сервис, а не файлы. Для него достаточно Supabase (таблица
`projects` + поиск) или GitHub как источник истины плюс кэш. Решение отложить
до первого внешнего автора: до этого мастерская — папка `public/campaigns` из
индекса, которая уже есть. Бесплатные лимиты и момент, когда нужен платный
тариф, — [`infrastructure.md`](./infrastructure.md).

## 8. Мультиплеер: что решить сейчас, а что потом

Сейчас — **не делать**. Но зафиксировать контракт, чтобы потом не переписывать
формат.

Два разных мультиплеера, их нельзя смешивать:

- **Пошаговый / асинхронный** (карты, тактика, нарратив). Состояние маленькое,
  ходы редкие. Сервер — авторитетный, хранит `rooms` (состояние ≤ нескольких
  МБ) и журнал событий с TTL. Игрок может вернуться через сутки. Это дёшево и
  закрывает 80 % запросов «хочу с другом».
- **Реального времени** (3D, 2D-физика). Нужен отдельный сервер на сессию,
  состояние эфемерное, ничего не хранится. Это дорого и делается последним.

Правило бюджета сервера: **храним только состояние комнаты и журнал, никогда —
ресурсы**. Комната живёт N часов после последнего хода, потом снапшот и
удаление. Всё, что больше лимита, — отказ на входе, а не деградация.
Бесплатный старт комнат — Cloudflare Durable Objects, см.
[`infrastructure.md`](./infrastructure.md).

## 9. Команда ИИ-агентов

Роли привязаны не к «темам», а к **зонам записи** и **гейтам**. Если роль нельзя
описать путями в репозитории и проверкой на выходе — это не роль, а пожелание.

### Производство

| Роль | Зона | Гейт на выходе |
|---|---|---|
| **Coordinator** | очереди, статусы, назначения | ни одной задачи без критерия |
| **Architect** | ADR, контракты паков, ревью пересечений | решение записано и не противоречит предыдущим |
| **Kernel** | `src/core/*`, детерминизм, сейвы | все фикстуры зелёные, хэш прогона стабилен |
| **Turn Runtime** | пошаговый исполнитель, narrative, state, grid | пробы паков проходят |
| **Realtime Runtime** | цикл реального времени, 2D-физика | бюджет кадра и памяти |
| **Studio** | `src/editor/*`, панели, схемы | проект открывается и не теряет поля |
| **Tools** | `cf-play`, валидаторы, кит | команда `check` на эталоне = 0 |
| **Data/Schema** | типы, JSON Schema, миграции | старый пакет читается новым движком |
| **Backend/Workshop** | каталог, хэши, лицензии | ссылка мертва → понятная ошибка, не пусто |
| **Build/Release** | Tauri, версии, подпись | сборка воспроизводима |

### Аудит (не чинят, только выносят вердикт)

| Роль | Что проверяет | Почему отдельно |
|---|---|---|
| **Spec Auditor** | соответствие ADR и контрактам; «второй источник истины» | архитектурная гниль дешевле ловится до кода |
| **Runtime Auditor** | регрессии, детерминизм, fuzz, бюджеты, матрица сейвов | поведение нельзя проверить глазами автора кода |
| **Security & Data Auditor** | внешние ссылки и хэши, права, подмена сейвов, модерация | у мастерской без хостинга больше внешних рисков |

Правила, без которых роли превращаются в толпу:

1. **Аудитор не имеет права писать в код.** Находка → задача → исполнитель.
   Иначе «проверяющий» начинает защищать свои правки.
2. **Одна зона — один владелец.** Два агента в одной подсистеме дают конфликты
   и размытую ответственность.
3. **Не больше трёх активных задач.** Четвёртая — это уже не параллелизм, а
   очередь в голове координатора.
4. **Гейт на выходе обязателен.** Роль без проверки = роль, которую нельзя
   принять или отклонить.
5. **Фикстуры — общий язык.** Каждая роль обязана прогнать эталонный набор
   проектов и приложить результат.

## 10. Что делает платформу отличной от Roblox

Не «мы тоже платформа». У Roblox одно направление и один способ делать игры.
Ставка этой платформы — **агент, который умеет проверить то, что сделал**:

- контент — данные, значит его можно сгенерировать и проверить машинно;
- `cf-play` — универсальная приёмка, а не «посмотрите глазами»;
- кит и паспорт — агент знает, какой версией движка он работал;
- пак — единица расширения, значит направление добавляется, не ломая другие.

Если это работает, платформа выигрывает не графой «3D», а тем, что игру можно
собрать и довести до играбельного состояния за часы, а не за месяцы.

## 11. Риски и что с ними делать

| Риск | Признак | Ответ |
|---|---|---|
| Пять направлений съедают фокус | ни одно не доведено до играбельного | держим один рантайм и три пака до первого релиза |
| Формат расползается | каждый пак тянет свои поля | схема пака версионируется, миграции обязательны |
| Мастерская умирает от битых ссылок | половина проектов не скачивается | хэши, зеркала, локальный кэш, «источник недоступен» как штатный статус |
| 3D съедает всё | «ещё пара месяцев до демо» | 3D — последним и только после двух работающих паков |
| Агенты пишут в одно место | конфликты, дубли | зоны записи и лимит WIP |
| Аудиторы становятся исполнителями | «проверил и поправил» | запрет на запись, находка → задача |

## 12. Порядок работ

Подробный план — [`phases.md`](./phases.md). Здесь карта и правило закрытия.

| № | Фаза | Результат | Замораживает |
|---|---|---|---|
| 1 | Ядро из `engine.ts` | 16 модулей, тонкий фасад, без циклов | карту зависимостей ядра |
| 2 | Шов «движок / пак» | narrative как пак, `adventure`, FMV, кит-среда | API шва и манифест пака |
| 3 | Второй рантайм | непрерывный цикл, детерминизм в обоих | интерфейс исполнителя |
| 4 | `state-ui` + формат v2 | первый не-narrative пак; формат заморожен | формат проекта v2 |
| 5 | Студия по пакам | панели из манифестов, локализация UI, слой кода | API панелей и песочницы |
| 6 | `grid-strategy` | сетка, A\*, экономика, ИИ | возможности сетки |
| 7 | `endless-2d` | физика 2D, генерация, мобильный ввод | возможности 2D-цикла |
| 8 | `spatial-3d` | модульный риг, 3D, анимация | формат рига и клипов |
| 9 | ИИ-цикл в продукте | headless-API, `shoot`, корпус, перевод | API кита и `check-upgrade` |
| 10 | Мастерская и 1.0 | каталог, метрики, установщик, релиз | контракт мастерской |

Критерий остановки на каждой фазе: играбельный проект на своём паке, `check`
= 0, эталонные фикстуры зелёные. Если фаза не даёт играбельного проекта — она
не закончена, сколько бы кода ни было написано.

| Разрез движка | два исполнителя и паки; проект не смешивает рантаймы (ADR 0002) |
| Формат проекта | `kind` + `caps` + `cap_options`, `project.json`; формат 1 читается бессрочно (ADR 0003, `format-v2.md`) |
| Граница пака | четыре обязательные части + объявленные швы; ядро не знает паков (ADR 0004) |
| Судьба пяти кампаний | отложены; эталон — `public/campaigns/ash-of-caerden` (см. фазу 1) |
| Аудитория | сначала свои агенты, формат сразу публичный; мастерская — после первого внешнего автора |

## 14. Слой кода: шов вместо форка

Свобода нужна, но «выключить движок и писать что угодно» уничтожает три вещи,
ради которых существует платформа: формат, сейвы и проверку. Поэтому код
допускается только в **объявленных швах**, и швы делятся надвое:

| Слой | Что делает | Проверяется | Может менять состояние |
|---|---|---|---|
| `sim` | логика подсистемы: ход, урон, торговля | да, headless и `check` | да, через `EngineCtx` |
| `view` | рисунок, звук, эффекты, камера | нет, только контактные кадры | нет |

Правила:

1. Пак объявляет свои швы в `provides.seams`: `id`, `kind` (`sim`/`view`),
   сигнатуру. Проект не может подключить код к шву, которого нет.
2. Режим объявляется по возможности: `core` (работает система), `code`
   (работает код в шве), `off` (данные остаются, поведение выключено).
   Переключается в `project.json`, не глобально.
3. Студия не умирает: при `code`/`off` пропадают формы подсистемы, но остаются
   дерево файлов, Monaco, запуск и `check`.
4. Песочница: отдельный воркер, права выдаются явно (`render`, `audio`,
   `input`, `state`), сети нет по умолчанию.
5. Если код меняет форму сохранения — миграцию пишет автор; если ломает
   `sim` — `check` краснеет, и это не баг платформы.

Подробно — ADR 0006. Форма полей — `format-v2.md` §4.

## 15. Ассеты и анимация: модульный риг

3D не начинается с «сделаем скелет и скиннинг». Для платформы, где авторы —
агенты, дешевле и надёжнее **модульный жёсткий риг**:

- `part` — деталь: примитив или импортированный меш;
- `socket` — якорь с осью, к которому крепится деталь;
- `assembly` — дерево деталей и сокетов (персонаж, дерево, дом);
- `clip` — кейфреймы трансформаций + события (шаг, удар, открыть);
- `palette` — материалы и цвета, чтобы мир выглядел одним.

Стыки закрываются нахлёстом деталей, поэтому скиннинг, веса и ретаргет не
нужны: анимация — это клип трансформаций. **Один формат на 2D и 3D**: у
вырезанного PNG и у модульной детали одни и те же сокеты и клипы.

Проверка анимации — не «скриншот каждый кадр»:

1. **Контактный лист**: 12–16 кадров в одной сетке + метрики (частицы, bbox,
   альфа, палитра).
2. **Golden frames**: базовый кадр в репозитории и перцептивный дифф.
3. **Метрики движения**: замыкание цикла (кадр N = кадр 0), поппинг между
   кадрами, профиль скорости, траектория центроида.

«Красиво» этим не проверяется — это остаётся человеку и визуальному аудитору.
Роль `Assets & Animation` появляется вместе с пайплайном (фаза 8), а не раньше:
до этого у неё нет зоны записи.

Подробно — ADR 0007.

## 16. Локализация

Две разные задачи, их нельзя решать одной ручкой.

**Интерфейс платформы.** Восемь языков: `en` (по умолчанию), `ru`, `zh-Hans`,
`ja`, `pt-BR`, `de`, `fr`, `ko`. Строки вынесены в `i18n/<lang>.json`, ключи —
по пути компонента, типизированы; CI падает на пропущенном ключе. Машинного
перевода интерфейса нет: только агенты и вычитка. CJK-шрифты — сабсетом или
системные; интерфейс обязан переживать немецкий +30 %.

**Контент.** Язык — свойство проекта: `default_language` + `languages` +
`locales/`. Строка адресуется **стабильным ID по структуре**
(`scene_outpost/npc_brann/greeting/2`), а не текстом и не хэшем текста: иначе
каждая правка реплики обнуляет перевод. Рядом хранится хэш исходника, по
которому сделан перевод; исходник изменился — перевод помечается устаревшим.

Инлайн-текст остаётся валидным: игра на одном языке ничего не переводит.
Машинный перевод — пак `localization` и бейдж «машинный / вычитан»: это ответ
на «китайская игра, немецкий игрок», и это то, чего нет у Steam и Roblox.

Подробно — ADR 0008, `format-v2.md` §8.

## 17. Мастерская: файлы у автора, доверие у платформы

Запись каталога — не архив, а манифест:

```json
{ "id": "…", "title": "…", "author": "…", "kind": "narrative",
  "manifest_url": "…", "manifest_sha256": "…", "size_estimate": 0,
  "license": "CC-BY-4.0", "check_report_sha256": "…" }
```

Файлы лежат у автора (GitHub Releases, свой сервер), платформа хранит ссылку,
хэш и лицензию. Следствия, заложенные сразу:

- **Рейтинг — по проверяемости и завершённости**, а не по голосам: `check = 0`,
  пройденная матрица seed'ов, заявленный объём, реальная длина. На платформе,
  где игры делает ИИ, дефицит — не количество, а качество; голоса накручиваются,
  проверка — нет.
- **Счётчики и отзывы — на сервере.** Это единственная серверная часть и
  единственный случай, когда платформа что-то хранит; файлов и ассетов там нет.
- **Доверие:** подпись манифеста, зеркала, «источник недоступен» как штатный
  статус, бейдж «здесь кастомный код».
- **Происхождение:** лицензия, отпечаток содержимого, детект производных
  («совпадает с X на 87 %»). Код локально закрыть нельзя, поэтому защищаем не
  секретность, а авторство.

Подробно — ADR 0010, [`workshop.md`](./workshop.md).

## 18. Совместимость механик

Формат и сейвы закрыты: четыре номера версии, `compat.json`, цепочка миграций,
починка сейва. Не закрыт **смысловой** дрейф: механика изменилась, формат тот
же, сейв валиден, игра играется неправильно.

Три слоя:

1. **Версия возможности.** Проект фиксирует версию поведения:
   `"cap_options": { "combat": { "version": 2 } }`. Движок катит v1 и v2
   параллельно на время депрекации; редактор предлагает миграцию.
2. **Поведенческий корпус.** У эталонных проектов хранится отпечаток:
   `(движок, версия проекта, seed, скрипт) → хэш конечного состояния и лога`.
   После обновления CI печатает не «что-то сломалось», а «в сценарии X урон
   12 → 10, seed 7».
3. **Тикет на починку.** `narthex check-upgrade --from 0.9 --to 0.10` собирает
   markdown: что изменилось, какие прогоны поехали, команда воспроизведения,
   где чинить. Агент правит проект и видит, как дифф сокращается.

Правило релиза: изменение поведения = новая версия возможности, а не тихая
правка. Корпус имеет смысл после фазы 1, когда поведение разделено по модулям.

Подробно — ADR 0009, [`compatibility.md`](./compatibility.md).

## 19. Кит как среда

Документ не может быть источником правды о коде: он отстаёт. Гайд на 268 КБ и
схема на 327 КБ — это ~150 тысяч токенов, которые агент всё равно не держит в
контексте, поэтому читает наугад и угадывает.

Кит перестаёт быть книгой:

| Инструмент | Что заменяет |
|---|---|
| `cf-play explain <код>` | раздел гайда «почему это ошибка» |
| `cf-play schema <тип>` | половину схемы: поля одного типа |
| `cf-play example <механика>` | пример из гайда, но исполняемый |
| `cf-play shoot` | «посмотри глазами»: детерминированные кадры сцены |
| `kit doctor` | «какая у меня версия кита и совпадает ли она с движком» |

Правила: гайд ≤ 10 % исходного объёма и только «почему»; корпус
`examples/<механика>/` гоняется в CI; ошибка без пути, минимального фикса и
якоря — дефект; мажорное расхождение кита с движком — отказ работать, а не
тихий неверный совет.

MCP-сервер — тонкая обёртка над тем же CLI, а не второй продукт.

Подробно — ADR 0011, [`playkit.md`](./playkit.md).
