# ADR 0009. Версия поведения возможности и поведенческий корпус

Дата: 2026-10-23
Статус: принято

## Контекст

Формат и сохранения уже версионируются: четыре номера, `compat.json`, цепочка
миграций, починка сейва. Остаётся **смысловой** дрейф: механика изменилась,
формат тот же, сейв валиден, игра играется неправильно. Именно этот случай
пользователь описал как «обновление в карточных играх тихо ломает кампании».

## Решение

Три слоя.

**1. Версия возможности.** Проект фиксирует версию поведения:
`cap_options[cap].version`. Движок держит старую и новую реализацию
параллельно на время депрекации; редактор предлагает миграцию. По умолчанию
проект остаётся на той версии, которую зафиксировал.

**2. Поведенческий корпус.** У эталонных проектов хранится отпечаток:

```
(движок, версия проекта, seed, скрипт) → хэш конечного состояния и лога
```

После обновления CI прогоняет корпус и печатает не «что-то сломалось», а «в
сценарии X урон 12 → 10, seed 7». Это воспроизводимый дифф, а не мнение.

**3. Тикет на починку.** `check-upgrade --from 0.9 --to 0.10` собирает
markdown: что изменилось, какие прогоны поехали, команда воспроизведения, где
чинить. Агент правит проект и видит, как дифф сокращается.

Правило релиза: **изменение поведения — новая версия возможности**, а не тихая
правка. Корпус имеет смысл после фазы 1, когда поведение разделено по модулям.

## Последствия

**Положительные.** Обновление движка перестаёт быть лотереей; автор получает
список конкретных поломок; агент может починить проект без чтения исходников.

**Отрицательные.** Движок обязан хранить несколько реализаций и объявлять
депрекацию. Это дороже, чем «поменять формулу и забыть», и это цена обещания
«проект не ломается».

## Что стало невозможным

- Менять поведение механики в минорном релизе без новой версии.
- Обновлять движок без прогона корпуса.
- Считать «сейв открылся» доказательством совместимости.
