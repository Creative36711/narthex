# ADR 0016. Граница ядра для строки реестра возможностей

Дата: 2026-10-28
Статус: proposed

## Контекст

Пак `state-ui` начинается с перевода возможности `state-machine` из `planned` в
`experimental` (карточка 5.3). Это не правка одного поля: реестр возможностей
существует в двух копиях, и проверка контрактов требует их совпадения.

| Копия реестра | Файл:строка | Строка сейчас |
|---|---|---|
| контракт | `docs/contracts/caps.json:43` | `{ "id": "state-machine", ..., "status": "planned", ..., "probe": null }` |
| рантайм | `src/core/caps.ts:32` | `{"id": "state-machine", ..., "status": "planned", ..., "probe": null}` |

Одновременно действуют два требования, которые нельзя выполнить вместе:

- оракул миссии требует **0 строк** в `src/core/**` в PR карточек 5.3–5.5;
- ТЗ §3 для карточки 5.3 прямо называет правку `docs/contracts/caps.json` **и**
  `src/core/caps.ts` — «согласованно».

Пока противоречие не разрешено записанным решением, 5.3 не может закрыться
честно: либо пак не включается (возможность остаётся `planned`), либо PR
карточки нарушает оракул. Этот ADR фиксирует находку и предлагает выбор; он не
меняет ни оракул, ни реестр, ни код.

## Находка

### 1. Синхронизация двух копий проверяется машинно

`registryProjection` и `registriesMatch` (`scripts/contracts-check.mts:70-87`)
сравнивают семь полей—`id`, `title`, `pack`, `status`, `since`, `enables`,
`probe`—и печатают проверку «caps.json совпадает с runtime-реестром
src/core/caps.ts». Любое расхождение по `status` или `probe` валит
`check:contracts`. Синтетическое расхождение тоже проверяется отдельно
(`scripts/contracts-check.mts:78-88`), то есть проверка не декоративная.

### 2. Одного `status` недостаточно: меняется и `probe`

`missingCapMetadata` (`scripts/contracts-check.mts:93-100`) требует, чтобы у
возможности в статусе `stable` или `experimental` был непустой `probe`, а у
`planned`—ровно `null`. Значит в той же строке вместе со статусом меняется
`probe`.

### 3. `probe` обязан существовать как npm-скрипт: это третий файл

`unknownProbes` (`scripts/contracts-check.mts:101-103`) проверяет, что имя из
`probe` есть в `package.json`. Скрипта `probe:state-ui` в `package.json` сейчас
**нет** (есть, например, `probe:adventure`, `probe:fmv`, `probe:pack-host`).
Общий скрипт на несколько возможностей—уже существующая практика: `smoke:core`
указан у `narrative`, `combat` и `skills`. Поэтому перевод статуса — это правка
**трёх** файлов, а не двух:

| Что меняется | Файл | Что проверяет |
|---|---|---|
| `status: planned → experimental` | `docs/contracts/caps.json:43` | `projectProblems` и `project.schema.json` разрешают включать только `stable`/`experimental` |
| `probe: null → "probe:state-ui"` | `docs/contracts/caps.json:43` | `missingCapMetadata` |
| та же строка целиком | `src/core/caps.ts:32` | `registriesMatch` |
| новый скрипт `probe:state-ui` | `package.json` | `unknownProbes` |

### 4. Замер: что именно краснеет

Проверка выполнена в памяти, без правок файлов: копия `caps.json` сравнивалась
с `CAPABILITY_REGISTRY` по той же проекции, что в проверке.

| Состояние | `registriesMatch` | проба по статусу | проба в npm scripts |
|---|---|---|---|
| как в репозитории | совпадает | ок | ок |
| только `caps.json`: `experimental`, `probe: null` | **расходится** (`state-machine`) | **ошибка** | ок |
| только `caps.json`: `experimental`, `probe: "probe:state-ui"` | **расходится** (`state-machine`) | ок | **ошибка** (`state-machine: probe:state-ui`) |
| оба файла согласованно + скрипт | совпадает | ок | ок |

### 5. `check:pack-boundary` — семантический гейт, а не счётчик строк

Замер на временной фикстуре вне репозитория: `packs/registry.json` с
перечисленным `state-ui` и таблицей `CAPABILITY_REGISTRY`, где у строки стоит
`"pack": "state-ui"`, дают `rc=0`; та же фикстура с ветвлением
`pack === 'state-ui'` в `src/core` даёт `rc=1` и две находки. Сканер
(`scripts/check-pack-boundary.mts:147-210`) ищет импорты из `packs/**` и
ветвления по id пака, а не изменения данных. Поэтому правка данных реестра шов
не ломает, а логика, зависящая от пака, ломает—и это как раз то, что защищает
оракул.

### 6. Побочная находка: примеры `state-ui` сейчас никем не проверяются

Файлы `docs/contracts/examples/project.state-ui.json` и
`docs/contracts/examples/pack.state-ui.json` (добавлены карточкой 5.2) не читает
ни один скрипт: `scripts/contracts-check.mts` перечисляет примеры поимённо
(строки 288–333), и этих имён в списке нет. Замер: та же семантика, что в
`projectProblems`, даёт на этом примере две ошибки—«возможность `state-machine` в
статусе `planned`, проект не может её включать» и то же для `cards`; после
перевода обеих возможностей в `experimental` ошибок нет. То есть `check:contracts`
зелен не потому, что пример валиден, а потому что пример не проверяется. Это
дефект покрытия 5.2/5.6; в этой карточке он только записан.

## Цитаты, между которыми выбирает Мастер

Оракул миссии, §1 п.2 ([`docs/agents/tz-nar-5.md:31-32`](../agents/tz-nar-5.md)):

> 2. **В ядро не добавлено ни одной строчки под пак.** Диф `src/core/**` в PR
>    карточек 5.3–5.5 — **0 строк**; `npm run check:pack-boundary` зелёный.

ТЗ §3, карточка 5.3, целиком ([тот же файл, строки 122–130](../agents/tz-nar-5.md)):

> ### 5.3 — Пак `state-ui`, часть 1: автомат состояний (Pack Author)
>
> - `packs/state-ui/`: манифест, `schema/`, панель, валидатор, проба. Возможность
>   `state-machine` переводится из `planned` в `experimental` (реестр
>   `docs/contracts/caps.json` и `src/core/caps.ts` — согласованно).
> - **Проверка:** `npm run check:packs && npm run probe:state-ui`; диф
>   `src/core/**` в PR — **0 строк**.
> - **Не делает:** не правит ядро «чтобы заработало». Если пак без этого не
>   собирается — находка фазы и строка в «Вопросах», а не расширение ядра.

Противоречие находится внутри самой карточки: первый пункт называет оба файла
реестра, второй тут же требует 0 строк в ядре. Оракул §1 п.2 делает это
требование общим для 5.3–5.5. Ослабить оракул, по его же формулировке, можно
только ADR `proposed` с ответом Мастера — этот документ и есть такое
предложение.

## Вариант A. Синхронизировать реестры внутри 5.3/5.4 (поправка к оракулу §1 п.2)

В карточке 5.3 меняются три файла: `docs/contracts/caps.json:43`,
`src/core/caps.ts:32` и `package.json` (скрипт `probe:state-ui`). Оракул §1 п.2
получает узкую поправку: 0 строк остаётся правилом, но строки таблицы
`CAPABILITY_REGISTRY`, перечисленные в описании PR, из него исключаются.

Последствия:

- **5.3:** PR трогает ядро на одну строку данных; `check:contracts` зелёный
  только когда все три файла согласованы (замер 4), `check:pack-boundary`
  зелёный (замер 5). Карточка выполнима без ослабления гейтов.
- **5.4:** та же операция для `cards` и `auto-battle`—ещё две строки в
  `caps.ts`, две в `caps.json`; проба может переиспользовать `probe:state-ui`.
- **5.5:** диф `src/core/**` — 0 строк; проект с `kind: state-ui` проходит
  `projectProblems` только потому, что возможности уже `experimental`.
- **5.9:** без изменений; корпус остаётся на семи целях, `state-ui`-кампания
  может добавиться в него отдельной карточкой Tools после 5.5.
- **`check:pack-boundary`:** зелёный; гейт проверяет ветвления и импорты, а не
  количество строк.
- **`check:contracts`:** зелёный при согласованных трёх файлах; любое частичное
  состояние даёт конкретную красную проверку (замер 4).
- **Цена:** формулировка «0 строк» перестаёт быть буквальной; фактический
  контроль переезжает в описание PR и ревью. **Обратимость:** откат трёх строк и
  одного скрипта.

## Вариант B. Один источник: ядро берёт реестр из контракта (отдельная карточка Kernel)

До 5.3 отдельная карточка Kernel делает `src/core/caps.ts` производным от
`docs/contracts/caps.json`: генератор в `scripts/**` пишет типизированный
литерал, в репозиторий кладётся результат, проверка сверяет его с контрактом.
После этого перевод статуса — правка одного `docs/contracts/caps.json`.

Последствия:

- **Подготовка:** одна карточка ядра **до** 5.3; она сама меняет
  `src/core/**`, поэтому должна стоять вне 5.3–5.5, иначе оракул §1 п.2
  нарушается той же карточкой, что его защищает.
- **5.3/5.4:** 0 строк в `src/core/**` без всякой поправки к оракулу; меняются
  только `docs/contracts/caps.json` и `packs/**`.
- **5.5:** как в A — проект проходит семантику после перевода возможностей.
- **5.9:** без изменений.
- **`check:pack-boundary`:** зелёный; генератор живёт в `scripts/**`, который
  сканер не обходит.
- **`check:contracts`:** требует переработки главной проверки. Сейчас
  `registriesMatch` сравнивает две независимые копии; если рантайм-литерал
  генерируется из того же `caps.json`, равенство становится тавтологией.
  Осмысленной остаётся только проверка «перегенерировать и потребовать пустой
  `git diff`»—новый гейт вместо существующего.
- **Цена:** шаг сборки в оснастке (территория ADR 0007), влияние на `tsconfig` и
  бандл, сгенерированный файл в git. **Обратимость:** вернуть ручной литерал и
  удалить генератор.

## Вариант C. Статус не двигать: пак собирается, возможность остаётся `planned`

Оракул §1 п.2 понимается буквально: 5.3 и 5.4 не трогают ни `src/core/**`, ни
`docs/contracts/**`. Пак `state-ui` поставляется, но `state-machine`, `cards` и
`auto-battle` остаются `planned`; перевод статуса выносится в отдельную карточку
после 5.5 (или в фазу 5).

Последствия:

- **5.3/5.4:** диф `src/core/**` — ровно 0 строк; `check:pack-boundary` и
  `check:contracts` зелёные, потому что ничего не меняется. Заодно нужен скрипт
  `probe:state-ui` в `package.json` — это не `src/core/**`, оракул не задет.
- **5.5:** невыполнима в текущей формулировке. `assertEnableable`
  (`src/core/caps.ts:77-86`) не пропускает возможность вне `stable`/
  `experimental`, а `projectProblems` (`scripts/contracts-check.mts:151-160`)
  отклоняет проект, который её включает. Игра на `state-ui` не запустится,
  оракул §1 п.1 («играется от начала до конца») останется открытым.
- **5.9:** корпус остаётся на семи целях; `state-ui`-проект в него добавить
  нельзя, пока возможность не включается. Оракул §1 п.7 при этом зелёный.
- **`check:pack-boundary`:** зелёный.
- **`check:contracts`:** зелёный, причём даже при невалидном примере —
  `project.state-ui.json` сегодня не читается (находка 6), так что зелёный здесь
  ничего не доказывает.
- **Цена:** главная цель фазы 4—первый пак с другим «директором» на том же
  цикле—не достигается; нужна перенумерация карточек или отдельная карточка
  перевода статуса перед 5.5. **Обратимость:** полная (ничего не меняется), но
  миссия закрывается без играбельного `state-ui`.

## Рекомендация Архитектора

**Вариант A.** Причины:

1. Он минимален и обратим: три строки данных и один npm-скрипт против отдельной
   карточки ядра (B) или срыва цели фазы (C).
2. Он не ослабляет ни один гейт: `check:pack-boundary` не считает строки и
   остаётся семантическим (замер 5), а `check:contracts` продолжает требовать
   совпадения двух независимых копий реестра (замер 4). В варианте B эта
   проверка как раз теряет смысл.
3. Он соответствует тексту самой карточки 5.3, который называет оба файла:
   ADR не вводит новую практику, а фиксирует поправку к формулировке оракула,
   без которой карточка внутренне противоречива.

Предлагаемая формулировка поправки к оракулу §1 п.2 (вступает в силу только при
ответе Мастера «принять»):

> 2. **В ядро не добавлено ни одной строчки логики под пак.** Диф `src/core/**`
>    в PR карточек 5.3–5.5 — 0 строк, кроме строк таблицы
>    `CAPABILITY_REGISTRY` в `src/core/caps.ts`, перечисленных в описании PR:
>    такая строка меняет только `status` и `probe` уже существующей возможности,
>    не добавляет ветвлений по id пака и импортов из `packs/**`;
>    `npm run check:pack-boundary` зелёный.

Рекомендация не действует сама по себе: до ответа Мастера оракул остаётся в
текущей редакции, и карточка 5.3 в работе должна трактоваться по варианту,
который выберет Мастер.

## Вступление в силу и что дальше

Предложение остаётся `proposed`, пока Координатор не запишет ответ Мастера.
После ответа статус меняется на `accepted` или `rejected` с датой—по правилу
[журнала решений](./README.md). Оракул §1 ТЗ этим ADR не меняется: правка
оракула—отдельное действие Координатора, и только после `accepted`. Если
выбран вариант B или C, этот ADR фиксирует отклонение A и не подменяет собою
карточки, которые эти варианты требуют.

## Неясно / решил / откат

неясно / Карточка называет путём ADR `docs/decisions/0016-capability-registry-boundary.md`, хотя действующие ADR 0001–0015 лежат в `docs/contracts/adr/`; отдельно неясно, нужен ли журнал `docs/decisions/NAR-5.13.md`, если оракул п.4 разрешает в диффе только два файла.

решил / Новый ADR пишется по Scope карточки в `docs/decisions/0016-capability-registry-boundary.md`; три строки выше стоят в конце того же файла, отдельный журнал миссии не создаётся, чтобы диф остался из двух файлов.

откат / Перенести ADR в `docs/contracts/adr/0016-capability-registry-boundary.md` и вынести три строки в `docs/decisions/NAR-5.13.md`; меняются только пути, текст решения остаётся тем же.
