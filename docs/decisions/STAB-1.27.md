# STAB-1.27 — таймаут и диагностика шага детерминизма

**Статус решения:** принято; приёмка STAB-1.27 остаётся открытой до успешных post-merge Actions на одном SHA

**Дата:** 2026-11-01

**Baseline main:** `a4d10a30148c8eaa6905dcf3adfe0ffdc9db2cd1`

## Неясно

- Visual run [`41240126889`](https://github.com/Creative36711/narthex/actions/runs/41240126889) завершил шаг `Детерминизм циклов` неуспешно: по Jobs API он шёл с `2026-10-31T20:42:49Z` до `20:48:02Z` (313 секунд), при заданном в workflow пределе 5 минут. Точный внутренний участок, остановившийся в этом прогоне, пока не установлен: две попытки получить Actions logs завершились `EOF` на `results-receiver.actions.githubusercontent.com`.
- В том же run cache браузерных пакетов был найден, а отдельный шаг их установки был `skipped`; поэтому наблюдавшиеся 313 секунд не объясняются ожиданием установки npm-пакетов. В конфигурации теста задан подготовленный browser prefix, а собственно parity использует фиксированную локальную фикстуру, не импорт кампании или сетевой ресурс. Точный скрытый системный stall всё же нельзя исключить без stdout неуспешного шага.
- Последний успешный visual до ошибки — [`41237276176`](https://github.com/Creative36711/narthex/actions/runs/41237276176), SHA `34e7326e84633f4d44b10dd6e05f9dba589cf236`; его шаг детерминизма занял 1 секунду по Jobs API. Сравнение коммитов `34e7326…` → `a4d10a3…` показывает только обновление отчёта/визуальной политики и `scripts/visual/playthrough.mjs`; `scripts/check-determinism.mts`, `scripts/check-parity.mts`, `scripts/parity-fixture.ts`, `scripts/visual/local-browser.mjs`, workflow и lockfile не менялись. Рост данных или числа прогонов между этими SHA не обнаружен.
- Статический учёт исходника: 20 обычных replay-циклов, 4 mutation-цикла, 20 Node parity-циклов и 20 Chromium parity-циклов — всего 64 вызова `runCycle` и 640 executor-step итераций при неизменной строке из 10 значений dt. Это сохранённый workload, а не сокращение/ослабление тестов.
- До диагностической правки тёплый локальный `npm run check:determinism` с заранее установленными browser-пакетами прошёл за **3.308 с** (`rc=0`). Установка browser-пакетов в отдельный temp-prefix заняла 3.923 с; в упавшем CI-run отдельный install step был пропущен из-за cache hit. Таким образом, доказанного роста объёма данных, числа прогонов или ожидания сети нет; доказано превышение 5-минутной CI-границы, но первичный источник аномальной задержки неизвестен.
- На post-merge SHA `8a36153957bab63356c2906cc2c8d1aa3291c274` visual run [`41243371213`](https://github.com/Creative36711/narthex/actions/runs/41243371213) прошёл детерминизм за 1 секунду и остальные шаги до browser exam, но завершился `SHOTS=0 PLAY=0 EXAM=1 START=0`: строгий exam увидел один битый `<img>` по объявленному D-076 пути `ash-of-caerden/assets/img/scenes/gates_front_day.jpg`. PR-run [`41242796399`](https://github.com/Creative36711/narthex/actions/runs/41242796399) на том же дереве прошёл полностью; точная гонка не воспроизведена локально. В harness `step()` ожидал `image.complete`, что не гарантирует, что `onError` и React fallback уже обновили DOM. Изменение ниже ждёт успешную загрузку всех оставшихся DOM-изображений; неразрешённое/всё ещё подключённое битое изображение остаётся находкой после существующего предела ожидания 3 секунды.
- Попытка ручного dispatch visual на `main` завершилась ответом GitHub API **403**: `could not create workflow dispatch event: HTTP 403: Resource not accessible by integration (https://api.github.com/repos/Creative36711/narthex/actions/workflows/393169608/dispatches)`. Попытка повторить failed main run также недоступна: `gh api -X POST repos/Creative36711/narthex/actions/runs/41243371213/rerun` вернула `{"message":"Resource not accessible by integration","documentation_url":"https://docs.github.com/rest/actions/workflow-runs#re-run-a-workflow","status":"403"}`; `gh run rerun 41243371213` ответила `run 41243371213 cannot be rerun; its workflow file may be broken`. Это не pass. Автоматические push/PR-triggered Actions запускаются; новую post-merge SHA необходимо проверить ими, а если они завершатся ошибкой, понадобится восстановить GitHub Actions permissions/повтор через владельца. Локальная проверка Actions не заменяет.

## Решил

- Оставить все seed, runtimes, повторы, mutation probe, parity-сравнения, фиксированную dt-строку, браузер и их критерии без изменений. Изменить только техническую обвязку visual: таймаут шага `Детерминизм циклов` увеличить с 5 до 10 минут в пределах 20-минутного job; запуск по-прежнему обязан завершиться с исходным кодом команды. Никаких `continue-on-error`, skip, ослабления порогов или сокращения прогонов нет.
- Сохранить полный stdout/stderr шага через `tee` в `out/visual/check-determinism.log`, который входит в существующий `visual-report` artifact. `pipefail` оставляет исходный ненулевой результат команды ненулевым. Это позволит установить последний завершённый этап при повторе задержки.
- Добавить только временные диагностические длительности для replay, mutation, Node parity, сборки browser bundle, подготовки/старта Chromium и двух browser повторов. Эти сообщения не влияют на результат проверки. Общий browser helper используется и visual, и golden; его подготовка/launch также получает явные start/completion markers.
- Проверка после инструментирования: `npm run check:determinism` с тем же тёплым prefix прошёл, все oracle-результаты совпали; Bash wall time **1.235 с** (`rc=0`). Внутренние замеры: replay `40.7 ms`, mutation `6.5 ms`, Node parity `24.6 ms`, bundle `77.6 ms`, Chromium startup `301.7 ms`, browser repeats `160.5 ms` и `139.6 ms`. Тёплый cache объясняет, почему это число нельзя напрямую считать временем холодного CI runner.
- В strict visual exam изменить только ожидание снимка: до прежнего лимита 3 секунд ждать, пока все оставшиеся в DOM `<img>` станут `complete` и получат `naturalWidth > 0`. Загрузившееся изображение удовлетворяет условию; обработанный `onError` fallback удаляет image из DOM; всё ещё подключённое битое или пустое изображение по таймауту остаётся в наблюдении и продолжает давать finding. Число шагов, known-absence/console registries, конечные состояния и критерии ошибки не меняются и не фильтруются. Локальная проверка после правки: `npm run playthrough:exam -- http://127.0.0.1:4173 /tmp/stab127-exam-after`, `rc=0`, wall time `66.808 с`, 28 шагов, 54/54 absences и 18/18 console observations зарегистрированы, broken/empty images `0/0`, findings `0`; это диагностика harness, не замена Actions.
- Добавить `scripts/visual/playthrough.mjs` в существующие `pull_request.paths` и `push.paths` у `.github/workflows/golden.yml`. Это только дополнительно запускает неизменённый полный golden при изменении visual-exam harness; не меняет команд, порогов, pinned import или реальный soak. Это нужно, чтобы после merge свежий Golden запускался от push-triggered Actions даже при недоступном `workflow_dispatch`.
- Запуск final `golden-playthrough` остаётся полным: pinned import, `playthrough:golden`, `cf-play:negative`, существующий реальный soak и его границы не меняются. Нельзя считать локальный результат, PR SHA, неполный run или запуск без 60 минут эквивалентом post-merge evidence.

## Откат

- Если дальнейшие Actions покажут, что задержка была единичной и расширенный запас не нужен, вернуть в `.github/workflows/visual.yml` `timeout-minutes: 5` и прямой `run: npm run check:determinism`; удалить только `tee`/комментарий к обвязке.
- Удалить диагностические импорты `performance` и только добавленные timing markers из `scripts/check-determinism.mts`, `scripts/check-parity.mts` и `scripts/visual/local-browser.mjs`. Не менять существующие проверочные ветки, фикстуры, браузерные флаги или данные.
- Если ожидание DOM-image settlement окажется не причиной гонки, вернуть в `scripts/visual/playthrough.mjs` исходный `waitForFunction` по `image.complete` и удалить добавленный путь `scripts/visual/playthrough.mjs` из обеих `paths` секций `.github/workflows/golden.yml`. При любом варианте не удалять и не ослаблять подсчёт/провал по broken/empty `<img>`.
- Если детерминизм снова длится аномально долго либо не завершается и за 10 минут, не увеличивать таймаут дальше и не обходить проверку: изучить приложенный `check-determinism.log`, изолировать зависший этап и эскалировать инфраструктурную причину. Откат не означает принятие красного результата.
