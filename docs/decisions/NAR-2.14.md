# NAR-2.14 — ADR proposed: буквальные проверки §3 и метрика диффа ядра
Дата: 2026-10-25. Основание: аудит NAR-2.13; базовая точка аудита — `44945f0`.

## Назначение и границы

Этот ADR фиксирует три предлагаемые трактовки расхождений аудита. Он не меняет действующий оракул, ТЗ, код игры, смоуки или гейты. До отдельного решения Мастера действуют текущие формулировки и проверки; предложенные ниже трактовки не являются исключениями, действующими сейчас.

`docs/agents/tz-nar-2.md` и `docs/agents/tz.md`, включая все пункты §2 и §3, остаются без изменений. Зона записи этой карточки — только `docs/decisions/`; единственный файл этой задачи — `docs/decisions/NAR-2.14.md`.

## Факты аудита

Ниже приведены исходные числа аудита без повторного подсчёта:

- `src/core/combat.ts` — `1765` строк.
- `src/core/savemigrate.ts` — `788` строк.
- `9 PR` миссии имеют дифф `src/core`.
- `1` буквальное grep-совпадение находится в `scripts/fmv-passport-probe.mts`.
- `9` строковых литералов находятся в `src/core/pack/registry.ts`.

Сводка аудита на базе `44945f0` содержит именно эти значения; числа здесь не пересчитывались. По аудиту NAR-2.13, ни два превышения размеров, ни фильтр пробы, ни строки диагностики не внесены этой миссией: они уже присутствовали на базовой точке. NAR-2.14 не меняет исходники и не вносит ни модульных превышений, ни grep-совпадений. Срабатывание в `fmv-passport-probe` — проверка данных пробы, а совпадения в `pack/registry.ts` — диагностические строки, не импорты. Девять PR относятся к общей истории миссии; PR `#60` — только один из них.

Связка с буквальными проверками §3: размерный пункт может дать красный результат на двух модулях вне зоны этой миссии; текстовые grep-проверки — на пробном фильтре и строках ошибок, а не на поведенческой ветке или ребре импорта. Метрика диффа отдельно измеряет один PR, хотя аудит перечисляет `9 PR` миссии с диффом ядра. Эти наблюдения описывают шум формулировки/области измерения, а не утверждают, что превышения размера разрешены, строки исчезли или кодовая проверка уже заменена.

## F3 — формулировка метрики диффа ядра

- **Было красным.** В §2.3 метрика названа «Диф ядра в PR пака» и дана команда `git diff --stat origin/main…HEAD -- src/core`. В отчёте PR `#60` такое измерение выглядит как оценка всей миссии, хотя аудит насчитал `9 PR` миссии с диффом `src/core`.
- **Почему.** `origin/main…HEAD` описывает границы одного PR. Это не тождественно сводному диффу всей миссии от её базовой точки. Без явного списка PR и baseline нельзя выводить состояние всего шва из одного PR; одновременно само наличие диффа не доказывает поведенческое ветвление или импорт пака из ядра.
- **Предлагается.** В следующем аудите явно разделить два показателя: PR-local diff каждого PR и сводку всех `9 PR` миссии относительно зафиксированной базы `44945f0`. Для сводки перечислять PR и файлы `src/core`, отмечать только заранее разрешённые изменения шва/переноса, а остальные изменения рассматривать как нарушение. Отдельно проверять смысловые запреты: ядро не выбирает поведение по идентификатору жанрового пака и не импортирует код из `packs/**`. До решения Мастера действующая метрика §2.3 не меняется.
- **Откат.** Если Мастер выберет прежнее толкование, оставить только буквальную PR-local команду `git diff --stat origin/main…HEAD -- src/core`, а сводку миссии не использовать как критерий. §2.3 и команды в ТЗ по-прежнему требуют отдельного изменения документа, которого эта карточка не делает.

## F4 — порог 450 строк для модулей вне миссии

- **Было красным.** При буквальном сканировании всего дерева порог `≤ 450` нарушают `src/core/combat.ts` (`1765` строк) и `src/core/savemigrate.ts` (`788` строк), хотя эти два модуля миссия не трогала.
- **Почему.** Глобальный обход смешивает ранее существовавший долг с результатом конкретного PR. Текущая миссия не изменяла эти модули; их размер не говорит о границах новых или изменённых ею модулей. Это не делает сами превышения соответствующими порогу.
- **Предлагается.** Сохранить `450` как жёсткий максимум для каждого нового или изменённого миссией модуля; если миссия меняет один из перечисленных модулей, его нужно привести к порогу в этой же задаче. Неизменённые `combat.ts` и `savemigrate.ts` оставить явно записанным внешним долгом для отдельной задачи: глобальный отчёт показывает их, но не блокирует несвязанный PR. Лимит фасада `engine.ts` `≤ 600` не меняется.
- **Откат.** Если Мастер выберет глобальное толкование, проверять весь `src/core` как единое целое; результат остаётся красным до снижения размеров обоих модулей ниже `450`. Не вводить исключения по имени файла и не поднимать порог.

## F5 — два буквальных grep-а

- **Было красным.** Один буквальный поиск находит в `scripts/fmv-passport-probe.mts` фильтр `entry.pack === 'narrative'`; другой находит текстовые литералы в `src/core/pack/registry.ts` (в аудите — `9`). Такое совпадение текста может быть прочитано как запретная проверка жанра или зависимость ядра от пака.
- **Почему.** Фильтрация записей реестра в пробе проверяет данные; сама по себе она не выбирает производственное поведение условной веткой. Строки `packs/registry.json` и `packs/${packId}/` в общих диагностических сообщениях описывают ожидаемую структуру данных и не являются `import`-ребром. Лексический поиск не различает исполняемую логику, тестовую проверку и строковый литерал.
- **Предлагается.** После отдельного решения Мастера проверять смысловые инварианты анализом исходников: (1) в исполняемой логике `src/core/**`, студии и `check` нет ветвления поведения по ID `narrative` или другого конкретного жанрового пака; (2) в графе зависимостей нет импорта из `src/core/**` в `packs/**`. Фильтр в пробе и диагностическая строка сами по себе не считаются нарушением, если анализ подтверждает отсутствие такой ветки/импорта. Сами grep-команды сохранить как диагностические подсказки, но не выдавать текстовое совпадение за семантическое нарушение. До решения Мастера никакая проверка не заменяется.
- **Откат.** Если Мастер выберет буквальное толкование, оставить оба grep-а строгими: любое совпадение, включая фильтр пробы и строки сообщений реестра, считается красным результатом. Это возвращает прежний лексический критерий без скрытой фильтрации совпадений.

## Применение до решения Мастера

- Пока статус остаётся `proposed`, действуют буквальные формулировки ТЗ, оракула и существующих гейтов.
- Этот текст не позволяет аудитору пропустить красное срабатывание по предложенному смысловому критерию вместо текущего буквального критерия.
- Если Мастер выберет одну из трактовок, статус и проверяющий алгоритм меняются только отдельной карточкой.
- По F3 базовая точка `44945f0` нужна для сводки миссии; список изменений этого PR сравнивается с текущим `main`, а не смешивается с историей предыдущих NAR-2 PR.
- По F4 два модуля остаются зафиксированным превышением, а не считаются соответствующими лимиту.
- По F5 текстовые совпадения остаются видимыми в диагностике; скрытого списка игнорирования результатов нет.
- В рамках NAR-2.14 не правятся тесты, скрипты проверки, манифесты или производственные файлы.
- Предложения не являются доказательством, что все остальные условия фазы выполнены; они описывают только три находки F3, F4 и F5.

## Ответ

Текущий ADR не меняет ни один гейт. Проверки выполнены после создания файла; ниже зафиксированы их фактические итоговые строки и коды возврата:

- `npm run check:contracts` — rc=0; вывод: «контракты согласованы: 41 проверок» и «check:packs passed».
- `npm run build` — rc=0; вывод: «✓ 1421 modules transformed.» и «✓ built in 2.37s».
- `npm run check:brand` — rc=0; вывод: «✓ старое имя не встречается (проверено файлов: 979)».

Проверка границ этой карточки: в diff к текущему `main` должен быть только `docs/decisions/NAR-2.14.md`; `docs/agents/tz-nar-2.md`, `docs/agents/tz.md`, `src/**`, `packs/**`, `scripts/**`, `public/**` и `package.json` не меняются.
