# Фазы: рабочая гипотеза плана

Документ превращает [`vision.md`](./vision.md) в проверяемую
последовательность. Каждая фаза — **проверка предыдущей**, а не пачка работ:
если фундамент ошибся, это видно на следующей фазе, а не через полгода.

**Это гипотеза, а не канон.** Десять фаз — текущая версия плана (v0.5,
2026-10-23), а не обещание. Число, порядок и состав фаз меняются, когда
проверка показывает другое; контрактом становятся только решения из
[`contracts/`](./contracts/README.md). План существует, чтобы из него было из
чего нарезать миссии, а не чтобы ему служить.

Фаза 0 (контракты) закрыта: формат v2, реестр возможностей, ADR 0001–0005,
`npm run check:contracts`. Дальше — текущий план из десяти фаз.

## Как меняется план

- **Менять можно всё:** добавить, убрать, слить, разделить или переставить
  фазу; переписать шаги и «готово, когда». Причина — результат проверки, а не
  желание.
- **Нельзя убрать проверяемость:** у фазы остаются цель, шаги, «замораживаем»,
  «готово, когда» и риск; сквозные гейты действуют всегда.
- **Номер — идентификатор, а не обещание порядка.** Удалённая фаза оставляет
  номер свободным; новая получает следующий свободный или буквенный суффикс
  (`5a`, `5b`). Перенумерация запрещена: она ломает ссылки в Notion, PR и
  миссиях.
- **Порядок — по зависимостям.** Фазу нельзя поставить раньше, если её
  «готово, когда» требует контракта, который замораживает более поздняя.
- **Изменение плана — отдельный PR** в этот файл; если меняется контракт
  (формат, API, риг) — сначала ADR. `README.md` и `docs/README.md` правятся
  там же.
- **Пересмотр после каждой фазы** — три вопроса из `vision.md` §10. По итогам
  фаза может быть переписана, а следующая — заменена.

## Как читать фазу

У каждой фазы пять частей:

- **Цель** — что становится возможным для автора или агента.
- **Шаги** — из чего состоит работа; шаг ≈ одна задача Координатора.
- **Замораживаем** — что после этой фазы меняется только через ADR и миграцию.
- **Готово, когда** — машинная проверка, а не мнение.
- **Риск** — что именно эта фаза проверяет в предыдущей.

Фаза не закрывается, пока на её паке нет **играбельного проекта** и
`check = 0`. Если фаза не даёт играбельного проекта — она не закончена,
сколько бы кода ни было написано.

**«Играбельный» проверяется в настоящем браузере, а не по исходникам.** С 26.10
(ADR D-072, `docs/decisions/NAR-2.md`) сквозной гейт включает
`npm run playthrough`: Chromium открывает собранное приложение и проходит путь
игрока — меню, создание героя, сцена, диалог, выбор реплики, переход. CLI,
`cf-play explore`, прямой вызов симуляции или «посмотрел код» заменой не
являются. Фраза «браузера в песочнице нет» запрещена стражем
`check:browser-gate`. Подробности — [`agents/browser.md`](./agents/browser.md)
и [`agents/visual.md`](./agents/visual.md).

## Оракул фазы

У каждой фазы есть **оракул** — то, что отвечает «готово» без человека:

- **команды** из блока «Готово, когда» и сквозные гейты ниже;
- **инварианты** — что обязано остаться правдой (эталон регрессии, публичный
  API, размеры модулей, детерминизм).

Оракул фиксируется **до** выдачи первой карточки миссии и дальше не меняется:
ни Координатором, ни исполнителем, ни Architect по ходу. Ослабить проверку или
поправить эталон под результат можно только ADR со статусом `proposed` — и это
законная остановка фазы, а не рабочая правка.

Зачем так строго: если экзамен можно переписать по ходу, «принято» перестаёт
что-либо значить. Подробно — [`agents/freedom.md`](./agents/freedom.md) §2.

## Сквозные гейты

Эти проверки обязаны быть зелёными в конце **каждой** фазы. Они не
обсуждаются в карточках и не входят в «готово, когда» отдельной строкой —
без них фаза не принимается.

```bash
npx tsc -b
npm run check:contracts
npm run check:brand
npm run check:version
npm run smoke:core
npm run check:browser-gate
npm run playthrough        # нужен собранный билд + vite preview на :4173
node public/ai/cf-play.mjs check public/campaigns/ash-of-caerden
```

Плюс:

- **Поведение меняется только там, где фаза это разрешает.** В остальных PR
  «стало лучше, но старый проект не открывается» — провал, а не улучшение.
- **Документы меняются в том же PR, что и код.** Расхождение docs ↔ код —
  блокирующая находка Spec Auditor.
- **Отчёт миссии печатает метрики** из `vision.md` §7: скорость, долговечность,
  выживание обновления, локализация, время до первого пака.
- **После фазы 5** в `src/editor/` и `src/player/` нет новых строк интерфейса
  прямо в компонентах — только ключи локалей.

## Фаза 1. Ядро из `engine.ts`

**Цель.** Разрезать монолит так, чтобы следующий жанр не пришлось впихивать в
тот же класс, и чтобы агент мог работать с подсистемой, а не с файлом на 5146
строк.

**Сейчас.** `src/core/engine.ts` — 5146 строк, один класс `GameEngine`,
253 метода. Уже вынесены `time.ts`, `prng.ts`, `savemigrate.ts`,
`combat.ts`, `dialogue.ts`, `hex.ts`, `conditions.ts`, `dice.ts`, `brp.ts`,
`charcreate.ts`, `loader.ts`.

**Шаги.** Задачи NAR-1.1–NAR-1.10 в [`agents/tz.md`](./agents/tz.md):

1. Карта 253 методов: имя, группа, «знает ли про нарратив», решение.
2. `EngineCtx` и страж графа импортов (`check:core-graph`).
3. Мир, сцены, переходы.
4. Инвентарь, износ, экипировка, груз.
5. Время, потребности, календарь.
6. Квесты, репутация, напарники.
7. Сцены: слоты, предмет→слот, навигация.
8. Крафт, торговля, встречи.
9. Эффекты, правила, сохранения, фасад.
10. Отчёт: карта после, эталон регрессии, найденные баги отдельными карточками.

**Замораживаем.** Карту зависимостей ядра: модуль не импортирует `engine.ts`,
циклов нет, публичный API `GameEngine` не меняется (22 файла UI).

**Готово, когда.**

- фасад — только делегирование; гейт по ТЗ NAR-1: ≤ 600 строк (цель — ≤ 400);
- каждый модуль ≤ 450 строк;
- `npm run check:core-graph` зелёный;
- все `smoke:*` зелёные **без правок в смоуках**;
- эталон `cf-play check public/campaigns/ash-of-caerden` не изменился:
  10 сцен · 8 локаций · 6 диалогов · 21 узел, 0 ошибок / 8 предупреждений,
  seeds 1–5 → те же 5 смертей, покрытие 6/10.

**Риск.** «Перенос» превращается в «переписывание», и поведение тихо меняется.
Поэтому четыре критерия из пяти — про сохранность поведения.

## Фаза 2. Шов «движок / пак»

**Цель.** Ввести границу, ради которой затевалась платформа: пак приносит
направление, ядро о жанрах не знает. И сразу проверить шов на дешёвом паке, а
не на новом рантайме.

**Шаги.**

1. **Шов.** У пака четыре части (`schema`, `panels`, `validators`, `probes`) и
   объявленные точки расширения (`provides.seams`): `sim` — чистые и
   детерминированные, `view` — только рисование и звук.
2. **`narrative` становится паком** — тем же кодом, но подключённым через шов.
3. **`adventure`** — первый пак поверх narrative: аватар с ходьбой к точке
   клика, режимы курсора, соединение предметов, крупные планы-загадки.
4. **FMV** — ветвящееся видео как возможность narrative: видео → выбор →
   следующий фрагмент, с предзагрузкой и субтитрами.
5. **Кит как среда, часть 1** (миссия Tools): `cf-play explain <код>`,
   `cf-play example <механика>`, корпус `examples/<механика>/` в CI, гайд
   сжимается до «почему», а не «какое поле».
6. **Режимы возможностей** — в проекте: `core`, `code`, `off` (форма
   заморожена ещё в контрактах, здесь появляется исполнение).

**Замораживаем.** API шва: сигнатуры `sim`-хуков, правило «`view` не влияет на
состояние», манифест пака.

**Готово, когда.**

- проект без пака `narrative` открывается и честно говорит «этот жанр не
  поддерживается», а не падает;
- квесты можно выключить, оставив сцены; данные при этом не теряются;
- проект `adventure` играется и даёт `check = 0`;
- FMV-сцена ветвится по выбору и не показывает чёрный кадр на стыке;
- `cf-play explain` отвечает на все коды ошибок narrative-пака;
- гайд ≤ 70 КБ (было 268 КБ), остальное — примеры и `explain`.

**Риск.** Шов окажется дырявым: паку понадобится правка ядра. Если в PR нового
пака диф ядра не пуст — архитектура неверна, и это дешевле узнать здесь.

## Фаза 3. Второй рантайм — настоящий realtime

**Цель.** Отделить «что происходит» от «когда считается». Появляется второй
цикл исполнения: непрерывное время, фиксированный шаг, ввод по нажатию.

**Шаги.**

1. Интерфейс исполнителя: `step(dt)`, ввод, пауза, детерминизм по seed.
2. `turn` переводится на этот интерфейс без изменения поведения.
3. `realtime`: фиксированный шаг симуляции, интерполяция отрисовки, бюджет
   кадра.
4. `cf-play` учится гонять оба цикла headless.
5. Эталонный realtime-проект: движение, столкновение, простой триггер.

**Замораживаем.** Интерфейс исполнителя: ядро не знает, чей цикл крутится.

**Готово, когда.**

- два эталонных проекта — по одному на рантайм — детерминированы по seed:
  одинаковый seed даёт одинаковый хэш состояния;
- один и тот же код симуляции даёт одинаковый результат в браузере и в
  `cf-play`;
- `cf-play` проходит оба проекта без ветвлений «если это realtime»;
- бюджет кадра зафиксирован в отчёте.

**Почему не «один проект в двух режимах».** Формат запрещает смешивать
рантаймы в одном проекте (ADR 0002): это два разных цикла и неуправляемое
состояние. Проверка — два проекта на одном интерфейсе исполнителя.

**Риск.** Realtime приносит недетерминизм: плавающая точка, порядок обхода,
время. Если хэш прогона плавает — фаза не закрыта.

## Фаза 9. ИИ-цикл в продукте

**Цель.** Цикл перестаёт жить снаружи движка. Агент открывает студию, получает
задание, делает проект, прогоняет проверки и отдаёт результат — без исходников
движка и без человека.

**Шаги.**

1. Headless-API движка: загрузить проект, шаг, состояние, снимок, проверка.
2. `cf-play shoot`: сборка в headless-браузере, детерминированный seed,
   скрипт действий, N кадров на выходе.
3. `kit doctor` и отказ устаревшего кита работать (мажорное расхождение).
4. **Поведенческий корпус**: `(движок, версия проекта, seed, скрипт) → хэш
   состояния и лога`; `check-upgrade --from … --to …` собирает тикет на починку.
5. **Локализация контента**: стабильные ID строк, `locales/<lang>.json`,
   устаревание перевода по хэшу исходника; пак `localization` — машинный
   перевод восьми языков с бейджем «машинный / вычитан».
6. MCP-обёртка над тем же CLI (тонкая, не второй продукт).

**Замораживаем.** API кита и формат `check-upgrade`.

**Готово, когда.**

- агент делает новый проект любого включённого жанра, ни разу не открыв
  `src/`;
- `cf-play shoot` даёт кадры, по которым видно сцену;
- старый проект после изменения механики получает автоматический тикет с
  воспроизведением и после правки проходит `check`;
- один проект переведён на восемь языков, бейджи и проценты устаревания видны
  в мастерской.

**Риск.** Кит снова превращается в документ. Гейт: гайд ≤ 10 % исходного
объёма, остальное — `explain`, `example` и `shoot`.

## Фаза 10. Мастерская и 1.0

**Цель.** Публикация, установка, обновление и рейтинг без хостинга файлов.
И релиз 1.0 по критерию ADR 0005, а не по дате.

## Сквозное: золотая кампания

Полигоны доказывают, что движок работает. Они не доказывают, что **игра
играется**. Для этого нужна одна большая настоящая кампания — «золотая»
([`golden-campaign.md`](./golden-campaign.md)): «Каркас: Дело о седьмой помпе»
из `campaign-1`, 5–7 часов, 12 сцен, 9 концовок, 462 изображения, 372 файла
озвучки.

- **Это не отдельная фаза.** Кампания заводится один раз и дальше служит
  проверкой для фаз 3, 4, 5, 9 и 10. Миссия на неё — одна, не «фаза золотой
  кампании».
- **Она не хостится платформой.** Архив лежит в релизе своего репозитория;
  в платформе — скрипт, который тянет его по хэшу в `.golden/` (в `.gitignore`).
  Правило «файлы не хостим» (`vision.md` §8) не нарушается.
- **Она же — доказательство медиа-политики** ([`decisions/NAR-4.1.md`](./decisions/NAR-4.1.md),
  D-077): картинки сгенерированы ИИ, озвучка русская и тоже ИИ, музыка и звуки —
  настоящие записи. Ни одной векторной заглушки и ни одного синтезированного
  звука в витрине.
- **Готово, когда** кампания проходит `audit:campaign` и `cf-play check` с нулём,
  60 минут по скрипту без `pageerror`, сохранение и загрузка не теряют флаги,
  а время до первой играбельной сцены записано числом.

## Как фаза превращается в миссию

1. **Координатор** берёт фазу и режет её шаги на карточки. У карточки обязательны
   `Намерение`, `Инварианты`, `Acceptance` (оракул: команда) и `Scope`.
   `Кому`, `Sequence` и число одновременных `Ready` — его решение, а не
   содержание ТЗ: ТЗ приходит черновиком.
2. **Исполнитель** работает только в своей зоне, коммитит и мержит PR сам.
3. **Аудитор** проверяет по гейту фазы, а не по впечатлению.
4. **Миссия закрывается**, когда все карточки `Accepted` и блок «Готово, когда»
   выполнен целиком. `Итог` миссии — отчёт с метриками.

Если шаг фазы не помещается в одну карточку — он режется. Если шаг нельзя
проверить командой — он переписывается, пока не станет проверяемым.

## Чего в плане нет

- **Мультиплеера** — имена зарезервированы (`multiplayer-turn`,
  `multiplayer-realtime`), контракта нет. Когда появится: комнаты хранят только
  состояние и журнал, бесплатный старт — Cloudflare Durable Objects
  ([`infrastructure.md`](./infrastructure.md)).
- **Внутриигровых покупок и магазина** — только внешние магазины; IAP требуют
  сервера и меняют экономику платформы.
- **Хостинга ассетов и игр** — вне границ по `vision.md`.
- **Покупки сервера до 1.0** — до фазы 10 сервер не нужен, дальше — только по
  триггерам из [`infrastructure.md`](./infrastructure.md).
- **Мобильной сборки и веб-плеера** — после 1.0, отдельным решением.
