# Визуальные роли: как смотреть на интерфейс без глаз человека

Роли `UI/UX Designer`, `UX Auditor` и любая проверка «как это выглядит» упираются
в вопрос: **чем смотреть**. Ответ один: **настоящим браузером в песочнице**.

> **ПРАВИЛО (обязательное для всех ролей).** Браузер в песочнице агента **есть**
> и работает: `Chromium 131.0.6778.0` поднимается без root через
> `@sparticuz/chromium` + `playwright-core`. Снимать экраны, кликать, читать
> консоль и проходить игру можно прямо здесь. Утверждение «браузера в песочнице
> нет» — ложь; карточка, где проверка подменена текстовым прогоном, возвращается
> на доработку. Команда установки и рабочий цикл — `browser.md`, §«Установка».

## Что проверено в песочнице (актуальный замер)

| Проверка | Результат |
|---|---|
| `npm i --no-save @sparticuz/chromium@131 playwright-core@1.49.1` | **ставится** (~5 с, без root, без apt) |
| `launchChromium()` из `scripts/visual/local-browser.mjs` | **работает**: `Chromium 131.0.6778.0` |
| `node scripts/visual/shot.mjs <url> out/x.png --console` | **HTTP 200**, PNG на диске, 0 ошибок консоли |
| Клики, `--text`, `--eval`, `--click`, `--size` | **проверены** на живой игре (меню, создание героя, диалог) |
| `npx playwright install` (обычный Playwright) | не тот путь: его CDN закрыт, а `--with-deps` требует root |

Первый замер (2026-10-24) дал `exit 127` на `libnss3.so` и был **ошибочным**:
Playwright не ставится не потому, что «браузера нет», а потому что его бинарник
качается с закрытого домена, а `--with-deps` требует root. Пакет
`@sparticuz/chromium` приносит и бинарник, и недостающие библиотеки NSS —
достаточно распаковать бандл и указать `LD_LIBRARY_PATH`.

Слои ниже остаются, но меняется их роль: слой 3 доступен прямо в песочнице,
а CI нужен как независимый свидетель и как история прогонов.

## Слой 1 — математика (работает в песочнице сегодня)

Контраст, размеры токенов, палитра — это числа, а не картинки. В репозитории уже
есть `scripts/theme-contrast-smoke.mts`: он читает токены темы и считает WCAG-
контраст поверхностей. Проверено: **OK**. Агент-дизайнер может менять токены и
сразу получать вердикт — без браузера.

Правила, которые проверяются на этом слое:

- контраст текста к фону ≥ 4.5:1, крупного текста ≥ 3:1;
- контраст границ фокуса ≥ 3:1;
- ни одна поверхность не «сливается» с соседней меньше чем на 1.2:1.

## Слой 2 — структура (работает в песочнице)

`scripts/visual-smoke.mts` уже проверяет разметку и подстановку темы без браузера.
Сюда же относится всё, что можно утверждать про DOM: порядок элементов, наличие
`aria-label`, состояния «пусто/ошибка/загрузка», отсутствие кнопок без имени.
Фактически это UX-аудит без картинки: он ловит «кнопка без подписи» и «нет
состояния ошибки», но не ловит «некрасиво» и «налезает друг на друга».

## Слой 3 — пиксели (доступен в песочнице и дублируется в CI)

Скриншоты снимаются двумя путями, оба проверены по отдельности:

* **в песочнице** — `npm i --no-save @sparticuz/chromium@131 playwright-core@1.49.1`
  и `node scripts/visual/shot.mjs <url> out/x.png` (`browser.md`);
* **в CI** — GitHub Actions: обычный Ubuntu с root, там
  `npx playwright install --with-deps chromium` проходит.

```
.github/workflows/visual.yml     # сборка → предпросмотр → снимки → артефакт
scripts/visual/shots.mjs         # снимки + машинные утверждения
```

Что снимается: `home` (1440×900 и 900×900) и `editor` (`/#editor`).

**Статус проверки.** Локальный путь подтверждён: `scripts/visual/shots.mjs`
отработал на `Chromium 131`, четыре экрана, `0` находок.

CI-путь пока не подтверждён, и причина техническая: GitHub регистрирует
воркфлоу из **основной ветки**. Пока `.github/workflows/visual.yml` живёт
только в PR-ветке, `gh workflow list` возвращает пусто, а `workflow_dispatch`
недоступен — это не поломка, а порядок регистрации. После слияния в `main`
воркфлоу появится во вкладке Actions и его можно будет запустить вручную.
Если репозиторий новый, Actions может быть выключен: тогда во вкладке Actions
будет баннер с кнопкой включения (см. `browser.md`, раздел «Что делать в
GitHub»).
Что проверяется автоматически, без «посмотреть»:

- горизонтальная прокрутка (элемент шире окна);
- интерактивные элементы без доступного имени;
- `<img>` без `alt`;
- ошибки страницы и консоли;
- сетевые запросы, которые упали.

Результат: `visual-report.json` и `visual-report.md` + PNG в артефакте
`visual-report`.

### Как агент смотрит на пиксели

1. CI прогоняет снимки, кладёт артефакт.
2. Агент скачивает артефакт: `gh run download <run-id> -n visual-report -D out/visual`
   (домен GitHub разрешён в песочнице).
3. Агент читает PNG **зрением** — картинка попадает в контекст как изображение,
   и он описывает, что видит: наложения, обрезанный текст, «пустое» состояние.
4. Находка становится карточкой в «Запросах» с путём к снимку.

Так «посмотреть глазами» остаётся возможным — глаза принадлежат модели, а
браузер поднимается **в песочнице**; CI — второй, независимый прогон того же
скрипта, а не единственный источник пикселей.

### Проверка игрой — обязательный минимум (26.10)

`shots.mjs` снимает только `home` и `editor`. Этого **недостаточно**, чтобы
сказать «проект играбелен»: игрок мог ни разу не дойти до сцены. Любая приёмка
фазы или карточки с UI обязана содержать браузерное прохождение:

```bash
npm run build
npx vite preview --port 4173 --host 0.0.0.0 --strictPort   # в start_process
node scripts/visual/shot.mjs http://localhost:4173 out/play/01.png --console
# дальше — свой скрипт на playwright-core: клики по меню, создание героя,
# сцена, диалог, выбор реплики; PNG каждого шага + список ошибок консоли
```

Минимум отчёта: сколько экранов пройдено, путь к PNG, число ошибок страницы и
консоли, есть ли на экране «Фон сцены не загрузился» / «Игра столкнулась с
ошибкой». Скриншоты смотреть **зрением**: `read_file` на PNG. Если браузер не
поднялся — это дефект установки (см. `browser.md`), а не повод сдать карточку
без прохождения.

**Прецедент 26.10.** Приёмка фазы 2 прошла без браузера: проверяли данные и CLI,
а не то, что видит игрок. В настоящем Chromium сразу нашлись вещи, которые
текстовый прогон не ловит: битые пути к изображениям сцен, сырой `id` вместо
имени NPC, а FMV-проект падал с `TypeError` при открытии (`nav.area.x`, потому
что у FMV-сцены нет `area`). Вывод: оракул, который не открывает игру в
браузере, не может закрыть фазу.

## Что роли не делают

- **Дизайнер не судит «красиво».** Он описывает состояния и правила, а проверяет
  их слой 1 и 2. Вкус не является гейтом, проверяемость — является.
- **UX-аудитор не правит код.** Находка → карточка → исполнитель.
- **Никто не прикладывает «я посмотрел, вроде нормально».** Либо снимок с
  вердиктом, либо машинная проверка.
