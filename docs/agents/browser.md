# Браузер в песочнице агента: как это делается

**ПРАВИЛО, обязательное для всех ролей без исключения.** Проверено на практике:
этим способом в этой же песочнице сняты экраны `home`, `editor`, меню кампании,
создание героя, игровая сцена и диалог — без root и без системных пакетов.

## Запрет (читать первым)

В песочнице агента **есть настоящий браузер**. Запрещено писать в отчётах,
карточках, комментариях и коде:

- «браузера в песочнице нет» / «браузер не запускается» / «нет браузера»;
- «проверю без браузера, потому что его нет»;
- «визуальную проверку сделает CI, а я посмотрю текстом».

Это ложь. Проверка, где UML-схема, `cf-play explore` или прямой вызов симуляции
выданы за «сыграл глазами», **не принимается**: карточка уходит на доработку.
Если браузер не поднялся — это дефект установки, а не свойство среды: повтори
команду из §«Установка», проверь `/tmp/cf-browser`, прочитай текст ошибки.
Стоп цикла возможен только с явной причиной (код возврата, лог), а не с фразой
«браузера нет».

Проверка игрой в браузере входит в оракул любой фазы (`docs/phases.md`,
сквозные гейты) и обязательна на приёмке: смотри `visual.md`, §«Проверка игрой
— обязательный минимум».

## Зачем браузер агенту, который не занимается визуалом

Браузер — не «инструмент дизайнера». Это способ задать вопрос «что видит
пользователь» вместо «что написано в коде». Полезен всем:

| Вопрос | Чем проверяется |
|---|---|
| сервер вообще стартует и отдаёт страницу? | открыть `http://localhost:4173` |
| после моей правки экран не пустой? | `--text` и один взгляд на PNG |
| кнопка «Создать кампанию» действительно работает? | `--click "text=Создать кампанию"` + снимок результата |
| почему у пользователя белый экран? | `--console`: ошибка страницы видна первой строкой |
| запрос к API вернул данные? | `--eval "await fetch('/api/health').then(r=>r.status)"` |
| верстка не поехала на узком окне? | `--size 900x900` |

Ни один из этих вопросов нельзя закрыть чтением JSX. Отсюда правило:
**браузер — общий инструмент, как `node` и `git`**. Визуальные роли обязаны им
пользоваться всегда; остальные — когда вопрос про поведение, а не про текст;
приёмка фазы — всегда (см. §«Проверка игрой»).

## Почему в песочнице это обычно не работает и почему теперь работает

Прошлый вывод был неверным. Playwright падает не потому, что «в песочнице нет
браузера», а потому что:

- свой браузер он качает с `cdn.playwright.dev`, а этот домен в песочнице
  закрыт;
- `--with-deps` ставит ~20 системных пакетов через `apt`, а `apt` требует root.

Оба пути закрыты. Но пакет **`@sparticuz/chromium`** (сборка Chromium для AWS
Lambda) кладёт рядом с бинарником архив `al2023.tar.br` — в нём ровно те
библиотеки, которых нет на минимальном Debian 12:

```
libnss3.so  libnssutil3.so  libnspr4.so  libfreebl3.so  libsoftokn3.so
libplc4.so  libplds4.so     libexpat.so.1                    (9 штук, 3 МБ)
```

Остальное (glibc, libX11, libxcb, libglib, fontconfig, freetype) в песочнице уже
есть. Достаточно распаковать бандл и бинарник и указать `LD_LIBRARY_PATH`.
Ни root, ни `apt`, ни системных изменений.

## Установка (одна команда, ~5 секунд)

```bash
npm i --no-save @sparticuz/chromium@131 playwright-core@1.49.1
```

`--no-save` — намеренно: `package.json` и lock-файл не меняются, потому что это
инструмент среды, а не зависимость продукта. В CI браузер ставится обычным
Playwright — там root есть.

## Два способа воспользоваться

### 1. Готовая команда «посмотреть страницу»

```bash
node scripts/visual/shot.mjs http://localhost:4173 out/home.png
node scripts/visual/shot.mjs http://localhost:4173 --text --console
node scripts/visual/shot.mjs "http://localhost:4173/#editor" out/editor.png --click "text=Создать кампанию"
node scripts/visual/shot.mjs http://localhost:4173 out/x.png --eval "document.querySelectorAll('button').length" --size 900x900
```

Код возврата: `0` — страница открылась и ошибок нет, `1` — есть ошибки
консоли/страницы, `2` — браузер не поднялся. Значит, пригодно для скриптов и
гейтов, а не только для «глянуть».

### 2. В своём скрипте

```js
import { launchChromium, chromiumVersion } from './scripts/visual/local-browser.mjs';

const browser = await launchChromium();          // кэш в /tmp/cf-browser
const page = await browser.newPage({ viewport: { width: 1440, height: 900 } });
const errors = [];
page.on('pageerror', (e) => errors.push(String(e)));

await page.goto('http://localhost:4173', { waitUntil: 'networkidle' });
await page.screenshot({ path: 'out/home.png', fullPage: true });
console.log(chromiumVersion(), errors);
await browser.close();
```

Дальше — обычный Playwright API: локаторы, клики, `evaluate`, перехват сети,
`context.storageState()` для сохранения сессии.

## Рабочий цикл, который стоит повторять

```bash
npm run build                                  # или npm run dev в start_process
npx vite preview --port 4173 --host 0.0.0.0 &   # отдать сборку
node scripts/visual/shot.mjs http://localhost:4173 out/home.png --console
# открыть out/home.png как изображение и посмотреть на него
```

Скриншот смотреть **глазами**, а не только проверять код возврата: машинные
утверждения ловят прокрутку и кнопки без подписи, но не ловят «текст выровнен
по ширине и между словами дыры». Именно так и была найдена эта правка на
главном экране — скрипт был зелёный.

## Границы и цена

| Что | Сколько/почему |
|---|---|
| установка пакетов | ~5 с, 20 пакетов; `node_modules` **не переживает ход** — повторять каждый ход |
| распаковка бандла | ~2 с, кэш в `/tmp/cf-browser` (тоже не переживает ход) |
| первый экран | ~3–5 с: старт браузера + `networkidle` + пауза |
| вес | 183 МБ бинарник + 3 МБ библиотеки, в git не попадают |
| GPU и шрифты | нет GPU; шрифты из бандла, кириллица рендерится, но не как в системе автора |
| «красиво ли» | браузер показывает пиксели, но эстетику оценивает тот, кто смотрит на PNG |
| снимки в репозитории | не нужны: `out/` в `.gitignore`, артефакты — во временной папке |

## Чего не делать

- Не тащить `playwright` (полный) в песочницу: он всё равно упрётся в
  `cdn.playwright.dev` и `apt`.
- Не добавлять браузерные пакеты в `dependencies`: это инструмент проверки, а не
  часть продукта; в CI он ставится отдельным шагом.
- Не считать «скрипт вернул 0» доказательством, что экран в порядке.
- Не коммитить PNG и `out/`.

## Проверка игрой (обязательный минимум при приёмке)

Одного снимка главной страницы недостаточно: на нём может быть пустой реестр
кампаний, а вся игра — за тремя кликами. Минимальный маршрут, который агент
проходит **в браузере** и прикладывает к отчёту:

```bash
npm run build
npx vite preview --port 4173 --host 0.0.0.0 --strictPort   # start_process
node scripts/visual/shot.mjs http://localhost:4173 out/play/01-menu.png --console
node scripts/visual/playthrough.mjs http://localhost:4173 out/play   # скрипт маршрута
```

`playthrough.mjs` — воспроизводимый маршрут (меню → кампания → новый забег →
создание героя → сцена → диалог → выбор реплики → переход), который сохраняет
PNG каждого шага, текст экрана, ошибки консоли и `pageerror` в
`out/play/report.json`. Он же вызывается в CI (`visual.yml`). Код возврата `0`
— только если все шаги дошли до конца и ошибок страницы нет.

**Что смотреть глазами в PNG:** не «открылось ли», а нет ли на экране
«Игра столкнулась с ошибкой», битых `<img>` вместо портретов, сырых `id` вместо
имён. Это дефекты, которые CLI не видит.

Технической плашки «Фон сцены не загрузился» в игре больше нет (D-076): игрок
видит нейтральный фон, а причина остаётся в `console.error` и в отчётах
`audit:campaign` / `playthrough:exam`. Поэтому отсутствие фона ищут не глазами
по плашке, а по `console-error` и разделу отчёта «известные намеренные
отсутствия»: у dev-полигона они объявлены в `dev-fixture.json`
(`known_absent_images`), у проекта витрины их не может быть вовсе.

**Строгий экзамен:** `npm run playthrough:exam -- http://localhost:4173 out/exam`.
Список допустимых отсутствий он берёт у самой кампании, а не из своего кода.
Любое необъявленное отсутствие, битый или пустой `<img>`, `pageerror`, экран
ошибки и сырой NPC id делают его красным.

## Что делать в GitHub (человеку, а не агенту)

Агенту GitHub нужен только как `git`/`gh`. Человеку — два экрана, и **GitHub
Desktop тут не нужен**: он умеет коммиты и пуши, но не умеет ни Actions, ни
артефакты.

### 1. Actions: что это и зачем

GitHub Actions — чужие компьютеры, которые запускают то, что описано в
`.github/workflows/*.yml`. У нас там один файл, `visual.yml`: он собирает
проект, поднимает предпросмотр, снимает экраны и кладёт PNG в артефакт.

Зачем, если браузер работает в песочнице: прогон **остаётся в истории**, его
видно в PR и можно перепроверить через месяц. Песочница живёт один ход — CI нет.

| Что | Где | Зачем |
|---|---|---|
| вкладка **Actions** | шапка репозитория | список прогонов, кнопка «Run workflow» |
| прогон | Actions → **visual** | шаги, логи, время |
| артефакт **visual-report** | внизу страницы прогона | PNG + `visual-report.md` |
| включение | баннер «Workflows aren't being run on this repository» | одна кнопка, если Actions выключен |

Два факта, которые снимают половину вопросов:

1. **Воркфлоу появляется в Actions только после слияния в `main`.** Пока файл
   лежит в PR-ветке, Github его не регистрирует — поэтому `gh workflow list`
   пуст, а кнопки «Run workflow» нет. Это порядок, а не поломка.
2. **На PR он запускается сам** после слияния: любой новый PR будет получать
   прогон `visual` и PNG в артефакте.

Порядок действий, если прогона нет:

```
GitHub → репозиторий → вкладка Actions
  → если баннер про выключенные workflows: нажать «I understand my workflows, go ahead and enable them»
  → слева выбрать «visual» → кнопка «Run workflow» → Branch: main → Run
  → открыть прогон → дождаться зелёной галочки → внизу «Artifacts» → visual-report
```

Проверить из терминала (агент это тоже может, когда Actions включён):

```bash
gh workflow list
gh run list --workflow visual --limit 5
gh run watch <run-id>
gh run download <run-id> -n visual-report -D out/visual
```

### 2. Конфликт в PR

«This branch has conflicts» означает, что обе ветки правили один файл и Git не
может слить автоматически. Решается **не кнопкой в браузере**, а слиянием
`main` в свою ветку: конфликт разрешается один раз, дальше PR снова mergeable.

```bash
git fetch origin main
git merge origin/main            # при несвязанных историях: --allow-unrelated-histories
# правим файлы, убираем маркеры <<<<<<< ======= >>>>>>>
git add <файлы> && git commit
git push
```

Если PR «залип» и показывает старый commit (наблюдалось 2026-10-22: ветка
`62ff188`, а PR показывает `head=b78feba`; после каждого пуша снова отстаёт),
помогает закрыть и снова открыть PR — GitHub перечитывает ссылку на ветку:

```bash
gh pr close <n>
gh pr reopen <n>
```

Признак именно этого залипания: `git ls-remote origin <branch>` даёт новый sha,
а `gh pr view <n> --json headRefOid` — старый. Пока head не совпал, любые
«конфликты» в PR относятся к устаревшему состоянию и чинить их бессмысленно.

### 3. Чего делать не нужно

- Ставить GitHub Desktop ради Actions — он их не показывает.
- Жать «Resolve conflicts» в веб-редакторе, если конфликт в `package.json`:
  проще слить `main` локально и собрать объединение, чем править маркеры мышью.
- Включать авто-мерж до первого зелёного прогона `visual`.
