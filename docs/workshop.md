# Мастерская кампаний (проект, фаза C)

Мастерской в коде ещё нет — документ фиксирует решения, чтобы к моменту
разработки не обсуждать их заново. Версионность, на которую мастерская
опирается, уже реализована: см. [`compatibility.md`](./compatibility.md).

---

## 1. Решения заказчика

| Вопрос | Решение |
|--------|---------|
| Где живёт мастерская | В десктоп-приложении (Tauri). Локальные тесты — в браузере (`npm run dev`), упрощённый вариант |
| Хранение кампаний | appdata приложения (`app.chronicleforge.desktop`) |
| Кто хранит файлы кампаний | **Мастер**, в своём репозитории GitHub. Мы храним только ссылки |
| Почему так | Кампании могут весить гигабайты; держать их (и все версии) на своём хостинге дорого |
| Установка | Игрок жмёт «Скачать», файл загружается и импортируется в игру; что источник — GitHub, игрок не видит |
| Автоимпорт при скачивании | Возможный шаг на будущее; сначала — отдельное действие |

Экономика: мастерская хранит байты-ссылки, гигабайты лежат у автора.
Отсюда же — требование к интерфейсу: клиент не должен зависеть от того, где
физически лежит файл.

### Идентичность кампании и глобальные конфликты

Новый редактор выдаёт кампании случайный UUID v4 и хранит его неизменным при
переименовании, обновлении и пересылке `.chronicle`. ИИ не назначает и не
переименовывает этот ID. Локальная проверка реестра и папок защищает текущую
установку, но не может знать о произвольных офлайн-файлах.

Для гарантии уникальности именно **в официальной мастерской** каталог должен
быть авторитетным реестром: публикация резервирует ещё не занятый ID, а
публикация новой версии под существующим ID разрешается только владельцу.
Проверка должна быть атомарной/повторяться при слиянии публикаций, чтобы две
одновременные заявки не заняли один ID. ID в реестре уникален глобально, не в
паре с автором. Старые slug-ID остаются допустимыми для уже выпущенных кампаний.

Для офлайн `.chronicle` абсолютная глобальная гарантия невозможна без общей
службы: импорт сохраняет ID свободного пакета, повтор идентичного импорта
распознаёт как ту же кампанию, а при разных данных под занятым ID предлагает
обновить её или импортировать как копию с новым UUID.

## 2. Источник кампании — GitHub

Мастер публикует релиз в своём репозитории; ссылка на файл версии выглядит
как `https://github.com/<owner>/<repo>/releases/download/<tag>/<file>`.

Что это даёт версионности:

- **релиз = версия кампании**: тег `1.5.0` даёт постоянный URL, история
  версий и возможность отката существуют сами по себе;
- **проверка обновлений не качает пакет**: читаются только метаданные
  (килобайты) — важно и для трафика игрока, и для гигабайтных кампаний;
- **контрольная сумма от источника**: API GitHub отдаёт `digest` и `size`
  каждого ассета — клиент сверяет их после скачивания и пишет в локальный
  реестр, мастеру не нужно считать хеши руками;
- **маленький `compat.json` отдельным ассетом** — мастер может опубликовать
  вердикт совместимости, не выкладывая пакет заново.

### 2.1 Ограничения GitHub, которые нужно учитывать

- ассет релиза — до **2 GiB** на файл; кампания большего размера публикуется
  частями (`campaign.chronicle.part-01`, …) или распакованным каталогом;
- обычный файл в git жёстко блокируется на **100 MiB** (через браузер —
  25 MiB), поэтому пакеты публикуются именно релизами, а не коммитами;
- релиз можно удалить или заменить — клиент обязан помнить digest,
  записанный при установке, и при расхождении показывать «файл версии X был
  заменён», а не молча переустанавливать;
- соглашение для мастеров: не перезаписывать опубликованную версию, а
  поднимать номер.

### 2.2 Доступ из браузера и из Tauri

Проверено из песочницы разработки (2026-09-27):

- `api.github.com` отдаёт `access-control-allow-origin: *` — метаданные
  релизов доступны из браузера напрямую (лимит 5000 запросов/час на IP без
  токена);
- скачивание ассета релиза — это редирект на
  `release-assets.githubusercontent.com`; по имеющимся данным этот хост CORS
  **не** отдаёт (в отличие от `raw.githubusercontent.com`), проверить из
  песочницы не удалось (CDN недоступен, `curl` — ошибка 35).

Практический вывод:

- **Tauri** — основной путь: `@tauri-apps/plugin-http` выполняет запрос на
  стороне Rust, CORS не мешает; права задаются шаблоном URL в `capabilities`.
  Сейчас в `src-tauri/capabilities/default.json` только `core:default`, а в
  `src-tauri/Cargo.toml` нет ни fs-, ни http-прав — их добавляет фаза C;
- **браузер** (`npm run dev`) — упрощённая мастерская: витрина и метаданные,
  установка из локального источника-заглушки (dev-эндпоинт vite) и из
  `.chronicle`. Многогигабайтные загрузки с GitHub в браузере не
  гарантируются и не нужны для тестов.

## 3. Архитектура клиента

```ts
/** единая точка доступа к пакетам кампаний */
interface CampaignStore {
  list(): Promise<InstalledCampaign[]>
  read(id: string, path: string): Promise<ArrayBuffer | string>
  write(id: string, path: string, data: ArrayBuffer | string): Promise<void>
  remove(id: string): Promise<void>
}
// реализации: DevHttpStore (vite, как сейчас) · TauriFsStore (appdata)

/** «витрина»: что доступно к установке */
interface CatalogSource {
  list(): Promise<CatalogIndex>
}
// реализации: HttpCatalogSource (index.json по URL) · LocalCatalogSource (dev)
```

Интерфейсы намеренно асинхронные и не завязаны на `fetch`: одна и та же
логика мастерской работает и в браузере, и в Tauri. Сейчас загрузка пакета
идёт через `fetch('/campaigns/<id>/…')` (`core/loader.ts`) — на фазе C она
переезжает за `CampaignStore`.

### 3.1 Хранение в appdata

```
appdata/
  registry.json                реестр установленных кампаний
  sources.json                 источники витрины (список URL)
  campaigns/<author_id>/<id>/  распакованные пакеты
  assets/<sha256>              контентно-адресные ассеты (общие для версий)
  saves/…                      сохранения (или localStorage — решается на фазе C)
```

**Контентно-адресные ассеты** — ключевое решение для гигабайтных кампаний:
картинки и звук хранятся один раз по хешу, версия кампании — это манифест
«путь → hash». Следствия:

- обновление качает только дельту (не изменилось 90 % ассетов — качаем 10 %);
- «бэкап версии» — это манифест на килобайты, а не копия пакета;
- откат версии = пересобрать пакет из общих ассетов; чего не хватает —
  докачать из релиза прежней версии (если автор его не удалил — иначе честно
  предупреждаем).

### 3.2 Реестр установленных кампаний

```jsonc
{
  "id": "ash-of-caerden",
  "author_id": "chronicle-forge",
  "installed_version": "1.5.0",
  "source": { "kind": "github-release", "owner": "…", "repo": "…", "tag": "1.5.0", "file": "…" },
  "digest": "sha256:…",
  "installed_at": "…",
  "previous": { "version": "1.4.2", "manifest": "manifests/ash-of-caerden-1.4.2.json" }
}
```

`author_id` обязателен как владелец/издательская запись, но не является частью
ID кампании и не разрешает дублировать его. Одинаковый ID под другим автором —
конфликт владения, а не отдельная кампания: публикация отклоняется или проходит
через явную процедуру передачи владения.

### 3.3 Каталог (`index.json`)

Формат `chronicle-index/1` — маленький JSON, который может лежать где угодно
(GitHub Pages, любой статический хостинг, репозиторий автора):

```jsonc
{
  "format": "chronicle-index/1",
  "updated_at": "2026-09-27T10:00:00Z",
  "campaigns": [{
    "id": "ash-of-caerden",
    "author_id": "chronicle-forge",
    "title": "Пепел Каэрдена",
    "description": "…",
    "versions": [{
      "version": "1.5.0",
      "file": "https://github.com/…/releases/download/1.5.0/ash-of-caerden-1.5.0.chronicle",
      "size": 18432000,
      "digest": "sha256:…",
      "min_engine": "0.7.0",
      "save_base_version": "1.4.0",
      "notes": "Переписана глава 3"
    }]
  }]
}
```

«Официальный каталог Chronicle Forge» может оставаться JSON-файлом на нашем
домене, но публикация в него обязана проходить через проверяемый единый процесс
с контролем уникальности ID и права владельца (включая повторную проверку при
слиянии параллельных публикаций). Одна только локальная проверка клиента не
гарантирует уникальность. Если появятся поиск, рейтинги и модерация, добавится
реализация `CatalogSource` поверх API — интерфейс клиента не изменится.

## 4. Сценарии

**Установка.** Витрина → «Скачать» → прогресс → проверка digest → распаковка
в appdata → ассеты в общее хранилище → запись в реестр → кампания доступна в
главном меню.

**Пустой реестр.** Поставка Chronicle Forge не содержит кампаний для игрока:
`public/campaigns/index.json` — пустой массив, и главное меню показывает экран
«Кампаний пока нет» с двумя путями (создать кампанию в редакторе, импортировать
пакет `.chronicle`). Это не ошибка установки, а обычное состояние: так же
ведёт себя удаление последней кампании. Полигон `ash-of-caerden` в поставке
есть, но в реестр не внесён и игроку недоступен — он нужен только
headless-смоукам движка.

**Обновление.** Проверка метаданных (без скачивания пакета) → сравнение
версий → вердикт совместимости по `compat.json`/`save_base_version` →
диалог:

> **Доступно обновление «Пепел Каэрдена»: 1.4.2 → 1.5.0**
> Переписана глава 3, добавлена локация «Перевал».
> ✅ Ваше сохранение (день 6, «Рынок») совместимо — будет перенесено.
> ⚠️ 1 предмет удалён из кампании: «Ржавый ключ». Он исчезнет из инвентаря.
> [Обновить] [Остаться на 1.4.2]

**Обновление, ломающее сохранения.** Тот же диалог, но вместо «✅» —
«сохранение от версии 1.0.0 не поддержится (поддержка с 1.4.0)», и кнопки
«Обновить и начать новый забег» / «Остаться на 1.4.2».

**Откат.** «Остаться на прежней версии» / «Вернуться к 1.4.2» — пакет
пересобирается из манифеста прежней версии; сохранения той версии лежат под
своим ключом и открываются как раньше.

**Удаление.** Пакет и его манифесты удаляются; общие ассеты — только если на
них больше никто не ссылается; сохранения — по явному подтверждению.

## 5. Что нужно доделать на фазе C

1. `CampaignStore` (DevHttp + TauriFs) и перевод `core/loader.ts`,
   `editor/store.ts` на него.
2. Права Tauri: `fs` (appdata), `http` (шаблоны URL источников), `dialog`
   (выбор `.chronicle`), `shell` (открыть папку) — в
   `src-tauri/capabilities/default.json`.
3. Реестр установленных кампаний, `sources.json`, контентно-адресное
   хранилище ассетов, докачка дельты.
4. Витрина: `HttpCatalogSource` + кэш метаданных, экран кампании
   (описание, версии, changelog, вердикт совместимости).
5. Мастеру: публикация из редактора (подготовка `index.json`, инструкция или
   вызов `gh release create`; токен GitHub в приложении не храним).
6. Упрощённая браузерная мастерская для тестов (локальный источник-заглушка).
7. Смоуки: установка, обновление с переносом сейва, откат версии, коллизия id.
