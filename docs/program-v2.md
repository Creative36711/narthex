# Программа разработки кампаний, v2

Документ заменяет прежнюю схему «Producer → TGD → QA → TD → Producer». Причина
замены не в качестве людей и агентов, а в инструментах: раньше единственной
проверкой был `campaign-audit.mjs` (структура), теперь есть `cf-play.mjs`
(движок целиком: граф, диалоги, прогоны, матрица seed'ов). Роль «Technical
Director» существовала, чтобы вручную запускать кампанию в движке; эту работу
делает `check`, поэтому TD упраздняется, а его обязанности делятся между
Architect (движок и инструменты) и QA (независимый прогон).

## 1. Роли

| Роль | Что делает | Чего не делает |
|---|---|---|
| **Architect** | движок, кит `__chronicle_ai__`, схемы, стандарты приёмки, разбор `cf-feedback` | не пишет контент кампаний, не мержит PR |
| **Master** (владелец) | merge в `main`, релизы, приоритеты, разрешение тупиков | не ведёт очередь задач |
| **Coordinator** | очередь, назначения, приёмка по чек-листу, эскалации | не пишет код и контент, не мержит, не меняет критерии |
| **TGD ×5** | одна кампания целиком: дизайн-документ, контент, медиа, самопроверка, PR | не трогает чужие кампании и движок |
| **QA** | независимый аудит и прогоны, вердикт | не коммитит, не правит контент |

Правила ролей остаются прежними: своя ветка, чужие — только чтение, `main` —
зона Мастера, merge делает только Мастер.

## 2. Конвейер: шесть гейтов

| Гейт | Кто закрывает | Условие |
|---|---|---|
| **G0. Задание** | Architect + Master | ID кампании, бриф, критерии завершения в карточке Notion |
| **G1. Дизайн** | Coordinator | `TASK.md` дословно + `design_doc` по бланку, заполнен до контента |
| **G2. Производство** | TGD | задачи по одной, коммит и пуш каждые 15 минут |
| **G3. Самопроверка** | TGD | `cf-play check` вернул `0`, отчёт и его `sha256` приложены |
| **G4. Приёмка** | QA → Coordinator | прогоны 5 seed'ов × 300 шагов, аудит `0` ошибок, вердикт в PR |
| **G5. Релиз** | Master | merge, сборка `.chronicle`, запись в `library/` |

Гейт — не формальность: без G3 задача не уходит в ревью, без G4 не мержится.
Возврат на доработку — норма; два возврата подряд по одной задаче — сигнал
Coordinator'у, что задача плохо нарезана.

## 3. Единица работы

Один Dispatch = один проверяемый результат: сцена, диалог, механика, правка
баланса, медиа-пакет. В карточке задачи обязательны:

```
Цель:        что должно измениться для игрока
Файлы:       какие пути можно менять (остальное — вне зоны)
Критерий:    проверяемое утверждение, а не «сделать хорошо»
Проверка:    node __chronicle_ai__/cf-play.mjs check . --seeds 1-5 --steps 300
Отчёт:       .cf-play/check/report.md + sha256
```

Задача без критерия и команды проверки не выдаётся: Coordinator возвращает её
автору, а не «додумывает» критерий сам.

## 4. Definition of Done кампании

1. `check` — `0` ошибок и ни одного нового предупреждения относительно прошлой
   сдачи.
2. Матрица seed'ов 1–5 × 300 шагов без падений и без тупиков.
3. Каждая сцена достижима хотя бы одним маршрутом из `routes/`, каждая
   концовка проверена.
4. Медиа лежит внутри пакета, относительными путями; у каждого файла источник и
   лицензия в `attribution`/`CREDITS.md`.
5. `design_doc` соответствует фактическому контенту, а не первоначальному плану.
6. `TASK.md` — дословная копия задания.
7. PR по шаблону, вердикт QA — `Accepted`, merge выполнил Мастер.

## 5. Что меняется в репозитории кампаний

- `__chronicle_ai__/` обновляется только из кита: `npm run sync:ai-kit -- ../campaign-2`
  в `chronicle-forge`. В папке появляется `KIT.json` с версией, коммитом и
  хэшами — по нему видно, на каком ките сделана сдача.
- `.cf-play/` добавляется в `.gitignore`: отчёты прогонов не коммитятся, в
  задачу идёт только хэш и ссылка на артефакт.
- `__chronicle_ai__/TASK.md` больше не обязателен как отдельный файл: задание
  приходит в карточке, а `TASK.md` в папке кампании остаётся дословной копией.

## 6. План внедрения

**Неделя 0 — инфраструктура (без контента).**
1. Обновить кит в `campaign-2` одной командой, проверить `KIT.json`.
2. Выпустить ScriptCat `0.14.0` (блок инструментов проверки в промпте, поля
   `check`/`report` в маркере).
3. Завести в Notion поля `Kit Version`, `Check`, `Report SHA` в базе запросов.
4. Запустить нового Coordinator по `docs/coordinator.md` (он не знает прошлого
   контекста, и это нормально — регламент самодостаточен).

**Неделя 1 — пилот на «Ночном перевале».**
Три задачи через новый цикл: починить недостижимую сцену, добавить одну сцену
с диалогом, закрыть предупреждения аудита. Замерить: время до `Accepted`,
число возвратов, сколько раз `check` был красным на сдаче.

**Недели 2–3 — конвейер на кампаниях 2–3.**
WIP: одна кампания в производстве, внутри — до трёх параллельных задач по
разным путям. Coordinator следит, чтобы зоны файлов не пересекались.

**Неделя 4 — ретроспектива.**
Решения по трём порогам: больше пяти агентов или двух проектов → очередь на
GitHub Issues; реальная гонка за задачи → Supabase; повторяющиеся ошибки
проверки → новые правила в анализатор.

## 7. Метрики

| Метрика | Цель |
|---|---|
| Доля задач, принятых с первого раза | ≥ 70 % |
| Медиана времени до `Accepted` | ≤ 1 рабочий цикл |
| Сдачи с `check ≠ 0` | 0 |
| Возвраты по одной задаче подряд | ≤ 1 |
| Сцены, покрытые маршрутами | 100 % |

## 8. Риски и что с ними делать

- **Userscript — единственная точка автоматизации.** Поэтому в нём нет
  «умных» решений: он только передаёт ход и пишет лог. Все правила — в
  регламенте и в карточке, их можно поменять без правки кода.
- **Rate limit Notion** (3 запроса/с): синк один, а не по агенту.
- **Контекст агента**: в задачу идёт ссылка и критерий, а не весь дизайн-док;
  дизайн-док читается один раз на кампанию.
- **WIP > 1 по одной кампании** допустим только при непересекающихся путях,
  иначе конфликты в ветке съедают выигрыш.
