# Взаимодействие агентов: плоскости, протокол, границы

Документ фиксирует, где что хранится и как агенты договариваются. Он не про пять
кампаний: тип проекта — параметр, а не отдельная система.

## 1. Принцип

**Указатель, а не полезная нагрузка.** Сообщение между агентами — короткий
конверт со ссылкой и хэшем. Длинный текст, код, медиа живут в артефакте, а не в
теле сообщения. Причина не в лимитах Notion, а в контексте модели: агент должен
читать ровно тот кусок, который ему нужен, а не весь документ.

**Один факт — одно место.** У каждого факта есть канонический дом. Остальные
системы хранят ссылку и, если надо, копию для человека.

**Личность — в данных, не в аккаунте.** Коннектор один на воркспейс: все агенты
ходят под одним сервисным аккаунтом, `created_by` бесполезен. Поэтому в каждой
записи есть `agent_id` и `run_id`, а в PR — строка `agent: <id>`.

## 2. Плоскости

| Плоскость | Дом | Что там канонично | Чего там нет |
|---|---|---|---|
| Исполнение | GitHub | код, кампании, md-документы, engine-dist, CI, PR, история | медиа-склады, человеческие обсуждения |
| Команды | Notion | проекты, задачи, роли, решения — короткими полями | длинные тексты, очереди, блокировки |
| Артефакты | Google Drive | арт, аудио, видео, PDF, экспорты, дизайн-доки | истина по коду и статусам |
| Документы для людей | Google Docs | документы, которые комментируют и правят руками | машинное состояние |
| Отчётность | Google Sheets | сводки, реестры, матрицы покрытия | конкурентная запись агентами |
| Шина (позже) | Supabase | задачи, события, прогоны, блокировки | документы для людей |
| Инженерный трекер (опц.) | Linear | баги движка, платформенные задачи | контент кампаний |

Правила перехода:

- GitHub → Notion: только ссылка на issue/PR + статус.
- GitHub → Drive: только собранные артефакты (билд, отчёт, видео).
- Drive → GitHub: никогда как источник; медиа лежит рядом с кампанией в репозитории,
  если оно часть пакета.
- Sheets и Notion-дашборды — производные, их можно пересобрать.

## 3. Протокол

### Задача

```json
{
  "id": "cf-01-night-pass#42",
  "project": "cf-01-night-pass",
  "type": "campaign",
  "title": "Починить мост: недостижимая сцена",
  "state": "ready",
  "owner": null,
  "acceptance": ["cf-play check = 0", "PR merged by Master"],
  "artifacts": [],
  "links": ["https://github.com/.../issues/42"]
}
```

Состояния: `proposed → ready → claimed → in_progress → review → accepted → done`,
плюс `blocked` и `cancelled`. Захват — атомарный: assignee в GitHub или
`update ... where state='ready' returning *` в Supabase. Аренда на 2 часа: если
агент умер, задача возвращается в `ready`.

### Конверт передачи

```json
{
  "id": "8f4c1e2a-...",
  "from": "TGD-1",
  "to": "QA-2",
  "task": "cf-01-night-pass#42",
  "state": "review",
  "summary": "≤ 500 знаков: что сделано, что проверять",
  "artifacts": [{ "url": "...", "sha256": "…", "kind": "report" }],
  "reply_to": "3fd6f0cf-..."
}
```

Всё, что длиннее 500 знаков, — артефакт. Конверт целиком влезает в Notion-блок,
в комментарий GitHub и в строку Supabase, поэтому его не надо переписывать под
каждую систему.

### Артефакт

Имя: `<project>__<task>__<kind>__v<N>__<sha8>.<ext>`.
В записи всегда `sha256`; приёмка проверяет хэш, а не «файл вроде тот».

## 4. Кто пишет куда

| Роль | GitHub | Notion | Drive | Sheets | Supabase |
|---|---|---|---|---|---|
| Агент-исполнитель | ветка, PR, `agent:` в теле | статус своей задачи | свой `out/` | — | события, прогоны |
| QA | комментарий к PR, отчёт | вердикт | отчёт | — | прогоны |
| Координатор | назначение, метки | карточки, решения | — | — | задачи |
| Мастер | merge, релиз | приоритеты | просмотр | дашборд | — |
| Синк-джоб | чтение | зеркало | — | сводка | чтение |

Синк — один процесс, а не каждый агент: иначе N агентов упираются в rate limit
Notion (3 запроса/с) и разъезжаются в статусах.

## 5. Границы и безопасность

- Коннектор — общий сервисный аккаунт. Разделение только по ресурсам:
  репозиторий, папка Drive, база Notion/Supabase.
- Агент кампании не имеет доступа к исходникам движка: только `engine-dist` и
  `cf-play.mjs`. Публичный интерфейс для внешних агентов — Git и npm, не Notion
  и не Drive (у внешнего агента нет наших коннекторов).
- Право merge — только у Мастера. Агенты не мержат и не закрывают PR.
- Аудит: все записи несут `agent_id`/`run_id`; раз в сутки выгрузка в `_audit/`.

## 6. Порядок внедрения

1. **Сейчас, без новой инфраструктуры.** Протокол + ID + конверты; Notion-карточки
   ≤1500 знаков со ссылками; длинные тексты — в Git; медиа — в Drive.
2. **Когда агентов больше пяти или проектов больше двух.** Очередь задач — GitHub
   Issues (assignee = захват, тело 65k, история бесплатно), Notion — зеркало для
   Мастера, Sheets — недельная сводка.
3. **Когда появляется реальная конкуренция за задачи.** Supabase: `tasks`,
   `events`, `runs`, `locks`; `SELECT … FOR UPDATE SKIP LOCKED`; Realtime вместо
   опроса. Notion остаётся витриной.

Linear подключается на шаге 2 только для инженерных задач; контент кампаний туда
не едет, иначе появляется второй трекер с теми же полями.

## 7. Чего не делать

- Notion как очередь: нет транзакций и блокировок, гонка двух агентов на одной
  карточке разрешается «кто последний записал».
- Drive как источник истины по тексту: нет диффов, нет CI, чтение тянет весь
  документ в контекст.
- Sheets как API: конкурентная запись теряет строки, формул и валидации нет.
- Docs как база: документ — поверхность ревью, не состояние.
- Дублировать статус в трёх местах руками: статус живёт в одном месте, остальные
  — производные.

## 8. Замеры (2026-10-20)

Всё ниже измерено на реальных коннекторах, не взято из документации. Тестовые
объекты после замера удалены.

| Что | Как | Результат |
|---|---|---|
| Notion: один `rich_text` в абзаце | `create_page`, ~2 140 знаков | запись принята, текст вернулся целиком (хвостовой маркер `END-P2-A` на месте) |
| Notion: абзац 1 600 знаков | `create_page` | принят (заведомо ниже паспортных 2 000 на объект) |
| Drive: md 10,4 КБ | `upload_file` + `md5Checksum` | байт-в-байт: `8fceb953…`, size 10 454 |
| Drive: md 13,9 КБ | `upload_file` + `md5Checksum` | байт-в-байт: `2a14588d…`, size 13 951 |
| Drive: правка на месте | `update_file_content` | сработала: size 129, `version: 3` — это ревизия того же файла |
| Drive → Google Doc | 19 575 Б md → Doc → текст | 19 299 знаков, `truncated: false` (−1,4 %, разметка md теряется) |
| Sheets: запись | `USER_ENTERED` | «0.9.3» → `36772`, «2026-10-20» → `46315` — данные испорчены |
| Sheets: запись | `RAW` + чтение | строки сохранены точно |
| Supabase | `list_projects` | 0 проектов; коннектор живой, но тестировать нечего |

Выводы, которые меняют протокол:

1. **Лимиты не оправдывают конверт в 500 знаков** — они оправдывают его ещё
   сильнее: Notion держит килобайты, Drive держит десятки килобайт байт-в-байт,
   значит ограничение диктует контекст модели, а не API. Паспортный потолок
   одного `rich_text` — 2 000 знаков, но замер на ~2 140 прошёл, так что
   жёсткого отказа на этой границе нет; полагаться на это всё равно не стоит.
2. **Drive годится как склад, но не как источник текста.** Хэш совпадает,
   правка на месте работает, а экспорт в Doc теряет разметку — поэтому канон
   текста в Git, а Drive хранит бинарники и снимки.
3. **Sheets принимает только `RAW`.** Один `USER_ENTERED` превращает версию
   `0.9.3` в число, а дату — в серийный номер; это молчаливая порча, которую
   потом никто не заметит. Таблицы — производные, пишет только синк-джоб.
4. **Supabase пока не проверен по существу**: организации есть, проектов нет.
   До первого проекта шина остаётся планом, а не зависимостью.
