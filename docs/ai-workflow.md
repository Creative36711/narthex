# Протокол работы ИИ-разработчика Chronicle Forge

Этот документ — официальный договор между мастером и ИИ-агентом, который
правит репозиторий `Creative36711/chronicle-forge`. Он отвечает на два
вопроса, из-за которых раньше терялась работа:

1. **Какие файлы агент обязан обновлять в каждом изменении** (не только код:
   схема, гайд, «Книга мастера», README, ARCHITECTURE, чемодан для ИИ, смоуки).
2. **Как часто фиксировать этапы коммитом и пушем**, чтобы поломка песочницы,
   протухший токен GitHub или обрыв связи не стирали прогресс.

Документ читается первым делом (сразу после `README.md`) и действует для
любой сессии доработки движка, редактора или документации.

---

## 1. Золотое правило

> Несуществующей считается работа, которой нет в `origin` на ветке сессии.

Код без синхронной документации — это половина правки, а правка без коммита и
пуша — это ноль. Каждый логический шаг заканчивается зелёными проверками,
коммитом с русским сообщением и пушем.

---

## 2. Обязательный набор файлов на каждое изменение

Если меняется что-то из левого столбца — правый столбец обновляется **в той же
сессии, тем же коммитом или следующим**.

| Что изменилось | Что обновить обязательно |
| --- | --- |
| `src/shared/types.ts` (любой тип формата) | `docs/campaign.schema.json` и `public/ai/campaign.schema.json` — команда `npm run generate:campaign-schema` (она же синхронизирует гайд, §0 «НАЧНИ С ЭТОГО», §21 «Автокаталог» и файлы чемодана `public/ai/`) |
| Новая/изменённая механика, поле, условие или эффект | `docs/ai-campaign-guide.md` (и mirrored-копия `public/ai/campaign-guide.md` генерируется автоматически), `docs/book/05-mechanics.md` или нужная глава «Книги мастера», `docs/campaign.schema.json` |
| Поведение, влияющее на совместимость сейвов/кампаний | `docs/compatibility.md` (контракт версий и §9 «Сознательно не делаем») |
| Сознательно отклонённый или пересмотренный запрос | `docs/compatibility.md` §9 **и** `docs/book/08-limits.md` §8.8 (два места — оба) |
| Возможности Player/Editor Mode | `README.md` (блок «Возможности») |
| Архитектура, слои, новые модули, новая итерация | `ARCHITECTURE.md` (раздел 10 — история итераций) |
| Новая механика или правка движка | смоук в `scripts/*-smoke.mts`, строка в README («Проверки») и при необходимости скрипт в `package.json` (`smoke:*`) |
| UI/интерфейсная гарантия (кнопка, экран, подсказка) | проверка в `scripts/release-ui-smoke.mts` (иначе гарантию никто не сторожит) |
| Изменение, ломающее демо-кампанию | `public/campaigns/ash-of-caerden` — тестовый полигон, правится вместе с движком |
| Новый термин для мастера | `docs/glossary.md` |
| Диалоги/интерактив в демо | `npx tsx scripts/regen-ink.mts` (`.ink` из документов конструктора) |

Дополнительные инварианты, которые проверяются смоуками и которые нельзя
нарушать:

- `npm run smoke:guide` — все JSON-примеры и inline-сигнатуры гайда должны
  проходить `docs/campaign.schema.json`, и каждый тип схемы должен быть
  упомянут в гайде (обратное покрытие 100 %).
- `npm run audit:campaign-formats` — согласованность схемы, монолита, отдельного
  пакета, AI-кита (`public/ai/*`) и структуры руководства.
- `scripts/book-md-smoke.mts` — «Книга мастера» рендерится без развалившихся
  списков и осиротевших абзацев.
- `scripts/release-ui-smoke.mts` — релизные UI-гарантии одним прогоном.
- `npx tsc -b` и `npx vite build` — сборка проекта.

## 3. Периодичность коммитов и пушей (установленный порядок)

**Коммитить и пушить:**

1. **После каждого логически завершённого шага** — «написал механику + смоук»,
   «обновил гайд и схему», «починил валидатор»: это одна единица работы.
2. **Не реже чем раз в 15 минут** активной разработки, даже если шаг не
   дописан: коммит с пометкой `WIP:` в сообщении лучше потерянной сессии.
3. **Сразу после прогона проверок, которые стали зелёными** — не копить
   несколько зелёных шагов в грязном дереве.
4. **Обязательно в конце хода (перед выдачей ответа мастеру)** — рабочее дерево
   должно быть чистым, всё запушено в ветку сессии.

**Правила пуша:**

- Пушить сразу после коммита, отдельной командой (`git push origin <ветка
  сессии>`). В этой сессии ветка — `arena/01a0ed66-chronicle-forge`, другие
  ветви не создаются и не трогаются.
- Если `git push` или `gh` отвечают отказом аутентификации — **не пытаться
  чинить токен самому**: сообщить мастеру, что соединение с GitHub требует
  внимания (переподключение в Arena), и продолжить с локальными коммитами,
  чтобы работа не потерялась.
- Один коммит — одна тема. Сообщение коммита — по-русски, в стиле
  «<область>: <что сделано>» (например, `P3: таймер реплики в диалоге`).

**Почему так:** песочница может упасть в любой момент, токен GitHub протухает,
а мастер может закрыть вкладку. Последний пуш — это точка восстановления: с
неё сессию можно продолжить, даже если локальный workspace потерян.

## 4. Порядок работы (чеклист агента)

1. Прочитать `README.md` и этот протокол; при задачах по формату — гайд
   (`docs/ai-campaign-guide.md`) и «Книгу мастера» (`docs/book/`).
2. Найти все места, которых касается правка (таблица §2), включая смоуки.
3. Внести изменения в код и типы.
4. Перегенерировать производные артефакты: `npm run generate:campaign-schema`
   (схема, гайд §0/§21, `public/ai/*`) и `npx tsx scripts/regen-ink.mts`
   (если правились диалоги демо).
5. Обновить документацию из таблицы §2 (гайд, книга, совместимость, README,
   ARCHITECTURE, глоссарий).
6. Добавить/обновить смоук под новую механику.
7. Прогнать проверки: `npx tsc -b`, затронутые смоуки, `npm run smoke:guide`,
   `scripts/release-ui-smoke.mts`, `scripts/book-md-smoke.mts`,
   `scripts/audit-campaign-formats.mts`, `npx vite build` (перед релизом).
8. Коммит + пуш (см. §3), затем короткая сводка мастеру: что сделано, чем
   проверено, что осталось.

## 5. Язык, стиль и запреты (действуют всегда)

- Всё по-русски: интерфейс, документация, сообщения коммитов, тексты в игре.
- **Не переименовывать существующие id** (кампаний, сущностей, узлов, правил):
  старые сейвы и пакеты должны продолжать открываться.
- Старые/неизвестные данные: молчаливая автопочинка с понятным русским отчётом
  мастеру; бэкапы — только на машине игрока.
- Никакого платёжного кода и выдуманных полей вне схемы.
- Prettier не используется; форматирование — как в соседних файлах.
- Звуки интерфейса и фоновые лупы в Editor Mode (вне плейтеста) не играют.

---

## 6. Шпаргалка: команды одного цикла

```bash
npx tsc -b                                   # типы
npm run generate:campaign-schema             # схема + гайд §0/§21 + public/ai/*
npx tsx scripts/regen-ink.mts                # .ink из документов конструктора
npm run smoke:guide                          # гайд ↔ схема
npx tsx scripts/release-ui-smoke.mts         # релизные UI-гарантии
npx tsx scripts/book-md-smoke.mts            # рендер «Книги мастера»
npm run audit:campaign-formats               # форматы, монолит, AI-кит
npx tsx scripts/time-pressure-smoke.mts      # смоук конкретной механики (пример)
npx vite build                               # сборка
git add -A && git commit -m "P3: …" && git push origin arena/01a0ed66-chronicle-forge
```

## 7. Если что-то сломалось

- **Песочница отвалилась / процесс убит** — продолжить с последнего коммита в
  `origin` (ветка сессии): `git fetch && git status`, дальше по чеклисту §4.
- **`git push` отказал по аутентификации** — сказать мастеру, что соединение с
  GitHub требует внимания (переподключить GitHub в Arena); локальные коммиты
  продолжать, они не потеряются.
- **Смоук упал на чужом контенте** — не «чинить» смоук под зеленый экран:
  сначала понять, какое поведение сломалось, и починить поведение.
