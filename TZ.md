# Техническое задание: «Гибкий движок для любого сеттинга»

**Проект:** Chronicle Forge — редактор и рантайм тактических визуальных новелл
(один кодбейс: Player Mode + Editor Mode, контент — пакеты кампаний).

**Статус на момент написания:** Фазы 0–4 завершены, 16 итераций фидбека
отработаны. Настоящее ТЗ описывает следующий крупный этап — набор блоков,
которые делают движок пригодным для **любого сеттинга** в рамках системы BRP.

**Как работать с этим документом:**

1. Сначала прочитать разделы **1–2** (что уже есть и какие решения зафиксированы —
   они обсуждены и одобрены заказчиком, пересматривать их не нужно).
2. Блоки выполняются **строго в порядке дорожной карты** (§3): каждый следующий
   блок опирается на предыдущие.
3. Для каждого блока раздел «Сквозные требования» (§15) обязателен: миграции,
   монолит, схема, гайд для ИИ, смоуки, документация.
4. «Готово» по блоку = выполнены его критерии приёмки (§ в конце каждого блока)
   И сквозные требования. Один блок — один осмысленный коммит (или несколько).

## 1. Краткое состояние проекта (что уже есть)

Подробно — в `ARCHITECTURE.md`; здесь только то, что нужно для этого ТЗ.

**Движок (`src/core/`):** `GameEngine` (тики, потребности, правила, квесты,
диалоги-ink, торговля, партия, сейвы `SAVE_VERSION = 3`), `CombatController`
(гекс-бой: инициатива по DEX, движение Дейкстрой, атака/уклонение/парирование,
предметы в бою, AI, лут), BRP d100 (`brp.ts`: проверки, криты/особые/провалы,
производные HP/MP, damage bonus, MOV), декларативные условия/эффекты
(`conditions.ts`, ~20 условий и ~30 эффектов в `types.ts`).

**Контент кампании:** `campaign.json` (метаданные + реестры: потребности,
навыки, флаги, фракции, категории предметов, типы слотов, валюты, эмоции,
музыка/звуки, правила бросков `DiceRules`), `world.json` (регионы/локации/пути),
сцены (состояния, слоты, зоны навигации), сущности (НПС/предметы), правила,
квесты, арены, таблицы встреч, катсцены, диалоги (`.dlg.json` конструктора →
генерируемый `.ink`).

**Что важно знать про изображения НПС сегодня:**

- `NpcDef.portrait: Record<emotion, image>` — портрет с состояниями
  (используется в диалогах; ключ `neutral` — состояние по умолчанию).
- `NpcDef.token?: string` — картинка жетона в бою; фолбэк
  `token ?? portrait.neutral` (см. `combat.ts`, создание бойцов).
- В сцене (`player/SceneScreen.tsx`) НПС рисуется через `portrait.neutral`
  внутри прямоугольного слота — отдельного «сценного» изображения нет.
- Жетон в бою (`player/CombatScreen.tsx`) — круглая маска + рамка по стороне
  (`token-player`/`token-dead`/`token-active`) + полоска HP.

**Оформление сегодня:** единственный шрифт — `Georgia, 'Times New Roman', serif`
(`src/index.css`, `:root`); моноширинный для JSON; у главного меню
(`player/MainMenu.tsx`) — только тёмная заливка (музыка меню уже есть:
`ui_sounds.menu_music`). Реестра шрифтов и темы кампании нет.

**Механики сегодня (всегда включены):** карта и путешествия, инвентарь и
экипировка (жёстко два слота: `weapon`/`armor`), потребности, навыки с
«галочками» роста, отношения (личные и фракционные −100…+100), торговля,
гекс-бой, время (тики/время суток, расписания НПС), квесты с журналом.
Выключателей нет. **Нет:** крафта, статусов, боевых способностей, морали,
предмета-на-слот, календаря/погоды, кодекса, создания персонажа.
`CharCreationDef` объявлен в `types.ts`, но нигде не используется.

**Редактор (`src/editor/`):** разделы — Кампания и реестры / Мир / Сцены
(Konva) / Арены / Сущности / Диалоги / Квесты / Катсцены / Правила; реестры
кампании — вкладки «Основное / Персонажи / Предметы и слоты / Флаги / Звук и
музыка / JSON»; условия и эффекты описаны декларативными схемами
(`editor/schemas.ts`), новые эффекты добавляются описанием схемы; формы полей —
`editor/Fields.tsx`; undo/dirty — `editor/store.ts`; «кампания одним JSON» —
`editor/monolith.ts` (экспорт/импорт/автопочинка); плейтест — кнопка в шапке.

**Демо-кампания:** `public/campaigns/ash-of-caerden/` («Пепел Каэрдена») —
единственная; все изменения формата обязаны быть с ней обратно совместимы
(мягкие миграции, без ручных правок файлов).

## 2. Зафиксированные решения и жёсткие ограничения

Обсуждено с заказчиком. Не пересматривать без явной команды.

1. **Движок — строго BRP.** Характеристики фиксированы (`StatBlock`:
   STR/CON/SIZ/DEX/INT/POW/CHA, формулы в `core/brp.ts`). Реестра
   характеристик НЕ делаем — это осознанная граница: любой сеттинг
   выражается контентом (реестры навыков/потребностей/категорий) и
   тумблерами механик, а не другой системой. «Рассудок» в стиле Зова Ктулху
   уже сегодня выражается потребностью (`NeedDef`) — код не нужен.
   Опциональные правила BRP (локации попаданий, импейл и т.п.) — в дальнем
   хвосте, по образцу существующих `DiceRules`, на усмотрение мастера (§14.2).
2. **Три вида изображений НПС** — одобрено: портрет (диалог, состояния),
   спрайт сцены (вырезанный фон), боевая фигурка (вместо жетона). Фолбэки:
   нет спрайта сцены → в сцене портрет; нет фигурки → круглый жетон из
   `token ?? portrait.neutral`. Стили жетонов к фигуркам не применяются.
3. **Тема кампании** — реестр шрифтов + роли (текст/заголовки/рукописный),
   фон главного меню и экрана финала, ограниченная палитра (только акцентный
   цвет — свободное переопределение всей палитры запрещено, чтобы не ломать
   контрасты). Тема применяется только к Player Mode; редактор остаётся в
   фирменном стиле (в редакторе — превью).
4. **Профиль механик (тумблеры)** — фундамент; делается первым. Каждая новая
   механика этого ТЗ рождается «модулем с выключателем», а не всегда-включённым
   слоем.
5. **Фракции и репутация уже существуют** (реестр `factions`, `dispositions`,
   эффект `change_disposition` с целью-фракцией, панель «Отношения») — не
   переделывать, только мелкое расширение в дальнем хвосте (§14.1).
6. **Порядок работ** — §3. «Долгие действия» (сон/отдых) отдельным механизмом
   НЕ делать: сон уже есть (external `sleep(ticks)` в диалогах, эффект
   `advance_time`), крафт покрывает «действие с длительностью и результатом».

### Неизменные конвенции проекта (нарушение = переделка)

- Весь UI по-русски; сырые id, английские ключи и JSON игроку/мастеру не
  показывать (русские сводки через `LabelSource`).
- Никаких `prompt/confirm/alert` — только `shared/modals.tsx`.
- Никаких эмодзи и нативных `title=` в коде — иконки `shared/icons.tsx`
  (`<Ico n="..."/>`), подсказки — атрибут `data-tip`.
- Списки редактора — по алфавиту (ru); id генерируются из названий
  (`editor/ids.ts`), вручную мастер id не вводит.
- Изображения/файлы — `AssetUpload` из `editor/Fields.tsx` (файл с компьютера
  ИЛИ внешняя ссылка со мгновенной проверкой).
- Контент кампании в движке не хардкодится: никаких `if (id === 'npc_x')`.
- Аудио-вызовы безопасны в headless (смоуки работают в Node без Web Audio).
- Новая декларативная сущность (условие/эффект) = запись в
  `editor/schemas.ts` + обработка в движке + (если доступна из диалога)
  `DlgEffect`/`dialogueDoc.ts`/`DialogueBuilder.tsx`/external в `core/dialogue.ts`.

## 4. Блок 1 — Тумблеры механик (профиль кампании)

**Цель:** мастер в редакторе включает/выключает подсистемы под сеттинг:
хоррор без карты и боя, «театральная» кампания без инвентаря и т.п.

### 4.1 Формат (`shared/types.ts`)

```ts
/** Профиль механик кампании. Отсутствующее поле = механика включена. */
export interface CampaignFeatures {
  map?: boolean           // карта мира и путешествия
  inventory?: boolean     // инвентарь, экипировка, предметы в бою
  needs?: boolean         // потребности и их убывание
  skills?: boolean        // навыки, проверки, рост
  relationships?: boolean // отношения (панель; эффекты продолжают работать)
  trade?: boolean         // торговля
  combat?: boolean        // тактический бой
  time?: boolean          // отображение часов/даты (ход времени остаётся)
}
// в CampaignMeta:
features?: CampaignFeatures
```

Добавить помощник в `types.ts`: `export function featureOn(meta, key): boolean`
(отсутствующее поле/отсутствующий `features` → `true`). Пользоваться везде
только им.

### 4.2 Семантика выключенных механик (обязательная таблица поведения)

| Механика | Выключено — движок | Выключено — плеер |
|---|---|---|
| `map` | `travelTo` недостижим из UI | кнопка «Карта» в HUD скрыта; `NavigationZone.open_map` не рендерится; `reveal_location`/`block_path` молча работают |
| `inventory` | `add/remove_item` продолжают работать (квесты могут зависеть) | кнопка «Вещи» скрыта; панель инвентаря недоступна; «Использовать предмет» в бою скрыто; сообщения о предметах без иконок инвентаря |
| `needs` | убыль/восстановление/`onNeedZero` пропускаются; `change_need` — no-op | шкалы потребностей скрыты |
| `skills` | `skill_check_gate` и `DlgCheck` resolving без броска в **ветку успеха**; `change_skill`/`markSkill`/`restAndGrow` — no-op | в листе персонажа нет секции навыков и «галочек»; подсказки про рост навыков не показываются |
| `relationships` | `change_disposition` продолжает применяться (может гейтить диалоги) | панель «Отношения» скрыта |
| `trade` | external `open_trade` — no-op (разговор продолжается) | — |
| `combat` | `start_combat` в эффектах правил/квестов: бой не создаётся, **немедленно применяется победа** — все `on_victory` (включая отложенные экраны: диалог/телепорт/катсцена — через обычный механизм `postCombatEffects`), запись в лог «Конфликт разрешился без боя»; в таблицах встреч записи `type: 'combat'` трактуются как `nothing` | CombatScreen недостижим |
| `time` | — (время идёт: тики нужны расписаниям/потребностям) | часы и время суток в HUD скрыты |

Валидация — мягкая: `repairMonolith` и редактор предупреждают (не ошибки), если
при выключенной механике контент на неё ссылается (правила со `start_combat`,
диалоги с `open_trade`, категории с `restores_needs` и т.п.) — список
предупреждений по-русски.

### 4.3 Редактор

В `CampaignEditor` новая вкладка **«Механики»** (после «Основное»):
тумблеры с русскими названиями и коротким описанием каждого («Карта мира —
путешествия между локациями; выключите для камерных кампаний в одной локации»).
Тумблеры — обычные чекбоксы; состояние «все включены по умолчанию».

### 4.4 Плеер

- `HUD.tsx`: рендер кнопок через `featureOn`; часы — `time`.
- `GameView.tsx`/`Panels.tsx`: панели и экраны недоступных механик не
  рендерятся и не открываются (защита от программных вызовов).
- `HelpPanel.tsx`: секции справки по выключенным механикам скрываются.
- `tips.ts`: подсказки выключенных механик не всплывают.

### 4.5 Критерии приёмки

- Новая кампания с `{needs:false, map:false, combat:false, inventory:false}`
  играбельна: нет соответствующих кнопок/шкал; правило со `start_combat`
  резолвится победой и применяет `on_victory` (смоук проверяет предметы/флаги
  из `on_victory`).
- «Пепел Каэрдена» без `features` работает ровно как раньше.
- Смоук: `scripts/tz1-features-smoke.mts` — оба сценария выше + проверка
  поведения `skill_check_gate` при `skills:false` (успех без броска, без отметки).

## 5. Блок 2 — Тема кампании: шрифты, фон меню, оформление

**Цель:** мастер загружает свои шрифты и фон главного меню — применяется ко
всему плееру кампании. Редактор остаётся в фирменном стиле.

### 5.1 Формат

```ts
/** Шрифт кампании: файл пакета (assets/fonts/…) или внешняя ссылка. */
export interface FontDef {
  id: string
  label: string
  src: string                 // .woff2/.woff/.ttf/.otf
  weight?: string             // '400', '700', 'normal'… (default '400')
  style?: 'normal' | 'italic'
}

export interface ThemeDoc {
  /** роли шрифтов — id из meta.fonts; нет — системный Georgia */
  fonts?: { body?: string; display?: string; hand?: string }
  menu?: {
    background?: string       // картинка (файл/ссылка/арт)
    dim?: number              // затемнение 0…0.9 (default 0.5) — читаемость
    ken_burns?: boolean       // медленный зум фона
    title_art?: string        // лого/арт кампании над заголовком
  }
  end?: { background?: string } // фон экрана финала (нет — фон меню)
  accent?: string             // акцентный цвет (заменяет --gold у плеера)
}
// в CampaignMeta:
fonts?: FontDef[]
theme?: ThemeDoc
```

Роли: `body` — основной текст (диалоги, панели, кнопки), `display` — заголовки
(названия сцен/панелей, заголовок меню), `hand` — «рукописный» (записи журнала
квестов, записи кодекса — когда появится в блоке 10).

### 5.2 Рантайм

- `core/loader.ts` (или `App.tsx` после загрузки кампании): для каждого
  `FontDef` — правило `@font-face` в отдельном `<style id="cf-campaign-fonts">`
  (создаётся/очищается при смене кампании; `font-display: swap`).
- Плеер оборачивается контейнером, на который ставятся CSS-переменные:
  `--cf-font-body/-display/-hand` (со стеками фолбэков, например
  `var(--cf-font-body, Georgia, 'Times New Roman', serif)`), `--cf-accent`.
  **Редактор переменные не наследует** (отдельная ветка дерева).
- В `index.css` использования `Georgia` в плеерных стилях заменить на
  `var(--cf-font-body, Georgia, …)` и т.п. Точечно: тело, диалоги, панели,
  кнопки, меню; моноширинные области (лог боя — можно оставить).
- `MainMenu`: фон `theme.menu.background` (поверх — затемнение `dim` через
  `rgba`-слой, опциональная CSS-анимация кен-бёрнса), `title_art` над
  заголовком кампании; `EndScreen` — фон `theme.end.background ?? menu.background`.
- Акцент: заменить `--gold` в **плеерной** области на `--cf-accent`, если задан
  (через переменную, без дублирования стилей).

### 5.3 Настройка размера текста (мелочь, делаем здесь же)

В `shared/SettingsPanel.tsx` — «Размер текста: мельче/обычный/крупнее»
(`shared/settings.ts`, localStorage). Применяется масштабом шрифта плеерного
контейнера (например 0.9/1/1.15 от базового `16px` через переменную).

### 5.4 Редактор

В `CampaignEditor` новая вкладка **«Оформление»** (после «Механики»):

- Реестр шрифтов: список + `AssetUpload` (принимать `.woff2/.woff/.ttf/.otf`;
  для ссылок — `checkExternalUrl`), поля «Название», «Начертание» (вес/стиль).
  Файлы пишутся в `assets/fonts/`.
- Назначение ролей: три селекта из реестра + **живое превью** образцом текста
  («Съешь же ещё этих мягких французских булок, да выпей чаю» — заголовок,
  абзац, рукописная строка).
- Меню: фон (`AssetUpload`), ползунок затемнения, чекбокс кен-бёрнса,
  лого-арт; финал: фон; акцент: цветовой ввод + предупреждение про контраст.
- **Счётчик веса темы** (сумма байтов загруженных шрифтов; подсказка:
  «Каждое начертание — десятки килобайт, кириллица тяжелее»).

### 5.5 Критерии приёмки

- Кампания со шрифтом (файл) и фоном меню: шрифт применяется в диалогах,
  панелях, меню; фон меню виден с затемнением; редактор визуально не изменился.
- Без темы — пиксель-в-пиксель как раньше (фолбэк-цепочки).
- Монолит гоняет `fonts`/`theme` без потерь; схема и гайд ИИ обновлены.
- Смоук: `scripts/tz2-theme-smoke.mts` — загрузка кампании с темой, наличие
  `@font-face`-правил в сгенерированном стиле, фолбэк без темы, экспорт/импорт
  монолита с темой.

## 6. Блок 3 — Три изображения НПС (портрет / спрайт сцены / фигурка боя)

**Цель:** у каждого НПС (и игрока-сущности) три независимых изображения с
фолбэками; боевая фигурка умеет разворачиваться; стили жетонов к ней не
применяются.

### 6.1 Термины (использовать их в UI и коде)

| Термин | Поле | Где видно |
|---|---|---|
| **Портрет** | `portrait` (есть) | диалог, катсцены; состояния-эмоции |
| **Спрайт сцены** | `scene_sprite?` (новое) | слоты сцен; PNG с прозрачностью |
| **Фигурка боя** | `combat_figure?` (новое) | гекс-арена вместо жетона |
| **Жетон** | `token?` (есть) | круглая фишка в бою, когда фигурки нет |

### 6.2 Формат

```ts
// в NpcDef:
scene_sprite?: string                // файл/ссылка; рекомендуется прозрачный PNG
combat_figure?: string               // фигурка вместо жетона
figure_mode?: 'topdown' | 'side' | 'static' // как разворачивать (default 'topdown')
shadow?: boolean                     // мягкая тень под спрайтом/фигуркой (default true)

// в SlotDef:
sprite_scale?: number                // множитель размера спрайта в этом слоте (default 1)
```

`figure_mode`:

- `topdown` — вид сверху: поворот по направлению движения/атаки
  (`transform: rotate`);
- `side` — вид сбоку: только зеркало по горизонтали (`scaleX(-1)`), цель
  левее — зеркалим;
- `static` — не разворачивать.

### 6.3 Фолбэки (ровно как одобрено заказчиком)

- Сцена: `scene_sprite ?? portrait.neutral`. Спрайт рисуется «как есть»
  (без рамки/маски), привязка — низ слота; портрет-фолбэк — как сейчас
  (вписан в прямоугольник слота).
- Бой: `combat_figure` задана → рисуется фигурка (без круглой маски и рамки
  стороны — **стили жетонов не применяются**); полоска HP и тултип остаются.
  Не задана → нынешний круглый жетон с `token ?? portrait.neutral`.

### 6.4 Движок боя: направление (`core/combat.ts`)

- `Combatant.facing: number` (градусы; для `side` — знак через `facingX: -1|1`).
- Выставляется: при движении — к следующему гексу пути; при атаке — к цели;
  у защитника при получении удара — к атакующему (опционально, по желанию).
- Никакая гекс-логика (подсветка, клики, досягаемость, A*) не меняется:
  вращается только картинка в `CombatScreen`.
- Смерть фигурки: текущее обесцвечивание `token-dead`; для `topdown` допустим
  дополнительный поворот на 90° (по вкусу).

### 6.5 Рендер

- `player/SceneScreen.tsx`: спрайт — `<img>` с `height = slot.h * sprite_scale`,
  позиционирование по нижнему краю слота (центр-низ); тень — радиальный
  градиент/эллипс под ногами, только если есть `scene_sprite` и
  `shadow !== false` (под портретом-фолбэком тени нет).
  **Z-порядок:** слоты с сущностями рендерить отсортированными по нижнему краю
  (`y + h`) — нижние персонажи перекрывают верхних.
- `player/CombatScreen.tsx`: ветка «фигурка» против ветки «жетон» (см. 6.3).
- Игрок: поля применяются к сущности `default_player` автоматически (это
  обычный `NpcDef`) — отдельных полей в `PlayerState` не заводить.

### 6.6 Редактор

Форма НПС (`EntityEditor.tsx`) — перегруппировать раздел изображений:

1. **«Портрет (диалог)»** — как сейчас (состояния-эмоции).
2. **«Спрайт в сцене»** — `AssetUpload` + подсказка: «Изображение с
   прозрачным фоном (PNG). Если не задано — в сцене используется портрет».
3. **«В бою»** — два поля: «Фигурка боя» (`AssetUpload`) и режим разворота
   (селект с пояснениями) + существующее «Изображение жетона» с подсказкой
   «Используется, только если фигурка не задана».

`SceneEditor.tsx`: у слота — поле «Масштаб спрайта» (`sprite_scale`, число,
пусто = 1).

### 6.7 Миграция и совместимость

- Поле `token` не трогать (читается как раньше); старые кампании без новых
  полей выглядят точно как сейчас.
- Демо: новые поля в «Пепле Каэрдена» не обязательны (нет готовых
  прозрачных артов) — достаточно проверить фолбэки.

### 6.8 Критерии приёмки

- Смоук `scripts/tz3-images-smoke.mts`: синтетическая кампания с НПС, у
  которого заданы все три изображения: `slotOccupants` + рендер-функции
  выбирают спрайт; боец с фигуркой не получает классы стиля жетона
  (проверка по данным рендера/функции-хелперу вида `combatVisual(c)`);
  НПС без фигурки — жетон из `token ?? neutral`; `figure_mode` сохраняется
  через монолит.
- Ручная проверка: фигурка разворачивается при движении и атаке.

## 7. Блок 4 — Крафт

**Цель:** кнопка крафта в игре; рецепты декларативные (компоненты, инструменты,
навык, время); проверка навыка даёт «галочку» опыта (родная BRP-механика).

### 7.1 Формат

Новый раздел пакета — `recipes/*.json` (как квесты): секция `recipes` в
`manifest.json`, `CampaignData.recipes: Record<string, RecipeDef>`, раздел в
`MonolithDoc`.

```ts
export interface RecipeDef {
  id: string
  label: string
  description?: string
  /** расходуемые компоненты */
  inputs: Array<{ item: string; quantity: number }>
  /** инструменты: нужны в инвентаре, НЕ расходуются */
  tools?: string[]
  /** декларативные условия возможности (локация/флаг/…) — переиспользовать Condition[] */
  requires?: Condition[]
  /** проверка навыка при изготовлении (успех = создал; провал = компоненты целы) */
  skill?: { id: string; difficulty: number }
  /** время изготовления (промотка тиков после успеха) */
  time_ticks?: number
  output: { item: string; quantity: number }
  message?: string            // сообщение об успехе (нет — стандартное)
}
```

Провал проверки: компоненты НЕ теряются (мягкий режим; жёсткий режим — дальний
хвост, не делать сейчас). Проверка идёт через существующий механизм движка
(`engine.rollSkillCheck`-подобный путь, который ставит отметку опыта — рост
навыка потом во сне, как за любые проверки).

### 7.2 Движок (`core/engine.ts`)

- `availableRecipes(): RecipeDef[]` — у кого в инвентаре компоненты и
  инструменты, и выполнены `requires`.
- `craft(recipeId)`: порядок — проверка условий → проверка наличия → бросок
  навыка (если есть; отметка опыта) → при успехе: снять компоненты,
  `advanceTicks(time_ticks ?? 0)`, выдать результат, сообщение + лог,
  `playInteraction('use', …)` (или новый опциональный хук `ui_sounds.craft` —
  по желанию, хуки расширять аккуратно); при провале — сообщение о неудаче.
- Крафт недоступен во время боя/диалога/торговли (как другие экраны).

### 7.3 Плеер

- Кнопка «Крафт» в `HUD` — видна, если есть хотя бы один рецепт
  (выключателя в `features` нет — механика контент-управляемая: нет рецептов —
  нет кнопки).
- Панель крафта (стиль прочих панелей `Panels.tsx`): список рецептов с
  состабом («Травы ×2 — есть 3» / «— нет»), инструментами, шансом (навык против
  сложности), временем («≈ 2 часа»); кнопка «Изготовить» (неактивна без
  компонентов; тултип — чего не хватает).

### 7.4 Редактор

- Новый раздел `EditorApp` **«Рецепты»** (в группе «Контент»: после квестов):
  список + форма: название/описание, компоненты (список
  «предмет + количество» — переиспользовать паттерн `rewardItems`),
  инструменты (мультивыбор предметов), условия `requires` (конструктор условий),
  навык (селект + сложность), время в тиках, результат.
- Русские сводки рецепта для списка.

### 7.5 Критерии приёмки

- Смоук `scripts/tz4-craft-smoke.mts`: крафт с навыком (подкрутить навык до
  гарантированного успеха): компоненты списаны, предмет выдан, тики прошли,
  отметка навыка поставлена; крафт без компонентов не выполняется; условия
  `requires` (флаг/локация) работают; монолит гоняет `recipes`.
- Демо: добавить 1–2 рецепта («Лечебная мазь»: травы ×2 → мазь; «Вяленое
  мясо» без навыка) и убедиться, что кнопка появилась в игре.

## 8. Блок 5 — Статусы (яд, кровотечение, баффы)

**Цель:** длительные изменяющие состояния: мир (тики) и бой (раунды).
Фундамент для блока 6.

### 8.1 Формат

Реестр в `campaign.json` (как потребности):

```ts
export interface StatusDef {
  id: string
  label: string
  description?: string
  icon?: string                       // файл/ссылка (нет — текстовый чип)
  /** мир — длительность в тиках, бой — в раундах; 'both' — и там и там */
  scope: 'world' | 'combat' | 'both'
  duration: number                    // длительность по умолчанию
  /** урон за тик (мир) / за раунд (бой) */
  dot?: { hp?: number; mp?: number }
  /** модификаторы навыков на время статуса */
  skill_mods?: Array<{ skill: string; delta: number }>
  /** аддитив к движению (мин. 1) */
  mov_mod?: number
  on_apply?: Effect[]
  on_expire?: Effect[]
  apply_message?: string
  expire_message?: string
}
// в CampaignMeta:
statuses?: StatusDef[]
```

Состояние:

- Мир: `GameState.player.statuses?: Array<{ id: string; left: number }>`
  (left — тики).
- Бой: `Combatant.statuses: Array<{ id: string; left: number }>` (left — раунды;
  в рамках одного боя, в сейв не сохраняется).

### 8.2 Движок

- `engine.applyStatus(target, id, duration?)` / `removeStatus`; цель в мире —
  игрок (и только игрок в v1).
- `advanceTicks`: после потребностей — тики статусов игрока: DoT (урон не ниже
  1 — статус не убивает сам, либо убивает — на выбор: **не убивает**, при 1
  остаётся), декремент, истечение → `on_expire` + сообщение.
- Модификаторы навыков: все проверки игрока (врата, диалоги, крафт, бой)
  учитывают `skill_mods` активных статусов (единая функция-обёртка в движке).
- Бой (`combat.ts`): статусы у бойцов; в конце раунда — тик (DoT, декремент,
  истечение); `mov_mod` учитывается в движении; `skill_mods` — в атаках/защите.
- Новые эффекты/условия:
  - эффект `apply_status { target: 'player'; status: string; duration?: number }`
    (в бою — доступ через способности, блок 6);
  - эффект `remove_status { target: 'player'; status: string }`;
  - условие `has_status { status: string }` (игрок);
  - зеркало в диалогах: `DlgEffect` + external'ы `apply_status/remove_status`
    + кодогенерация + конструктор.

### 8.3 Редактор и UI

- `CampaignEditor`: реестр статусов — **новая вкладка «Статусы и способности»**
  (используется и блоком 6): список + форма по полям выше.
- `schemas.ts`: схемы новых эффекта/условия с русскими сводками.
- Плеер: чипы статусов у портрета/панели героя (иконка или название +
  оставшиеся тики); в бою — иконки на тултипе бойца и в ростере; строки лога
  («Отравлен», «Яд наносит 2 урона»).

### 8.4 Критерии приёмки

- Смоук `scripts/tz5-statuses-smoke.mts`: наложить статус с DoT через эффект →
  `advanceTicks` снимает HP и по истечению применяет `on_expire`; модификатор
  навыка виден в проверке (подкрутить сложность и поймать разницу); условие
  `has_status` срабатывает; бой: статус в раундах тикает и истекает.

## 9. Блок 6 — Боевые способности и мораль

**Цель:** в бою появляется выбор: атака / способность / предмет. Враги могут
убегать.

### 9.1 Формат

Реестр в `campaign.json` (в той же вкладке редактора, что и статусы):

```ts
export interface AbilityDef {
  id: string
  label: string
  description?: string
  mp_cost: number
  cooldown_rounds?: number       // default 0
  range: number                  // гексы (1 = вплотную)
  /** навык попадания; нет — атака без проверки (гарантированное применение) */
  skill?: string
  kind: 'damage' | 'status' | 'heal'
  damage?: string                // '1d6+2' — для kind 'damage' (damage bonus НЕ добавляется)
  status?: string                // для kind 'status'
  status_duration?: number
  heal?: string                  // '1d6' — для kind 'heal'
}
// в CampaignMeta:
abilities?: AbilityDef[]
// в NpcDef (и у сущности-игрока):
abilities?: string[]
```

Мораль (там же, в форме НПС):

```ts
// в NpcDef:
morale?: { below_hp_pct: number; flee_chance: number } // 0…100 / 0…100
```

### 9.2 Бой (`core/combat.ts`)

- `Combatant.abilities` (из сущности), `cooldowns: Record<abilityId, number>`,
  MP у бойца — из `StatBlock.MP`/производного (`derivedMP`); у игрока — синхрон
  с `PlayerState.mp` в начале и конце боя (как сейчас с HP).
- Действие игрока «Способности» (вместо атаки, ход завершается): список
  доступных (хватает MP, кулдаун 0), выбор цели в радиусе (подсветка как у
  атаки). Применение: расход MP, кулдаун, проверка навыка (если есть; цель
  защищается как от атаки — уклонение/парирование), эффект по `kind`
  (урон без брони? — **броня поглощает как обычно**, кроме оговорённого в
  описании; в v1 — как обычная атака, только со своим уроном/эффектом;
  `status` — накладывает статус блока 5; `heal` — лечит цель в радиусе, цель —
  любой союзник).
- Кулдауны тикают в конце раунда бойца.
- ИИ: враг/напарник со способностью применяет её вместо атаки, если может
  (есть цель в радиусе, хватает MP, кулдаун 0) с вероятностью 50% через
  `rng` — детерминизм сохраняется.
- **Мораль:** в начале хода врага с `morale`: если `hp/maxHp*100 < below_hp_pct`
  — бросок `flee_chance`: успех → боец покидает бой (строка лога «обращён в
  бегство», не считается убитым, лута нет), оставшиеся продолжают. Победа —
  когда врагов не осталось (убиты или сбежали).

### 9.3 Редактор и UI

- Вкладка «Статусы и способности» (блок 5): конструктор способностей.
- Форма НПС: мультивыбор способностей + поля морали («Порог HP %», «Шанс
  бегства %»).
- `CombatScreen`: панель «Способности» (иконка/название, стоимость MP,
  тултип-описание); радиус — подсветка гексов; в ростере — иконки статусов;
  в панели героя (`Panels`) — MP (есть и сейчас — проверить отображение).

### 9.4 Критерии приёмки

- Смоук `scripts/tz6-abilities-smoke.mts`: синтетический бой: игрок применяет
  способность-урон (урон прошёл, MP списаны, кулдаун пошёл), способность-статус
  (статус на цели тикает), лечение союзника; мораль: враг с 1% при 100% шансе
  сбегает, бой завершается победой без лута с него; детерминизм (один seed —
  один исход).
- Демо: гигантской крысе — способность «Укус» с ядом (статус из блока 5) —
  яд реально тикает в бою.

## 10. Блок 7 — Слоты экипировки (реестр вместо жёсткой пары)

**Цель:** слоты экипировки задаёт кампания: фэнтези-амулеты, киберпанк-
импланты, детективная рация — всё это предметы в слотах.

### 10.1 Формат

```ts
// в CampaignMeta:
equipment_slots?: Array<{ id: string; label: string }> // нет — встроенные Оружие/Броня

// в ItemDef:
equip_slot?: string             // id слота; нет — предмет не экипируется
```

- Встроенные по умолчанию: `[{id:'weapon', label:'Оружие'}, {id:'armor', label:'Броня'}]` —
  присутствуют всегда (даже если мастер добавил свои).
- **Мягкая миграция при загрузке** (`shared/migrate.ts`): предметам с
  `weapon_data` без `equip_slot` → `'weapon'`; с `armor_data` → `'armor'`.
- `PlayerState.equipment`: вместо `{weapon?, armor?}` — **`Record<slotId, itemId>`**.
  Сейвы: `SAVE_VERSION = 3 → 4`; `loadSave` мигрирует в3-сейвы
  (`{weapon, armor}` → рекорд) вместо отбрасывания; старше в2 — отбрасываются
  как сейчас.
- `NpcDef.equipment` уже `Record<string, string>` — ключи теперь просто id
  слотов (старые ключи `weapon/armor` валидны).

### 10.2 Правила экипировки

- Экипировка/снятие — из инвентаря по списку слотов кампании.
- Бой: оружие бойца — предмет в слоте `'weapon'` (как сейчас, включая
  `natural_weapon` при отсутствии). Броня: **сумма `armor_data.points` всех
  надетых предметов** (не только одного) — так работают шлем+кираса.
- Вес, стоимость, продажа надетого — без изменений логики.

### 10.3 Редактор и UI

- `CampaignEditor` → вкладка «Предметы и слоты»: список слотов экипировки
  (добавить/переименовать; встроенные неудаляемы).
- Форма предмета: селект «Слот экипировки» (реестр + «Не экипируется»).
- `Panels.tsx` (инвентарь): секция «Экипировка» — все слоты кампании с
  надетыми предметами/«пусто», снять/надеть.

### 10.4 Критерии приёмки

- Смоук `scripts/tz7-slots-smoke.mts`: миграция старого сейва с
  `{weapon, armor}`; старый предмет без `equip_slot` экипируется по данным;
  броня из двух слотов суммируется в бою; монолит/схема/гайд обновлены.
- «Пепел Каэрдена» без правок: слоты как раньше (Оружие/Броня).

## 11. Блок 8 — Предмет → слот сцены («ключ к двери»)

**Цель:** применение предмета инвентаря к слоту сцены — механика загадок без
скриптов.

### 11.1 Формат

```ts
export interface SlotUseWith {
  item: string               // предмет из инвентаря игрока
  consume?: boolean          // израсходовать (default false)
  effects: Effect[]
  message?: string
}
// в SlotDef:
use_with?: SlotUseWith[]
```

### 11.2 Поведение (`engine.interactWithSlot`)

Порядок при клике на слот:

1. В слоте НПС → диалог (как сейчас; `use_with` игнорируется).
2. У слота есть `use_with`, и хотя бы один предмет есть у игрока →
   **стилизованная модалка выбора** («Использовать: Ключ / Отмычка / Отмена»);
   после выбора: расход (если `consume`), эффекты, сообщение, `checkRules`.
3. Иначе — текущая логика (предмет с `on_interact`, описание, ничего).

Несколько подходящих предметов — выбор; один — модалка с подтверждением
(предмет может быть израсходован — игрок должен видеть, что произойдёт).

### 11.3 Редактор

`SceneEditor.tsx`, форма слота: список «Использование предмета»: предмет
(селект), чекбокс «Израсходовать», эффекты (конструктор), сообщение.

### 11.4 Критерии приёмки

- Смоук `scripts/tz8-usewith-smoke.mts`: клик по слоту с ключом в инвентаре →
  эффекты применены, предмет израсходован по флагу; без предмета — обычное
  поведение; модалка выбора при двух предметах (проверить выбор движкового
  метода `useItemOnSlot(slotId, itemId)` напрямую).
- Демо (по желанию): запертый сундук в таверне + ключ у Брана — один маленький
  пазл на новую механику.

## 12. Блок 9 — Календарь и погода

### 12.1 Календарь

```ts
// в CampaignMeta:
calendar?: {
  year_label?: string        // «Летопись Каэрдена», «г.э.»…
  start_year?: number        // default 1
  days_per_month?: number    // default 30
  months?: string[]          // названия месяцев (циклы; нет — «Месяц 1»)
  day_names?: string[]       // названия дней недели (циклы; нет — без имён)
}
```

- `core/time.ts`: `tickToDate(meta, tick) → { year, monthIndex, day, dayName?,
  monthName }` (день = `floor(tick / ticks_per_day)`).
- HUD: под часами — строка даты («12 Вереска, 3-й день недели»), если
  календарь задан. Эффекты/условия по дате в v1 не нужны (хватает
  `tick_elapsed`); не добавлять.

### 12.2 Погода

```ts
export interface WeatherDef {
  id: string
  label: string
  /** визуальный слой поверх сцены (чистый CSS, без библиотек) */
  overlay?: 'rain' | 'snow' | 'fog' | 'ash' | 'none'
  /** зацикленные звуки погоды (ид из реестра) — слои к эмбиенту локации/сцены */
  ambient?: string[]
}
// в CampaignMeta:
weathers?: WeatherDef[]
// в GameState:
weather?: string             // id погоды; нет — ясно
```

- Эффект `set_weather { weather: string }` (`''` — ясно); условие
  `weather_is { weather: string }`; схемы + сводки + диалоговое зеркало
  (по образцу `set_description`).
- `MusicCondition` и `SceneCondition`: опциональное поле `weather` (паттерн
  уже есть у `time_of_day`/`flag`).
- Плеер: `SceneScreen` — слой оверлея по типу (капли/снежинки/туман/пепел —
  лёгкие CSS-анимации, полупрозрачные, не мешают кликам: `pointer-events: none`);
  эмбиент погоды подмешивается в `refreshAmbient` (`shared/audio.ts`) к слоям
  локации/сцены.
- Редактор: реестр погод в `CampaignEditor` (вкладка «Основное», блок рядом с
  календарём); поля эффекта/условия в `schemas.ts`.

### 12.3 Критерии приёмки

- Смоук `scripts/tz9-weather-smoke.mts`: `set_weather` меняет состояние,
  условие `weather_is` срабатывает в правиле; календарь корректно считает даты
  (граничные тики: полночь, конец месяца, конец года); экспорт/импорт погоды и
  календаря монолитом.

## 13. Блок 10 — Кодекс/бестиарий

**Цель:** разблокируемые лор-записи (твари, места, события) — экран «Кодекс» в
плеере.

### 13.1 Формат

Новый раздел пакета `codex/*.json` (секция `codex` в manifest/`CampaignData`/
`MonolithDoc`):

```ts
export interface CodexEntryDef {
  id: string
  label: string              // название записи
  category?: string          // id из meta.codex_categories (нет — «Хроники»)
  text: string               // основной текст
  image?: string             // файл/ссылка (нет — без картинки)
}
// в CampaignMeta:
codex_categories?: Array<{ id: string; label: string }> // нет — встроенные три
// встроенные: существа / места / хроники
```

- Состояние: `GameState.codex_unlocked?: string[]`.
- Эффект `unlock_codex { entry: string }`: добавляет запись (повтор — no-op),
  сообщение «Новая запись в кодексе: …»; схема + диалоговое зеркало.

### 13.2 Плеер и редактор

- Кнопка «Кодекс» в HUD — только при хотя бы одной разблокированной записи.
- Панель кодекса: категории → записи (текст, картинка; стиль с учётом
  шрифтовой роли `hand` из темы, блок 2).
- Редактор: новый раздел **«Кодекс»** в `EditorApp` (список/форма: категория,
  название, текст, изображение).

### 13.3 Критерии приёмки

- Смоук `scripts/tz10-codex-smoke.mts`: эффект разблокирует запись, повторная
  разблокировка не дублирует; панель появляется только с записями; монолит.
- Демо: 2–3 записи («Гигантская крыса», «Долина Каэрден»), разблокируемые
  правилами (первая победа над крысами / вход в долину — через уже горящие
  правила демо).

## 14. Блок 11 — Создание персонажа; дальний хвост (фракции, опц. правила)

### 14.1 Фракции — расширение (по желанию, после основных блоков)

Репутация фракций **уже есть** (−100…+100, влияет на цены и диалоги; скрытые
служебные фракции). Единственное обсуждённое расширение: отношения
фракция↔фракция (`meta.faction_relations?: Array<{a,b,value}>`, влияющие на
личное отношение НПС к игроку как сумма: база фракции НПС + личная поправка +
отношения фракции игрока… в демо отношения «фракция игрока» нет — делать только
если появится механика принадлежности игрока к фракции). **По умолчанию — не
делать**, зафиксировать как идею.

### 14.2 Опциональные правила BRP (дальний хвост, на усмотрение мастера)

По образцу `DiceRules` (прецедент уже есть): блок `CampaignMeta.brp_options?` —
например, локации попаданий, импейл-урон, усталость. Сейчас **не делать**;
архитектура позволяет добавить без ломающих изменений.

### 14.3 Создание персонажа

`CharCreationDef` в `types.ts` существует, но не используется — реализуем его
и расширяем.

```ts
export interface ProfessionDef {
  id: string
  label: string
  description?: string
  skill_bonus: Record<string, number>       // бонусы к навыкам
  items?: Array<{ item: string; quantity: number }> // стартовое снаряжение
}
export interface CharCreationDef {
  total_points: number                       // бюджет характеристик
  stat_limits: { min: number; max: number }  // рамки каждой характеристики
  skill_points?: number                      // бюджет навыков (нет — без бюджета)
  skill_cap?: number                         // максимум навыка на старте
  mandatory_skills?: string[]                // обязательные (стартуют с 25%)
  forbidden_skills?: string[]                // нельзя покупать
  professions?: ProfessionDef[]              // выбор «происхождения» (может быть пусто)
  choose_name?: boolean                      // ввод имени героя
}
```

**Поток:** «Новый забег» → если `meta.char_creation` задан — экран
`player/CharacterCreation.tsx` (стиль плеера):

1. Имя (если `choose_name`; иначе — имя сущности-шаблона).
2. Характеристики: старт с минимума из `stat_limits` для всех семи; бюджет
   `total_points` распределяется кнопками ±, без выхода за рамки; остаток
   бюджета виден.
3. Профессия (если есть): карточки с описанием и бонусами.
4. Навыки (если `skill_points`): покупка очков навыков до `skill_cap`,
   обязательные предзаполнены (25%), запрещённые заблокированы.
5. «Начать забег» — неактивна, пока бюджет не потрачен/валиден.

**Движок:** `freshRun` применяет выбор к шаблону `default_player` (имя →
`label` в сейве/логе, характеристики → пересчёт производных через `brp.ts`,
навыки, предметы профессии в инвентарь). Сейв хранит выбранные значения как
сейчас (они и есть состояние персонажа).

**Редактор:** в вкладке «Основное» — блок «Создание персонажа» (включить
чекбоксом → поля бюджетов/рамок/списков; профессии — тут же списком).

**Критерии приёмки:** смоук `scripts/tz11-charcreate-smoke.mts` (валидация
бюджетов на уровне движкового хелпера валидации выбора; применение выбора к
шаблону: производные HP/MP пересчитаны; предметы профессии выданы); кампания
без `char_creation` стартует как раньше.

## 15. Сквозные требования для КАЖДОГО блока

Выполняются для каждого блока без исключений (иначе блок не считается готовым):

1. **Типы** — все изменения формата в `src/shared/types.ts` (единый источник
   правды), с комментариями на русском; новые поля — опциональные.
2. **Схема** — после правок типов перегенерировать
   `docs/campaign.schema.json` (`npx tsx scripts/gen-schema.mts`).
3. **Монолит** — новые секции/поля: экспорт, импорт и **автопочинка**
   (`editor/monolith.ts`) + round-trip без потерь; новые эффекты/условия — в
   валидацию ссылок.
4. **Гайд ИИ** — обновить `docs/ai-campaign-guide.md` (новые поля в примерах,
   новые эффекты в списках, при необходимости — короткий раздел).
5. **Миграции** — старые пакеты и сейвы читаются без ручных правок: мягкие
   миграции в `shared/migrate.ts`/`loader.ts`; при изменении формы сейва —
   поднять `SAVE_VERSION` и мигрировать предыдущую версию (не отбрасывать).
6. **Редактор** — любая новая сущность доступна без кода и без ручных id:
   схемы полей (`schemas.ts`), селекты по реестрам (`store.options`), русские
   сводки; новые реестры — выпадающие списки везде, где сущность упоминается.
7. **Документация** — обновить `README.md` (раздел «Возможности») и
   `ARCHITECTURE.md` (соответствующий раздел + итерационный хвост, по образцу
   §10–15 текущего документа).
8. **Смоук** — новый скрипт `scripts/tzN-<имя>-smoke.mts` (по образцу
   `feedback*-smoke.mts`: headless против dev-сервера `:5173`, заглушка
   `localStorage`, детерминизм через seed); **все существующие смоуки
   (`feedback…`) продолжают проходить** — запускать выборочно после каждого
   блока.
9. **Сборка** — `npm run build` (tsc strict) без ошибок; `npm run lint`
   (oxlint) без новых замечаний.
10. **Стиль** — конвенции §2: русский UI без сырых id, `<Ico>` вместо эмодзи,
    `data-tip` вместо `title`, модалки из `shared/modals.tsx`, алфавитные
    списки, контент не хардкодится.
11. **Демо** — где блоку нужен контент (рецепты, статусы, записи кодекса) —
    добавить 1–2 демонстрационных объекта в «Пепел Каэрдена»; где нужен
    уникальный арт (спрайты/фигурки, блок 3) — демо не обязательно, но
    фолбэки проверены.

### Общая приёмка всего ТЗ

- `npm ci && npm run build` — зелёные; все смоуки `feedback*` и новые `tz*` —
  проходят.
- «Пепел Каэрдена» (без изменений файлов кампании, кроме явно оговорённого демо)
  загружается, играется от меню до любого исхода; экспорт/импорт `.chronicle` и
  монолит-экспорт→импорт→экспорт без потерь и предупреждений.
- Новая синтетическая кампания в смоуках использует ВСЕ новые механики сразу
  (профиль с выключенными механиками + тема + спрайт/фигурка + рецепт + статусы
  + способность + доп. слот экипировки + use_with + погода + кодекс) — это
  главный интеграционный смоук финального блока.

## 16. Словарь терминов

- **Портрет** — диалоговое изображение НПС с состояниями (`portrait`).
- **Спрайт сцены** — изображение НПС для сцен с вырезанным фоном
  (`scene_sprite`), фолбэк — портрет.
- **Фигурка боя** — изображение НПС на гекс-арене вместо жетона
  (`combat_figure`), с режимом разворота (`figure_mode`).
- **Жетон** — круглая боевая фишка (стиль по стороне), когда фигурки нет.
- **Тумблер/профиль механик** — `meta.features`.
- **Тема кампании** — `meta.fonts` + `meta.theme` (шрифты, меню, акцент).
- **Долгие действия** — НЕ новый механизм: сон/отдых уже есть (`sleep`,
  `advance_time`), крафт — частный случай «затраты + время + результат».
